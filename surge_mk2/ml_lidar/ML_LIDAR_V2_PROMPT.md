# ml_lidar（v2）新規設計 — セッション開始プロンプト

このファイルの内容をそのまま新しいセッションの最初のメッセージとして渡すことを想定している。

---

## 背景

SURGE Mark.2（Raspberry Pi 5搭載の小型自律走行RCカー、2D LiDARのみ搭載）向けに、LiDAR点群のみを入力としたEnd-to-End強化学習（PPO、Stable-Baselines3）の学習パイプラインを**ゼロから設計・実装したい**。

旧`ml_lidar/`・`sim/gym_env.py`・`sim/random_course.py`は、v9〜v16の切り分け実験を重ねるうちに報酬7項目・4段階カリキュラム学習など複雑化しすぎたため、2026-09-06に全削除した（コミット`bdd7f64`に残る）。**旧実装は参照・復元しないこと**——設計をやり直すのが目的のため（過去に同じ理由でシミュレータ全体`surge_sim/`を削除した前例があり、この方針を踏襲する）。実車で現在使用中のモデルは無いので、しがらみなくゼロから設計してよい。

## 残っている基盤（変更しない・そのまま使う）

`sim/`配下には車両物理・センサモデル・コース表現の基盤モジュールが残っている。これらは`sim.bench`/`sim.run`（他plannerの実車再現評価）や`slam2d/tests/`（SLAM評価）からも共有されているため、**新しいml_lidarの都合で変更しないこと**。新設するコードはこれらの上に構築する。

| モジュール | 役割 |
|---|---|
| `sim/course.py` | `Course`（占有格子・レイキャスト・車体外形の衝突判定・PNG+JSON永続化） |
| `sim/vehicle.py` | `VehicleModel`/`VehicleSpec`（自転車モデル+操舵むだ時間+1次遅れ+横方向グリップ限界） |
| `sim/lidar.py` | `VirtualLidar`（仮想LD06、レイキャスト・距離ノイズ・欠損・遅延） |
| `sim/track.py` | 直線+円弧をつないで走路を作るセンターライン方式のコース生成 |
| `sim/raceline.py` | `compute_raceline_offsets`/`compute_speed_profile`（理想ライン・目標速度、Trajectory-Aided Learning用。必要なら再利用可、必須ではない） |
| `sim/sketch.py`・`sim/wall_track.py`・`sim/editor.py` | 手作業のコースエディタ（頂点スケッチ＋壁モード）。人手でコースを作る用途 |
| `sim/params.py` | `SimParams`（LiDARノイズ・欠損率などのシムパラメータ） |
| `sim/bench.py`・`sim/run.py`・`sim/gui.py`・`sim/ui.py`・`sim/stm32.py`・`sim/link.py`・`sim/channel.py` | 実機同等のUARTフレーミングを通す評価基盤（RL訓練では通さない設計方針だった。踏襲するかは要検討） |

`raspi/auto/e2e_lidar.py`（実車側の推論planner本体、`planning_node`が呼ぶ）は現存している。学習した方策をONNX化して読み込む契約は維持する必要がある——観測ベクトルの構成（点群＋α）を変えるなら、こちらとの整合を必ず確認すること。

## GUI（学習・観戦・エクスポート操作、削除対象ではない）

ターミナル操作をなるべく避けたいという運用方針があり、`ml_cam`/`ml_cam_e2e`/旧`ml_lidar`はいずれもTkinterのネイティブGUIから学習・観戦・エクスポートを操作していた。この方針・共通基盤は削除していないので、新しいml_lidarでもGUIから操作できるようにすること。

- `ml_common/`（`close_handler.py`・`dialogs.py`・`job_runner.py`・`log_console.py`・`naming.py`・`notes.py`・`paths.py`・`train_graph.py`・`epoch_log.py`）: 3つの学習GUIが共有するTkinter部品一式。現存しており、そのまま再利用できる
- `ml_cam/app.py`・`ml_cam_e2e/app.py`: 現存する実装例。GUIの作り方（サブプロセス起動・ログ配線・複数ジョブ管理・run一覧）の参考にしてよい
- 旧`ml_lidar/app.py`の設計パターン自体（1つの「run名」で学習出力先・エクスポート先・観戦対象を自動的に紐付ける、`JobRunner(allow_concurrent=True)`で学習中でもTensorBoard・観戦・エクスポートを並行実行できる、run一覧タブ、備考(note)機能）は**報酬・カリキュラムの複雑化とは別軸の話で、それ自体に問題は無かった**ため踏襲してよい
- ただし旧app.pyは「①学習タブに`train_rl.py`の全パラメータを網羅的に露出」させた結果、縦に長大化しスクロール必須になっていた（2026-09-06の変更）。**これは報酬をシンプルにする今回の方針で自然に解消されるはず**——GUIの入力項目は実際に調整する見込みのあるものだけに絞ること

## 外部調査で得た知見（F1TENTH文脈のLiDAR-only E2E学習、要点）

このセッションの前段で、F1TENTHや同種の小型RCカーレーシングにおけるLiDAR-only E2E学習の一般的手法を調査済み。要点:

- **アルゴリズム**: TD3・SAC・PPOが主流、model-freeが中心（[Unifying F1TENTH Autonomous Racing survey, arXiv:2402.18558](https://arxiv.org/html/2402.18558v1)）
- **アーキテクチャ**: RL文献ではMLPが標準（TAL論文は2層×100ユニットのみ）。模倣学習系では1D-CNNが明確に優位（[TinyLidarNet, arXiv:2410.07447](https://arxiv.org/html/2410.07447v1)、実走試験でMLP系0%成功・CNN系80〜100%成功）
- **報酬設計**: 最も完走率が高いとされる**TAL (Trajectory-Aided Learning)**（[Bosello et al., arXiv:2306.07003](https://arxiv.org/pdf/2306.07003)）は実質2〜3項目で構成される:
  ```
  r = 1 − |v_agent − v_classic| − |δ_agent − δ_classic|   （+ 衝突/完走のスパース項）
  ```
  他の主要実装（[racing-rl](https://github.com/luigiberducci/racing-rl)等）も「進捗+衝突ペナルティのみ」が中心。**7項目規模の重み付き和は先行研究の主流から明確に逸脱している**——これが旧実装複雑化の主因だったと判断している
- **ドメインランダム化**: F1TENTH界隈では記述が薄い（LiDARノイズ程度が典型）。車両ダイナミクス（グリップ・遅延等）まで踏み込むのは、ドローンレーシングのSwift（[Nature 2023](https://www.nature.com/articles/s41586-023-06419-4)）のような体系的sim-to-real設計の水準では妥当な部類
- **カリキュラム学習**: 調査した主要論文・サーベイにF1TENTH文脈での明示的な前例は見当たらなかった。「単一の複雑環境+強いドメインランダム化」で済ませるのが多数派

## 設計方針の推奨（叩き台。合意の上で確定させること）

1. **報酬は最小構成から始める**: `progress`（前進量）＋`collision_penalty`（終端）の2項目のみでまず1本学習を通す。TAL的に理想ライン（`sim/raceline.py`が既にある）との速度・舵角差分を足すのは、この最小構成の限界が見えてから検討する
2. **カリキュラム学習は最初から作り込まない**: 前例が乏しく、複雑さ・チューニングコストの主因だった。まずカリキュラム無しでどこまで走るか見る
3. **観測空間**: LiDAR点群＋速度＋ステア角の構成は妥当（後述の教訓参照）。1D-CNN特徴抽出器も踏襲してよい
4. **ドメインランダム化**: LiDARノイズ・車両ダイナミクス（mu/tau/dead_time等）のランダム化は残してよい。ただし観測できる証拠が無いままレンジを増やさないこと

## 過去に踏んだ落とし穴（再発防止チェックリスト）

新規実装でも同種のバグ・設計ミスを踏む可能性があるので、実装時に意識すること:

- **カスタム特徴抽出器のConv1d層がSB3のorthogonal初期化から漏れる**（`isinstance`チェックが`nn.Linear`/`nn.Conv2d`限定でConv1dが対象外）。独自層を使うなら初期化を明示確認する
- **むだ時間シムを「1step=1エントリ」キューで実装すると、大きなstep幅では実効遅延が量子化されて`dead_time_s`のドメインランダム化が実質無効化される**。時刻ベースの補間か、十分細かいサブステップ分割が必要
- **観測にステア状態（現在の平滑化後ステア角）を含めないと、速度依存の減速判断を学びにくい**（点群だけでは「今どれだけ舵を切っているか」が分からない）
- **方策の生出力に一次遅れフィルタ（steer_tau）を学習側にも入れないと、推論側だけに付いたフィルタの分だけ訓練時と実行時で応答が食い違う**
- **訓練環境（ランダム化・探索ノイズあり）の衝突率でモデル選定・早期終了を判断してはいけない**。固定コース・ノイズ無効化（`randomize_lidar=False`/`randomize_dynamics=False`相当）した専用評価環境が必須
- **評価コースの構成自体が「何を良しとするか」を決める**。単純な形状だけで評価すると、狭路・障害物のような難所での崩壊が学習曲線に一切現れなくなる実例があった。評価コースは複数アーキタイプを混ぜること
- **PPOの`log_std_init`や早期終了(`early_stop_patience`)がスケジュール（`clip_range`/`learning_rate`の線形減衰）と噛み合わないと、学習途中の未収束状態で`best_model`を選んでしまう**。早期終了を使うなら十分な猶予を持たせる

## ランダムコース生成の要件

新設するコース生成は**`ml_lidar/`配下に閉じて実装し、`sim/`直下の共有モジュールから独立させること**。旧`sim/random_course.py`がSLAM評価（`sim/courses/make_random_courses.py`経由）からも依存されてしまい、削除時の依存関係の洗い出しに手間取った反省を踏まえる。

- SLAM評価用の固定コース資産（`sim/courses/circuit_chicane_a/b/c.{png,json,npz}`）とは完全に別物として扱う。混同・共用しない
- 複雑さは最小から始める。円弧＋直線のシンプルな閉ループのみでまず学習を通し、狭路・障害物・ヘアピン等は「必要になった証拠（衝突パターンの分析等）」が出てから段階的に追加する。最初からアーキタイプを何種類も用意しない
- `sim/course.py`の`Course`データクラス（`grid`/`centerline`/`width`/`obstacles`）が既存の入出力契約なので、これに合わせて生成する

## 自作コースの扱い

`sim/courses/`には、手作業エディタ（`sim/editor.py`）で作った実コースが既に用意されている（`course1.json`・`course2.json`・`course3.json`・`toyota.json`・`normal.json`、`role`フィールド付き）。SLAM評価用の`circuit_chicane_*`固定資産とは別物。読み込みは`sim/course.py::list_role_courses(target)`という既存の仕組みが既にある。

**学習パイプライン（train用のコース生成・`EvalCallback`のeval双方）には混ぜないこと。** 少数個（5個）の固定コースを学習に混ぜると壁配置そのものを暗記するリスクがあり、これはヘアピン・シケインのような基本パターンなら手続き生成で十分カバーできるので必要性が薄い。evalは勾配更新こそしないが`best_model`選定・early stopping判定というモデル選択のフィードバックループには乗るため、少数固定コースをここに使うと「evalセットへの過適合」（選ばれる`best_model`がその5個に都合よく選ばれるだけ）が起きうる——バリデーションとテストの違いと同じ話。

**自作コースの用途は、学習プロセスに一切関与しない独立した確認専用に限定する**: `watch.py`的な観戦での目視確認、実車投入前の最終チェック。学習中のいかなる自動判定（`best_model`選定・早期終了・カリキュラム昇格）にも使わないことで、「学習が一度も最適化目標にしていない、純粋に未知の形状でどれだけ走れるか」という最も信頼できる指標として温存する。

新しい自作コースが要るなら`sim/editor.py`で作るだけで既存インフラに乗る（`role`の意味は上記方針に合わせて見直しが要るかもしれない）。追加のコードは不要。

## 進め方の提案

1. 調査（既存基盤モジュールのAPI確認）→設計方針の最終合意→実装→検証、の順で進める
2. 報酬は「progress + collision_penalty」の最小構成で最初の1本を学習させ、具体的な失敗モード（コーナーで詰まる／速度が出ない／特定アーキタイプで衝突する等）を確認してから、必要な項目だけを足す
3. `raspi/auto/e2e_lidar.py`との観測ベクトル契約は都度確認し、変更するなら両方揃えて直す
