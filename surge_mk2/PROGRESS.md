## 2026-11-02 Pi⇄STM32 の通信の遅れの見直し（未コミット・Pi 未反映）

実測（`surge_20261102_093957.mcap` と、駆動電源なしの実機のバス）:
- TELEMETRY: STM32 のスナップショット → Pi のバスで受信 中央 1.5ms（UART の線上 1.09ms）。100Hz の周期 = 値の古さ平均 5ms
- 指令: `auto/cmd` → `/cmd` の中継 中央 0.3ms。io_node・telemetry_node は変化をその場で送る。STM32 は受けた周期（500us）で反映。`cmd_rtt_ms` 6.6ms は TELEMETRY 待ちが大半
- 点群: `scan` の発行が最後のセクタの開始から 19.3ms 後。`ScanAssembler` が次の周の 0 が届くまで1周を閉じていなかった（1セクタ 8.3ms の待ち）
- **直した**: `ScanAssembler` は最後のセクタ（11）でその場で出す（11 が落ちた周は従来どおり番号が戻った時点）。点群 → `plan()` が約 8.3ms 早まる。
  シム（toyota2・3種）では走りは変わらない。**実機では未確認**（駆動電源が無いと LiDAR が回らない）。
  **`control_latency_s`（校正 4、12.1ms）はこの待ちを含んで測った値なので、反映後に校正 4 を測り直す**（約 4ms になる見込み）
- **試して入れなかった**: 追従（`tick()`）を 50Hz → `vehicle_state` ごと（100Hz）。Pi で `tick()` 平均 0.71ms（1 コアの +3.6%）。
  シムで ラップ −0.13%・真の横偏差 +0.2cm（遅延補償が過大になる。姿勢の古さを実測して補償に使っても同じ傾向、`delay_trim` で両者が入れ替わるだけ）。
  シムは姿勢の古さが中央 5ms（実機 1.5ms）で実機の遅れを再現できず、効果を示せないので見送り
- 上げなくてよい: COMMAND（変化は即時。定期 100Hz は途絶監視用）・TELEMETRY（200Hz にしても古さ平均 −2.5ms、Pi の全購読者の処理が倍）・LiDAR（LD06 の 10Hz で決まる）

## 2026-11-02 駐車（Hybrid A*）と駐車中の毎周期の処理を C に（2026-11-02 Pi 反映済み・実機では未検証）

`sim.park_bench --scenario all --n 5 --errors real`（同じ種）で Mac と Pi を比べると、Pi は**探索が時間予算（120ms）に負けて駐車を失敗する**:
Mac 成功 20/20・Hybrid A* の予算切れ 1/27・`plan()` 中央 4.8ms／Pi 成功 16/20（deadend 2/5・parallel 4/5）・予算切れ 18/35・`plan()` 中央 30.6ms・最大 223ms（150ms 超 18 回）。
決勝の駐車チャレンジは配点最大級（`docs/competition_plan.md` ⑧）。予算で打ち切るので結果は CPU の速さで変わる——検証は「予算に当たらない条件で Python 版と同じ経路」＋「Pi のベンチの成功率」
- 探索の中身（Mac で park_bench の問題 27 件を保存し予算なしで解く）: 1展開 534µs、大半が Reeds-Shepp（ヒューリスティックで子ごとに
  `shortest_path(...).length`、候補 48 通りを経路のオブジェクトで作る）、次いで解析展開（全候補をオブジェクトにして並べる）・子の生成と衝突判定・格子の Dijkstra
- `raspi/nav/_native.c` に、`rs_shortest_length`（長さだけ）・`rs_candidates`（全候補を表で。解析展開は上位 6 本だけ経路にする）・
  `hy_successors`（子の標本化と車体の余裕）・`hy_path_clearance`（解析展開の衝突判定）・`hy_dijkstra`（格子のヒューリスティック）。すべて Python 版とビット一致:
  CPython の `math.hypot`（独自の vector_norm）・float の `%`・3.12 以降の `sum`（Neumaier）を写し、heapq と同じ (費用, 行, 列) の順のヒープ。
  clang が同じ角の sin・cos を `sincos` にまとめて 1ulp ずれた → `-fno-builtin-sin/cos/sincos`（`slam2d/core/cbuild.py`）。numpy の cos・sin・exp は libm と同じ値（Mac・Pi で確認）
- 予算なしの 27 件の結果の指紋は変更前と同じ。1展開 534 → 70µs（Mac）。予算 120ms で解けなかった問題が Mac で 1864 展開まで進む
- Pi の park_bench（`--n 5 --errors real`）: 成功 16/20 → **20/20**、予算切れ 18/35 → 2/28。`plan()` の 150ms 超 18 → 2 回

## 2026-11-02 slam2d_route の経路生成を速くする（線は変えない。2026-11-02 Pi 反映済み・走行では未検証）

バンビの要望「magp2 など長いコースで経路生成に時間がかかる」。Pi で magp2 の真値地図の自動経路（既定設定）を測ると、
**仕上げなし（まず走れる線）15.1s・仕上げ込み 75.4s**（Mac は 0.53s・9.4s）。原因は2つ:
① QP（`min_curvature_alpha`）を n×n の密行列で解いていた（Pi の numpy は参照 BLAS で n³ が効く。仕上げなしの 13.7s がこれ）、
② 仕上げ（`refine_time`）が出発点2本×上限15000評価に張り付き、1評価 1.7ms（Python の速度プロファイル・車体外形・曲率）。

- 仕上げの評価は**前回の評価から変わった点の周りだけ**計算し直す（ビット単位で変わる点は平均 1/4）。同じ2点の hypot は1回だけ。こぶの形は roll で使い回す

## 2026-10-31 STM32 の車速が 32.767 に張り付きリセットまで戻らない不具合を修正（2026-10-31 ファーム書き込み済み）

バンビ報告「STM32 の速度が 32.なんぼに発散し、リセットボタンで直る」。32.767 は TELEMETRY の `speed`（i16・0.001）の上限で、内部はもっと大きい。
**原因は車速 KF（`src/control/speed_kf.c`）が一度外れると自分で戻れないこと**:
走行距離の残差は累積値 `s_meas − s` なので、6σ（約5mm）を超えるとゲートが効きっぱなしになり、距離が効かない間に加速度 a とバイアス b が
逆向きに膨らんで（加速度計は a+b しか縛らない）車速が上がり続け、最後は drive.c の 1 回転の折り返しの補正が累積の残差込みの「予測の増分」に
測定を合わせて 188m/s 付近に張り付く。初期化は起動時だけ。ホストで再現した引き金: 推定のずれ 2m/s 以上・前輪の空転（加速度計 0）・
加速度計（**±2g**）が飽和する衝突（2m/s から 10ms、3m/s から 20ms など）。加速度計の異常値・ループの停止（〜0.9s）では起きない。

- ゲートが `SPEED_KF_RESYNC_S`(20ms) 続いたら、その間の走行距離 ÷ 時間を車速として初期化し直す（`resync_count`。TELEMETRY には出さない）
- `SpeedKf_ExpectedDistanceStep` を `s − s_meas` から**その周期の予測で進んだ量**（`predicted_step_m`）へ。正常時は同じ値
- 最後の砦: |車速| > `SPEED_KF_MAX_SPEED_M_S`(20) で初期化（1 周期に半回転を超える外れは折り返しで見分けられないため）

## Pi 実機（surge-mk2）

接続情報の詳細と機密は `docs/setup_credentials.md`（gitignore 済み）。要点だけ:

- **Raspberry Pi 5 / Debian 13 (Trixie) / Python 3.13.5**
- **接続は Ethernet 直結**。Mac の USB アダプタ ↔ Pi。**Pi eth0 = 固定 `169.254.55.2`**。
  `ssh surge-mk2` で決め打ち接続（`~/.ssh/config` 設定済み、鍵は `~/.ssh/id_surge_mk2` でパスフレーズ無し。
  `sshpass` は今は不要）
- **UART**: `/dev/serial0 -> ttyAMA0`。io_node では `/dev/serial0` を使う（名前直書き禁止）
- リポジトリは **Mac → Pi へ rsync**（`~/surge_mk2`）。push は不定期（origin が遅れていることが多い）
- venv は `~/surge_mk2/.venv`（`--system-site-packages`）
- **電源は 5V/5A（27W）USB-C PD 必須**（USB給電では不足してハングする実績あり。解決済みだが忘れないこと）

### よく使うコマンド

```bash
rsync -az --exclude __pycache__ --exclude '*.pyc' --exclude .venv --exclude docs/setup_credentials.md \
  surge_mk2/ surge-mk2:~/surge_mk2/
ssh surge-mk2 'cd ~/surge_mk2 && .venv/bin/python -m unittest discover -s raspi/tests -t .'

# 反映（毎回rsyncを手打ちしていたのをスクリプト化。何を再起動すべきかはスクリプト冒頭の表を見る）
tools/deploy.sh                # GUI をビルドして rsync（既定・いちばん安全）
tools/deploy.sh --no-gui       # Python だけ直したとき
tools/deploy.sh --services     # systemd unit を入れ直す（--max-speed 等を変えたとき）
tools/deploy.sh --restart      # surge-telemetry / surge-camera を再起動（E-Stop 無関係）
tools/deploy.sh --restart-io   # ★ surge-io を再起動（E-Stop がラッチする。車体のそばで実行）
```

### mDNS（`surge-mk2.local`）— IP を探す作業は不要

`surge-mk2.local` が直結・Wi-Fi のどちらでも生きている方を指す（`ssh surge-mk2` /
`http://surge-mk2.local:8000/` が常に通る）。運用上ハマりやすい点:

- **`~/.ssh/config` に `AddressFamily inet` が必須。** 無いと直結があるのに IPv6 リンクローカル
  （Wi-Fi 経由）へ迷い込む。curl は `-4`
- **IF を落として戻すと avahi が再広告しないことがある。**
  「直結が生きているのに遅い」ときは `ssh surge-mk2 'sudo systemctl restart avahi-daemon'`
- **素の `ping 169.254.55.2` は直結が生きていても失敗しうる。**（169.254/16 のルート重複のため）
  直結の生死は **`ping -b <IF名> 169.254.55.2`** で確認（IF名は挿し直すと変わる）
- mDNS が使えない環境では MAC のベンダ prefix `2c:cf:67`（Raspberry Pi Ltd）で `arp -an` を grep
