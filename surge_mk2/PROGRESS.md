## Pi 実機（surge-mk2）

接続情報の詳細と機密は `docs/setup_credentials.md`（gitignore 済み）。要点だけ:

- **Raspberry Pi 5 / Debian 13 (Trixie) / Python 3.13.5**
- **接続は Ethernet 直結**。Mac の USB アダプタ(en18) ↔ Pi。
  **Pi eth0 = 固定 `169.254.55.2`**。`ssh surge-mk2` で決め打ち接続（`~/.ssh/config` 更新済み）
- **UART**: `/dev/serial0 -> ttyAMA0`。io_node では `/dev/serial0` を使う（名前直書き禁止）
- リポジトリは **Mac → Pi へ rsync**（`~/surge_mk2`）。git remote はあるが未 push
- venv は `~/surge_mk2/.venv`（`--system-site-packages`）。pyserial 3.5。
  gpiozero/lgpio は OS プリインストール利用

### ⚠ 原因不明の再起動が 2026-08-07 に**2回**

作業中に SSH が切れ、繋ぎ直すと `up 4 min` / `up 5 min`。**Pi が勝手に再起動している。**
`vcgencmd get_throttled` は `0x0`、温度 49.4°C で、電源・熱ともに異常なし。
Ethernet 直結のリンクも一度落ちている（Mac 側 link-local アドレスが変わった、
ping ロス 33%）が、これは Pi が落ちた結果と思われる。

**原因は未特定。1回目は journald の永続ログが無く前回起動のログが取れなかった。**
→ **永続ジャーナルを有効化済み（2026-08-07）。次に再発したら原因を追える。**

```bash
sudo journalctl --list-boots        # 起動履歴
sudo journalctl -b -1 -n 50         # 前回起動の最後
```

走行中に落ちるとハートビートが止まって E-Stop になる（フェイルセーフではある）が、
**信頼性の問題として残っている。再発したら必ずログを見ること。**

### ★ 不安定だった原因＝電源不足（解決済み）

Pi が「起動 → 数十秒 → ハングして消える」を繰り返していたのは **Pi 5 の電源不足**。
USB 給電では足りず、**5V/5A（27W）USB-C PD に交換して解決**。`vcgencmd get_throttled`=`0x0`。
緑 LED が点いていても OS はハングし得るので、LED だけで健全判断しないこと。

### Mac ↔ Pi の同期（現状の運用）

秘密鍵にパスフレーズがあり agent 未ロードのため、当面 **sshpass + パスワード**で運用
（パスワードは `docs/setup_credentials.md`）。バンビが一度 `ssh-add ~/.ssh/id_ed25519` すれば
鍵認証に移行できる。

```bash
export SSHPASS='<パスワード>'
OPT='-o StrictHostKeyChecking=no -o PreferredAuthentications=password -o PubkeyAuthentication=no'
rsync -az --exclude __pycache__ --exclude '*.pyc' --exclude .venv --exclude docs/setup_credentials.md \
  -e "sshpass -e ssh $OPT" surge_mk2/ pi@169.254.55.2:~/surge_mk2/
ssh surge-mk2 'cd ~/surge_mk2 && .venv/bin/python -m unittest discover -s raspi/tests -t .'
```

#### ★★ mDNS（`surge-mk2.local`）で運用する — 2026-08-08 に確立

**IP を探す作業はもう要らない。** `surge-mk2.local` が直結・Wi-Fi のどちらでも
生きている方を指すので、`ssh surge-mk2` / `rsync ... surge-mk2:` /
`http://surge-mk2.local:8000/` が常に通る。詳細は `docs/setup_credentials.md`。

**発端は「avahi が入っていない」という記録が誤りだったこと。** 実際には
`avahi-daemon` は `enabled` かつ `active` だった（picamera2 の apt 導入時に
依存で入ったとみられる）。**入れる作業ではなく、記録を直す作業だった。**

実測（`nmcli device disconnect eth0` でフェイルオーバーを検証済み）:

| 状況 | 解決先 | 実測 |
|---|---|---|
| 直結あり | `169.254.55.2` | ssh・HTTP とも 6ms |
| 直結なし | `192.168.68.87` | HTTP 10ms |
| 直結が復旧 | `169.254.55.2` に戻る | — |

- **`AddressFamily inet` を必ず付ける。** avahi は IPv6 リンクローカルも広告し、
  ssh は IPv6 を優先するので、**直結があるのに `fe80::…%wlan0`（Wi-Fi 経由）へ行く**。
  `~/.ssh/config` には設定済み。curl は `-4`
- **IF を落として戻すと avahi が再広告しないことがある。**
  eth0 を `nmcli` で切って戻したら、リンクは復活したのに mDNS が Wi-Fi 側しか
  返さなくなった。**`ssh surge-mk2 'sudo systemctl restart avahi-daemon'` で直る。**
  「直結が生きているのに遅い」ときはこれを疑う
- **素の `ping 169.254.55.2` は直結が生きていても失敗する。** `169.254/16` の
  ルートが複数 IF に重複して載り、既定が別の IF に出るため。
  **これで「直結が死んだ」と誤診した**（実際は 1000baseT でリンクしていた）。
  直結の生死は **`ping -b en18 169.254.55.2`** のように IF を明示して見る。
  **アダプタの IF 名は挿し直すと変わる**（en18 → en19 になっていた）
- **zsh は `$OPT` を単語分割しない。** `-e "sshpass -e ssh $OPT"` は rsync では
  効くが、`ssh $OPT host` と直に書くと `keyword ... extra arguments` で落ちる。
  `ssh` に渡すときは `-o` を並べて書くか `${=OPT}` にすること

（参考）mDNS が使えない環境で IP から探す場合は、**MAC のベンダ prefix
`2c:cf:67`（Raspberry Pi Ltd）**が速い:

```bash
for i in $(seq 1 254); do ping -c1 -t1 192.168.68.$i >/dev/null 2>&1 & done; wait
arp -an | grep -i 2c:cf:67          # → 192.168.68.87 のように出る
```

## 決まっていること

### UART プロトコル v0.4（確定・実装済み）

`docs/uart_protocol.md` が正。`raspi/proto/protocol.toml` が実装上の唯一の定義で、
そこから Python パーサと STM32 側 C ヘッダを生成する。

策定中に **`TELEMETRY` のフィールド順が Pi 側と STM32 側で食い違ったまま2往復した**ため、
定義を1箇所に閉じて機械生成する形にした。同じ事故を防ぐのが目的。

確定した主な内容:

- `TELEMETRY` LEN = 66。順序は `wheel_speed`(16) → **`odom_dist`(24)** → `accel`(32)
- `STATS` は**累積 u32**（増分ではない）。ロスしても情報が失われないため
- `VERSION_REQ` は `0x14`（`0x07` の双方向化はやめた）
- `param 0x0040` は LiDAR 出力フォーマットの **enum**（0=通常 / 1=強度付き / 2=圧縮）
- `CONFIG_SET` は**揮発**。Flash に書くのはステア原点と IMU キャリブレーションのみ
- CALIB モードは**廃止**。`calib_done` → `steer_center_valid` に改名
- `COMMAND` 途絶 100ms で自動ブレーキ / `TELEMETRY` 途絶は 100ms 警告・200ms FAULT

### 知覚・自己位置推定の方式 — **未定**

**LiDAR 主体とは限らない。カメラベースになる可能性がある。** Phase 3 で決める。
**LiDAR SLAM 前提で先回りして作らないこと。**

議論して分かったこと（`docs/architecture.md` §15-1 に記載）:

- **オドメトリ単独のデッドレコニングは成立しない。** 地磁気センサが無く、
  方位ドリフトが 1°/min。位置誤差は時間の2乗で効くので 1 m/s なら1分後に約 50cm ずれる
- LiDAR 主体にするなら、姿勢はスキャンマッチングが決め、オドメトリと IMU は
  歪み補正とマッチング初期値（100ms スケール）を担う
- **Phase 0〜2 はこの選択に依存しない**ので先に作れる

### 前輪オドメトリの扱い（どの方式でも共通）

エンコーダは**前輪 = 操舵輪**に付いている。`odom_dist` / `wheel_speed[FL,FR]` は
車輪自身の軌跡に沿った値で、車体中心線方向ではない。

- **射影は累積値ではなく差分に対して行う。** `cos(δ)` を累積距離に掛けるのは誤り
- 射影済みなのは `speed` だけ（STM32 側で処理）
- 前輪のスリップ量を見るときも射影が要る

### ★ ネットワーク — **Pi は常に STA。AP モードは実装しない**（2026-08-08 決定）

設計当初は「本番・屋外は AP モード」としていたが、**取りやめた。**
**屋外では Wi-Fi ルーターを持ち込み、Pi と PC の両方をそれに STA 接続する。**
Pi から見れば繋ぎ先の SSID が変わるだけで、**モード切替という操作が存在しなくなる。**
詳細と手順は `docs/architecture.md` §9.1。

| 場面 | 構成 |
|---|---|
| 据置開発 | 有線 Ethernet 直結（`169.254.55.2`） |
| 研究室での走行テスト | STA（`tplink`） |
| **屋外・大会** | **STA（持込ルーター）** |
| ルーターを忘れた/壊れた | **Ethernet 直結**（AP モードではない） |

**やめた理由（重い順）:**

1. **電波は「弱い側」が親機になると全体が弱くなる。** AP モードでは Pi の基板上の
   小さなアンテナが上限になり、距離が開くと STA より先に切れる。
   **切断は `cmd` の 150ms 途絶 → DISARM に直結する**（走行が勝手に止まる）。
   ルーターなら外部アンテナ・MIMO の強い側が親機になる
2. **ヘッドレスの Pi でモード切替に失敗すると救出手段が消える。** 屋外で AP 起動に
   失敗し STA にも戻れないと、その場では SD カードを抜くしかない。
   **STA のままなら、この事故が原理的に起きない**
3. **屋外の 5GHz は日本の電波法で W56 のみ**（W52/W53 は屋内限定）。W56 は DFS 必須で
   レーダー検出時に**最大60秒**通信が止まる。走行中の1分の途絶は使えない。
   → 屋外の AP は実質 2.4GHz 一択になり、混雑した会場で不利
4. **インターネットが来ないと NTP が効かず時計がずれる**（実際に約1日ずれた実績あり）。
   SIM 入りモバイルルーターなら解決する
5. Pi がビーコン送信と DHCP を負担しなくて済む（Phase 3 以降で効く）

**★ 屋外に出る前に、研究室で SSID を登録しておくこと。**
NetworkManager は知らない SSID に自動接続しない。**現地で登録しようとすると、
Pi に繋ぐ手段が直結 Ethernet しか無い状態になる。**

```bash
ssh surge-mk2 'sudo nmcli device wifi connect "SURGE-FIELD" password "********" ifname wlan0'
ssh surge-mk2 'sudo nmcli connection modify "SURGE-FIELD" connection.autoconnect-priority 20'
ssh surge-mk2 'sudo nmcli connection modify "tplink"      connection.autoconnect-priority 10'
```

これで**会場ではルーターの電源を入れるだけ**、研究室に戻れば自動で `tplink` に戻る。
**IP が変わっても mDNS があるので `surge-mk2.local` で届く。**

## STM32 実機との疎通（2026-08-07 確認済み）

`raspi/tools/probe_uart.py` で Pi ↔ STM32 の双方向通信を実機確認した。**ファームは v0.4 準拠。**

- 受信: `TELEMETRY` 50Hz / `STATS` 1Hz が正しい頻度で来る。**CRC・長さ・ロスすべて 0**
- 送信: `VERSION_REQ` → `VERSION` 応答（`protocol_version=0x0004` 一致、`fw_id=0x4D463303`）、
  `PING` → `PONG` 応答
- ベンチ状態の観測（正常）:
  - `accel_z ≈ +9.87 m/s²`（IMU 健全、静止で重力を検出）
  - `flags` に `fault_drive_undervoltage`(0x2000) + `armed`
    → **当時は「駆動バッテリー未接続」と解釈したが誤り**。2026-08-08 に判明した
    「Pi が DISARM を送ると駆動電源が切れる」現象を見ていた（後述）
  - `md_status` 全 `0x00`（`comm_ok` ビット無し）— この時点では MD 未接続。
    2026-08-08 に接続し、**駆動電源がある間は `comm_ok` が立つ**ことを確認済み
  - `batt_signal` 9.55V は正常、`batt_drive` 1.55V は未接続
- 診断ツール: `.venv/bin/python raspi/tools/probe_uart.py [--passive|--ping]`

**注意: STM32 に給電・配線されていないと 0 バイトになる**（最初はそれで空振りした）。

## io_node 中核（2026-08-07・方針 A で実装）

バス（ZeroMQ）を入れる前に、シリアル送受信と時刻同期だけの単体版を作り、実機で回した。

- `raspi/core/timesync.py` — PING/PONG 4タイムスタンプ。u32 μs の unwrap、min filter、
  線形回帰でドリフト推定。**短い時間スパン（<15秒）では回帰せずオフセットのみ**にフォールバック
- `raspi/io/serial_link.py` — pyserial ラッパ。poll()/send() で T1/T4 を ns で取得
- `raspi/nodes/io_node.py` — 起動時 VERSION 照合 → PING(5Hz/warmup 20Hz) →
  **COMMAND は常に DISARM（安全ハートビート、arm は絶対しない）** → 受信集計 → ライブ表示
- テスト計 50件（proto 37 + timesync 13）。実行:
  `.venv/bin/python -m raspi.nodes.io_node --duration 10`

### 実機での実証結果（電源修正後・安定）
- VERSION 一致（0x0004、fw=0x4D463303="MF3"）、health INIT→OK
- TELEMETRY 50Hz / LIDAR 120Hz(12セクタ) / STATS 1Hz を正しい頻度で受信
- **loss=0・crc=0・resync=0B**（45秒実証）。リンクは完全にクリーン

### 確定した実機の性質（2つ）

1. **STM32 のクロックが約 -3360ppm ドリフトしている。**
   4回の実行で -3339/-3352/-3353/-3362ppm と安定。0.336% は水晶にしては大きく、
   **STM32 が外部水晶でなく内蔵 RC(HSI, ±1%級)で μs タイマを回している**とみられる。
   時刻同期の回帰補正がこれを吸収するので実害なし。**15秒未満は回帰せずオフセットのみ**の
   ガードも入れた（短窓だとジッタで傾きが暴れて -3300 のような値が出るため）。

2. **STM32 は送信優先度キューで SEQ を数個ぶん並べ替える**（TELEMETRY が LIDAR を追い越す）。
   逆行しても実フレームは全部届く（`tx_drop=0`）。
   → **framing.py の loss 計算バグを修正**（逆行を 254 ロスと誤計上していた）。
   逆行は `reordered` として別集計し、飛び計上を相殺して loss=実ロスだけにした。

### 補足: MD は未接続（2026-08-07 時点の話。08-08 に接続済み）
`STATS.md_rx_error` が巨大・`md_rx_count=0`・`md_status=0x00`。モータドライバ未接続の
ベンチ状態なので正常。この間 temp/current/wheel_speed は当てにしない。

## ★★ 駆動電源が落ちる件 — 原因判明（2026-08-08）

**結論: ファームは仕様どおり。バグではない。落としていたのは Pi 側だった。**

### 何が起きていたか

STM32 の `ApplyRasCommand()` は、COMMAND が届いている間
`Power_SetDrivePower(&power, arm_requested)` を実行する。
**io_node は安全のため常に `arm=0` を送っている**ので、
**Pi が COMMAND を送り始めた瞬間に駆動電源が OFF になる。**

記録した `.sfl`（送信フレームも残している）から確定した:

```
初 COMMAND   : Pi 時刻 0.001s
駆動電圧の崩壊: Pi 時刻 0.015s（STM32 稼働 50.04s、9.60V から）
               差 +13 ms
COMMAND は 89.7Hz・100ms 超の間隔 0回・arm ビットは常に 0
cmd_seq_echo は 0..255 で変化 → STM32 は確かに受信していた
```

**検証実験（COMMAND を一切送らず 60秒受信のみ）**:

```
駆動 11.00V / 信号 10.90V を 60秒間まったく落とさず維持
```

### これで訂正されること（過去の記録は誤りだった）

1. **「駆動バッテリー未接続」は誤り。** ずっと繋がっていて **11.00V** あった。
   過去のセッションで一貫して `batt_drive = 1.55〜1.60V` だったのは、
   **io_node が DISARM を送って電源を切った後の残留電圧**を見ていたため
2. **「ステアがストール」は誤り。** ST 電流 0.91A は一定で急増はない。
   1秒間隔のサンプルで通信断の過程を拾って誤読した
3. **「駆動電流センサが効いていない」は根拠不足。** スイッチが開いていれば 0.00A は正常
4. **`VOLTAGE_P` (PC3) のタップは DRIVE_POWER スイッチの後ろ**（切った瞬間に落ちるため）
5. **MD の配線は正常。** 駆動電源がある間は `md_status` に `comm_ok` が立つ。
   MD の通信断は電源喪失の**結果**

### ここから効いてくること

**Pi が接続していて arm していない間、駆動電源は必ず OFF になる。**

- **ベンチで駆動電源を上げたまま観測することはできない**（COMMAND を送った時点で落ちる）
- 駆動系の確認をするには **arm を通すしかない**
- 逆に、受信だけしたいときは**何も送らなければ**電源が保たれる

### ⚠ フェイルセーフの向きが逆（STM32 側と要相談）

| Pi の状態 | 車両 |
|---|---|
| **繋がっていない** | **ARMED + 駆動電源 ON**（監視者なし。BUTTON1 で走行テストが走りうる） |
| 繋がって DISARM 送信 | DISARM + 駆動電源 OFF |

`flags = 0x0584`（ARMED）を Pi 沈黙中に観測。`uart_timeout` は立たない
（その起動以降 COMMAND を1度も受けていないとタイムアウト判定が始まらないとみられる）。
ベンチの BUTTON1 単独テスト用の設計と思われるが、**監視者がいないときのほうが
動ける状態**になっている点は共有しておくこと。

記録: `logs/drive_20260808_153220.sfl`（崩壊の瞬間）/
`logs/passive_20260808_154409.sfl`（60秒維持の証拠）

## ★ arm を通す最小実験 — 合格（2026-08-08・車輪を浮かせて実施）

`raspi/tools/arm_test.py`。**車輪が動きうるので `--wheels-clear` を付けないと動かない。**

```
段階1  arm=0 / DISARM :  1.55V  ← 電源 OFF（再現）
段階2  arm=1 / DISARM : 11.45V  ← 電源維持、トルク 0、後輪 +0.003/+0.001 m/s
段階3  arm=1 / MANUAL : 11.45V  ← 電源維持、トルク 0、後輪 +0.000/-0.001 m/s
                        MD 0x31 ×3（全部 comm_ok）  flags 0x0585
```

**`arm=1` で駆動電源が維持され、MANUAL で速度制御ループが回っていても
目標速度0なら駆動トルクはゼロ。** これで駆動系を安全に通電・制御できる。

### 安全のための作り

- **E-Stop ハートビート必須**（GPIO が開けなければ実行しない）
- 目標速度は**常にゼロ**。舵角は**現在位置を保持**（中央へ戻す動きを起こさない）
- **`torque_cmd` が本命の判定。** 「車両が自分で駆動する」直接の証拠であり、
  MD 通信に依存せず常に有効。車輪速度は惰性・外力と区別できないので補助
- 車輪速度は **MANUAL のときだけ**見る（DISARM 中は駆動されないので無意味）
- **`comm_ok` が無い間の `wheel_speed[RL/RR]` は無効値**として除外する
- **150ms 継続したときだけ中断**（comm_ok 復帰直後は MD の古い値が数フレーム残る）

### ★★ `wheel_speed[FL,FR]` は低速で使い物にならない（実測）

静止20秒の測定（`logs/odom_20260808_161532.sfl`）:

| 量 | 静止時の値 | 判定 |
|---|---|---|
| `odom_dist` FL / FR | +0.8mm / 0.0mm（20秒） | **正常** |
| `speed` | 平均 +0.000、範囲 ±0.026 m/s | **正常**（ローパス済み） |
| `wheel_speed[FL]` | 中央値 0.000 だが **±12 m/s** が **72%** のサンプル | **使用不可** |
| `wheel_speed[FR]` | 同様に 26% のサンプルが 0.5m/s 超 | **使用不可** |

スパイクは単発ではなく**最大15サンプル連続**する。符号が交互に振れるため
平均と積分（`odom_dist`）はきれいなまま。粗い絶対角エンコーダを微分した結果で、
**`speed` に掛かっているローパスが `wheel_speed[]` には掛かっていない**とみられる。

**Pi 側の指針:**
- **低速域で `wheel_speed[FL,FR]` を使わない。** 静止判定・スリップ検出には使えない
- 車体速度は `speed` を使う（射影済み・ローパス済み）
- 輪ごとの速度が要るなら **`odom_dist` を差分する**（積分値はきれい）
- STM32 側に「`wheel_speed[]` にもフィルタを掛けるか、生値と明示するか」を相談する価値あり

### 台上試験の構造的な制約

**台上では前輪（センシング）と後輪（駆動）が機械的に切り離される。**
前輪を手で回すと `speed` が非ゼロになり、MANUAL の速度制御が
「減速しろ」と後輪に制動トルクを出す（実際に -0.0283 N.m を観測して中断した）。
**MANUAL に入る前に `speed` の静止を確認すること。**
閉ループ速度制御そのものは台上では正しく検証できない。

## ログ記録 `.sfl`（2026-08-07）

### なぜ MCAP を実時間パスに置かなかったか

設計書（`docs/architecture.md` §11）はログを MCAP と決めているが、**MCAP はトピック
（意味のあるメッセージ）の器**であり、`msgs/`（msgspec 型）と `bus/` が決まってから。
今それをやるとメッセージ型を先に凍結することになる（知覚方式が Phase 3 まで未定なのに）。
（当時は「Mac に pip が無い」と誤解しており、それも理由に挙げていた。
前提は誤りだったが、**実時間パスに外部依存を持ち込まない**という判断自体は維持する。）

そこで **生フレームログを先に作り、MCAP は後段のエクスポータ**にした。

- **生フレームこそが真実** — CRC エラー・SEQ 逆行・リンク断は、デコード後の
  きれいなメッセージには残らない。デバッグで要るのはそこ
- protocol.toml が変わっても、**過去のログを新しいパーサで読み直せる**
- 実時間で回る io_node に外部依存を持ち込まない（stdlib のみ）

### 形式

`raspi/rec/framelog.py` のモジュール docstring が正。要点だけ:

- 32B ヘッダ + `(kind, ptype, seq, t_ns, len, payload)` 14B の追記レコード
- `kind` = RX / TX / META(JSON) / EVENT(JSON)
- 時刻は **Pi CLOCK_MONOTONIC の絶対値**。TELEMETRY 内の STM32 時刻や
  TimeSync の推定と突き合わせるときに変換を挟まないため
- **末尾が切れていても前半は必ず読める**（追記のみ・インデックス無し）。
  正常終了したログには `close` イベントが入るので、電源断ログを判別できる
- **flush はレコードの t_ns 基準（既定1秒）＋4096件の歯止め**。
  時刻だけで判定すると、t_ns が想定外だと永久に flush されず記録が黙って消える

フレームに現れない情報は EVENT で残す:
`handshake` / `health` 遷移 / `linkstats`（1Hz・CRC エラーや resync バイト数、
時刻同期の推定値）。**捨てたフレームは RX レコードに残らない**ので、
数字として別に持たないと再生しても異常が見えない。

### 使い方

```bash
# 記録（--log は値なしで logs/ に自動命名、*.sfl でファイル指定）
.venv/bin/python -m raspi.nodes.io_node --duration 20 --log

# 要約（頻度・期待Hzとの比較・最大間隔・リンク統計・イベント）
python3 -m raspi.tools.logcat logs/surge_20260807_055014.sfl
python3 -m raspi.tools.logcat run.sfl --dump 40 --type TELEMETRY
python3 -m raspi.tools.logcat run.sfl --csv telem.csv --type TELEMETRY  # 物理量で出る
```

### 実機での実証（20秒・STM32 接続）

```
LIDAR_SECTOR 2403 (120.1Hz)  TELEMETRY 998 (49.9Hz)  PONG 144  STATS 20 (1.0Hz)
COMMAND 2001 (100.0Hz)  PING 144  VERSION_REQ 1
loss=0 crc=0 reordered=96   0.34MB / 20s ≈ 17KB/s ≈ 61MB/時
```

送受信フレーム数がログのレコード数と完全一致。Mac に持ち帰って CSV 化まで確認済み。
**記録が壊れても走行は止めない**（ログ書き込みの例外はカウントするだけでループ継続）。

ログだけで実機に触らず分かったこと（＝この仕組みの狙い通り）:

- `flags` は `0x2580`。`imu_ok` / `lidar_ok` / `steer_center_valid` が立ち、
  `armed` は立っていない（DISARM 固定が効いている）
- `uart_timeout` は**最初の1フレームだけ ON**（998 中1）。io_node 起動前は
  COMMAND が来ていないので当然で、0.034s には消えている。異常ではない

### ★ 実データで見つかった定義の誤り — `rot_speed_dps`（修正済み）

`LIDAR_SECTOR.rot_speed_dps` を **`scale = 0.01` deg/s** と定義していたが、
**実ファームは deg/s をそのまま送っていた**。**定義が誤りでファームが正しい。**

- 生値の中央値 **3594**（2403 セクタ）。同フレームの `duration_us` から逆算した
  回転速度は **3642 deg/s** → スケール 1.0 なら一致、0.01 だと 100倍ずれる
- そもそも **u16 × 0.01 は最大 655.4 deg/s** で、実回転（約 3600 deg/s）を表現できない

**2026-08-07 に `scale = 1.0` へ修正**（`protocol.toml` 3箇所 → 再生成、
`uart_protocol.md` §5.1/§5.2 と変更履歴）。

- **ワイヤ形式は無変更**。生成物の差分は Python の `META` と C のコメントだけで、
  構造体サイズもオフセットも v0.4 のまま（`cc -Werror` + `offsetof` で検証済み）
- `protocol_version` は **0x0004 のまま**。**STM32 側の変更は不要**
- **修正前に記録した `.sfl` が、新しい定義でそのまま正しく読み直せた**
  （CSV に `3589.0 deg/s` と出る）。生フレームで残す設計の狙い通り

#### 教訓

**スケールを決めたら「その型で実値が表現できるか」を必ず検算する。**
u16×0.01 の上限 655 deg/s は、LD06 の 10 rps = 3600 deg/s を最初から表現できなかった。
`protocol.toml` は単一定義にはなっているが、値域の妥当性までは見てくれない。

**他の全フィールドも同じやり方で監査済み（2026-08-07）。`rot_speed_dps` 以外は問題なし。**
電源系は 8セル NiMH（8.0〜11.2V）に対し u8×0.05 = 0〜12.75V で余裕 1.55V、
電流も過電流しきい値（駆動 5.0A / シグナル 3.0A）に対し 2.5倍 / 1.7倍 とれている。

### ★ GUI の点群が左右反転していた（2026-08-08・修正済み）

**LD06 は PCB 面を下にして裏向きに取り付けてある。** 0° は機体前方を向いているが、
角度が増える向きが上から見て車両座標（反時計回りが正）と**逆**になる。
STM32 は「センサ基準の角度をそのまま送り、解釈は Pi 側で行う」設計（`stm32_interface.md` §7.1）
なのに、`ScanAssembler` が `sector_idx * 30 + i` をそのまま度として使っていたのが原因。

**`raspi/msgs/convert.py` の `ScanAssembler` 1箇所だけ**で
`車両角 = (360 - センサ角) % 360` に直す。`Scan.dist` の添字は車両角なので、
以降のノード・GUI・地図生成は反転を意識しなくてよい。

- 反転で**1周は添字の降順に取得される**ため、`sector_t_ns` / `sector_dur_us` /
  `sector_seen` も車両座標のセクタ番号 `11 - sector_idx` へ移した。
  GUI の欠測セクタ表示（扇形ハッチ）が点群とずれないようにするため
- セクタ内の時刻の向きも逆になり、**30° の境界も 1° ずれる**。セクタ `s` が持つのは
  `30*s+1` 〜 `(30*s+30) % 360` で、`30*s` の点だけ隣のパケット由来。
  点の時刻は**車両角をセンサ角に戻してから**引くこと（式は `types.py`）。
  車両角のまま `30*s+j` と分解すると `j=0` の点で**最大 108ms（ほぼ1周）外す**。
  歪み補正はまだ実装していないが、実装時に必ず踏むので回帰テストで固定してある
- `t_capture` は「先頭の非ゼロ」ではなく**最小**を取るように変更。
  添字が時刻順に並ばなくなったため
- ワイヤ形式・`protocol_version` は無変更。**STM32 側の変更は不要**
- 回帰テスト `test_sensor_angles_are_mirrored_into_the_vehicle_frame` を追加
  （センサ 90° → 車両 270°、前方 0° は反転軸上なので不動）
- 回帰テスト `test_point_times_stay_continuous_across_sector_boundaries` を追加
  （全周360点の時刻が等間隔に並ぶか。境界の分解ミスがあれば1セクタぶん飛ぶ）

**STM32 側で直さないのは意図的。** 0°/180° がセクタ境界に乗るため1セクタが出力側の
隣接2セクタに分裂するうえ、実際に試したところ原因不明の通信エラー増発が再現している
（STM32 の `src/sensing/lidar.h` に経緯あり）。

## replay_node（2026-08-07）

`.sfl` を実時間で流して io_node の代わりをするノード。**これが事実上のシミュレータ代わり。**
実車・STM32・シリアルなしで知覚・経路生成・GUI を開発できる。pyserial にも依存しない。

### 実機と食い違わせないための作り

- **`LinkTracker`（`raspi/core/link_tracker.py`）を io_node と共有する。**
  受信ディスパッチ・時刻同期・health 判定を2箇所に書けば必ずズレる
  （プロトコル定義が2箇所にあってズレた前科がある）。io_node も載せ替えた
- **ログ時刻の座標系のまま動かす。** 「今」は壁時計ではなく再生カーソル。
  壁時計は待ち時間の計算にしか使わない。**何度流しても同じ結果になる**
- **PING の T1 は TX レコードから復元。** PONG(RX) と突き合わせるので、
  時刻同期は記録時とまったく同じ4タイムスタンプで動く
- **フレームの無い区間でもカーソルを 10ms 刻みで進めて health を更新する。**
  リンクが完全に切れた区間はレコードが空になるので、次のフレームまで待つ実装だと
  DEGRADED/FAULT を丸ごと見落とす
- CRC エラー・再同期バイト数は捨てたフレームなので復元不能 →
  1Hz の `linkstats` イベントから読み戻す（**そのために記録している**）

### 使い方

```bash
python3 -m raspi.nodes.replay_node logs/run.sfl               # 等速
python3 -m raspi.nodes.replay_node logs/run.sfl --speed 4     # 4倍速
python3 -m raspi.nodes.replay_node logs/run.sfl --speed 0     # 最速（待たない）
python3 -m raspi.nodes.replay_node logs/run.sfl --start 12 --end 18
python3 -m raspi.nodes.replay_node logs/run.sfl --verify      # 記録と突き合わせ
```

`--start` は早送りで**状態を温めてから**その位置に入る（冷えた状態から始めても役に立たない）。

### `--verify` — ログが十分かを検査する

再生結果を記録内容と突き合わせる。**合わなければ「ログに足りない情報がある」**という意味で、
再生器のバグとして片付けないこと。実機ログ（20秒 / 3566フレーム）で全項目一致:

```
✓ 受信フレーム数: 再生 3566 / 記録 frame_ok 3566
✓ クロックドリフト: 再生 -3366.35ppm / 記録 -3366.35ppm
✓ 時刻同期サンプル数: 再生 144 / 記録 144
✓ health 遷移: 再生 [('INIT','OK')] / 記録 [('INIT','OK')]
```

別の15秒ログでも `offset` が実機ライブと**完全一致**（`-10961548404 ns`）。
20秒ぶんの再生に 0.01秒。テスト計 **127件**（+40: link_tracker 20 / replay_node 20）。

## GPIO E-Stop ハートビート（2026-08-07）

`raspi/io/gpio.py`。GPIO6 に 100Hz の矩形波を出し続け、STM32 が「エッジが 50ms
途切れたら即ブレーキ」で受ける（`docs/architecture.md` §7.1）。

### 設計上ここだけは外せない2点

**1. ハードウェア PWM を使ってはいけない。**
PWM に任せると **Python プロセスが死んでも波形が出続け**、STM32 が「Pi は生きている」と
誤認して安全機構が丸ごと無効になる。波形はプロセス自身が出す。プロセスが死ねば
OS が GPIO を解放し、プルアップで High に張り付いてエッジが消える＝フェイルセーフ。

**2. スレッドが生きているだけでは不十分 → `kick()`。**
専用スレッドで叩くだけだと、**メインループが固まってもスレッドが元気に波形を出し続ける**。
それでは「Pi のフリーズ」を検出できない。メインループが毎周 `kick()` を呼び、
100ms 途切れたら**ハートビート側が意図的に波形を止める**。

```
メインループ停止 → kick 途絶(100ms) → 波形停止 → STM32 が 50ms で E-Stop
                                                  合計およそ 150ms
```

### 実機での実測（Pi 5・STM32 接続・60秒）

```
edges=12000 (100.0Hz)  最大遅れ=0.46ms  停止=0回  skip=0  {'<1ms': 12000}
同時に frames_ok=10608 crc_err=0 loss=0   ← シリアルにも影響していない
```

**12000 エッジ全部が 1ms 未満の遅れ。最悪 0.46ms は 50ms の予算に対して約 108倍の余裕。**
→ **Python のスレッドでこれを回して問題ない**と判断できる。

フリーズ検出も実機で確認（`kick` を止めると 19本＝タイムアウト分だけ出して停止、
再開すると 100Hz に復帰）。ハートビートの実測値は `.sfl` の `linkstats` と
`heartbeat_start` / `heartbeat_stop` イベントに残る（GPIO はフレームに現れないため）。

### 仕様からの逸脱を1つ（意図的）

仕様は「オープンドレイン推奨」だが**プッシュプルにした**。Pi も STM32 も 3.3V で
電位差が無く、gpiozero がオープンドレインを直接持たないため入出力切替で模擬すると
毎秒 200回の切替でジッタが増える。Pi 電源断ならピンはハイインピーダンスになり
STM32 側プルアップが High を保つので、フェイルセーフ性は失われない。

### STM32 側の確定挙動（2026-08-07 に判明）— 詳細は `uart_protocol.md` §9

STM32 側は**実装済み**（2kHz ポーリング）。当初「ハートビートを送っていないのに
`estop_active` が立たない」のを不審に思ったが、**仕様どおりだった**:

> ハートビートを**一度も見ていない間は緊急停止を発動しない**（ベンチ確認のため）。
> エッジを10回（50ms 分）数えて初めて「Pi が繋がっている」とみなす。

**Pi 側が守ること:**

- **出し始めたら出し続ける。途中でやめると E-Stop がラッチする。**
  解除には**車両のボタン2を人間が押す**必要がある（自動復帰しない）
- 逆に**一度も出さなければ発動しない**ので、ベンチ診断では `--no-heartbeat` を使う
- **`estop_active` 中は `COMMAND` が一切効かない。** リンク断（health）とは別の軸
- 発動しても**駆動電源は切られない**（切ると MD が制動できず惰行して停止距離が伸びる）

これを受けて Pi 側に入れた対応:

- `LinkState.estop_active` / `.drive_power_locked` を追加し、
  **立ち上がりを `on_latch` コールバックで捉えて `.sfl` に `latch` イベントで残す**。
  人間の物理操作でしか戻らないので、立った瞬間を逃すと原因が追えなくなる
- ステータス行に `★E-STOP発動中(車両のボタン2で解除)` を出す（16進フラグに埋もれさせない）
- LED は **E-Stop を health より優先**（赤 4Hz 点滅＋0.6秒ブザー。FAULT の 2Hz/0.2秒と区別）
- io_node 起動時と終了時に「止めるとラッチする」ことを明示表示

**オープンドレインは「でよい」と確認された**（基板に外付けプルアップあり）。
プッシュプルのままで問題ないが、切り替えたければ電気的にはどちらでも通る。

### ★ E-Stop 端から端までの動作確認 — **合格**（2026-08-07・実車）

`raspi/tools/estop_test.py`。**ファーム・配線・Pi 側のどれかを触ったら回し直すこと。**
「波形は出ている」だけでは安全機構が効いている証拠にならない。

```
.venv/bin/python -m raspi.tools.estop_test                  # 4項目を通しで検査
.venv/bin/python -m raspi.tools.estop_test --release-only   # 後片付け（解除だけ待つ）
```

| 検査項目 | 結果 |
|---|---|
| ハートビート中は正常運転（E-Stop なし） | ✓ |
| **途絶でラッチする** | ✓ **64ms**（3回測って 65 / 60 / 64ms。期待 50〜90ms） |
| **自動復帰しない**（ハートビートを戻しても解除されない） | ✓ |
| ボタン2で解除される | ✓ |

`estop_active` 発動時の `flags` は **`0x2588`**（通常 `0x2580` + bit3）。

検査は E-Stop をラッチさせるので、**開始時にラッチしていたらまず解除を待つ**構造にした。
その解除待ちがそのまま「人間の操作でしか戻らない」ことの確認になっている。
**終了時に車両をラッチしたまま残さない**（残った場合は `--release-only` で戻せる）。

判定は「安全項目の合否」と「車両をラッチしたまま終えたか」を**別に集計する**。
混ぜると「安全機構が壊れている」と「ボタンの押し忘れ」が区別できなくなる。

#### 1回目が不合格だった件（原因判明・実装の問題ではない）

初回は「ハートビートを止めても `estop_active` が立たない」で落ちた。
**原因は STM32 のファーム書き込み忘れ**（E-Stop 未実装のファームが載っていた）。
ログがそれを裏付けている: 受信が **8.01秒でぴたりと途絶**し（TELEMETRY 403本で終わり、
以降 90秒間ゼロ）、書き込み開始の瞬間と一致する。2回目は 95秒間 4744本で正常。

**検査は正しく「反応なし」を捉えていた。** 生ログを残していたから、
「ツールのバグ」ではなく「載っているファームが違う」と切り分けられた。

#### 配線の切り分け方（同じことが起きたとき用）

Pi 側がシロであることは、ソフトを疑う前にハードで確かめられる。

```bash
pinctrl set 6 ip pd && pinctrl get 6   # 内部プルダウンを掛けて読む
```

**`hi` のままなら外部プルアップが吊っている＝線が繋がっている。**
未接続のピン（GPIO5/16 で対照実験した）は `lo` になる。
出力の駆動確認は `pinctrl get 6` が `op dh|hi` / `op dl|lo` と書いた値に追従するかを見る。

### LED — 配線確認済み・表示仕様も実機で目視確認（2026-08-08）

**GPIO19=緑 / GPIO13=赤、アクティブ High**（`raspi/tools/led_test.py` で確認）。
ブザー（GPIO18）は**まだ鳴らしていない**。

表示の設計は「異常」で一括りにせず、**人間が何をすべきか**で分けた。
実機で 8パターンを目視確認済み（`raspi/tools/led_demo.py`）。

**緑 — 生存と可動性**

| 緑 | 意味 |
|---|---|
| 消灯 | **Pi が動いていない**（電源断・フリーズ・未起動） |
| 速い点滅 4Hz | 起動中・通信待ち（INIT） |
| 短い明滅 1Hz | 正常・**DISARM**（動かない） |
| 点灯 | **ARMED — 車輪が動きうる** |

**「点いている」ことより「変化し続けている」ことに意味を持たせた。**
明滅そのものがソフトウェアが生きている証拠で、固まれば LED も固まる。
**原因不明の再起動が2回**起きているので、車体を見るだけで判別できる価値がある。
一番安全に関わる ARMED だけを点灯しっぱなしにして最も目立たせる。

**赤 — 異常の重さ（＝要求される行動）**

| 赤 | 意味 | すべきこと |
|---|---|---|
| 消灯 | 異常なし | — |
| ゆっくり点滅 1Hz | 警告（低電圧・DEGRADED） | 覚えておく。走行は継続可 |
| 速い点滅 4Hz | FAULT（リンク断） | 見に行く。自動復帰しうる |
| 点灯 | **ラッチ**（E-Stop / 駆動電源） | **今すぐ車両を触りに行く** |

点灯しっぱなしを最上位にしたのは、**ラッチ系だけが「歩いて車両まで行く」必要がある**から。
緑と赤は独立した軸なので、ARMED かつ警告あり、のような同時表示もできる。

状態は `Indication`（`raspi/io/gpio.py`）に集約し、io_node が `LinkState` から作る。
ピンが開けなければ黙って無視する（表示が出ないだけで走行に影響しない）。

### 使い方

```bash
.venv/bin/python -m raspi.nodes.io_node --duration 60 --log   # 既定でハートビート ON
.venv/bin/python -m raspi.nodes.io_node --no-heartbeat        # 出さない（診断用）
.venv/bin/python -m raspi.nodes.io_node --require-gpio        # GPIO が開けなければ起動しない
```

GPIO が開けない環境（Mac など）では警告を出して続行する。`--require-gpio` で止められる。

## カメラの実力測定（2026-08-08）

`raspi/tools/camera_probe.py`。**「映った」で終わらせないための道具。**
`camera_node` を書く前に、設計を変えさせ得る数字を先に取った。

### 構成

- **imx219（Camera Module v2, 8MP）×2**。別々の CSI ポートで両方検出
- 対応モード: `640x480@200fps` / `1640x1232@81fps` / `1920x1080@47fps` / `3280x2464@21fps`
- **`python3-picamera2` は apt でしか入らない**（libcamera の Python バインディングは
  C++ を meson でビルドしたもの。pip 不可）。**`--no-install-recommends` で入れること** —
  既定だと PyQt5 / Qt 一式（プレビュー GUI 用）まで付いてくる
- 導入のため **Pi を Wi-Fi に接続した**（`docs/setup_credentials.md`）。
  eth0 直結は維持される

### ★ `SensorTimestamp` は `CLOCK_MONOTONIC` 基準だった

**これが一番知りたかったこと。**

```
SensorTimestamp と CLOCK_MONOTONIC の差:               31.3 ms （＝パイプライン遅延）
                  CLOCK_REALTIME  の差:  1,786,166,048,935.7 ms
```

`t_capture` にそのまま使える。**STM32 のような時刻同期は要らない。**
`docs/architecture.md` §6.3 の「全メッセージが Pi の `CLOCK_MONOTONIC` で
`t_capture` を持つ」前提がそのまま通る。

### 実測（2台同時・カメラごとにスレッドを分けた場合）

| 解像度 | fps | 取得レイテンシ | 帯域/台 | 備考 |
|---|---|---|---|---|
| 640x480 | **30.0** | **5.9ms** | 28 MB/s | センサのネイティブモード |
| 1280x720 | 30.0 | 23.8ms | 83 MB/s | **ネイティブに無い**→縮小されて遅い |
| 1640x1232 | 30.0 | 15.7ms | 182 MB/s | ネイティブモード（2MP） |

- フレーム間隔の揺らぎは **±0.01ms**。フレーム落ちなし
- **1280x720 は 1640x1232 より遅い。** ネイティブモードに無く libcamera が縮小するため。
  **解像度を選ぶときはネイティブモードから選ぶこと**
- 640x480 の 28 MB/s は設計書の見積り 27 MB/s とほぼ一致 →
  **「画像は ZMQ に流さず共有メモリ」の判断は正しい**

### ★ io_node と共存できる

カメラ2台を 30fps で回しながら io_node を 30秒:

```
frames_ok=5326  crc_err=0  loss=0     ← リンクは完全にクリーンなまま
CPU: user 3-4% / system 1% / idle 95-96%（4コア）
```

**余裕は桁違いにある。** プロセスを分ける設計はそのままで問題ない。
ただし**取得しているだけで何も処理していない**数字である点に注意
（ISP はハードウェアが担当）。知覚処理を載せたら当然変わる。

### ★ 設計上の落とし穴 — 1スレッドで2台を順に取ってはいけない

最初の測定でカメラ1だけレイテンシが **38.1ms**（カメラ0は 5.6ms）になった。
カメラ1単独で測ると 5.5ms だったので、**カメラではなく測り方の問題**と判明。

1スレッドで2台を順にブロッキング取得すると、1台目を待つ間に2台目のキューが
1フレーム溜まり、**常に1フレーム古いものを取り続ける**（+33ms）。
カメラごとにスレッドを分けたら両方 6.0ms になった。

**`camera_node` は必ずカメラごとに独立して取得すること。**

### 補足: ネットが無いと壁時計がずれる

Wi-Fi を繋ぐまで NTP が効かず、Pi の時計が約1日ずれていた
（apt の署名検証が「まだ有効時刻でない」で失敗して発覚）。
**記録データは全部 `CLOCK_MONOTONIC` 基準なので影響を受けない** —
この設計判断が効いた形。ただし `.sfl` のファイル名と `t0_unix_ns` は壁時計依存。

## camera_node と共有メモリリング（2026-08-08）

`raspi/bus/shm_ring.py` + `raspi/nodes/camera_node.py` + `raspi/tools/shm_view.py`。
設計は `docs/architecture.md` §6.2 の「画像は ZMQ に流さず共有メモリ」そのまま。

### 構造

```
┌ ヘッダ 64B ────────────────────────────────────┐  /dev/shm/surge_cam0
│ magic / n_slots / slot_bytes / w / h / stride  │
│ format / write_seq                             │
├ スロット表 32B × n_slots ──────────────────────┤
│ seq(seqlock) / t_capture_ns / frame_id / nbytes│
├ データ領域 slot_bytes × n_slots ───────────────┤
└────────────────────────────────────────────────┘
```

- `write_seq` は累積フレーム数。書き込み先は `write_seq % n_slots` なので
  **読み手は「最新」を一意に特定できる**
- バスに流すのは `FrameDesc`（名前・スロット・seq・`t_capture_ns` など数十バイト）だけ。
  **画素は流さない**
- 640x480x3 × 8枚 = **7.4MB / カメラ**

### seqlock — 上書きを「検出できる」ようにする

8枚あれば書き手が同じスロットに戻るまで 266ms（30fps）あり、実用上は衝突しない。
問題は**衝突したときに気づけないこと**なので seqlock を入れた。

```
書き手: seq += 1（奇数=書込中） → 画素を書く → seq += 1（偶数=安定）
読み手: seq を読む → 画素を読む → seq を読み直す → 変わっていたら破棄
```

**正直に書くと、Python には明示的なメモリバリアが無い**ので厳密な保証ではない。
実効的な守りは段数を十分取ることで、seqlock はその**検出手段**。
`still_valid()` が False なら捨てて次を待つ。

### 実機での実証

カメラ2台 + io_node + 読み手2プロセスを**同時に**走らせた:

```
camera_node : cam0/cam1 とも 30.1fps 落ち0  共有メモリ書込 平均223-261μs 最大536μs
io_node     : frames_ok=3566 crc_err=0 loss=0        ← シリアルは無傷
読み手×2    : 29.7 / 29.9fps  上書き検出0  ゼロコピー確認済み
撮像→読み手 : 中央値 11-12ms
```

`shm_view --save` で PNG に落として**画素が本物であることを目視確認**した
（配管が通っただけでは画が正しい保証にならない）。PNG 書き出しは zlib のみで
外部依存なし。

### ★ 踏んだ落とし穴2つ

**1. DMA バッファは `release()` 前に共有メモリへ書くこと。**
`req.make_array()` は DMA バッファへの view であって、`release()` すると無効になる。
最初 release してから書く実装にしていた（解放済みメモリを読む）。
コピーは「DMA → 共有メモリ」の1回だけで済む。

**2. 参照を残したまま共有メモリを閉じられない。**
numpy 配列や memoryview が生きていると `BufferError`。握り潰すと後で
`SharedMemory.__del__` が「Exception ignored」を吐いて原因が追えなくなるので、
**`close_blocked` を立てて呼び出し側に見せる**ようにした。
読み手は使い終わったら参照を手放すこと。

### ★ RGB / BGR — 実測で確定し、修正済み（2026-08-08）

**libcamera の形式名はメモリ上のバイト順ではない。** 32bit ワードにパックしたときの
並びを指すので、リトルエンディアンのメモリ上では逆になる。

カメラの前に**赤いシート**を置いて撮ったところ、`format="RGB888"` で
配列の **ch2 が最大**になった（ch0=151 ch1=115 **ch2=198**）。
PNG に素直に書くと赤が青紫に写る。**メモリ上は `B, G, R` で確定。**

修正方針は「PNG 側でごまかす」ではなく **リングにメモリ上の実際の並びを記録する**:

- `camera_node` が libcamera の名前を変換して入れる
  （`RGB888 → BGR888`、`BGR888 → RGB888`。`memory_format()`）
- 下流は `FrameDesc.fmt` をそのまま信じてよい。
  **名前を信じて色が入れ替わる事故**が起きない形にした
- `shm_view` は `fmt` を見て、必要なときだけ入れ替えて PNG にする
- 対応表は `raspi/tests/test_camera_format.py` で固定（往復して元に戻ることも検査）

修正後、実機で**赤いシートが赤く写ることを確認済み**。

### カメラの取り付け向きは正しい（2026-08-08 確認）

FFC が下から出る向き（imx219 の標準）で、**画像は正立**する。
上下反転も左右反転もしていない。根拠:

- Apple ロゴが正立して写った（葉が上、かじり跡が右）
- 車体が画面**下**に写る — 前を向いたカメラが自分の車体を下端に捉える正しい位置関係

将来カメラを回して付けるなら、**picamera2 の `transform`（hflip/vflip）で
設定時に直すこと**。ISP が処理するので実質ゼロコストで、
下流でソフト的に回すより安い。

### ★ ZeroMQ で踏むと分かりにくい落とし穴2つ（対処済み）

**1. `ZMQ_CONFLATE` は multipart に対応していない。**
素直に `[topic, payload]` の2フレームで送ると、CONFLATE が黙って壊れる。
症状は「古い点群で舵を切る」なので**見た目は正常に動いてしまう**。
→ `topic + b"\0" + msgpack` の**1フレーム**にした。SUB の前方一致もそのまま効く。

**2. CONFLATE はソケット単位であってトピック単位ではない。**
1本の SUB に `vehicle_state` と `scan` を相乗りさせて CONFLATE すると、
**LiDAR が来るたびに車両状態が捨てられる。**
→ **トピック1本につきソケット1本**にした。ソケットは軽いので素直さを取る。

どちらも `raspi/tests/test_zbus.py` で固定してある。

### 走行指令の安全設計 — 独立した3つの条件

**モータが回るには全部そろう必要がある。** どれか1つでも欠けたら DISARM。

1. **io_node に `--allow-arm`**。付けなければ、GUI・WS・バスに何が流れていても
   `COMMAND` は DISARM 固定（`msgs/convert.py: command_from_cmd`）
2. **`cmd` が 150ms 以内に来ていること**。途絶＝上位が死んだ、なので止める
3. **Pi 側のクランプ**（`--max-speed` 既定 1.0 m/s / `--max-steer` 既定 0.35 rad）

GUI 側のデッドマンは「離したら **`speed=0` を送る**」ではなく
「**送信そのものを止める**」。0 を送る設計だと、その指令が届かない状況
（＝一番止めたい状況）で止まらない。ブラウザのフリーズ・タブの離脱・Wi-Fi 断が
すべて同じ経路で停止になる。

telemetry_node は**誰も操縦していなくても 50Hz で明示的な DISARM を流し続ける**。
沈黙ではなく DISARM を流すことで、io_node 側の途絶判定は
「telemetry_node が死んだか」だけを見ればよくなる。

**操縦権は同時に1人。** 2画面から舵を切ると「なぜか勝手にハンドルが戻る」という
再現困難な症状になる。E-Stop だけは権限を問わず誰でも押せる。

### GUI で決めたこと

- レイアウトは `architecture.md` §10.3 のまま（左=カメラ、右=LiDAR 俯瞰、下=速度と舵角）
- 入力は**ゲームパッド（R2 デッドマン）とキーボード（Space デッドマン）の両方**
- 20Hz のデータは **React の state に入れない**。`bus/live.ts` に置いて
  Canvas が rAF で読み、数値だけ 8Hz に間引いて配る（§10.4）

**★ 累積カウンタを「異常時のみ開く」パネルの自動展開条件にしない。**
最初にそう書いたら、CRC エラーが起動直後に1回出ただけでパネルが開きっぱなしになり、
層 C を畳んだ意味が消えた。**「今まさに異常」（温度・電圧・fault・health）だけを
自動展開の条件にし、累積はバッジで数字だけ出す**ように直した。

同じ理由で、LiDAR ビューの欠測バッジは**その1周ぶん**（`sector_seen`）を出す。
累積を出すと走るほど増えて常時点灯になり、意味を失う。

### 欠測を「障害物なし」に見せない

受信できなかった LiDAR セクタは `dist=0` で来る。点を打たないだけだと
**「そこには何も無い」と同じ絵**になるので、欠測セクタは扇形を塗って区別する。
圧縮フォーマットの `255`（= 5.10m **以上**）も、実測点として打つと
実在しない壁が円状に生成されるので別マーカーにしてある。

### ★★ STM32 の時刻が **+3378 ppm 速い**（STM32 側と要相談）

`TimeSync` の回帰が **−3355 ppm** を出した。水晶の典型値（50 ppm）の **67倍**で、
推定の不具合を疑ったので、記録した `.sfl` から独立に検算した:

```
Pi 経過   70.126655 s   (CLOCK_MONOTONIC)
STM32 経過 70.363545 s   (TELEMETRY.t_us)
比 1.00337803 → +3378 ppm
```

**回帰は正しい。実機の性質である。** 0.338% は STM32F4 の内蔵 RC（HSI, ±1%）の
範囲内なので、**外部水晶(HSE)ではなく HSI で動いている可能性が高い**。
STM32 側に確認してもらうこと。

影響と、影響しないこと:

- **LiDAR 1周（100ms）では 0.34ms のずれ。歪み補正には実害なし**
- `uart_protocol.md` §1 の「ボーレート誤差は 0%」は**分周比の話であって、
  クロック源が 0.34% ずれていれば実効誤差も 0.34%**。UART の許容（約2%）には収まる
- STM32 内の制御ループ周期（100Hz〜1kHz）も同じだけずれている
- **`TimeSync` の線形回帰（`uart_protocol.md` §6.3-2）が効いている。**
  オフセットのみの2タイムスタンプ方式だったら 3.4ms/秒 で誤差が積み上がっていた。
  「典型 50ppm だから回帰まで要るか？」という設計判断が、結果的に正解だった

### ★ `steer_actual` の張り付きは異常ではなかった（過去の記録を訂正）

通電した瞬間に **0.462 rad（26.5°）→ −0.070 rad** へ動いた。
**原点は正常で、「非通電の前輪が物理的に切れていた」だけだった。**
「ベンチ観測で `steer_actual ≈ +0.392 rad` が張り付いている／原点がずれているかもしれない」
という過去の記録は**誤り**。arm すれば原点位置に戻る。

### ★★ 後右(RR)の MD は正常。**起動が約5秒遅いだけ**（誤診を訂正）

当初「後右 MD が応答しない＝車体側のハード故障」と判断したが**誤り**だった。
バンビが「MD に問題はない、STM32 からは動かせる」と指摘し、`STATS.md_rx_count` を
**MD ごとに**見たところ次のとおりだった:

```
armed 後の1秒ごとの増分（受信数 [RL,RR,ST] / エラー数 [RL,RR,ST]）
  1s      [0, 0, 0]              [0, 0, 0]              ← 全台まだ起動前
  2s   [1392, 0, 1388]        [415, 0, 419]             ← RL/ST は動き出す
  3-5s [17xx, 0, 17xx]        [5xx, 0, 5xx]             ← ★ RR だけ 0 が続く
  6s    [990, 993, 998]       [303, 304, 296]           ← ★ RR が起動
  7s以降 [1742, 1718, 1729]   [529, 555, 542]           ← 3台とも同じレート
```

**RR MD は arm から約5秒遅れて起動する。** 他の2台は約1秒。
最初の観測（6秒）がちょうど遷移点で、`md_status=[49,0,49]` を見て
「応答しない」と早合点した。**操作上は「デッドマンを6秒握ってから両輪が回る」**
という性質として扱えばよい。

#### なぜ誤診したか — 計器の作りが悪かった（修正済み）

`LinkDiag` に `md_rx_count` を **合計** でしか載せていなかった。
`sum([15452, 15496, 15609])` を見ても「1台だけ黙っている」は絶対に分からない。

→ **`md_rx_count` / `md_rx_error` を [RL, RR, ST] の配列のまま流すよう修正**し、
GUI の診断パネルに MD ごとの受信数とエラー率を出すようにした。
**合計は異常を隠す。** 同じ理由で `rx` と `stm_rx` も最初から分けてある。

### ★★ MD バスの CRC エラー率が **3台とも 23〜25%**（STM32 側と要相談）

上の増分表のとおり、**受信 1700件/s に対しエラー 530件/s** が3台すべてで一定して出ている。

- **Pi ⇄ STM32 は完全に無傷**（crc_error=0 / loss=0）。**問題は STM32 ⇄ MD 側だけ**
  （`uart_protocol.md` §5.10 の切り分け表で「`md_rx_error` のみ増 → MD 側の配線」）
- 3台とも同率・時間的にも一定なので、**1本の配線不良ではなく共通要因**
  （終端・GND・ボーレート・ポーリング周期など）を疑うのが筋
- `md_status` の `comm_ok` がちらつく（`(49,49,49)` と `(49,0,49)` が混在）のは
  この結果だと考えられる。100ms 以内に有効フレームが来ない瞬間があるということ
- **STM32 のクロックが +3378 ppm ずれている件（上記）との関連は要確認。**
  0.34% は UART の許容（約2%）内なので単独では 24% を説明できないが、
  MD 側の誤差と重なっている可能性はある

#### 関連する実装漏れ

`uart_protocol.md` §5.5 は「Pi 側は `comm_ok = 0` を検出したら該当値を GUI 上で
グレーアウトし、**FAULT へ遷移する**」と定めているが、**FAULT 遷移は未実装**。
GUI のグレーアウト（温度の「通信断」表示）だけが効いている。
**`comm_ok` がちらつく現状でこれを入れると走行中に FAULT を連発する。**
MD バスのエラー率を先に片付けること。

### ★ デッドマンを「ARM ボタン ＋ 無操作タイムアウト」に変更（安全性を一段下げている）

「Space を押しながら WASD」が操作しづらい、というバンビの指摘による。
**3つの案（走行キー自体をデッドマンにする／ARM ボタン＋タイムアウト／別キーに移す）を
リスク付きで提示し、バンビが 2番目を選んだ。**

| | 変更前 | 変更後 |
|---|---|---|
| 開始 | Space を押し続ける | `Enter` または画面の ARM ボタン |
| 走行 | Space + W/A/S/D | W/A/S/D だけ |
| 停止 | Space を離す（即） | **20秒** 無操作で自動解除 / `Esc` / ARM 再押下 |

**失ったもの: 「手を離した瞬間に止まる」性質。** 無操作でも最大20秒は armed のまま
（速度指令は 0 に落ちるので進みはしないが、モータは励磁されている）。

タイムアウトは当初3秒で入れたが、**バンビの指示で20秒に延ばした**（`ARM_IDLE_TIMEOUT_MS`）。
**20秒はこの保険がほぼ効かない長さ**であり、実質的な停止手段は下の即時系の方である。
このタイマーは「操作を忘れて放置した」場合の最後の受け皿として残っているにすぎない。

**残したもの**（操作性と衝突しないので削らない）:

- `Esc` / E-STOP ボタン / パッドの B … 即 DISARM。権限も条件も要らない
- ウィンドウのフォーカス喪失・タブが背後に回る … 即 DISARM
- 送信が止まれば 150ms でサーバが DISARM、さらに io_node が 150ms で DISARM

つまり「ブラウザが固まる」「Wi-Fi が切れる」「PC を閉じる」は従来どおり止まる。
**弱くなったのは人間が意図して手を離した場合だけ。**

**押しっぱなしも「操作中」に数える**のが実装上の要点。`keydown` だけを見ると、
W を握り続けているのに3秒で切れる。

## MCAP 記録を実装した（2026-08-08）— Mac で確認済み・**実機未検証**

Phase 0 の達成条件の残り半分「**全データが記録できる**」に対応する。

### なぜ `.sfl` だけでは足りなかったか

**カメラ画像がどこにも記録されていなかった。** LiDAR も車両状態も UART 経由なので
`.sfl` に入っているが、カメラは共有メモリに置いて捨てているだけだった。
記録点をバス側にもう1つ足す必要がある、というのが `logger_node` を作った理由。

**`.sfl` を置き換えるのではなく2段構えにした**（`docs/architecture.md` §11）。
`.sfl` にしか残らないもの（CRC エラー・SEQ 逆行・再同期バイト数＝捨てたフレームの証拠）と、
`.mcap` にしか残らないもの（カメラ画像）があるため。**両方回すのが既定。**

| | `.sfl`（io_node） | `.mcap`（logger_node） |
|---|---|---|
| 中身 | UART の生バイト | 解釈済みトピック＋画像 |
| 依存 | stdlib のみ | `mcap` |
| 量 | 2.5MB/分 | **10.3MB/分（実測）**。大半は画像。→ **PC 側で録る**ことにした |

### 作ったもの

- `raspi/rec/mcap_log.py` — MCAP 書き出し。スキーマは `msgspec.json.schema()` が
  型から生成する（**手書きしないので、型を足したときに書き忘れる余地がない**）
- `raspi/nodes/logger_node.py` — バス全トピック → `.mcap`。画像は共有メモリから
  読んで JPEG に焼く
- `raspi/tools/sfl2mcap.py` — 既存の `.sfl` を後から変換
- `raspi/tools/mcap_repair.py` — 電源断で索引が書かれなかった `.mcap` を救う
- `raspi/core/jpeg.py` — 共有メモリ → JPEG。**telemetry_node と共有**
  （2箇所に書くと片方だけ BGR/RGB が入れ替わる事故になる）
- テスト 34件（`raspi/tests/test_mcap.py`）。**書いた MCAP を読み直して**検査している。
  画像経路（共有メモリ → JPEG → MCAP）と色順（BGR/RGB）も含む。
  **Mac で試すには `pip install pillow` が要る**（無ければ画像テストは skip）

### 効いた設計判断

- **変換ではなく「再生してから書く」。** `sfl2mcap` は `replay_node` + `BusBridge` を
  そのまま通す。SI 換算・前輪射影・LiDAR 12セクタ組み立てを書き直すと実機とズレる
- **中身は JSON にした。** Foxglove Studio が MCAP で読める符号化に msgpack が無い。
  内部バス（msgpack）とは形を変えている。**開けなければ MCAP にした意味がない**
- **時刻は UNIX epoch に直して `log_time` に入れる。** 単調時刻のままだと Foxglove が
  1970年と表示する。**メッセージ内の `t_capture` は単調時刻のまま**なので
  `.sfl` と突き合わせられる。換算に使った1組はメタデータ `surge` に残してある
- **`/viz/scan` では無効点（`dist=0`）を落とす。** 残すと原点を囲む円状の壁として描かれる
- **`mcap` は io_node に入れない。** 実時間で回るコードは stdlib のみ、の方針は維持。
  `mcap` が入っていなくても車は走る（記録が MCAP にならないだけ）

## 実機検証（2026-08-08 夜）— 合格。ただし**共有メモリの罠を1つ踏んだ**

Pi 実機で `logger_node` を回し、実写・実点群を記録できることを確認した。
テストは **Pi 上でも 291件すべてパス**。

### ★★★ `RemoveIPC=yes` で `/dev/shm/surge_cam*` が消える（発見・修正済み）

**最初の記録で画像だけが 448件すべて失敗した。** 原因は Pi 側の設定だった。

```
$ ls /dev/shm/            # 空
$ sudo grep surge_cam /proc/<camera_node>/maps
7ffeb38f4000-... /dev/shm/surge_cam0 (deleted)     ← 掴んだまま動いている
$ loginctl show-user pi | grep Linger
Linger=no
```

**systemd-logind の既定 `RemoveIPC=yes` は、そのユーザーの最後のセッションが
終わった時点で uid 所有の POSIX 共有メモリを全部消す。`User=pi` で動く
systemd サービスの分まで巻き添えになる。** つまり **SSH を切った瞬間に
`camera_node` の共有メモリが unlink される。**

症状が分かりにくいのが厄介だった:

- `camera_node` 自身はマッピングを保持しているので**動き続ける**
  （`image/front` は 30Hz で流れ続ける。バスを見ても異常が無い）
- **新しく attach するプロセスだけが失敗する**（`FileNotFoundError: /surge_cam0`）
- したがって **`telemetry_node` の GUI カメラも同じ理由で映らなくなる。**
  「再起動すると直る」ので原因に辿り着きにくい

修正（Pi 側に投入済み）:

```
/etc/systemd/logind.conf.d/10-surge-removeipc.conf
[Login]
RemoveIPC=no
```

`sudo systemctl restart systemd-logind` で反映。**SSH を切っても
`/dev/shm/surge_cam0` が `(deleted)` にならないことを確認済み。**
（代替として `loginctl enable-linger pi` でも防げるが、こちらの方が意図が明確）

### ★ 計器が悪くて原因に辿り着けなかった（修正済み）

最初の失敗は `画像の取りこぼし: エラー 448` としか出ず、**なぜ失敗したのかが
どこにも残っていなかった。** `md_rx_count` を合計で出して MD の誤診をしたのと
まったく同じ失敗。`RingJpeg.last_error` に**直近の例外を文字列で残す**ようにした。

ついでに、より悪い壊れ方も塞いだ。**`camera_node` を再起動すると共有メモリは
作り直されるが、既に attach しているプロセスは古い方を掴んだままになる**
（Linux では unlink 後もマッピングが生きる）。これは**エラーすら出さずに
同じ画像を記録し続ける。** `ImageRef.ring_seq` と手元の `write_seq` を比べて
掴み直すようにした（`core/jpeg.py` の `STALE_GAP`）。テストで固定済み。

### ★★ SD カードの書き換え寿命 → **MCAP は PC 側で録るように変更**（バンビの指摘）

「SD は書き換えに弱いので、周期が落ちても PC 側でログを取れないか」という指摘。
**正しい。実測すると 1日 15GB を SD に書いていた。**

`/sys/block/mmcblk0/stat` で A/B 測定（デバイスへの実書き込み量）:

```
ロガー有り: 10.54 MB/分   ← 1日 15GB。28GB の SD を毎日半分書き潰す勢い
ロガー無し:  2.42 MB/分   ← 現在の既定（.sfl ＋ journald ＋ FS のオーバーヘッド）
```

**77%減。** 判断の根拠は「数値だけなら `.mcap` は `.sfl` とほぼ同じ内容」
（どちらも UART 由来）であること。**SD に二重に書く価値があるのは実質カメラ画像だけ**
なので、その画像を PC 側へ逃がした。

#### `logger_node -o -` — MCAP を標準出力に流す

```bash
tools/record.sh                    # Mac で実行。Ctrl-C で終了
tools/record.sh --image-hz 15      # PC のディスクなので画像を増やしてもよい
tools/record.sh --duration 60 -o ~/logs/test.mcap
```

中身はこれだけ:

```bash
ssh surge-mk2 '… -m raspi.nodes.logger_node -o -' > run.mcap
```

**SD には1バイトも書かれない。** MCAP は追記型なのでパイプでそのまま成立する。
実測 3.6MB/20秒 = 約 200KB/s なので Wi-Fi でも足りる。**周期を落とす必要すら
無かった**（`vehicle_state` 49.9Hz・画像 5Hz をそのまま PC で受けられた）。

実装で1つ詰まった: `mcap.writer.Writer` は索引のオフセットを `stream.tell()` で
取るので、**パイプだと `OSError: Illegal seek` で落ちる。** MCAP は追記専用で
**書いたバイト数がそのままオフセット**なので、ラッパで数えて返すようにした。

#### Pi 側の既定を変えた

- `install_services.sh` は **`surge-logger` を enable しない**（unit は置くので
  `sudo systemctl start surge-logger` で一時的に録れる）
- Pi 単体で画像も録りたいときは `sudo ./raspi/setup/install_services.sh --with-logger`
- **`.sfl` は常時記録のまま。** PC を繋いでいない間や Wi-Fi が切れた瞬間の
  記録が失われては意味がない

### ★ `.mcap` は尻切れに弱い → 復旧ツールを用意した

**MCAP は `finish()` を呼んで初めて索引が書かれる。** 記録途中のファイルを
読もうとすると、データは書けているのにリーダが落ちる:

```
RecordLengthLimitExceeded: unknown (opcode 0) record has length ... exceeds limit
```

`.sfl` は尻切れでも必ず前半が読めるのに、`.mcap` はそうではない。
**原因不明の再起動が2回あった Pi でこれは放置できない**ので
`raspi/tools/mcap_repair.py` を作った。先頭から舐めて切れたところで打ち切り、
索引付きで書き直す。

```bash
python3 -m raspi.tools.mcap_repair logs/surge_20260808_233813.mcap
```

**実機の記録中のファイル（87MB）から 10万件・カメラ画像 4869枚を復旧できた。**

（実装上の落とし穴: 正常な MCAP は Schema/Channel をデータ部と要約部の
**両方**に持つので、素直に舐めると同じトピックのチャネルが2本でき、
片方が0件になる。id で重複を弾くこと。テストで固定済み）

空きは 22GB しかないので、**「毎日・7日より古いものを消す」では掃除が来る前に
カードが埋まる**（そもそも `.sfl` 単独でも 6日で埋まる計算だった）。

- タイマーを**毎時**に変更
- **合計 8GB を超えている間、古い順に消す**処理を追加（連続運転の保険）

## 操縦レスポンスの作り直し（2026-08-09）— **実車未検証**

「押している時間だけ加速する仕組みだと、もっさりして操りにくい」というバンビの指摘による。
`gui/src/input/useDriving.ts` を全面的に書き直した。**Mac でビルド確認までしかしていない。
実車で走らせて数値を詰めるのはこれから。**

### もっさりの原因は4つあった

| | 変更前 | 変更後 |
|---|---|---|
| ① 入力ループ | `setInterval` **20Hz** で積分と送信を兼用 | 積分は **rAF（≈60Hz・実 dt）**、送信は **50Hz** |
| ② ランプ | 加速 0.8 m/s²（全開まで1.25秒）／ステア 1.2 rad/s（フルロック0.87秒） | 加速 **2.0**（0.5秒）／ステア **2.6 rad/s**（0.40秒）、戻り **5.2**（0.20秒） |
| ③ ブレーキ | 無い。逆キーは逆方向に積分し直すだけ | 逆キー = **5.0 m/s² のブレーキ**。0 を跨いだら後退へ |
| ④ 発進 | 0 からじわじわ | **発進キック** `KICK_SPEED = 0.12 m/s` へ跳ばしてから積分 |

**① が一番効く。** 下流は telemetry_node が 50Hz、io_node が 100Hz で回っていたので、
**20Hz だった GUI だけがボトルネックだった**。パッドのスティックも 20Hz でしか
読んでいなかったのでカクついていた。

**④ の理由**: 停止から指令をじわじわ上げると、STM32 の速度 PI ループが実際に
車体を動かし始めるまで無駄時間が出て、「押した→無反応→急に出る」になる。
**`KICK_SPEED` は実車が転がり始める指令値に合わせて調整する**（大きすぎると飛び出す）。
低速では `wheel_speed` が使えないので、DriveBar の `speed` 生値と目視で詰めること。

### ★ レートリミットを「GUI で作り、STM32 は保険」に一元化した

**これが今回一番大きい設計変更。** 以前は `accel_limit=0` / `steer_rate_limit=0`
（＝STM32 の既定に任せる）を送っていたので、GUI 側のランプと STM32 側のリミットが
**二重にかかり、どちらが操作感を決めているのか分からなかった**。

今は GUI から明示的に送る（`ACCEL_LIMIT = 6.0 m/s²` / `STEER_RATE_LIMIT = 7.0 rad/s`）。
**GUI のランプよりわざと速い値**にしてあるので、通常走行では GUI のランプが支配的になり、
STM32 側は「指令が飛んだ／GUI が壊れた」ときにメカを守る保険として残る。

**STM32 側の既定値を上書きすることになる**ので、実車で試すときは
ステアが発振しないかを最初に確認すること（`steer_rate_limit` はオーバーシュート抑制用）。
発振したら `STEER_RATE_LIMIT` を下げる。

### ★ 速度上限を 0.3 → 0.6 m/s に上げた（バンビの判断）

**GUI の `UI_MAX_SPEED` と io_node の `--max-speed` がずれていた。**
`install_services.sh` は `--max-speed 0.3` なのに GUI は 1.0 のつもりで指令を作っていたので、
**GUI が「0.55 m/s 出している」と表示しているのに Pi 側で 0.3 に切られていた。**
しかも 0.3 m/s では 0.15 秒で頭打ちになるため、上の加速ランプもブレーキも体感できない。

3案（0.6 に上げる / 0.3 のまま GUI を合わせる / 1.0 に上げる）を提示し、**バンビが 0.6 を選択**。

| | 値 |
|---|---|
| `gui/src/store/ui.ts` の `UI_MAX_SPEED` | **0.6** |
| `raspi/setup/install_services.sh` の `--max-speed` | **0.6** |

**この2つは手で合わせるしかない。片方だけ変えないこと**（両方のファイルに警告コメントを入れた）。
Pi 側のクランプは「上位が壊れたときに下位が守る」多層防御なので、GUI から取得する形にはしない。

反映するには Pi で `sudo raspi/setup/install_services.sh` を再実行して unit を入れ直す。

### 速度レンジを2段にした（既定は低速）

- 通常は `UI_MAX_SPEED × 0.55`（＝0.33 m/s）、**`Shift`（パッドは R1）を押している間だけ全開**（0.6 m/s）
- 定数は `store/ui.ts` の `CRUISE_SCALE` / `BOOST_SCALE`
- StatusBar に「低速 0.55 / BOOST 1.00」のピルを出した。**握る前に知りたい情報**なので
  armed かどうかに関係なく常時出す

「いつでも全開が出せる」より「全開には意識的な操作が要る」方が、狭い場所で壁に刺さらない。

### そのほか

- **ゲームパッドはランプを挟まない。** アナログ入力は指がすでにランプなので、
  二重に鈍らせない。目標をそのまま出し、整形は STM32 の accel_limit に任せる
- デッドゾーンを**切り落としから再スケールに**変更（0.12 を超えた瞬間に 0.12 が出る段差を解消）
- 舵とスロットルに expo（中央付近を緩く）
- **入力元は「最後に動かした側」で固定**。今どちらが動いているかで選ぶと、
  パッドのトリガーを戻した瞬間だけキーボードの惰行カーブに落ちる
- `take_control` の再要求を 250ms 間隔に絞った（rAF ごとだと 60発/秒になる）

## プロトコル v0.5 に追従した（2026-08-09）— **実車未検証**

STM32 側から差分仕様が届いての対応。**変わったのは `COMMAND` (0x10) だけ**で、
`TELEMETRY` 以下は v0.4 のまま。

### 破壊的変更である（版数がずれている間は走行指令が一切通らない）

`COMMAND` の **LEN が 10 → 12** に変わる。STM32 は LEN 不一致のフレームを捨てて
`STATS.rx_len_error` に計上するので、**Pi 側を更新するまで一切効かない**。
中途半端に効くより完全に弾かれる方が安全なので、これは意図した設計。

→ **実機に反映するときは Pi と STM32 の両方を同時に上げること。**
片方だけ上げた状態は「GUI は動いているように見えるのに車が反応しない」になる。
切り分けは `probe_uart.py`（`protocol_version` の照合）と
`DiagStrip` の `rx_len_error` を見る。

### 何が増えたか

| 追加 | 中身 |
|---|---|
| `brake_torque : u16` | 後輪各輪の制動トルク [0.0001 N·m]。**`0` は「制動 0」ではなく「未指定＝最大制動」** |
| `light_mode`（bit3-4） | 消灯 / DAYTIME（減光）/ NORMAL の3段。**旧 `light=1`(全光量) と新 `1`(DAYTIME) で値の意味が違う** |
| `passing`（bit5） | 立てている間、前照灯だけ全光量。**尾灯は連動しない** |
| `horn`（bit2・挙動変更） | 単発ビープ → **立てている間ずっと鳴る** |

**`brake` 中は STM32 の車速 PI が迂回され、指定トルクが直接掛かる**（`target_speed` は無視）。
`torque_cmd` の符号も明確化された（**正 = 駆動 / 負 = 制動**）ので、
GUI からブレーキが効いているかを確認できるようになった。

### ゼロ値の扱いで1つ罠がある

`brake_torque = 0` が「未指定＝最大制動」なので、**GUI で弱いトルクを指定したつもりが
丸めで 0 に落ちると、最大制動という正反対の挙動になる**。
`msgs/convert.py` の `_brake_torque_raw()` で正値は最小 1 LSB に留めてあり、
GUI のスライダ下限も `0.005 N·m` にして 0 を選べなくしてある。

### GUI 側の操作（`useDriving.ts` / `AuxPanel.tsx`）

| | ブレーキ | クラクション | パッシング | 灯火切替 |
|---|---|---|---|---|
| キーボード | `Space` | `H` | `P` | `L`（消灯→DAY→NORMAL→…） |
| ゲームパッド | L1 | A/× | X/□ | Y/△ |

- **灯火切替以外はすべて「押している間だけ」。** STM32 の意味論に素直に合わせた。
  GUI 側でタイマーを持つと DISARM やタブ切替と競合したときに消し忘れる
- **ブレーキ中は GUI の速度指令も 0 に落とす。** STM32 は離すと 0 から再加速するので、
  ランプを走らせたままにすると画面と実挙動が食い違う
- **マウスでは鳴らせない**（ホーン／パッシングは表示のみ）。ボタンの外でカーソルを
  離したときに `horn` が立ったまま残ると、v0.5 では**鳴りっぱなし**になるため
- ⚠ **補機は ARM 保持中しか効かない。** `cmd` を送るのが armed のときだけで、
  途絶すれば io_node が DISARM（`flags = 0`）に落として灯火も消える。
  「停めたまま前照灯だけ点ける」には cmd の送信条件そのものを変える必要がある

### 緊急停止まわりの STM32 側の変更（Pi 側が知っておくこと）

- 緊急停止・`COMMAND` 途絶時は**最大制動トルクを直接掛ける**ようになった。**停止距離が短くなる**
  （舵角は最後の指令値のまま保持。直進に戻すと予期しない方向へ動くため）
- **起動時に駆動電源が一瞬 ON になる問題が直った。** 起動から Pi が `arm` するまで
  `TELEMETRY.flags` の `armed` は一度も立たない（原点較正時を除く）

### ★ 未解決 2: GUI のカメラが前後とも 14fps

Phase 1 の「可視化の完成」で効いてくるので、そこで潰す。

### MD の「通信断 / err 100%」は異常ではない（DISARM 中だから）

温度3点が「通信断」、MD バスが3台とも `err 100.0%`、駆動 1.55V / 0.00A で
`drive_undervoltage` — **これは DISARM で駆動電源が切れている状態の正しい姿**。
`io_node` が DISARM を送ると駆動電源が切れる仕様のとおり。

**ただし、以前記録した「MD バスの CRC エラー率 23〜25%」が改善したかどうかは
この画面では判断できない。ARM 中の値を見る必要がある。**
次に ARM したとき MD バス欄を控えておくこと（STM32 側と相談する材料になる）。

### 時刻同期 offset −9.9 秒について

`offset −9908842.3µs`。これは既知の **STM32 が +3378 ppm 速い**問題。
9.9 秒 ÷ 3378ppm ≈ 2930 秒 ≈ 49 分なので、STM32 の連続稼働時間と辻褄が合う。
**新しい異常ではない。** 対処は STM32 側と要相談のまま。

## ★ `estop_test.py` の回し直し（2026-08-10）— 合格。**これで Phase 0 完了**

`--allow-arm` を足したときから「再検査が要る」と積んでいた宿題。回す前に
**テスト自体を直す必要があった**（下記）。実車で2回に分けて回し、全項目合格。

### なぜテストを直す必要があったか

**旧 `estop_test.py` は検査中ずっと `DISARM` を送り続ける作りだった。**
つまり **E-Stop が本当に守るべき状態（駆動電源が入っている状態）を一度も作らずに
合格を出していた。** そのまま回しても「arm 経路を足したことによる再検査」にならない。

足した検査は2つ:

1. **ARM 中に E-Stop が発動するか**（駆動電源が入った状態で途絶させる）
2. **ラッチ中に arm できないか** — 仕様「`estop_active` 中は COMMAND が一切効かない」。
   **ここが破れていると、E-Stop 中に GUI の ARM ボタンで駆動が復活する**

### ★★ ラッチ中は arm 状態が「凍結」する — だから2回に分けて回す

1回目（arm したまま途絶）で分かったこと: **ラッチ中は `arm=0` を送っても `armed` が
落ちない。** COMMAND が本当に一切効いていない（仕様どおり）。

**しかしそのせいで、危険な向き（arm 0→1）をこの順では観測できない。**
GUI の ARM ボタンに相当するのはまさに 0→1 の向きなので、ここを空けたままでは
「合格」と言ってはいけない。そこで `--disarm-before-trip` を足し、
**arm を一度入れて確認してから降ろし、降ろした状態で途絶させる**ようにした。

```bash
# ① ARM 中でも発動する / 駆動電源が維持される
.venv/bin/python -m raspi.tools.estop_test --wheels-clear
# ② ラッチ中に arm=1 が拒否される（GUI の ARM ボタン相当）
.venv/bin/python -m raspi.tools.estop_test --wheels-clear --disarm-before-trip
```

**片方だけでは Phase 0 を閉じる根拠にならない。** ファームを触ったら両方回すこと。

### 実測（2026-08-10・車輪を浮かせて実施）

記録: `logs/estop_20260810_164431.sfl` / `logs/estop_20260810_164712.sfl`

### ★ `armed` が落ちることを期待してはいけない（テストを書くときの罠）

最初に書いたテストは「E-Stop 発動 → `armed` が落ちるはず」と判定していた。**これは誤り。**
`uart_protocol.md` §9 の仕様は **「駆動電源は切らない」**（切ると MD が制動をかけられず
惰行して停止距離が伸びるため）。**E-Stop 中も `armed` が立っているのが正常。**
実車に掛ける前に気付いたが、そのまま回していたら正常な車両を不合格にしていた。

**安全検査を書くときは、期待値を仕様書から引くこと。直感で書かない。**

### 回すときの手順（`surge-io` を止める必要がある）

systemd の io_node が GPIO6 にハートビートを出したまま `/dev/serial0` も掴んでいる。
**止めないとポートを開けないし、開けても io_node 側が波形を出し続けるので途絶を作れない。**

```bash
ssh surge-mk2 'sudo systemctl stop surge-io'     # ← この瞬間に E-Stop がラッチする
ssh surge-mk2 'cd ~/surge_mk2 && .venv/bin/python -u -m raspi.tools.estop_test --wheels-clear'
ssh surge-mk2 'sudo systemctl start surge-io'
# → テスト終了時にもハートビートが止まるので**もう一度ボタン2**を押す
```

**ボタン2を押す回数は1回の実行につき2回**（開始時のラッチ解除と、検査の最後）。
さらに終了後にもう1回。押し忘れると走らせられないので、`--release-only` で待てる。

## UART プロトコル v0.7（2026-08-11）— 超音波による自動停止。**STM32 側実装済み → Pi/GUI 対応完了**

STM32 側発の変更（`pi_uart_protocol_v0.7_delta.md`）。前後の超音波センサを使い、
**STM32 単独で障害物への自動停止**ができるようになった。Pi は毎周期「許可」を送るだけ。

### 変更内容（ワイヤ形式）

- **LEN はどのパケットも変わらない。** `flags` の空きビットを使うだけなので、
  片側が未対応でも通信は継続する（v0.6 とワイヤ非互換ではない）
- `COMMAND` (0x10) の `flags` **bit7 = `auto_stop`**。立っている間、**進行方向**の
  超音波が **20cm 未満**になると STM32 が指令を無視して最大制動する
- `TELEMETRY` (0x02) の `flags` **bit16 = `auto_stop_active`**（今まさに介入中）。
  `tc_active`/`tv_active` と同じ「介入中」の意味で、有効/無効そのものではない
- `protocol_version` **0x0006 → 0x0007**

### 仕様で押さえておくこと

- **進行方向の判定**は `torque_mode` なら `target_torque`、そうでなければ `target_speed` の符号。
  `>= 0` で前方センサ、負で後方センサ**だけ**を見る。**逆方向は見ないので後退で抜けられる**
- 検知不能（`ULTRASONIC_NO_ECHO`・範囲外）では作動しない
- 優先順位は **`brake` > `auto_stop` > 通常指令**。`auto_stop` 単独作動時は
  `brake_torque` を見ず**常に最大制動**
- **ラッチしない**が**ヒステリシスも無い**ので、20cm 前後ではチャタリングし得る。
  壁に詰める作業では GUI 側で切ること
- **DISARM はされない。** 停止手段ではなく衝突緩和で、E-Stop とは別系統

## 2026-08-11 GUI を4タブに再編・ラジコンモードのスポーティ化

### 何を変えたか

`運転 / 地図 / 診断 / 設定 / ログ` → **`ラジコン / 自動運転 / 診断 / ログ`**。

きっかけは2つ。**(1) 設定タブの中身はすべてラジコン操作の値なのに独立タブを占有していた。**
**(2) 運転ビューは開発者がデバッグする画面として設計されており、スリップ量・CRC エラー・
時刻同期オフセットといった「運転を楽しむのに要らない数字」が前に出ていた。**

| タブ | 中身 |
|---|---|
| **ラジコン**（既定） | 新規。カメラ大 + 速度計・G メータ・舵角計 + 介入ランプ。設定は ⚙ ドロワー |
| **自動運転** | 旧「運転」そのまま（`DriveView.tsx` → `AutoView.tsx` にリネーム） |
| **診断** | 新規。`DiagGrid`（現在値の全項目）+ uPlot の時系列グラフ6枚 |
| **ログ** | 変更なし |

「地図」は削除（プレースホルダのままだった）。Phase 3 で SLAM を作るときに置き場を決め直す。
既定タブをラジコンにしたのは、自動運転が Phase 3 まで中身を持たないため。

### ラジコンビューの選別基準

**「運転者が知りたいか」で層 C/D をふるい直した**（`architecture.md` §10.1 に追記）。

- 出す: 速度（円弧メータ・BOOST 域をレッドゾーンに）、G メータ（前後G/横G の軌跡）、
  舵角、TC/TV/自動停止の**ランプ**（数値なし）、温度4点の最悪値、駆動電圧、超音波、走行距離
- 出さない: スリップ量の数値、CRC/loss、時刻同期、UART/WS の RTT、受信 Hz、モータ電流、pitch/roll
- **隠すのは正常時の数字だけ。** E-STOP・ARM・ラッチ警告は据え置き、リンクが劣化したら
  `StatusBar` が「通信 遅延/途絶」の1ピルで割り込む（`variant='rc'`）

### 実装で引っかかった点

- **介入ランプは 300ms ラッチする。** `tc_active` は1〜2フレームで落ちるので、8Hz の
  `useNumbers()` で光らせると**介入したのに光らない**。rAF で `live.vs` を見て保持する
- **G メータは rAF + Canvas。** 軌跡を描くので 8Hz では点が飛ぶ。
  ⚠ `AX_SIGN`/`AY_SIGN` は IMU の取り付け向き依存。**実車で前進加速＝上、右旋回＝右を確認して合わせること**
- **⚠ uPlot の欠測は `null` であって `NaN` ではない。** uPlot の範囲計算は `v != null` で
  値を拾うため、`NaN` が `Math.min/max` に入って **min/max が丸ごと NaN に汚染され、
  グラフが1本も描かれない**（データは正しいのに白紙になる）。実際にこれで詰まった。
  リングバッファは Float32Array なので保持は NaN、`readHistory()` で null に変換して渡す
- **平らな系列は uPlot の既定で軸が 0〜100 になる。** 停車中の速度グラフに「100」の目盛りが
  付いて一瞬あり得ない値に見えるので、チャートごとに `minSpan` で最小レンジを決めた
- **切断時に履歴を消さない。** 「切れたこと自体」が後から見たい事象なので、
  全系列 NaN の1点を積んで線だけ断つ（`markHistoryGap()`）
- 設定ドロワーは **Esc で閉じない**（Esc は E-STOP。パニックで叩いた Esc がパネルを

## Mac 上で動く 2D シミュレータを作った（2026-08-12）

自律走行（Phase 1 以降）に入る前に、**Mac 単体で制御ループを回せる場所**を用意した。
実車は研究室にしか無く、走らせるたびに E-Stop の解除と電池の管理が要るため。

### 入れ替え点は `SerialLink` の位置に決めた

このリポジトリは既にシミュレータを差せる構造になっていた。

- `IoNode.__init__(self, link, ...)` が link をコンストラクタ注入で受け取る（`io_node.py:100`）
- `import serial` はリポジトリ全体で `raspi/io/serial_link.py:13` の 1 箇所だけ
- `open_output()` は GPIO が開けなければ `None` を返す（`gpio.py:110-113` に
  「Mac でも io_node が起動できるように」と書いてある）

なので **`SerialLink` と同じ顔をした `SimLink` を差すだけで、`io_node` より上流は
1 行も変えずに動く**。結果、以下が全部実機と同じコードで走る:

`protocol.toml` のパケット定義 / CRC-16 とフレーミング / `convert.py` の SI ↔ 整数換算と
クランプ / `ScanAssembler` の鏡像反転 / `LinkTracker` と PING-PONG 時刻同期 /
`--allow-arm` ゲート / `cmd` 150ms タイムアウト / `bus_bridge` / `telemetry_node` / GUI。

`bus_demo.py` は役割が違う（GUI の配管確認用の運動学モック）ので**そのまま残した**。

### 実機側を汚さない — バンビの指摘で設計が変わった

最初のプランでは実機 GUI にコース切替 UI と `sim/ctrl` バストピックを足す形にしていた。
バンビから「シミュレータはあくまで実機のシミュレーションを忠実に行うだけ。
コース切替などシミュレーションのパラメータはシミュレータの GUI 上で切り替えたい」と指摘があり、
**シムの概念を実機側に一切持ち込まない**方針に変更した。理由:

1. シム用 UI を実機 GUI に置くと、表示判定を 1 つ間違えた瞬間に実車の画面に出る。
   GUI がシミュレータを知らなければ、その事故は原理的に起きない
2. コース・ノイズ量・欠損率は**実機に対応物が無い概念**。責務としてねじれている
3. 結果、実機コードへの変更が **約120行 → 約30行** に落ちた

これに伴い、シム ↔ シミュレータGUI の通信も ZeroMQ の内部バスをやめて
**UDP ループバックの私設チャンネル**にした。バスに乗せると `raspi/msgs/types.py` に
真値の型を、`raspi/bus/zbus.py` にトピックの持ち主を登録することになるため。

### 実機側に入れた変更（これで全部）

| ファイル | 変更 |
|---|---|
| `raspi/nodes/io_node.py` | `--sim` / `--course` 引数と link 生成の分岐（`sim.link` は**遅延 import**）。`publish_diag(..., sim=...)`。`log_meta` と起動表示を `link.port` から取るように |
| `raspi/msgs/types.py` | `LinkDiag.sim`（bool 1 個） |
| `raspi/core/bus_bridge.py` | `build_diag` に `sim` kwarg を通す |
| `gui/src/types.ts` | `LinkDiag.sim` |
| `gui/src/components/StatusBar.tsx` + `styles.css` | **SIM バッジ** |

**SIM バッジだけは安全要件として入れた。** シムと実機の画面が見分けられないと
「シムのつもりで `--allow-arm` した実車が動く」が起きる。`SerialLink` には何も足さず
`getattr(link, "is_sim", False)` で読むので、実機側は偽リンクの存在を知らない。

### 実装で踏んだこと

- **`SimLink.poll()` は必ず寝ないといけない。** 本物の `SerialLink.poll()` は
  `read_timeout=0.005` でブロックし、io_node のループには sleep が無く**そこで待つ前提**。
  即座に返すと CPU 100% の暴走ループになる
- **ただし毎回まるごと 5ms 寝るのも駄目。** 本物の `read()` は「1バイト来たら起きる」ので、
  固定 5ms 寝ると受信時刻 T4 に下駄が乗る。**片道遅延の推定が 5.77ms** になり実機より
  数倍大きく出た。次の到着時刻まで（上限 `read_timeout`）にしたら **1.30ms** に落ちた
- **UART の線上時間を入れる必要がある。** 250kbps では TELEMETRY(73B) が 2.9ms、
  LIDAR_SECTOR(76B) が 3.0ms かかり、合計で帯域の 52% を使う。無視すると
  「全部が同時刻に届く」不自然に綺麗なシムになる
- **レイキャストは numpy でベクトル化必須。** 12m ÷ 0.02m = 最大 600 セル × 360 本。
  Python の for では 120Hz に間に合わない。「全レイ × 全ステップ」を一度に作って
  `argmax` で最初の当たりを取る形にした → 10 秒ぶんの負荷が 259ms（CPU 2.6%）
- **車体外形のサンプル点は輪郭も別に刻む。** 交差数判定は輪郭上の点を「外」と返すので、
  内部格子だけだと車体の縁 1cm が判定から抜ける（前端 0.31m が 0.30m 扱いになった）
- **コースのスタート姿勢が壁に埋まる**のが一番やりがちな間違い。oval を y=0.3 と書いて
  走行帯の外に置いてしまい、「車が動かない・超音波 2cm・auto_stop が効き続ける」という
  分かりにくい症状になった。`make_courses.py` と `create_sim_link()` の両方で検出する
- **`torque_mode`(v0.6) は最小でも実装が要る。** 加速度への換算を入れないと
  「スポーティなラジコンモード」で車が一切動かない

### 鏡像反転をわざと入れてある

実機の LD06 は裏向き実装で、`ScanAssembler` が `車両角 = (360 − センサ角) % 360` で
戻している（`convert.py:281-298`）。**シミュレータは反転した状態で出す。**
素直に車両座標で出すと、反転処理が壊れていても画面が正しく見えてしまう。

検算用に `courses/room.png` を**左右非対称**にした（ブロックが左だけ）。
(3.0, 2.0) yaw=0 から見て 車両角 90° = 1.00m / 270° = 1.89m。入れ替わったら反転が壊れている。

### Mac で起動できないときに疑う2つ（2026-08-12 に両方踏んだ）

**1. `ImportError: incompatible architecture (have 'arm64', need 'x86_64')`**

ターミナルが **Rosetta（x86_64）で動いている**。python.org の Python 3.12 は
universal2 で、**親プロセスのアーキを継承する**ため、Rosetta のターミナルから起動すると
x86_64 として動き、venv の arm64 ホイール（msgspec / pygame）を読めない。

```bash
arch                     # i386 と出たら Rosetta
arch -arm64 zsh          # その場しのぎ。以降このシェルは arm64
```

恒久対応は Finder で **Terminal.app → ⌘I →「Rosetta を使用して開く」のチェックを外す**。
VSCode の統合ターミナルは arm64 なのでそちらでもよい。
**シミュレータ固有の問題ではなく、実機接続でも同じように落ちる。**

**2. `OSError: [Errno 48] address already in use ('0.0.0.0', 8000)`**

古い `telemetry_node` が生き残っている。実際に **4日前に起動したものが居座っていて**、
古いコードを配っていたため「SIM バッジが出ない」と誤診しかけた。

```bash
lsof -nP -iTCP:8000 -sTCP:LISTEN     # PID を確認
ps -o lstart= -p <PID>              # いつから動いているか。**古かったら疑う**
kill <PID>
```

**GUI の表示がコードと合わないときは、まず配っているプロセスの起動時刻を見ること。**

### 1コマンドで立ち上げる `sim.run` を足した（2026-08-12）

3つのターミナルを開くのが面倒だったので、`io_node --sim` / `telemetry_node --no-camera` /
`sim.gui` を子プロセスとして起動するランチャを作った。

```bash
.venv/bin/python -m sim.run                  # これだけ
.venv/bin/python -m sim.run --course slalom --no-gui --kill-stale
```

出力に `[io ] [tele] [gui ]` の印を付けて1画面に流し、**Ctrl-C で全部まとめて落とす**。

**上に書いた罠を、エラーを分かりやすくするのではなく「そもそも踏ませない」形にした。**

- Rosetta で起動されたら `arch -arm64` で**自分を起動し直す**（`os.execv`）
- ポートと `io` endpoint を掴んでいるプロセスを**起動時刻つきで**報告する。
  `--kill-stale` で落としてから起動できる
- `gui/dist` が無ければ警告する

このファイルは **stdlib だけで書いてある**。numpy や pygame を import すると、
Rosetta の診断をする前に ImportError で落ちてしまうため。

実装で踏んだこと:

- **`KeyboardInterrupt` を待つだけでは足りない。** `kill`（SIGTERM）で親だけが死んで
  子が残る。さらに `&` でバックグラウンド起動すると SIGINT が **SIG_IGN として継承**され
  Ctrl-C も効かない（POSIX の挙動）。`signal.signal` で両方を明示的に捕まえて解決した
- 子は `start_new_session=True` で別プロセスグループにし、停止は `killpg` で送る。
  io_node は SIGINT で DISARM を1発送って畳む作りなので、SIGKILL を先に送ってはいけない
- `SURGE_BUS_DIR` が設定されていたら endpoint の相手検査を飛ばす
  （別バスを指しているなら競合しないため。2スタック並走のテストで誤検出しない）

**この作業中に、8月8日から `bus_demo --allow-arm --faults` が動きっぱなしなのを発見した。**
`io_node` と同じ `io` endpoint に bind するので、GUI に偽データが出ていた可能性がある。

### シミュレータGUI の見た目を作り直した（2026-08-12）

「pygame だからダサいのは仕方ない」と思われがちだが、原因は pygame ではなく次の3つだった。

1. **コース PNG を生で貼っていた。** 白背景＋黒壁がダークな画面から浮いて、
   スクショを貼ったように見えていた。→ 占有格子から**作り直す**。
   走行可能面を背景より少し明るい「床」に、壁は沈めて**縁だけ**明るくする。
   逆（壁を明るく）にすると走れる場所が背景に溶けてコースに見えないので、向きが重要
2. **アンチエイリアスが無かった。** `set_at` の 1px 点と `draw.polygon` のギザギザが
   安っぽさの正体。→ 点はグロー付きのスプライトを blit、多角形は `gfxdraw` で描く
3. **余白と字に規則が無かった。** → 余白は 4px の倍数だけ、数字は等幅（Menlo）で桁を
   揃える、見出しは字間を空けた小さい大文字（ヒラギノ W6）。
   数字が等幅でないと計器に見えない

加えて 1m グリッドとスケールバー（尺度が分からない俯瞰図は読めない）、
パラメータ値の位置を示す 2px の帯（数字だけだと相場が分からない）、
軌跡の前半を薄くする（一様な線だとどちらに走っているか読めない）。

**macOS の SDL は高 DPI のバッキングストアを返さない**（`set_mode((400,300))` の surface も
window も 400×300）ので、Retina の物理解像度は稼げない。そこは諦めて上の3つで作った。

実装で踏んだこと:

- `self._tracked` を dict とメソッドの両方に使っていて、**属性がメソッドを隠して**いた
- **半透明はアルファ面に描いてから blit する。** 画面へ直接 `draw.rect(screen, (r,g,b,a))`
  すると **a が無視されてベタ塗り**になり、ピルが全部主張してしまう
- 下のバーはピルと数値を**別の行に分けないと重なる**（実際に重なった）
- **点と軌跡は盤面にクリップする。** はみ出すとどこまでがコースか読めなくなる

### コースをセンターライン方式で作れるようにした + GUI のレイアウト整理（2026-08-12）

**コース作成（`sim/track.py`）** — 中心線を直線と円弧でつなぎ、道幅から左右の壁を
**自動生成**する。壁を1本ずつ置く案も検討したが、こちらにした理由:

- 左右の壁が常に平行（手で置くと道幅がばらつき、継ぎ目に隙間ができる）
- スタート姿勢が中心線上に自動で決まるので、**壁に埋まりようがない**（前に踏んだ罠）
- **中心線そのものが Phase 3 の経路追従の正解データになる**

```json
{ "width": 1.0, "origin": [1.0,1.0,0.0], "loop": true,
  "path": [["straight",4.0], ["arc",1.2,90], ["straight",2.0], ["arc",1.2,90], ...] }
```

ラスタライズは**全部壁で埋めてから中心線に沿って円盤で掘る**。左右の壁を別々に描くより
単純で、継ぎ目や自己交差（8の字）が自然に処理される。生成は 8×6m で 4ms。

PNG 方式との判別は **JSON に `"path"` があるかどうかの1点だけ**（`Course.load`）。
同梱例は `circuit.json`（閉ループ・8.2×6.2m）と `chicane.json`（S字の連続・17.2×4.9m）。
`loop: true` なら始点と終点のずれを検査して警告する（繋ぎ目に細い壁が残ると
「なぜかそこで必ず止まる」になるため）。

**GUI のレイアウト** — 下のバーを廃止し、走行の数値を右パネルに縦に並べた。
シムのパラメータ（LIDAR / LINK）とコース一覧は `P` で開くページに退けた。
実機 GUI が設定を ⚙ ドロワーに隠しているのと同じ作法。

**ウィンドウをリサイズ可能にした。** これが一番効く。コースは横長なので表示倍率は
**幅で頭打ち**になり、下バーを消しても 88 → 90 px/m にしかならない（+2%）。
窓を 1400px にすると 129 px/m（+47%）。**レイアウトを詰めるより窓を広げる方が効く。**

細かいこと:

- **`回` は等幅フォント（Menlo）に無い**ので豆腐になった。数字だけ等幅にして
  単位はラベル側（`衝突 [回]`）に移した。`°` `—` `rad/s` は Menlo にある
- 有効点数（`点群 有効 354/360`）をパネルに出した。**ノイズや欠損をいじったときの
  効きが数字で見える**ようになり、設定ページと繋がる
- 中心線を地図に薄く描いた。これは経路追従の正解データそのもの

### コースエディタを作った（2026-08-12）

```bash
.venv/bin/python -m sim.editor            # 新規
.venv/bin/python -m sim.editor circuit    # 既存を開いて編集
```

センターライン方式にしておいたので、エディタは**「配列に要素を足す UI」**で済んだ。
パレットから直線（0.5/1/2/3 m）と円弧（R0.5/1/1.5/2 m × 30/45/90/180°）をクリックして
つないでいく。出力は手書き JSON と**完全に同じ形式**なので、エディタで作って手で微調整、
その逆もできる。

設計で効いたこと:

- **閉ループのずれを常に出す。** 終点から始点へ線を引き、位置と角度のずれを数字で出す。
  数字だけだとどちらに戻ればよいか分からないので、線が要る
- **プレビューは俯瞰ビューと同じ描画コードを通す**（`sim/ui.py` の `map_surface` を新設して
  `gui.py` と共有）。**エディタで見た物と走らせた物が違って見えたら、エディタを信用できない。**
  2箇所にコピーすると必ずずれる
- 区間の並びは**末尾8個だけ**出す。全部出すとパネルが溢れるし、直すのは末尾だから

実装で踏んだこと:

- `meta()` の中で `closed()` を呼んだら **`meta → closed → course → meta` の無限再帰**。
  `loop` は呼び出し側から渡す形にした
- **また等幅フォントの豆腐。** `閉じた` を Menlo で描いていた。`Ui.kv(..., mono=False)` を
  足して、値に日本語が入るときは UI フォントを使うようにした。
  **数字は等幅、日本語は UI フォント**を徹底する
- PNG 方式のコースを開こうとしたら「編集できません」と出す（`path` キーの有無で判別）
- ファイル名は**半角英数のみ**受ける（pygame は IME を扱えないし、ファイル名になるため）

**共通化（`sim/ui.py`）で踏んだこと。** 色の定数を移したとき `OK` の import を落としていて
`NameError` になった。**単体で `python -m sim.gui` を起動しても出ない**（真値が来ないので
待機画面しか描かず、車体の描画に到達しないため）。`sim.run` から実走させて初めて出た。
**描画のテストは「データが流れている状態」で回さないと意味がない。**

これを機に `sim.run` を2点直した。

- 俯瞰ビュー（`sim.gui`）が落ちても**他を巻き添えにしない**（`Child(essential=False)`）。
  GUI が開けなくてもシミュレーションは成立する
- 起動前点検に **UDP 5598/5599（シムの私設チャンネル）** を追加。`sim.gui` の二重起動で
  ここが埋まると GUI だけ黙って落ちるので、起動前に PID を出す。
  `sim.gui` 単体でも「別の sim.gui が使っている可能性」と出すようにした

### エディタの詰め — グリッドのずれと、閉ループの作りやすさ（2026-08-12）

**1m グリッドが世界座標とずれていた（欠陥）。** グリッド線を「画像の左端から 1m ごと」に
引いていたため、画像の原点（外接矩形から決まる半端な値）ぶんずれていた。
**世界座標の整数メートルに引く**のが正しい。これで 1m の直線を置けばグリッドに乗る。

**45°/30° で閉ループを作るのが難しい**という指摘への対応。本質は「あと何度回れば
360°になるか」が見えていないことだったので、3つの数字を出した。

- **総回頭** — 360 の倍数でなければ絶対に閉じない。「あと 90」まで出す。
  パレットの角度は 30/45/60/90/180 で、**どれも 360 を割り切る**（同じ角度の繰り返しで必ず閉じる）
- **始点まで 前 / 左** — 進行方向を基準にした差。世界座標の差を出しても
  「どちらに直せばよいか」が分からない
- **直線で閉じる**ボタン（`Enter`）— 回頭差と横ずれが無ければ必要な長さの直線を 1 本足す。
  無理なときは「回頭差 90° / 横ずれ +3.00m」と残りを言う

実装で踏んだこと: `centerline` は numpy 配列なので、そこから作った長さをそのまま区間に
入れると **`np.float64` が混じって JSON 保存が TypeError で落ちる**。`float()` で素の型に
落とすこと。保存まで通すテストを書いていなければ気づかなかった。

### エディタをシミュレータGUI の `F2` から開けるようにした（2026-08-12）

**画面に組み込まず、別プロセスとして起動する。** 俯瞰ビューは「走っている物を見る画面」、
エディタは「未保存の状態を持つ作成ツール」で性質が違う。同じプロセスに入れると
シムを止めた瞬間に作りかけのコースが消えるし、走らせながら編集もできない。

`start_new_session=True` を付けてある。**これが無いと `sim.run` が子のプロセスグループごと
止めるときにエディタも道連れになり、未保存のコースが飛ぶ。**

**先に潰したバグ。** `sim.gui` はコースを**パスだけをキーに**キャッシュしていた。
シム側（`SimChannel._apply`）は `set_course` のたびに読み直すので、エディタで直した
コースを開き直すと **車は新しい形を走っているのに俯瞰ビューだけ古い地図**という、
一番たちの悪いずれ方をする。キーに更新時刻（`st_mtime_ns`）を含めて解決した。
エディタが1キーで開けるようになると必ず踏むので、機能を足す前に直した。

### 操作を全部ボタンにも出した / F キーをやめた（2026-08-12）

**macOS では F キーがメディアキーに取られている**ので `F2` は使えない。
コースエディタの起動を `M` に変えた。

**ショートカットだけだと機能に届かない。** キーに割り当てた操作はパネル下部のボタンにも
出すようにした（`Act` / `Btn(kind="act")`）。ラベルにキーを併記（`次のコース  N`）してあるので、
ボタンを使ううちにショートカットも覚えられる。

- シミュレータGUI 走行ページ: 設定 / 次のコース / 姿勢リセット / 軌跡消去 / コースエディタ / **E-STOP（赤）**
- 同 設定ページ: 設定を閉じる / 既定値に戻す / 次のコース / コースエディタ
- エディタ: 直前を削除 / 全消去 / 既存を開く / 保存

**キーとボタンは同じ関数を呼ぶ**（`_reset_pose` / `_toggle_estop` など）。
片方だけ直して挙動がずれるのを防ぐため。

ついでにエディタの **`C`（全消去）を2度押しに**した。`Backspace`（直前を削除）と違って
取り消せないうえ、ボタンにもなったので誤爆すると作業が全部消える。

### 俯瞰ビューの窓を閉じたらセッション全体を終える（2026-08-12）

端末に戻って Ctrl-C を押させないため。ただし**そのまま「GUI が死んだら全部止める」に
すると穴がある** — 二重起動や描画のバグで落ちただけのときに、走っている車まで巻き添えになる。

**終了コードで区別する。**

| `sim.gui` の終了 | 意味 | `sim.run` の挙動 |
|---|---|---|
| コード 0（窓を閉じた・`Q`・`kill`） | 人が終わりにした | **全部止める** |
| 非0（二重起動・例外） | 事故 | シムは続行。開き直せる |

そのため `sim.gui` は SIGINT / SIGTERM を捕まえて**綺麗に畳んで 0 を返す**ようにした。
ここで例外を投げて非0で死ぬと、事故扱いされてセッションが止まらなくなる。

検証: `kill -TERM`（→ 0）で全部停止・残骸 0、`kill -9`（→ -9）でシム続行を両方確認。

ついでに UDP の私設チャンネルを `SURGE_SIM_TRUTH_PORT` / `SURGE_SIM_CTRL_PORT` で
差し替えられるようにした（`SURGE_BUS_DIR` と同じ流儀）。**動いているセッションを
止めずに検証する**ために要る。
