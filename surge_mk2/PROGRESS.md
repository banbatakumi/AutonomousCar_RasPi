## MPC の舵指令のばたつき（約 11Hz）の原因と修正（2026-10-13。**Pi 未反映・実機未検証**・未コミット）

バンビ「舵指令のばたつきを調査して」（下の節で、実機の『雑音』の大半は舵が約 11Hz でばたつき、車がそれに応えている
動きだと分かった続き）。

- **原因**: `raspi/nav/mpc.py` が向き・横の偏差を**経路上の最寄りの点**の接線に対して測っていた。点と点の間（10cm）を
  進む間に向きの偏差が κ·刻み（κ 1.85 で 0.1rad）だけ直線的に増え、次の点へ移った瞬間に跳ね戻る**のこぎり波**になる。
  10Hz で回していた間は 1 周期に 1 点以上進むので隠れていたが、50Hz（`tick` 1）では 1 点を 2〜5 周期かけて通る。
  ヘアピン 1.1m/s で 1 点 90ms＝約 11Hz、2〜2.8m/s では 1 周期おきの反転（実機の記録: 指令の差分の符号が 47〜68% で
  毎回反転・1 周期の変化 0.02〜0.036rad）
- **確かめ方**: ①実機の記録で MPC を開ループで回し直すと同じばたつきが出る（高周波 σ 0.034 / 記録 0.039rad）。向きの偏差は
  添字が変わる周期に 0.057rad、変わらない周期に 0.021rad 動き、舵指令の変化との相関 −0.89。遅延補償・未反映の指令・
  車速・実舵角・重みを変えても消えない ②円（半径 0.55m）の上をぴったり走る車への指令が幅 0.16rad で振れる
- **修正**: 偏差を経路上へ射影した位置で測る（点からの進み `s_off` ぶん、参照の向きを κ·s_off 回す・円弧のぶん横偏差を
  直す）。先の曲率も点へ丸めず線形に補間して読む
- **結果**: 円の上の指令の幅 0.158 → 0.0003rad。実機の記録の流し直し（開ループ）: 10/12 の記録 0.034 → 0.013rad、
  10/11 の記録 0.039 → 0.030rad（速い走行。残りは 10Hz の自己位置の更新ごとの向きの動きに MPC が応えているぶんで、
  開ループでは記録の車の揺れも入力に入る）。**シム（`--set ctrl_mode=1`）: 高周波 σ 0.0276 → 0.0067rad、差分の符号反転
  0.65 → 0.23、ラップ 11.23 → 11.21s、|横偏差| p99 2.7cm**（修正前の走行は ★）
- ★**`sim.bench` の既定は Pure Pursuit（`ctrl_mode` 0）で、実機は MPC（1）**。下の節の学習の検証（`--real-noise` を含む）は
  全部 Pure Pursuit で走っていた。MPC を使う検証には `--set ctrl_mode=1` を付けること
- 下の節の「実機の雑音」（`REAL_VIBRATION`）にはこのばたつきが含まれている。直した版を実機で走らせたら雑音は減るはずで、
  学習のしきい値は走行中に測った雑音の幅から決まるので自動で追従する。記録を取り直したら `REAL_VIBRATION` を測り直す
- 残り: MPC は 10Hz の自己位置の更新ごとの向きの動きにそのまま応える（舵の変化のコスト `r_d` は 0.1 秒刻みの前提で、
  50Hz の呼び出し間隔には合わせていない）。開ループの試算では `r_d` 5 → 30 で指令の高周波が 3 割減るが、追従への
  影響を閉ループで見ていないので変えていない

## 走行中の学習が実機で遅くなった件: 前兆の誤検出の修正（2026-10-12 深夜。**Pi 未反映・実機未検証**・未コミット）

バンビ「slam2d の走行をコース固有のパラメータは最適化するように改良した。しかし実機で動かすと非常に遅くなった」。
記録 2 本（`surge_20261012_122614.mcap`＝学習あり、`surge_20261011_092231.mcap`＝前日・学習なし）と地図
`course_20261012_212123.npz` を解析。**1 周 5.7s → 13.1s。原因は 2 つ。**

### 原因 1（主因）: 横の「前兆」の誤検出で学習値が下限まで落ち、戻らなかった
- 記録の推移: 横 3.48 → 3.91（探索）→ 13 秒目に前兆 → … → 52 秒目に **1.00m/s²（下限）**、加速 2.66→1.33、減速 1.91→0.95。
  以後も毎周 3〜5 回（計 46 回）。**車は滑っていない**（前兆の瞬間の横偏差 1〜2cm、実曲率 ≧ 舵の曲率。前日の記録は
  横 4〜5.8m/s² を実曲率÷舵の曲率 1.00 で走れている）
- しきい値（上限の 5%・40ms）はシムの雑音で決めた値だった。**実機の走行中の雑音はシムの既定の 15〜25 倍**:
  ジャイロの高周波 σ 4.5〜8°/s（シム 0.3°/s）・車速 σ 0.03〜0.05m/s・実舵角 σ 0.016rad、約 11Hz で揺れる
  （舵指令が σ 0.03rad でばたつき、車がそれに応えている）。不足の 200ms 平均でも p99.9 が横加速度の 17〜19%
- しきい値が「上限の割合」だったので、**上限が下がるほど絶対値のしきい値も下がって誤検出が増える**（上限 1.0 で 0.05m/s²）。
  離れた 2 か所で近い値の前兆がそろうと全体の値になり、上へ戻る道が無い。「想定外」1 回で加速・減速も同じ割合で下がる
- ★**検証器が現象を測れていなかった**: シムに実機の雑音が入っておらず、実機の記録を学習に流す手段も無かった

### 原因 2: 見通しの上限（`sight_use`）が GUI から隠れて 1.0 固定になっていた
前日は 0 で走っていた。今日の地図での見積もり（閉じたライン・`line_margin` 0.10）: 学習なしで 6.26s → 見通しあり 7.98s、
学習が上限 6.0 まで届いても 5.39s → 7.50s。**バンビの判断で GUI に戻し、既定を 0 にした**（GUI の設定は 21 項目）。

### 先に作った検証器
- **`raspi/tools/grip_replay.py`**: 実機の記録（MCAP）を `GripLearner` に流し直す。前兆の判定は 100Hz の車両状態だけで
  決まるので、実機で何が前兆と判定されたかが手元で再現できる（直す前: 今日の記録で 23 回・1.00 まで低下、
  前日の記録は上限を 4.0/4.9/5.5 に固定しても 19〜27 回）。`--pin` で上限を固定、`--export` でテスト用の npz に抜く
- **`sim.bench --real-noise`**（`sim/params.py` の `REAL_VIBRATION`・`sim/stm32.py` の `_vibration`）: 実機で測った揺れ
  （2 次の共振に通した雑音。ヨーレート・車速は車速に比例）をテレメトリに足す。**直す前の版はこれで崩壊を再現**
  （μ0.55・0.42 とも前兆 60〜64 回・全部が真値の超過 0%・横 1.00）
- 回帰テスト: `raspi/tests/data/grip_real_2026101{1,2}.npz`（実機の記録から抜いた列）を `test_grip.TestRealNoise` が流す

### 直したこと（`raspi/nav/grip.py`。詳しくはモジュール docstring）
1. **しきい値は雑音より下げない**: 曲率の差のばらつき `GripMap.noise` [1/m] を走行中ずっと測り（保存する）、
   しきい値を「上限の 5%」と「(幅 − 0.015) × 車速² × 12」の大きい方にする。続けて超える回数も雑音に応じて
   最大 15（150ms）まで延ばす。上限が下がっても絶対値は変わらない。雑音なしのシムでは今までの感度のまま
   （シムの幅は 0.009。0.015 以下は数えない——数えると速いコーナーの感度が落ち、路面が 2 割下がった直後に 30cm 外れた）
2. **コーナー 1 つぶんで見る前兆**（抜けた後に記録）: 不足の平均（上限の 3% かつ平均の雑音の 3 倍）と、
   その場所の普段より横偏差が 4cm 以上増えたこと。即時の層は実機の雑音だと遅いコーナーで上限の 1 割、
   速いコーナーで数割の不足しか見えない
3. **歯止め**: 横の下限は出発点の 0.5 倍。雑音が大きいとき、「想定外」で加速・減速まで下げるのは大きな不足か
   横偏差の前兆だけ。横偏差（12cm）の前兆は、求めていた値の 0.95 倍までを記録して想定外として扱う
4. 雑音が大きいとき: 上げ幅を半分（6→3%）、試行に書く「出た横加速度」を長めにならす（雑音の山で前兆の値が消え、
   上限が 19% 跳ねた）
5. **加速・減速（`LongLearner`）**: 車速の雑音があるときは 1 つの窓で決めない（傾きの誤差を 2 階の差分から出し、
   窓を溜めて下の端で上げる）。1 つの窓で決めると、たまたま高く出た窓のたびに減速が 15% ずつ上がって真値を
   17% 上回った。加速は TC の旗が窓の半分以上で立っていれば路面で頭打ちとみなす
6. 局所の値で走っている区間の頭打ちは全体の値を動かさない／前兆の値を書いた周りのセルは、通ったセルの値に合わせる
7. 記録: `AutoState.grip`（学習値・不足としきい値・雑音の幅・試行の平均・横偏差の増え・計画の速度と加速度）を 10Hz で
   載せ、reason に直近の前兆の種類を出す。今回、加速・減速の学習は記録に入力が無く再生できなかった

- **試して捨てたもの**: 前兆なしで通り続けたら前兆の値を 3% ずつ上へ見直す（誤検出の跡を消すため）——雑音なしの
  シムで前兆 3→6 回・横偏差 4→17cm に増えた。**誤って出た前兆の値は残る**（`.grip.json` を消す）
- `sight_use` を GUI へ戻した（`raspi/auto/slam2d_raceline.py`）

## Pi⇄PC の通信遅延の削減（2026-10-12。**Pi 反映済み・実機で計測**・未コミット）

バンビ「ラズパイとパソコン間の通信の遅延を可能な限り減らしたい。消費電力が大きく増えるなら判断は委ねて」。
PC は有線でルーター（メッシュの子機）へ、Pi は 5GHz・80MHz・−36dBm。Wi-Fi の省電力は元から切ってあった。

- **測ったこと**: 通信が流れている間のネットワーク往復は中央値 約2ms（`/ws/control` の ping→pong 1.85ms、ICMP 2.6ms）で、
  ここに削れる余地はほぼ無い。遅れていたのは Pi の配信の待ちと、Wi-Fi の定期スキャンだった
- **映像（`_camera_pump`）**: `1/gui_hz` の刻みで見に行っていた → **フレームがバスに届いた周に送る**（`_bus_pump` が画像のソケットでも起き、
  `_cam_wake` を立てる）。`gui_hz` は上限として残る（`CAMERA_DUE_SLACK` 15% まで早出しを許す）。
  バスに出てから WS に出るまで: カメラ 10fps（DISARM）で **36.9→3.6ms**、30fps（走行時の設定）で **平均 7.4（最大 35.9）→3.3ms（最大 4.7）**。
  30fps では旧実装が 443 枚中 350 枚しか送れていなかった（位相が合わず取りこぼし）のも無くなった
- **WebSocket の圧縮（permessage-deflate）を切った**（`serve(compression=None)`）。JPEG は縮まないのに 1枚 約1.5〜1.9ms
  イベントループを塞いでいた（その間 `cmd` の中継も待つ）

### 原因 → 対策
1. **減速が下がらない・低く止まる・加速が学習されない（課題 1〜3）**
   - 原因①: 区間の始めと終わりの速度²の変化を計画と比べる形は、出た÷求めた が 0.93〜1.20（中央 1.02〜1.09）に
     ばらつき、85%／95% のしきい値では 1 割の不足に気づけない
   - 原因②（★以前からの不具合）: 横の学習がコーナーを抜けるたびに、値が変わっていなくても速度プロファイルを
     作り直していた。「足元は前の速度のまま」の上限を、減速を試す形を重ねた後の速度から作っていたので、
     制動区間の途中で作り直されるたびに制動が手前へずれ、**目標速度に 0.4m/s の段差**ができていた。
     作り直しのたびに加速・減速の測定も 0.4 秒止まり、評価できる区間が 1 周に 1〜3 個しか無かった
   - 対策: `grip.LongLearner` を作り直した。**出ない加速度を求めて、出た値を測る**——求めている間の車速の傾き
     （0.15〜0.4 秒の窓の最小二乗）を出し、「車速が計画から遅れていき、傾きが一定」なら路面で頭打ち＝
     出た値がそのまま限界（1 回で採る）。求めたぶん出ていれば、出た値まで上げる
     - 減速: 制動を始める位置は変えず、制動区間の初めの 0.35 秒だけ確かめた値の 1.15 倍を求める
       （`raceline.probe_brake`。その後は元のプロファイルへ 1.2m かけて戻す）。近い値が 2 回そろったら
       「決まった」として強く求めるのをやめる。ふだんの制動で頭打ちになれば、その区間のうちに下げる
     - 加速: 出たら 10% 上げ、頭打ちになったら出た値の 0.97 倍で止める。出続ければ 3% ずつ見直す
     - 取り違えを防ぐ条件: 横が限界の 5 割未満・区間の初め 0.06 秒と求めるのをやめる手前 0.08 秒は除く・
       計画の速度が跳んだ窓は捨てる・計画より先に居て追いつかれているだけの窓は数えない・「追いつく途中」
       （計画より 0.3m/s 以上遅い）は測らない
     - 横の学習は、値が変わったときだけ版を進める。上げただけの変更では測定を止めない
   - 試して捨てたもの: 強く求める幅 1.25 倍・落とす速度²の 7 割まで（真値に近いと車が目標から 0.2m/s 遅れた
     ままコーナーへ入り、毎周 前兆）／強く求めた後すぐ元へ戻して途中の速度で保つ形（頭打ちの間に車速PIの
     積分が戻され、遅れが 0.3 秒残る）／60 秒ごとの測り直し（線から 18cm・横の値を 1 割低く誤った）／

     下がった）／壁際の横偏差でその場所の値を下げる（ヘアピンの横偏差 5〜7cm は速度を落としても減らず、
     毎周下がり続けた）
2. **路面が急に下がったとき（課題 5 の一部）**

### シムと実機の違い（そのまま実機に使わない）
- シムは限界で曲率がいきなり頭打ちになる。実機のタイヤは徐々に逃げる
- シムには後輪の巻き込みとロックが無い。**減速を強く求めて測る間、実機は後輪がロックへ向かう**（速度指令での
  減速は回生で、ABS は制動モードのもの）。シムではただ頭打ちになるだけ
- シムの前後の限界は「加速度の上限でいきなり頭打ち」。実機はスリップ率とともに力が変わり、TC が介入する。
  「傾きが一定」の判定が実機でどれだけ通るかは未確認
- **シムの車速には雑音が無い**（ローパスだけ）。実機の前輪エンコーダは粗い。単体テストでは σ 0.02m/s の雑音で
  6% 以内だが、窓 0.15〜0.4 秒・傾きの一致 15% という定数は実機の記録で決め直す
- シムの摩擦円は `1/sqrt(1+横²)`、学習は `sqrt(1−横²)` で直線の値に直す（横 5 割で 3% の差）
- シムの前兆の量は限界内で上限の 3〜5% しか動かない。実機は普段から 10% 動く
- シムの TC の旗は作り物（駆動の加速度が上限で頭打ちの間だけ立つ）
- STM32 のデッドマン: ベンチではホストが詰まると車が止まる。実機でも、指令が 150ms 途切れると同じことが起きる
  （走り直す所で線から 17cm 外れて壁に当たった。学習とは別の問題として残る）

### 実機で最初に試す手順（`docs/development.md` §4.3 も同じ）
1. `grip_learn` 0 のまま周回を録る。MCAP から ①前兆の量（車速²×（舵角の曲率 − 実曲率））が限界内でどれだけ動くか
   ②制動・加速の区間で、車速の 0.15〜0.4 秒の窓の傾きがどれだけばらつくか を出す
2. `grip_learn` 1・`grip_down_only` 1（上げない・強く求めない）で、何もない所で前兆や「下げた」が増えないか見る
3. `grip_down_only` 0・`grip_max` 5.0・`v_max` は普段より少し下げる。壁の外側に緩衝材。**最初の数周、長い直線の
   後の制動で車が目標より速く残る**（減速を測っている）。reason の「減速」が 2 回そろって動かなくなれば測り終わり
4. 落ち着いたら `grip_max` を上げる。本番の計測走行は保存した値＋`grip_down_only` 1

## 横グリップのリアルタイム最適化（2026-10-12、Pi 未反映・実機未検証・未コミット。既定は切）

バンビの方針（2026-10-11）: 車に固有の値はシステム同定、**路面で変わる値は走行中に決める**。
旋回試験の `mu` 0.417（4.09m/s²）はコースの限界ではなかった（下の「見通しの上限なし…」の節）。
`slam2d_raceline` / `slam2d_route` の速度プロファイルが使う横加速度の上限を、走行中の車の反応から
場所ごとに決める仕組みを足した。`vehicle.toml` の `mu` は初期値として読むだけで、書き戻さない。

### 作ったもの
- **`raspi/nav/grip.py`**（新規）: 地図座標 0.25m 格子の `GripMap`（セルごとに「通った横加速度の最大」
  「前兆が出た横加速度の最小」[m/s²] と前兆の量の普段の値）、`GripLearner`、`LaunchFit`
  - **即時に下げる層**（100Hz、`on_vehicle_state`）: 前兆が出たその周期に目標速度の上限を出し
    （出ている横加速度で回れる速度の 0.97 倍）、その場所のセルに値を書く。次の `tick`（50Hz）で指令に効く
  - **コーナー1つ＝1回の試行**: 実際の横加速度（車速×ヨーレート）が上限の 88% 以上まで出た区間を
    抜けたら評価。`v_max`・加減速で決まっている区間は数えない
  - **共有と挟み込み**: 通るたびに全体の値を `grip_step`（既定 6%）上げる。前兆はまずその場所だけ
    下げ、ほかの場所で「それより上を求めても出ない」が 2 回続くか、離れた別の場所でも近い値で
    出たら全体の限界にして、通った値との幅 3% まで詰めて止める。収束後も下げる方は働く
  - **前兆の量** = 車速²×（舵角から出る曲率 − ヨーレート÷車速）。舵角側には同定したヨーの2次遅れを通し、
    その場所の普段の値との差が上限の 5% を 4 回（40ms）続けて超えたら前兆。舵が動いている間は判定しない。
    補助に横偏差 12cm。短いコーナーで判定できない場合に備え、「前より高い上限で通ったのに出た
    横加速度が増えない」（頭打ち）と「これまでの最大より上を求めても出ないが 3 回続く」でも止める
  - 加減速しながら出た前兆は、前後の加速度を合成した半径で記録（「横」「加速＋横」「減速＋横」）
  - **初期値**: 同定値×`grip_init`（既定 0.85）。発進で TC が介入した区間の車速の傾き（＋転がり抵抗）×比×0.92 が
    最初の試行より前に出れば、そちら。比（横の限界÷発進の加速度）は収束したとき `saved_maps/_grip_vehicle.json` に保存
- **速度プロファイル**: `raceline.speed_profile` / `retime`・`speedctl.catch_up` の `a_lat`・`a_grip` を点ごとの配列に
  対応（配列のときだけ別関数へ分岐。スカラーの速さは 0.180→0.179ms/回で変わらず）
- **planner**: `a_lat_max` を直に読んでいた所（`speed_kwargs`・`_speed_cmd` の余力と `catch_up`）と `retime` 5 か所＋
  回避の引き直しの速度を学習値へ通した（`_spd`・`_grip_levels`）。`slam2d_route` は周回の経路に学習値で
  速度を付け直す（`_grip_timed`）。**`LINE_KEYS` には入れていない**（学習で値が変わっても線は引き直さない）
  - 上げた速度は車の先 1.5m（または 0.6 秒ぶん）より先にだけ反映（`_grip_hold`）。下げる変更は全体へすぐ

### 設計から変えた点（理由）
- **前兆を比（実曲率÷舵角の曲率）で見ない。** 舵の切り返しで分母が 0 を通り、限界内でも ±1 まで振れて
  60 秒に 18〜33 回誤検出した。横加速度の不足量にし、ヨーの2次遅れを通し、舵が動いている間は判定しない形にして、
  限界内の最大 0.03〜0.05（しきい値 0.05）・最終版の全シナリオで誤検出 0
- ★同じ時刻の `vehicle_state` が続けて届く（受信がまとまる。間隔は 0〜35ms）。これを「間が空いた」と扱って
  遅れの状態を捨てていたのが誤検出の残りの原因だった。同時刻は捨てる
- **発進の加速度は 0.3 秒続いた窓に直線を当てはめる形にできなかった。** シムの TC の旗は 0.01〜0.2 秒の細切れで、
  続いた 0.3 秒を待つと最初のコーナーに間に合わない。介入が続いた区間ごとに当てはめ、長さの重みで合計 0.3 秒
  集める。傾きには転がり抵抗を足す（足さないと比が路面で 1.46〜1.52 と動く）
- 上げ幅の設定 `grip_step` を足した（指定の 4 項目のほか。実機で小さく始めるため）
- **探している間は `lat_use` を掛けず、限界の見積もりそのものを求める。収束してから見積もり×`lat_use` で走る。**
  割合を掛けたまま探すと、求める横加速度が限界に届くのは見積もりが「限界÷割合」まで上がった後で、
  `grip_max` に先に当たると限界いっぱいで走っているのに気づかなかった（`lat_use` 0.9・`grip_max` 6.0・真値 5.40 で
  見積もり 6.00 のまま）。直した後は見積もり 5.30。`grip_down_only` 1 は探さないので、いつも見積もり×`lat_use`

**分かったこと（先に検証器）**

- 速度が目標に 0.2s 遅れる正体は**速度PIの比例項**（加速度 a を出すのに偏差 a×0.157s が要る。`1/(speed_plant_gain×speed_kp)`）。ランプ 3.0 は同定の加減速（正味 2.51/2.55m/s²）より上だが、目標を急に下げても偏差が 3.0m/s² でしか溜まらないので、減速の立ち上がりには効いている。旧方式をファームの写しに 1 次元で当てると、コーナー進入で +0.48m/s（実車の 0.5 と一致）
- **最小曲率のラインは遅い。** 最高速度で頭打ちの所（3m/s・3.7m/s² なら半径 2.4m より緩い所）は半径を開いても速くならず、大回りした距離だけ損する。同じ制約のまま見積もりラップを直接下げると toyota2 −14%・toyota −7.5%・チケイン −4%
- 曲率の上限は現行の再重み付けで 0.5% 以内に守れていた → **計画していた汎用 QP（ADMM）は作らなかった**（費用に見合わない）
- `sim.bench` は `on_vehicle_state` を渡しておらず SLAM の脱スキューが一定 twist だった。前後の力に摩擦円が無く立ち上がりが楽観的だった。両方直した
- 実コースの再現（`real_20261006`）は壁に穴があり、当時の `.routes.json` が無いので周回させられなかった（検証は上の3コース）

**変えたもの**

1. **走りの限界を同定値から**（`raspi/core/vehicle.py`）: `a_lat_max`（mu×g）・`a_accel_max(v)`・`a_decel_max`・`speed_loop_tau_s`・`steer_delay_s`。GUI の `a_lat`/`a_accel`/`a_brake`（絶対値）は廃止し、**利用率** `lat_use` 0.9・`accel_use` 0.95・`brake_use` 0.9 に（`slam2d_raceline.with_limits` が `p["a_lat"]` 等を足す。下流は従来のキーを読む）。摩擦円は利用率ではなく限界で引く（`a_grip`）
2. **ライン**（`raspi/nav/raceline.py`）: `kappa_use` 0.9（経路に許す曲率 = 限界×0.9 ＝ 半径 53cm）。最小曲率の解を初期値に、**見積もりラップを直接最小化**（`refine_time`。ガウス形のこぶ×多重スケールの決定的なパターン探索、制約を破る解は採らない。評価 5000 回まで。切り替えの設定 `line_refine` は一度足したが消した——常に仕上げる）。速度プロファイルの内側をリスト化して 0.84→0.22ms。`TIGHT_FLOOR` 0.6→1.0（削らない）。曲がり切れない区間が残れば reason に出す（`tight_sections`）。**速度の設定を変えるとラインも引き直す**（`LINE_KEYS`）

- **ファーム**（`MainF446RE_V3/src/control/drive.c` の `SpeedFeedforward()`）: 車速PIの出力に「目標車速の傾き（20ms のローパス後）× `speed_ff_nm_per_m_s2` ＋ 進む向き × `speed_ff_rr_nm`」（後輪2輪の合計トルク）を足す。`param_id` 0x00B1・0x00B2、既定 0（＝従来と同じ）。`protocol_version` 0x0014→0x0015。ビルド済み、`docs/pi_uart_protocol_v0.21_delta.md`
- **値**は `[control]` の同名のキー。`speed_ff_nm_per_m_s2` = 1÷`speed_plant_gain`（0.046458）、`speed_ff_rr_nm` = `rolling_resistance`÷`speed_plant_gain`（0.012693）。**同定を適用すると `tools/sysid/toml_update.py` が書き直す**（0 より大きいときだけ）。新しい同定は要らない（②前後運動試験の値）
- **Pi**: `[control]` の値が 0 より大きければ（`Vehicle.speed_ff_firmware`）、planner は「プロファイルの速度＋その傾き（`AutoState.accel_limit`）」を渡すだけになる（`speedctl.ref_command`）。先読みは 半周期 10ms＋通信（同定の遅延）＋ローパス 20ms で、**合わせ込む係数が無い**。0 なら従来の Pi 側の前倒し（`SpeedFF`）
- **シム**: `sim.vehicle.SpeedController` に同じ式。`sim.bench --control KEY=VALUE` でシムの STM32 だけ値を変えられる
- **確かめたこと**: 実ファームのホストビルド（`tools/ctrl_tune/tests`）で、傾き 2.0m/s² の間の遅れ 0.205→0.041m/s（残りはローパスぶん）、値 0 なら足す前と同じ動き。1次元の周回でコーナー進入の出過ぎ 0.12（Pi 側の前倒し）→0.09m/s、誤差 0.047→0.025m/s、利得を ±20% 外しても 0.11 以下。`sim.bench`（1本ずつ、衝突0）: toyota2 11.95→**11.74s**（理想 11.76s）、toyota 13.33→**13.06s**（理想 13.09s）、チケイン 8.69→8.66s——**プロファイルどおりに走れるようになった**
- ★`tools/sysid/bench.py` の真値が Kp/Ki を 0.25/0.5 と決め打ちしていて、toml を 0.3/0.6 に直した後は回復テスト3件が落ちていた（利得 22→18.4 と出る）。決め打ちをやめた
- ★**書き込む順番**: Pi と STM32 を一緒に入れ替える（io_node は版が合わない STM32 を ARM しない）。実機ではまず直線の加減速で、車速が目標に遅れないこと・TC の介入が増えていないことを見る。効かせたくなければ `[control]` の 2 つを 0 にする

**回避の結果**（toyota、半径10cm、障害物なし 13.29s）: 直線の広い所は**減速せず 3m/s のまま避けて** 14.9s（計算 最大14ms）。コーナーの頂点付近は横を通れず「止まる→Hybrid A*」で 19.4〜20.9s。

**残っていること**

- ★**実機・Pi で未検証。** まず `plan_ms_max` とライン生成の時間（Mac 1〜3s、Pi は 3〜8s の見込み。ワーカースレッド）を見る
- ★**ファームの `drive.h` が未コミットで `DRIVE_SPEED_KP/KI` 0.3/0.6、toml は 0.25/0.5。** 書き込み済みなら toml を直す（前倒しの時定数が 0.157→0.131s になる。ずれたままでも走りは壊れない）
- `tools/check.sh` の「vehicle.toml → vehicle.ts が古い」は今回の変更の前から（toml は触っていない）。`vehicle.toml` の `mu` のコメント 4.48 も古い（今の値は 4.09）
- 壁との最小距離が 2cm の周がある（`line_margin=0.05`。ラインが壁沿いを長く走るようになった）。実機は 0.08 から始めること
- 見通しの利かないコーナーの直後の障害物（0.8m 手前で初めて見える）は止まり切れない。半径30cm は Hybrid A* が2回失敗して待つ（以前からの未解決）
- MPC（`ctrl_mode=1`）は toyota2 で 13.08s と Pure Pursuit と同等。既定は PP のまま。MPC は合間の更新をしない（10Hz）。`_sent` の二重前進は未修正
- 実車の `auto.json` は `ctrl_mode=1`・`v_min=1.0` のまま。旧キー（`a_lat` 等・`delay_s`）は無視される

# 運用メモ

## Pi 実機（surge-mk2）

接続情報の詳細と機密は `docs/setup_credentials.md`（gitignore 済み）。要点だけ:

- **Raspberry Pi 5 / Debian 13 (Trixie) / Python 3.13.5**
- **接続は Ethernet 直結**。Mac の USB アダプタ ↔ Pi。**Pi eth0 = 固定 `169.254.55.2`**。
  `ssh surge-mk2` で決め打ち接続（`~/.ssh/config` 設定済み、鍵は `~/.ssh/id_surge_mk2` でパスフレーズ無し。
  `sshpass` は今は不要）
- **UART**: `/dev/serial0 -> ttyAMA0`。io_node では `/dev/serial0` を使う（名前直書き禁止）
- リポジトリは **Mac → Pi へ rsync**（`~/surge_mk2`）。git remote はあるが未 push
- venv は `~/surge_mk2/.venv`（`--system-site-packages`）
- **電源は 5V/5A（27W）USB-C PD 必須**（USB給電では不足してハングする実績あり。解決済みだが忘れないこと）

### よく使うコマンド

```bash
rsync -az --exclude __pycache__ --exclude '*.pyc' --exclude .venv --exclude docs/setup_credentials.md \
  surge_mk2/ surge-mk2:~/surge_mk2/
ssh surge-mk2 'cd ~/surge_mk2 && .venv/bin/python -m unittest discover -s raspi/tests -t .'

# 反映（毎回rsyncを手打ちしていたのをスクリプト化。何を再起動すべきかはスクリプト冒頭の表を見る）
tools/deploy.sh                # GUI をビルドして rsync（既定・いちばん安全）
tools/deploy.sh --no-gui       # Python だけ直したとき
tools/deploy.sh --services     # systemd unit を入れ直す（--max-speed 等を変えたとき）
tools/deploy.sh --restart      # surge-telemetry / surge-camera を再起動（E-Stop 無関係）
tools/deploy.sh --restart-io   # ★ surge-io を再起動（E-Stop がラッチする。車体のそばで実行）
```

### mDNS（`surge-mk2.local`）— IP を探す作業は不要

`surge-mk2.local` が直結・Wi-Fi のどちらでも生きている方を指す（`ssh surge-mk2` /
`http://surge-mk2.local:8000/` が常に通る）。運用上ハマりやすい点:

- **`~/.ssh/config` に `AddressFamily inet` が必須。** 無いと直結があるのに IPv6 リンクローカル
  （Wi-Fi 経由）へ迷い込む。curl は `-4`
- **IF を落として戻すと avahi が再広告しないことがある。**
  「直結が生きているのに遅い」ときは `ssh surge-mk2 'sudo systemctl restart avahi-daemon'`
- **素の `ping 169.254.55.2` は直結が生きていても失敗しうる。**（169.254/16 のルート重複のため）
  直結の生死は **`ping -b <IF名> 169.254.55.2`** で確認（IF名は挿し直すと変わる）
- mDNS が使えない環境では MAC のベンダ prefix `2c:cf:67`（Raspberry Pi Ltd）で `arp -an` を grep
