# SURGE Mark.2 UART プロトコル仕様

**バージョン**: v0.31（`protocol_version = 0x001F`。唯一の定義は `raspi/proto/protocol.toml`）
**対象**: Raspberry Pi 5 ⇄ STM32F446RE 間の通信

> **数値・バイト配置・ビット定義の正は `raspi/proto/protocol.toml`**（生成物 `raspi/proto/generated/`）。
> 本書は意味・使い方・設計理由を書く。フィールド表は読みやすさのための写しで、食い違ったら toml が正。
> 調整パラメータの名前・範囲・仮置きはファームの `src/control/control_params.h` の表が正。
> ファームの実装は `AutonomousCar/Program/MainF446RE_V3/`（`src/comm/ras_link.[ch]`）、Pi 側は `raspi/proto/`・`raspi/msgs/convert.py`・`raspi/nodes/io_node.py`。

- 全フィールドはリトルエンディアン。TYPE の方向規約: `0x01-0x0F` = STM32 → Pi、`0x10-0x1F` = Pi → STM32

---

## 1. 物理層

| 項目 | 値 |
|---|---|
| ボーレート | **1000000 bps**（Pi 側は `raspi/proto` の `UART_BAUD`） |
| フォーマット | 8N1、フロー制御なし |
| 実効スループット | **100 kB/s**（1バイト = 10ビット） |
| 配線 | Pi GPIO14 (TX) → STM32 RX / Pi GPIO15 (RX) ← STM32 TX。3.3V 同士でレベル変換不要 |

STM32 側は USART1（APB2 45MHz、オーバーサンプリング16）で USARTDIV = 2.8125 = 2+13/16 となり、ボーレート誤差は 0%。
Pi 5 側の誤差は `STATS` のフレーム・CRC エラーが 0 付近かで確かめる。

**1Mbps の理由**: 基板内の短い配線で余裕があり、フレームの線上時間が短い（TELEMETRY 1.09ms、COMMAND 0.22ms）ので
順番待ちがほぼ無い（使用率は §11）。STM32 の受信リングは 2048B で、上書きとみなすまでの猶予は約 20ms。

## 2. 設計方針

### 2.1 責務分割

| 担当 | 内容 |
|---|---|
| **STM32** | モータ電流/速度制御、ステア角度制御、TC・ABS・TV、LD06 パース、超音波、電流・温度リミッタ、通信途絶時の自動ブレーキ、**モータ機械角 ⇄ 路面舵角**・**車輪角速度 → 周速**の換算、**`speed` の車体中心線方向への射影** |
| **Raspberry Pi 5** | 知覚、自己位置推定、経路生成、行動判断、テレメトリ配信、**前輪オドメトリの射影**（§5.3） |

**Pi が送るのは目標速度・加速度上限・目標舵角（と brake・torque_mode 等のモード）だけ**で、PWM やトルク配分は送らない。
TC/TV など数 ms で効かせる制御は、UART 往復 + Python の遅延（30〜50ms）を挟めないので STM32 内で閉じる。

**機械定数は STM32 に閉じる。** Pi は車輪半径・ギア比を知らず、UART 上の物理量はすべて SI 単位（m/s、rad、N·m、0.1mm）。
例外はステアのリンク換算の係数（`STEER_LINK_GAIN`/`STEER_LINK_CUBIC`）で、同定値を Pi の `vehicle.toml` が持ち `CONFIG_SET` で送る（§5.8.4）。

### 2.2 プロトコル設計の原則

1. **可変長・パケット種別付きフレーム**（固定長単一フレームは拡張で破綻する）
2. **CRC16 必須**（ヘッダ・フッタだけでは単一ビット化けを見逃す）
3. **LiDAR は1周を12分割して送る**（遅延削減・タイムスタンプ付与・バス占有回避・損失局所化）
4. **周期コマンドと設定変更を混ぜない**（設定は個別ID + ack）
5. **全パケットにタイムスタンプを載せる**
6. **積算量は差分ではなく累積値で送る**（パケットロスで情報が永久に失われない）。`odom_dist` と `STATS` に適用
7. **1つの TYPE は 1つの LEN と 1つの方向だけを持つ**（可変長は `LOG` のみ）

## 3. フレーム構造（両方向共通）

```
┌────────┬────────┬──────┬──────┬──────┬───────────┬────────────┐
│ 0xAA   │ 0x55   │ TYPE │ SEQ  │ LEN  │ PAYLOAD   │ CRC16      │
│ 1B     │ 1B     │ 1B   │ 1B   │ 1B   │ LEN bytes │ 2B         │
└────────┴────────┴──────┴──────┴──────┴───────────┴────────────┘
  0        1        2      3      4      5           5+LEN

オーバーヘッド 7 バイト / PAYLOAD 最大 255 バイト
CRC 計算範囲: TYPE(offset 2) から PAYLOAD 末尾まで（= LEN + 3 バイト）
```

### 3.1 各フィールド

| フィールド | 説明 |
|---|---|
| `SYNC` (0xAA 0x55) | 同期ワード。1バイトだとバイナリ中に頻出して誤検出するので 2バイト |
| `TYPE` | パケット種別（§4） |
| `SEQ` | 0-255 のローリングカウンタ。**送信方向ごとに独立**。欠番でロスを検出 |
| `LEN` | PAYLOAD のバイト数 |
| `CRC16` | CRC-16/CCITT-FALSE（§3.2） |

STM32 は SEQ と CRC を**送信の直前（DMA 起動の直前）**に確定する（PONG の T3 と同じ場所）。優先度の高いキューから送るので
送出順に SEQ が単調増加し、正常なら Pi の `FrameParser.stats.reordered` は 0 のまま（増えたら実際の異常）。
Pi は追い越された分をいったん `packet_loss` に数え、遅れて届いたら差し引く。送信キューの溢れは SEQ の欠番にならず
`STATS.tx_drop` に出る。どのストリームが落ちたかは SEQ では分からないが、LiDAR は `sector_idx` の連続性で追える。

### 3.2 CRC 仕様

**CRC-16/CCITT-FALSE**: 多項式 `0x1021`、初期値 `0xFFFF`、入出力反転なし、最終XOR `0x0000`、検査値 `"123456789"` → `0x29B1`。

実装は Pi 側 `raspi/proto/framing.py`、STM32 側 `lib/crc16/crc16.h`。実装を変えたら検査値で確かめる。
STM32 ⇄ MD 間の CRC-8/AUTOSAR は STM32 内部で閉じており、本プロトコルとは無関係。

## 5. パケット詳細

### 5.1 `LIDAR_SECTOR` (0x01) — LEN = 69

1周（360点）を12セクタ（各30点 = 30°）に分割して送る。

| offset | size | type | field | 単位・備考 |
|---|---|---|---|---|
| 0 | 1 | u8 | `sector_idx` | 0-11 |
| 1 | 4 | u32 | `t_start_us` | STM32 monotonic μs（セクタ先頭点の取得時刻） |
| 5 | 2 | u16 | `duration_us` | セクタ30点の取得に要した時間 |
| 7 | 2 | u16 | `rot_speed_dps` | **deg/s そのまま（スケール 1）**。LD06 が報告する回転速度 |
| 9 | 60 | u16×30 | `dist[30]` | mm。**0 = 無効 / 範囲外** |

#### 角度の求め方

**角度は `sector_idx * 30 + i` [degree]（i = 0..29）で一意に決まる。** STM32 が 1° ビンに整形した時点で角度は格子に乗っているので、角度フィールドは持たない。

#### ★ 左右の鏡像反転（Pi 側で直す）

**この角度はセンサ基準で、そのまま車両角に使うと点群が左右反転する。** LD06 は裏向き（PCB 面が下）に付いており、
0° は前方だが角度の増える向きが車両座標（反時計回り正）と逆。

```
車両角 [deg] = (360 - (sector_idx * 30 + i)) % 360
```

STM32 はこの補正を**あえて行わない**。0°/180° がセクタ境界に乗って1セクタが隣接2セクタに分裂するうえ、
試したところ原因不明の通信エラー増発が再現したため（ファームの `src/sensing/lidar.h`）。

Pi 側では `ScanAssembler`（`raspi/msgs/convert.py`）が**この1箇所だけ**で反転する。`Scan.dist` の添字は車両角なので、
ノード・GUI・地図生成は反転を意識しなくてよい。反転の結果 **1周は添字の降順に取得される**ため、
`sector_t_ns` / `sector_dur_us` / `sector_seen` は車両座標のセクタ番号 `11 - sector_idx` へ移して持つ。

**30° の境界も 1° ずれる。** セクタ `s` が持つのは車両角 `30*s+1` 〜 `(30*s+30) % 360` で、`30*s` ちょうどの点は隣のセクタ `s-1` のパケット由来。

#### 各点の時刻の求め方

```
t[i] = t_start_us + duration_us * i / 29        (i = 0..29、パケット内の添字＝センサ基準)
```

`Scan` に組み上げた後は、車両角 `deg` から**センサ角に戻してから**引く（`raspi/msgs/types.py`）。

```
sensor = (360 - deg) % 360
s, i   = 11 - sensor // 30, sensor % 30
t_ns   = sector_t_ns[s] + sector_dur_us[s] * 1000 * i / 29
```

**車両角のまま `30*s + j` と分解しないこと。** 上の 1° ずれで `j = 0` の点だけ別パケット由来になり、最大1周（約 100ms）外す。

`duration_us` があるので、セクタを1つ落としても歪み補正が壊れない（前セクタとの `t_start_us` 差に頼らない）。
`rot_speed_dps` は回転異常の検出と妥当性チェックに使う（`duration_us` から求まる 30° の所要時間と大きく食い違えばそのセクタを捨てる）。
スケールが 1 deg/s なのは、0.01 deg/s では u16 で 655 deg/s までしか表せず、LD06 の実回転（10 rps ≒ 3600 deg/s）が入らないため。

#### 設計意図

- **1周まとめて送らない理由**: 貯めるだけで 100ms の遅延が乗る／720B の送信中は TELEMETRY が割り込めない／
  セクタごとのタイムスタンプで走行中の歪み補正ができる／CRC エラー時の損失が 1/12 で済む
- **点群歪み補正**: 1周 100ms の間に車体が動く（10km/h で約 28cm）。Pi 側で `t_start_us` / `duration_us` とオドメトリから各点を補正する
- **STM32 側のビニング**: LD06 の生データ（約 450点/周、約 0.8° 刻み）から、各ビン中心の角度での距離を前後2点の線形補間で求める。
  2点の距離差が 50mm を超える（物体の縁）・どちらかが無効・角度の間隔が 2° を超える（欠落）ときは補間せず、ビン中心に近い方の点を採る
  （`src/sensing/lidar.[ch]`）。**最小距離は採らない**: 衝突判定には安全側でも、地図用のデータを近距離側へ系統的に歪ませ、
  平均化で消えないバイアスとしてスキャンマッチングの精度を落とすため。安全用途の最短距離判定は STM32 内部で完結させる

### 5.2 `LIDAR_SECTOR_I` (0x05) — LEN = 99 / `LIDAR_SECTOR_C` (0x09) — LEN = 39

いずれも既定 OFF。`0x01` と排他（§5.8.1）。

**`LIDAR_SECTOR_I`（強度付き）** — `0x01` と同じレイアウトの末尾（offset 69）に `intensity[30]`（u8×30、LD06 の信頼度をそのまま）を追加。

**`LIDAR_SECTOR_C`（圧縮）** — `0x01` と同じレイアウトで、`dist[30]` だけ u8×30・**2 cm/LSB**。`0` = 無効、`255` = **5.10m 以上（飽和）**。

**`255` は「5.10m ちょうど」ではなく「5.10m 以上」。**

```python
if d == 0:            continue                 # 無効。何も更新しない
elif d == 255:        mark_free_upto(5.10)     # 「5.1m まで障害物なし」— 点は打たない
else:                 mark_hit(d * 0.02)
```

**`255` を 5.10m の実測点として占有格子に打つと、実在しない壁が円状にできる。** Pi 側は `Scan.saturated` で区別する（`raspi/msgs/convert.py`）。
LD06 の測距精度が ±1.5cm 程度なので 2cm 量子化の損失はほぼ無く、失うのは 5.1m 以遠だけ。

### 5.3 `TELEMETRY` (0x02) — LEN = 102

**`t_us` は送信時刻ではなく、中身のスナップショットを取った時刻**（新しいスナップショットごとに1回だけ送る）。
送信時刻にすると送信待ちのぶん中身が新しく見え、制御遅延の同定（`calib_latency`）がずれる。
`cmd_seq_echo` だけは送信時点で最後に受けた COMMAND の SEQ（他より最大1周期新しく、往復時間の測定にはこの方が正しい）。
`VERSION.fw_id` が `0x4D463304` 未満のファームの記録は `t_us` の意味が違うので、遅延（`control_latency_s`）の同定に使わない。

#### ★ 前輪データの射影（Pi 側の必須処理）

**`odom_dist[]` と `wheel_speed[FL/FR]` は「その車輪自身の軌跡に沿った距離・速度」で、車体中心線方向ではない**（前輪は操舵輪）。
舵角 δ で前輪の走行距離は中心線距離の 1/cos(δ) 倍（30° で +15.5%、60° で +100%）。**射影済みなのは `speed` だけ。**

**射影は累積値ではなく、1周期ごとの差分にその時点の舵角で掛けて積算する。** 累積値に現在の舵角を掛けると、
直進 100m 後にハンドルを 60° 切っただけで累積距離が半分になる。

```python
# TELEMETRY（100Hz）を受けるたびに
d_front = ((odom_dist[FL] - prev[FL]) + (odom_dist[FR] - prev[FR])) / 2 * 1e-4   # [m]
d_center += d_front * math.cos(steer_actual)
prev = odom_dist[:]
```

- **パケットロス時**: 距離は累積値なので次の1発で戻るが、区間の舵角の履歴は失われ、射影は前後の `steer_actual` による近似になる。
  大舵角でのロスは誤差が残るので、連続ロス時は SLAM のスキャンマッチングに重みを寄せる
- **左右差からのヨー推定**: 操舵輪なので後輪差動の式は使えない（Ackermann で δ_L ≠ δ_R、`steer_actual` は自転車モデル等価の単一値）。
  **ヨーレートの第一情報源は IMU（`yaw_rate`）**とし、前輪差分は妥当性チェックに使う
- **スリップの計算**: `slip_front = wheel_speed[FL] * cos(steer_actual) - speed`（後輪は非操舵輪なのでそのまま）。射影を忘れると舵角 30° で常時 15.5% の滑りに見える

#### 設計意図

- **`speed` と `wheel_speed[4]` を両方送る**: 差がそのままスリップ量になり、TC の挙動が GUI で見える。
  `wheel_speed` を角速度でなく周速 [m/s] にするのは、Pi が車輪径を知らずに引き算だけで済むため
- **`odom_dist` を累積で送る**: `speed` の積分では1パケット落ちるごとに 10ms 分の移動が永久に失われる。累積値なら次の1発で戻る
- **`torque_cmd` は指令値で実測ではない**（MD が返すのは `iq [mA]` だけで、トルク定数 Kt が未実測）。GUI でもそう明示する。
  符号は**正 = 駆動、負 = 制動**で、停車保持中も掛けている制動トルクを負で入れる（`0` だと押さえているのか区別できない）。
  「車両が自分で駆動している」判定には正値だけを使う
- **トルクのスケール 0.0001 N·m/LSB**: 上限が 0.15 N·m と小さく、0.001 刻みでは分解能が足りない
- **`steer_actual` / `steer_cmd_echo` は路面舵角**（モータ機械角ではない。換算は §5.8.4）。同じパケットにあるので差を取るだけで舵の遅延が測れる
- **`cmd_seq_echo`**: Pi が SEQ=57 を送った時刻と echo=57 が返った時刻の差がエンドツーエンド遅延。GUI に常時出し、50ms を超えたら警告
- **電源2系統**: 駆動系（MD、過電流 12.0A）とシグナル系（マイコン・Pi・LiDAR・ライト、過電流 6.0A）で別バッテリー（どちらも 8セル Ni-MH、
  放電終止 8.0V / 満充電 11.2V）。モータの突入電流で Pi が落ちるのを防ぐ分離なので両方を監視する
- **電池電流は単方向（u8）、モータ電流は双方向（i16）**: 電池側は INA180A2 + シャントの GND 基準・単方向で、回生時は 0 に張り付く。
  **Pi は回生中の電池電流を信用しない**

#### 更新レートに関する注意

100Hz で届いても 100Hz で更新されているとは限らない。

| フィールド | 実更新レート | Pi 側の扱い |
|---|---|---|
| `us_front` / `us_rear` | **実質 20Hz 以下**（前後交互） | 同じ値が続く前提。エッジ検出に使わない |
| `temp[4]` | 数 Hz | 傾向監視のみ |
| `batt_*` | 数十 Hz | フィルタ済み |
| `speed` | 100Hz（STM32 内は 2kHz）。カルマンフィルタの車速（§5.3.1） | リアルタイム用途にそのまま使ってよい |
| `wheel_speed`（前輪） | 100Hz。時定数 9.95ms の1次ローパス（`DRIVE_LPF_TAU_FRONT_S`）後の報告用の値 | 車速の計算には使わない |

**`speed` / `wheel_speed` を微分して加速度を求めない。** 前輪エンコーダはアナログ絶対角の ADC 読みで分解能が粗い
（STM32 は1制御周期ぶん＝32スキャン・約444µs 平均した角度を使う）。**加速度は `accel_x/y/z`（IMU）か `accel_kf` から取る。**
`wheel_speed` は 100Hz への間引きで 50Hz より上のノイズが折り返すので、**記録を後から解析する用途（システム同定）は
`odom_dist`（ローパス前の積算位置）を前後のサンプルでゼロ位相に微分する**（`tools/calib` はこうしている）。
シムは `speed` を `config/vehicle.toml` の `speed_kf_lag_s`、`wheel_speed` を `speed_filter_s` で遅らせる。

**前輪エンコーダ由来の制約**: 静止付近で前進/後退の符号がばたつく（`|speed| < 0.05 m/s` 程度をデッドバンドとして 0 とみなす）。
`odom_dist` も静止時にゆっくりドリフトしうる。

**IMU（MPU6050 + Mahony 相補フィルタ、地磁気なし）**: yaw の絶対方位は出せず積分ドリフトするので `yaw` は載せず `yaw_rate` だけ。
**絶対方位は Pi 側の SLAM で決める。** `pitch` / `roll` は重力で補正されドリフトしない。ジャイロバイアスは静止時に STM32 が追従補正し、
キャリブレーション値は Flash に持つ。

#### 5.3.1 車速の推定とその一貫性の診断

`speed` は**走行距離と加速度計のカルマンフィルタ**（ファーム `src/control/speed_kf.h`）の車速で、車速PI・TC/ABS のスリップの基準・
自動停止の前後判定がすべてこれを使う。調整値は `CONFIG_SET`（`0x00E1`-`0x00E6`、§5.8）。

- `accel_kf`・`accel_bias_kf` はフィルタの状態。`accel_bias_kf` は加速度計の取付ずれと重力の傾き成分の合計で、坂・傾きで動く
- `kf_gated` が走行中に増える＝前輪の距離が予測と大きく食い違った（ロック・スリップ・衝撃）。そのたびに測定ノイズを膨らませて効きを弱めている
- **一貫性の診断**: フィルタは測定ごとに z = 残差 ÷ 自分が主張する標準偏差 を作る。調整値が合っていれば z は平均 0・分散 1 の白色雑音になる。
  `kf_z_rms_*` は前回の TELEMETRY からの z の RMS（2乗が NIS。1 より大きい＝誤差が主張より大きい）、`kf_rho_*` は隣り合う z の相関係数
  （0 でない＝周期誤差などモデルが表せない誤差がある）。`*_dist` は走行距離（2kHz）、`*_accel` は加速度（200Hz）。z は ±10 で切ってあり、0 はその間に測定が無かったこと。
  NIS を直接送らないのは、静止で 1e-3 まで小さくなり量子化で潰れるため（RMS と ρ なら窓ごとの NIS・自己相関に戻せる）。
  検証は `python3 -m raspi.tools.kf_consistency <記録>.mcap`
- `front_angle` は前輪エンコーダの絶対角で、角度の関数である周期誤差（INL）の同定用（車速の計算には使わない）。
  **校正前の生の読み**（ADC の読み÷フルスケール×2π、取付向きの符号のまま）なので、校正（`ENC_*`）を入れた後の記録でも同定し直せる

### 5.4 `flags` (u32) ビット定義

| bit | 名称 | 意味 |
|---|---|---|
| 0-1 | `mode` | STM32 が**実際に採用している**モード（0=DISARM / 1=MANUAL / 2=AUTO / 3=予約） |
| 2 | `armed` | **上位の指令で走れる状態**（この間だけ車速・舵角の指令が効く）。ARM を要求しても、MD の起動待ち（約1秒）・ステア未較正・`mode` が MANUAL/AUTO 以外・E-Stop・`COMMAND` 途絶・ARM が外れたあとの停止待ちの間は 0 |
| 3 | `estop_active` | ハートビート断で発動中（§9） |
| 4 | `uart_timeout` | `COMMAND` 途絶で自動ブレーキ中 |
| 5 | `tc_active` | TC が今まさに介入中 |
| 6 | `tv_active` | TV が今まさに介入中 |
| 7 | `imu_ok` | IMU 正常 |
| 8 | `lidar_ok` | LD06 正常受信中（300ms 途絶で 0） |
| 9 | — | 予約（0） |
| 10 | `steer_center_valid` | ステア原点が Flash に保存されている（0 なら走行不可） |
| 11 | `fault_drive_overcurrent` | 駆動系過電流 → DRIVE_POWER 遮断。**ラッチ** |
| 12 | `fault_signal_overcurrent` | シグナル系過電流 → LiDAR/駆動電源を遮断。**ラッチ** |
| 13 | `fault_drive_undervoltage` | 駆動系の電圧低下。警告のみ・**自動クリア** |
| 14 | `fault_signal_undervoltage` | シグナル系の電圧低下。警告のみ・**自動クリア** |
| 15 | `drive_power_locked` | 過電流ラッチにより `arm` 要求を拒否中 |
| 16 | `auto_stop_active` | 自動停止が今まさに制動へ介入中（§5.6.4） |
| 17 | `side_brake_active` | 後輪が今まさに位置保持で固定中（サイドブレーキ・ブレーキホールド。§5.6.5） |
| 18 | `winker_left_active` | 左ウィンカーが今まさに点滅中（§5.6.6） |
| 19 | `winker_right_active` | 右ウィンカーが今まさに点滅中 |
| 20 | `abs_active` | ABS が今まさに制動トルクを要求より削っている（フォールバック中は偽） |
| 21 | `wheel_lift_active` | 片輪浮き対策が今まさにトルクを削っている（このとき `tc_active` は立たない＝どちらが効いたかを分ける） |
| 22 | `drive_power_on` | 駆動電源が入っている。`armed` なら必ず 1。ARM が外れたあと停車を待って制動している間も 1 |
| 23 | `md_fault` | MD（3台のいずれか）が使えず走行を止めている（起動で揃わない・走行中の無応答・異常ビット・トルク上限の不一致）。走行中なら両後輪を最大制動。**駆動電源が切れるまでラッチ**。どの MD かは `md_status`、理由は `LOG` |
| 24 | `launch_active` | ローンチコントロールで今まさに発進中（§5.6.7） |

| 26 | `auto_stop_blind` | ARM 中に LiDAR も前後の超音波も使えず、自動停止が何も検知できない状態が3秒続いている |

  有効/無効は Pi が送った `COMMAND`・`CONFIG_SET` で分かるので返さない
- **bit11/12 はリセットまで消えない。** bit13/14 は電圧が戻れば消える（8.0V 未満が 1秒続くと立ち、8.8V で戻る）
- **bit15 が立っている間、`arm` を要求しても bit2 は立たない。これは仕様で FAULT 扱いにしない。**
  GUI は「駆動電源ラッチ中 — 電源を入れ直してください」と出し、通信 FAULT と区別する
- ARM が外れたあとの停止待ちは、停車するか `最高速 5m/s ÷ BRAKE_DECEL_M_S2 × 1.5` 秒経つまで（`vehicle.c` の `DisarmBrakeTimeoutS`）

### 5.5 `md_status[i]` (u8) ビット定義

MD が返す status バイトをそのまま転送し、STM32 が上位ビットを付加する。

| bit | 名称 | 出所 |
|---|---|---|
| 0 | `running` | MD が受理済みの指令を実行中（停止モードでない）。「回転中」ではない |
| 1 | `voltage_out_of_range` | MD が電源電圧異常を検知 |
| 2 | `overheat` | MD が過熱を検知 |
| 3 | `overcurrent` | MD が過電流を検知 |
| 4 | `comm_ok` | **STM32 が付加**。直近 100ms で MD の状態フレームを受信できている |
| 5 | `limit_synced` | **STM32 が付加**。MD が適用中のトルク上限が指令値と一致 |
| 6 | `uncalibrated` | MD のエンコーダが未校正（MD は制限値を受け付けず動かない） |
| 7 | — | 予約 |

**`comm_ok = 0` のとき、そのモータの `temp` / `motor_current` / `wheel_speed` / `torque_cmd` を信用しない。**
MD が無言になると status は最後の値のまま固まるため。Pi は該当値を GUI でグレーアウトする。

### 5.6 `COMMAND` (0x10) — LEN = 15

| offset | size | type | field | 単位 |
|---|---|---|---|---|
| 0 | 1 | u8 | `mode` | 0=DISARM / 1=MANUAL / 2=AUTO（3 は予約・送らない） |
| 1 | 1 | u8 | `flags` | §5.6.1 |
| 2 | 2 | i16 | `target_speed` | 0.001 m/s（負 = 後退）。`brake`／`torque_mode` 中は無視 |
| 4 | 2 | i16 | `target_steer` | 0.0001 rad **路面舵角**（反時計回り正 = 左旋回） |
| 6 | 2 | u16 | `accel_limit` | 0.001 m/s²。目標車速を動かす傾き。`0` = 未指定（既定 3.0 m/s²） |
| 8 | 2 | u16 | `steer_rate_limit` | 0.001 rad/s。舵角のレートリミット。`0` = 未指定（既定 0.5 rad/s） |
| 10 | 2 | u16 | `brake_torque` | 0.0001 N·m **後輪各輪**。`0` = 未指定（最大で制動） |
| 12 | 2 | i16 | `target_torque` | 0.0001 N·m 駆動トルク直接指令（負 = 後退方向）。`torque_mode` 時のみ有効 |
| 14 | 1 | u8 | `flags2` | §5.6.5 |

フレーム 22 バイト、100Hz で 2.20 kB/s。時刻同期は `PING`/`PONG` に分けてあるので Pi 側タイムスタンプは含めない。

#### 5.6.1 `flags` (u8) ビット定義

| bit | 名称 | 意味 |
|---|---|---|
| 0 | `arm` | 走行（駆動電源投入）を要求 |
| 1 | `brake` | ブレーキ（強さは `brake_torque`）。`torque_mode` より優先 |
| 2 | `horn` | クラクション。立てている間ずっと鳴る |
| 3-4 | `light_mode` | 0=`OFF` / 1=`DAYTIME` / 2=`NORMAL`（3 は予約） |
| 5 | `passing` | パッシング |
| 6 | `torque_mode` | 立っている間 `target_speed` を無視し `target_torque` を直接掛ける（§5.6.3） |
| 7 | `auto_stop` | 立っている間、進行方向の動的停止距離未満で STM32 が自動で最大制動（§5.6.4） |

| `light_mode` | 前照灯 | 尾灯 |
|---|---|---|
| 0 `OFF` | 消灯 | 消灯 |
| 1 `DAYTIME` | 減光（duty 0.1） | 薄点灯（duty 0.1） |
| 2 `NORMAL` | 全光量 | 薄点灯（duty 0.1） |

- ブレーキランプは `light_mode` と独立。制動中（`brake`・自動停止・フェイルセーフ）は全光量。加えて、制動していなくても
  実際の減速度が 1.5m/s² を超えたら点け、0.5m/s² を下回ったら消す（最短 0.3s。`VEHICLE_BRAKE_LIGHT_*`）。
  高速点滅（緊急制動表示）は、制動中に 1m/s 以上から強く減速したときだけ（`VEHICLE_ESS_*`）
- `passing` は立てている間 `light_mode` に関わらず**前照灯だけ**全光量。尾灯は連動しない（消灯中のパッシングが制動と紛らわしいため）
- E-Stop 発動時と `COMMAND` 途絶時は、`horn`・`passing`・ウィンカー要求を STM32 が強制解除する

#### 5.6.2 `brake_torque` の約束

- **`0` は「制動トルク 0」ではなく「未指定」**で、STM32 の最大値で制動する。`accel_limit` / `steer_rate_limit` と同じ約束で、
  **埋め忘れでブレーキが効かなくなる方が危険**なのでゼロ値を安全側に倒してある。Pi は正の指定が丸めで 0 に落ちないよう最小 1 LSB に留める（`msgs/convert.py`）
- 上限は **0.15 N·m/輪**（`DRIVE_MAX_BRAKE_TORQUE_NM` = `DRIVE_MAX_TORQUE_NM`、`LIMITS.max_torque_nm` で届く）。超えた値は黙ってクランプされるので、
  Pi 側でも同じ上限でクランプする（`msgs.convert.MAX_BRAKE_TORQUE_NM`。`LIMITS` 受信後はその値）
- **`brake` の間、車速 PI は迂回される。** MD を制動モードにして指定トルクを直接掛ける。離すと目標車速 0 から `accel_limit` で加速し直すので、
  ブレーキ中に `target_speed` を保持していても離した瞬間に飛び出さない

#### 5.6.3 `torque_mode` / `target_torque` の約束

- 速度指令ではなく駆動トルクを直接指令する（主に MANUAL）。スケールは `brake_torque` と同じ 0.0001 N·m/LSB
- **`target_torque` の `0` に特別な意味はない**（そのまま「駆動トルク 0」。丸めで 0 に落ちても危険側に振れない）
- 上限は 0.15 N·m（`DRIVE_MAX_TORQUE_NM`）。STM32 がクランプし、Pi 側も同じ上限を持つ（`msgs.convert.MAX_TARGET_TORQUE_NM`。`LIMITS` 受信後はその値）
- `torque_mode` の間は車速 PI を迂回して `target_torque` を各輪へ直接掛ける。**`brake` と同時なら `brake` が優先**
- `torque_mode` 中も TC・片輪浮き対策は各輪の上限として効き、TV の左右差も載る。ABS は掛からない（車速PIの減速と制動モードだけ）

#### 5.6.4 `auto_stop` の約束

**判定と制動は STM32 だけが持つ。** Pi は許可（bit7）を毎周期出すだけで、判定にも制動にも関与しない。
**Pi 側で `us_front`/`us_rear`/LiDAR/ステレオを見て速度を落とす二重制御を書かないこと**（どちらが止めたのか分からなくなる）。
ステレオ（§5.6.5）も同じで、Pi は障害物の**点を渡す**だけ。最終防壁が Pi・UART の生死に依存しないよう、判定を Pi に移さない。

- 立っている間、**進行方向**の障害物までの距離が動的停止距離 `d_stop` 未満になると、STM32 が `target_speed`/`target_torque` を無視して**最大制動トルクで停止**する
- `d_stop = v・t_delay + v²/(2・a_max) + margin`。`v` は進行方向の実車速の絶対値、`t_delay` = LiDAR の1回転 0.1s ＋判定の間引き 5ms ＋
  MD のトルクの遅れ（`MD_TORQUE_LAG_S`）、`a_max` = 制動の減速度（`BRAKE_DECEL_M_S2`）、`margin` は `0x0060`（§5.8.3）。
  `MD_TORQUE_LAG_S`・`BRAKE_DECEL_M_S2` も Pi が送る（§5.8）
- **判定は3つの条件の OR**:
  1. **LiDAR（主）**: **今の実舵角のまま止まるまでに車体が掃く範囲**（予想進路。曲率 `tan(実舵角)/ホイールベース` の円弧に沿って車体の先端が `d_stop` 進むまで、
     左右 ±15cm＝半車幅 9cm ＋余裕 6cm）に、直近300ms以内の点が **3点以上**あれば障害物あり（1点の反射ノイズを弾く）。
     扇形にしないのは、遠方ほど幅が広がりコースの壁で誤って止まるため。横滑りで外へ膨らむ分は余裕 6cm の内側でしか拾えない。
     車体の外形（`vehicle.toml` の `footprint`）の内側の点は数えない。判定は 5ms ごと。式はファームの `src/control/auto_stop_path.h`（確かめは `tools/fwsim/tests/test_auto_stop_path.py`）
  2. **超音波（フォールバック）**: LiDAR の進行方向 ±89° に直近300ms以内のデータが1点も無いときだけ、超音波の距離を `d_stop` と比べる
  3. **超音波（近接フェイルセーフ）**: LiDAR によらず、超音波が **5cm未満**を検知したら常に作動（LiDAR の最短測距・取付高さの死角を補う）
  4. **ステレオ（前進のみ、§5.6.5）**: 条件1と同じ予想進路に、`STEREO_OBS` の点が**直近2フレームの両方で5点以上**あれば作動（自車付近は除く）
- **進行方向**は実車速（カルマンフィルタの `speed`）の符号で決める。`>= 0` なら前方、負なら後方**だけ**を見る（前方に障害物があっても後退で抜けられる）。
  `|speed| < 0.05 m/s` のときは指令の向き（`torque_mode` なら `target_torque`、それ以外は `target_speed` の符号）を使う
- 超音波が無反射（検知範囲外）ならその条件は作動しない。`0 = 無効` を「距離 0」と読まないのと同じく、「見えていない」を「近い」に倒さない
- `brake` と同時なら `brake` が優先（制動トルクは `brake_torque`）。`auto_stop` 単独の作動は常に最大制動トルク。
  優先順位は **`side_brake` > `brake` > `auto_stop` > 通常指令**
- **作動したら止まるまで解除しない**（減速で `d_stop` が縮んで範囲外になり再加速するのを避ける）。`|speed|` が 0.05 m/s 以下になってからは毎周期判定し直すので、
  障害物が無くなれば（または逆方向を指令すれば）動ける。ARM していないときは働かない。
  壁に詰める作業では GUI の設定パネルで `auto_stop` を切るか `margin` を下げる
- **DISARM はしない。** 停止手段ではなく衝突緩和で、E-Stop・DISARM・`COMMAND` 途絶とは別系統

#### 5.6.5 ステレオの障害物（`STEREO_OBS` 0x16）

前方ステレオ（`stereo_node` の `scan/stereo`）の障害物を、`auto_stop` の入力に**足す**。実装は STM32 の `src/control/stereo_obstacle.[ch]`
（確かめは `tools/fwsim/tests/test_stereo_obstacle.py`）、Pi 側は `raspi/core/stereo_obs.py`（`io_node._forward_stereo`）。

- **ペイロード**: `age_ms`（撮影から送出直前まで、255 で飽和）・`count`（最大 40）・`xy`（base_link の x, y を i16 mm で 40 点分。残りは 0）。10Hz
- **Pi が送るもの**: 1° の方位ごとの距離（床より上の障害物）を 2° の箱ごとの最近点にし、多ければ近い順に 40 点。**停止の判断・距離のしきい値は持たない**
- **「見つからない」は送らない**: 照合の失敗・左右が揃わない周期・`Scan` が 250ms より古いときは送らない。**点が 0 個でも照合できた周期は送る**（STM32 が「ステレオは生きている」と分かる）
- **STM32 の扱い**
  - 最新フレームが 300ms より古ければ**無視する**。LiDAR・超音波だけの判定に戻るだけで、ステレオが落ちても新たな故障モードは無い（足すだけの入力）
  - 前進のみ。ステレオは前方にしか付いていないので、後退では見ない
  - **直近2フレームの両方**で予想進路内に**5点以上**あるときだけ当たり。床の取り違えなど単発の誤検知を弾く
  - **自車除外**: 車体の外形を前へ0.05m・横へ0.04m広げた範囲の点は数えない。ステレオは車体の外に出ている前輪・ナックルを障害物として拾う
    （x≈0.31m, y≈−0.10m。2本の実走行ログで確認）。除外の手前は LiDAR・超音波の近接（5cm）が受け持つ
  - **古さの補正**: 点は撮影から Pi の処理・通信・受信後の経過だけ古く、その間に車は進んだ。予想進路の長さを `d_stop + v × (点の古さ + 通信 10ms + 確認の1フレーム 0.1s)` にする。点ごとに自分の古さで見る
  - 判定は 5ms ごと（LiDAR と同じ間引き）
- **フラグ**: TELEMETRY の `stereo_ok`（bit27）、介入のきっかけにステレオが含まれるとき `auto_stop_stereo`（bit28）
- **Pi 側の条件**: ARM 中は自動運転モードに関わらず `stereo_node` が照合を回す（`telemetry_node.STEREO_AUTO_STOP`。+約 150mA・CPU）。
  DISARM 中は回さないので `STEREO_OBS` も出ず、`stereo_ok` は立たない
- **しきい値の根拠（実走行ログの再生、`python -m tools.fwsim.stereo_replay LOG.mcap...`）**: 衝突4回のコース走行 43 秒と衝突なしの周回 120 秒（最高 4m/s）。
  - 3点・除外なしだと、周回中に LiDAR と無関係なステレオ単独の検出が 32 区間（平均 0.08 秒）。作動したら止まるまで解除しないので、短くても完全停止になる
  - 5点・除外ありで 8 区間に減る。代わりに衝突前の検出は縮む（1回目 1.32→0.29s、3回目 1.18→0.59s）。ただし縮んだ分は車体先端付近の自車の点由来で、
    3回目は LiDAR（0.30s前）より早い。確認を3フレームにするとリードがさらに縮むので2のまま。点数を8にすると単独は3区間だが、衝突前の検出がほぼ消える
  - **ピッチは原因ではない**: 機首上げ（`pitch` 正）ではカメラが実質上を向き、床は沈む。LiDAR の水平面が上に傾いて低い物を見逃す方が先。
    LiDAR に裏付けのない遠方の検出は半分が数フレーム持続（実物の低い物）、残りは単発。ピッチ補正は入れない
  - 「作動したら止まるまで解除しない」ので、周回走行（壁際を通る）では LiDAR だけでも 120 秒に 76 回作動する。**コース走行中は `auto_stop` を切る運用**が前提
- **未確認**: 実機で止めたときの停止距離・誤検知。しきい値は `vehicle.h` の `VEHICLE_AUTO_STOP_STEREO_*`

#### 5.6.5 `flags2` (u8) ビット定義・`side_brake` の約束

| bit | 名称 | 意味 |
|---|---|---|
| 0 | `side_brake` | 立てている間、**速度に関わらず即座に**後輪を位置制御へ切り替えて固定（パーキングロック） |
| 1 | `winker_left` | 左ウィンカー（§5.6.6） |
| 2 | `winker_right` | 右ウィンカー（§5.6.6） |
| 3 | `launch` | ローンチコントロール（§5.6.7） |
| 4-5 | `winker_mode` | 点滅パターン（0=旧クライアント互換の滑らか、1=通常、2=滑らか、3=豆電球風。§5.6.6） |
| 6-7 | — | 予約（0） |

- **`side_brake` は `brake` より優先。** `brake` は制動トルクを掛けるだけで惰性で多少動くが、`side_brake` は後輪の目標を機械角に切り替えてその場に固定する
- **停止を待たずに切り替わる**ので、走行中に誤って立てると急激な挙動になる。Pi の指令生成で走行中に立てないこと
- 連続コマンド（立てている間だけ効く）
- MD のフレームが無効（給電直後など）で角度を保持できない間は最大制動にフォールバックする。**実際に固定できたかは `flags` bit17** で確かめる
- ARM が外れたあとの停止待ち・`md_fault` の強制制動の間は `side_brake` 要求を無視して最大制動で止める（止まってから位置保持へ移る）
- ブレーキホールド（`0x0090`）が有効なら、制動して止まったときも自動で位置保持へ移る（bit17 が立つ）

#### 5.6.6 `winker_left` / `winker_right` の約束

灯火系（`light_mode`/`horn`/`passing` と同じ）で後輪の励磁とは無関係なので、**未 ARM でも効く**（Pi の `command_from_cmd` は灯火系を `arm` と独立に組む）。

- **独立ビットで、両方立てるとハザード。** 専用のハザードビットは無い
- **点滅の周期・位相は STM32 が持つ。** Pi は点灯を要求しているかを毎周期送るだけ。曲がり終わったら Pi が明示的に OFF にする（転舵完了での自動消灯は無い）
- 実際に点滅しているかは `flags` bit18/19
- GUI の点滅モードはこの `flags2` bit4-5 に同梱され、AUTO中も選択を維持する。周期設定が届かない旧クライアント（0）は滑らかモードとして扱う。
- **モード1（通常）**は500ms点灯/500ms消灯、**モード2（滑らか）**は素早い立ち上がり・保持・ゆっくり消灯、**モード3（豆電球風）**はフィラメントを模した遅い立ち上がりと消灯。ハザードにも同じパターンを適用する。
- **電源系の異常（`flags` bit11〜14 のいずれか）か E-Stop の間は、要求に関わらず STM32 が強制的にハザードにする**（`indicator.c`）。
  Pi が OFF を送っていても bit18/19 が両方 1 なのはバグではない

#### 5.6.7 `launch`（`flags2` bit3）の約束

車速指令の加速は、STM32 が目標車速を `accel_limit` の傾きでランプさせて車速PIが追うので、グリップの限界のトルクに届くまで約0.3秒かかる。
`launch` が立っている間、目標が車速より大きく離れた加速では、STM32 がランプと PI を迂回して**全開のトルクを要求し、TC にグリップの限界へ絞らせる**
（= `torque_mode` の全開と同じ加速）。条件・定数の正はファームの `src/control/drive.h`「ローンチコントロール」。

- **始める**: `launch` が立っている・`target_speed` が車速より 0.5m/s 以上速い（後退も同じ）・目標と逆向きに 0.3m/s 以上で動いていない・TC が有効（`0x0010`）。
  車速は問わない（低速で経路に乗ってから要求することがある）
- **終える**: 車速が `target_speed` の 0.05m/s 手前に届いた／`launch` が下りた／`target_speed` が小さく・逆向きになった／`brake`・`torque_mode`・`side_brake`・フェイルセーフ／3秒経った。
  終えたら車速PIへ戻り、積分は `LAUNCH_EXIT_TORQUE_NM`（§5.8.4）から始める
- **1回の要求で1回だけ。** `launch` を下ろす・制動する・止まって惰行する、のどれかでまた使える（届かず時間切れのあと、止まったまま全開を繰り返さない）
- **`target_speed` は「そこまで全開で加速してよい速度」**。いつ立てるかは Pi 側が決める（手動は GUI の手順 `gui/src/input/useDriving.ts`、
  自律は planner の `launch` パラメータ・既定 0）。TC が保つスリップ率では横グリップが4割ほどしか残らないので、舵を切った加速には向かない
- 実際に発進中かは `flags` bit24

#### 設計意図

- **`target_speed` は目標速度で、目標加速度ではない。** `accel_limit` はその目標へ向かうときの傾きの上限。速度制御（PI）は STM32 に閉じる
- **`target_steer` は路面舵角**（STM32 がリンクの換算でモータ角へ直す）
- **`steer_rate_limit`** は舵の急変を防ぎ、停車中の据え切りで MD ステアが過熱するのも抑える（`temp[2]` の監視と併せる）
- **`mode` は Pi の要求で、STM32 は拒否できる。** 実際のモードは `flags` bit0-1。`mode = 3` は STM32 が無視して現在のモードを維持する。
  `drive_power_locked` による `arm` 拒否は正常動作（§5.4）
- **`COMMAND` が 100ms 途絶したら STM32 は自動ブレーキ**（100Hz に対して 10発分。200ms だと 3 m/s で 60cm 進んでしまう）。
  E-Stop・途絶とも最大制動トルク（`DRIVE_MAX_BRAKE_TORQUE_NM`）を直接掛ける（速度 PI 任せにしない＝停止距離が短い）。
  舵角は最後の指令値のまま（直進に戻すと予期しない方向へ動く）

### 5.7 `PING` (0x12) — LEN = 4 / `PONG` (0x06) — LEN = 12

時刻同期専用の往復（§6）。**STM32 は `PING` を受けたら最優先で即座に `PONG` を返す**（送信キューの先頭に割り込ませる）。

- `PING`: `ping_id`（u32、Pi が採番する連番）
- `PONG`: `ping_id`（エコー）・`t_ping_rx_us`（T2）・`t_pong_tx_us`（T3）、各 u32

**タイムスタンプの取得タイミングが精度に直結する。**

- `t_ping_rx_us` は **UART IDLE 割り込みで PING 最終バイト到着の瞬間**に取る。メインループで取るとループ周期分のジッタがオフセットのバイアスになる
- `t_pong_tx_us` は **1バイト目が線に出る瞬間**。送信キュー投入時に取ると、送信中のフレーム（LiDAR セクタ1個で 0.76ms）の待ちが T3 以降の非対称遅延になり、
  4タイムスタンプ方式でも除去されずオフセットにその半分のバイアスが乗る。STM32 は DMA 起動の直前に `t_pong_tx_us` を書いて CRC を計算し直す（`ras_link.c` の `PumpTx`）

### 5.8 `CONFIG_SET` (0x11) / `CONFIG_GET` (0x13) / `CONFIG_ACK` (0x03)

```
CONFIG_SET : [param_id : u16][value   : f32]                 = 6 B   (Pi → STM32)
CONFIG_GET : [param_id : u16]                                = 2 B   (Pi → STM32)
CONFIG_ACK : [param_id : u16][applied : f32][result : u8]    = 7 B   (STM32 → Pi)
```

`CONFIG_SET` / `CONFIG_GET` のどちらにも必ず `CONFIG_ACK` が返る。`CONFIG_GET` は現在値を `applied` に入れて返す（GUI 起動時に実機の値を同期するため）。

| `result` | 意味 |
|---|---|
| 0 | OK |
| 1 | 不明な `param_id` |
| 2 | 範囲外（`applied` に丸めた後の値。非数は仮置きの値になる） |
| 3 | 現在のモードでは変更不可 |

#### 設定は Flash に永続化しない（揮発）

**`CONFIG_SET` の値は RAM 上のみ。** STM32 は上位が送るまでの仮置き（調整パラメータは各範囲の下限＝何もしない値、ステアのリンクは恒等の 1・0、TC/TV は無効）で起動し、
Pi が接続のたびに `config/vehicle.toml` の値を送る。設定値の唯一の定義を git 管理下のファイルに置き、「誰も知らない古い設定が STM32 にだけ残る」のを防ぐため。
**STM32 が Flash に持つのはステア原点と IMU キャリブレーションだけ**（STM32 でしか測れない値）。`CONFIG_SAVE` は無い。

Pi 側の実装（`raspi/nodes/io_node.py`）:

- 調整パラメータと `[control]` に書いた ON/OFF（`tc_enable`・`tv_enable`・`wheel_lift_guard_enable`・`abs_enable`）は `ControlParamSync` が送って確かめる（§5.8.4）
- ON/OFF（`0x0010`/`0x0020`/`0x0050`/`0x0070`/`0x0090`）と自動停止のマージン（`0x0060`）は、接続時と STM32 の再起動の検出時に `CONFIG_GET` で読み直し、
  以降は GUI の操作に応じて `CONFIG_SET` を送る

| `0x00E1`-`0x00E6` | 車速のカルマンフィルタの調整値 | f32 | `KF_SIGMA_S_M`/`KF_SIGMA_A_M_S2`/`KF_SIGMA_A_PER_M_S`/`KF_JERK_PSD`/`KF_BIAS_WALK_PSD`/`KF_LEVER_ARM_M` |
| `0x00F1` | ジャイロ z 軸の感度の補正 | f32 | `IMU_GYRO_Z_SCALE`（倍率）。バイアスを引いた後の z の角速度に掛ける（`yaw_rate`・TC/TV・姿勢推定のすべてに効く） |
| `0x0101`・`0x0102` | 制動の減速度・MD のトルクの遅れ | f32 | `BRAKE_DECEL_M_S2` [m/s²]・`MD_TORQUE_LAG_S` [s]。自動停止の停止距離（§5.6.4）と、ARM が外れたあとの制動の上限（§5.4）に使う。`[control]` には書かず、`[limits] abs_brake_decel_m_s2` と `[control.plant] md_delay_s + md_tau_s` から io_node が作る（`raspi/core/control_params.py` の `DERIVED`） |

`0x0001`-`0x0003`（最大速度・加速度・舵角）・`0x0021`-`0x0029`・`0x0041` は欠番で、STM32 は `result=1` を返す。
上限は `LIMITS`（§5.12）で知る。加速度の上限は Pi の `[safety] cmd_accel_limit_m_s2`。

#### 5.8.1 LiDAR 出力フォーマット（`param_id = 0x0040`）

| 値 | 送信される TYPE | 帯域 |
|---|---|---|
| **0（既定）** | `0x01` `LIDAR_SECTOR` | 9.12 kB/s |
| 1 | `0x05` `LIDAR_SECTOR_I` | 12.7 kB/s |
| 2 | `0x09` `LIDAR_SECTOR_C` | 5.52 kB/s |

bool 2本（強度・圧縮）にしないのは、未実装の「圧縮かつ強度付き」が表現できてしまうため。範囲外は 0〜2 に丸めて `result=2`。**走行中でも切り替え可能。**

#### 5.8.2 片輪浮き対策（Wheel Lift Guard、`param_id = 0x0050`）

後輪が段差などで片側だけ浮くと、その車輪のモータが無負荷で回転数を張り上げる。その対策で、**TC 本体（`0x0010`）とは独立**に ON/OFF できる。

- 後輪左右の速度差がしきい値（`0x0051`）を超えると、速い方（浮いている方）だけトルク上限を絞る
- 後輪の周速が物理的にあり得ない値（`DRIVE_MAX_SPEED_M_S` の1.5倍）を超えたら、左右差によらずその車輪のトルク上限を即 0 にする
- 無効にするとこの機構の絞り込みは一切行わない（TC が有効ならスリップによる絞り込みは効く）。誤介入を疑うときはまず OFF にして切り分ける

#### 5.8.3 自動停止の安全マージン（`param_id = 0x0060`, `auto_stop_margin_cm`）

`auto_stop`（§5.6.4）の `d_stop` のうち **`margin` だけ**を cm 単位の f32 で直接指定する。範囲 0.0〜100.0、**既定 15.0**。
範囲外はクランプして適用し `result=2`。走行中でも変更可。停車中（`v = 0`）は `margin` だけが効き、速度が上がるほど物理項で `d_stop` が伸びる。

#### 5.8.4 足回りの制御の調整パラメータ

TC・ABS・片輪浮き対策・TV・車速PI のゲインやしきい値、ステアのリンク・前輪エンコーダ・車速 KF・ジャイロの補正・制動の見積もりを実行時に読み書きする。
ON/OFF（`0x0010`/`0x0020`/`0x0050`/`0x0070`）とは別。

- **値の唯一の定義は Pi 側 `config/vehicle.toml`**（`[control]`。`speed_kp`・`speed_ki` は `[dynamics]`、`0x0101`/`0x0102` は上表のとおり他節から作る）。
  **全項目が揃っていなければ io_node は読み込みをエラーにして ARM を通さない**（STM32 に値が無いため）
- **Pi 側の手順**（`raspi/core/control_params.py` の `ControlParamSync`）:
  1. 接続したら全項目を `CONFIG_SET` で送り、`applied` が送った値と一致するまで 0.3s ごとに再送（回数の上限は無く、揃うまで ARM を通さない）。
     範囲外で丸められた項目は再送しても同じなので止めて `mismatch` とする
  2. 一致した後も 0.5s ごとに1項目ずつ `CONFIG_GET` で読み戻す。食い違えば STM32 だけが再起動したと見て全項目を送り直す
     （`diag/link` の `control_params_drift` が増え、入り直すまで ARM を通さない）
  3. STM32 の再起動（`t_us` の後退）を検出したら最初からやり直す
  4. 結果は `diag/link` の `control_params_status`（`ok`/`pending`/`mismatch`/`unsupported`/`invalid`/`none`）と `control_params`（STM32 が答えた値）。GUI の「設定 → 走行アシスト」に出る
- **一時的な上書き**: 校正の試験（`raspi/auto/calib_*.py`）は `AutoState.fw_overrides` → `DriveCmd.fw_overrides` に名前と値を書く（調整パラメータと ON/OFF 4種）。
  io_node は**その指令が届いている間だけ**入れ、届かなくなったら元へ戻す（試験が中断しても TC を切ったままにならない）
- `TV_TEST_MOMENT_NM` は同定用: 0 以外の間 STM32 は TV の配分を止めてこのヨーモーメントだけを出す。`[control]` には書かない（上書きでだけ使う）
- **TV は荷重比例の配分**: `左右差 (右−左) = 総駆動トルク × clamp(TV_LOAD_GAIN_S2_PER_M × 車速 × ヨーレート, ±TV_MAX_RATIO)`。
  旋回で荷重の乗る外輪へ多く配り、内輪を空転させない。減速（総トルクが負）では外輪が多く制動する。定速の旋回では何もしない。積分を持たず、TC はその後段で各輪を絞る
- **ステアのリンクの換算（`0x0081`/`0x0082`）** は同定の結果: `路面舵角 = gain·x + cubic·x³`、x = ステアモータの角度×0.5（可動範囲 ±30°）。
  STM32 は指令・報告・`LIMITS.max_steer_rad`・車速の射影のすべてに使う。端での傾き `gain + 3·cubic·x²` が 0.3 を下回る `cubic` は丸めて `result=2`
  （逆変換が一意でなくなるため）。**受けた値は保持するだけで、停車して DISARM のときに適用し**、`LIMITS` を送り直す（走行中に舵角の意味が変わらないように）。
  値は校正 2（`calib_steer`）が `[control]`・`[dynamics]`・`max_steer` をそろえて書く。記録（mcap）の舵角の意味はそのとき STM32 に入っていた換算で決まる
  （`/diag/link` の `control_params` に残る。解析は `analyze.fold_steer_link`）
- **`LAUNCH_EXIT_TORQUE_NM`（`0x00A1`）**: 発進（§5.6.7）を終えて車速PIへ戻すときの積分の初期値。0 だと積分が溜まるまで車速が落ち込むので、
  その車速を保つトルク（`rolling_resistance ÷ speed_plant_gain ÷ 2`）を書く
- **車速PIのフィードフォワード（`0x00B1`・`0x00B2`）**: PI だけだと車速が目標に約 0.15 秒遅れる。STM32 は目標車速の傾き（20ms のローパス後）× `0x00B1` と、
  目標車速の向きへ `0x00B2` を PI の出力に足す（制動・トルク指令・ローンチ・停車の惰行の間は足さない）。値は `1 ÷ speed_plant_gain`・`rolling_resistance ÷ speed_plant_gain`
- 値を決める手順は車両の校正（[`calibration.md`](calibration.md)）

**設定を周期 `COMMAND` に混ぜない理由**: 混ぜるとパケットロスで設定値が化けても誰も気づかない。個別 ID + ack + `applied` に実際の値を返すことで、
GUI が常に実機の真の値を表示できる。

### 5.9 `VERSION` (0x07) — LEN = 10 / `VERSION_REQ` (0x14) — LEN = 0

ファームと Pi 側コードの食い違いに気づかないまま「原因不明のバグ」を追わないよう、リンク確立時に必ず交換する。

| offset | size | type | field | 備考 |
|---|---|---|---|---|
| 0 | 2 | u16 | `protocol_version` | 上位バイト = メジャー、下位 = マイナー（`protocol.toml` の `[meta]`） |
| 2 | 4 | u32 | `fw_id` | ファーム識別子の定数（`RAS_FIRMWARE_ID`）。git ハッシュではない |
| 6 | 4 | u32 | `build_epoch` | ビルド時刻（UNIX epoch 秒。ビルドの git コミットは起動時の `LOG` に出る） |

- 要求と応答で TYPE を分けている（同じ TYPE で LEN を変えず、方向規約を守るため）
- STM32 は起動直後に 3回（100ms 間隔）自発送信する。補助なので、**Pi はリンク確立時に必ず `VERSION_REQ` を送る**
- Pi は `protocol_version` が**完全に一致しない限り ARM を通さない**（メジャー・マイナーを区別しない。DISARM を送り続け、通信・表示は続ける。
  理由は `diag/link` の `arm_inhibit_reason`）。未受信の間も同じ
- `fw_id` / `build_epoch` はログとテレメトリ記録に残す

### 5.10 `STATS` (0x08) — LEN = 48

1Hz。**上下どちらの線が悪いのかを切り分ける**ための STM32 側の統計（Pi 側のカウンタだけでは STM32 → Pi の品質しか分からない）。

| offset | size | type | field | 備考 |
|---|---|---|---|---|
| 0 | 4 | u32 | `t_us` | このスナップショットの時刻 |
| 4 | 4 | u32 | `rx_frame_ok` | 正常受理したフレーム数 |
| 8 | 4 | u32 | `rx_crc_error` | CRC 不一致で破棄した数 |
| 12 | 4 | u32 | `rx_len_error` | LEN が TYPE の期待値と不一致 |
| 16 | 4 | u32 | `rx_unknown_type` | 未知の TYPE |
| 20 | 4 | u32 | `tx_drop` | 送信キュー溢れで破棄した数（主に `LOG`） |
| 24 | 12 | u32×3 | `md_rx_count[3]` | MD 状態フレームの正常受信数 [RL, RR, ST] |
| 36 | 12 | u32×3 | `md_rx_error[3]` | MD 状態フレームの CRC 不一致数 [RL, RR, ST] |

**すべて起動からの累積値**（増分にすると `STATS` が1個落ちたときその1秒分が失われる。§2.2-6）。u32 なので 1000件/s でも 49日かかり実質ラップしない。
レートは連続する2つの差を `t_us` の差（`(b - a) & 0xFFFFFFFF`）で割って出す。途中で `STATS` が落ちても平均レートは正しい。

Pi 側の `crc_error` / `packet_loss`（下り）と並べて GUI に出す（`DiagGrid`）。

| 症状 | 推定原因 |
|---|---|
| Pi 側のみエラー増 | STM32 → Pi の配線 / Pi の受信バッファ溢れ |
| STM32 側（`rx_*`）のみ増 | Pi → STM32 の配線 / Pi 側の送信処理 |
| 両方向で同時に増 | 電源ノイズ、GND ループ、モータノイズの回り込み |
| `md_rx_error` のみ増 | MD 側の配線。UART リンクは無関係 |
| `tx_drop` が増 | 上りの帯域不足。`param 0x0040 = 2` を検討 |

### 5.11 `LOG` (0x04) — LEN = 1〜128

`severity`（u8: 0=DEBUG / 1=INFO / 2=WARN / 3=ERROR）＋ `message`（ASCII、改行なし、NUL 終端なし。空もありうる）。

STM32 は本文を 127 文字で打ち切る（プロトコル上は 254 文字まで載る）。Pi は LEN = 0（`severity` すら無い）を `len_error` として捨てる。
**最低優先度**で、帯域が逼迫したら破棄してよい（`STATS.tx_drop` に計上）。Pi は既定で WARN 以上を GUI に出す。

### 5.12 `LIMITS` (0x0A) — LEN = 16 / `LIMITS_REQ` (0x15) — LEN = 0

**車両の物理的な上限を STM32 側の権威として Pi に伝える、読み取り専用パケット。** 上限はファームの固定定数（舵角はリンクの換算で変わる）で、
`config/vehicle.toml` の想定と食い違っても気づけるように Pi が実際の値を受け取る。すべて生の f32。

| offset | size | type | field | 備考 |
|---|---|---|---|---|
| 0 | 4 | f32 | `max_speed_m_s` | `target_speed` の上限（`DRIVE_MAX_SPEED_M_S`）。超えると STM32 がクランプ |
| 4 | 4 | f32 | `max_accel_m_s2` | `accel_limit` の上限。STM32 は上限を掛けないので、ワイヤ（u16×0.001）で表せる最大 65.535 を返す |
| 8 | 4 | f32 | `max_torque_nm` | 1輪あたりのトルク上限。`target_torque`/`brake_torque` 共通（`DRIVE_MAX_TORQUE_NM`） |
| 12 | 4 | f32 | `max_steer_rad` | 路面舵角の上限（片側の振れ幅。`Steering_GetMaxRoadWheelAngleRad()`） |

- STM32 は `VERSION` と同じく起動直後に 3回自発送信する。Pi はリンク確立時に `VERSION_REQ` と併せて `LIMITS_REQ` を送る（`io_node.py` の `handshake()`）
- ステアのリンクの換算が適用されると `max_steer_rad` が変わり、STM32 は `LIMITS` を送り直す。それ以外は実行時に変わらない
- Pi は MANUAL・AUTO どちらの指令も `LIMITS` の値で速度・舵角・加速度・トルクをクランプする（`IoNode._command_packet` の1箇所を必ず通る）。
  **`LIMITS` を受信するまで ARM を通さない。** `--max-speed`/`--max-steer` は ARM していない間の表示用の既定。GUI の `effectiveRange()`（`gui/src/store/ui.ts`）も受信済みの値を優先する
- `sim/stm32.py` も `LIMITS`/`LIMITS_REQ` に対応している

## 6. 時刻同期（STM32 ⇄ Pi）

SLAM・アクチュエータ遅延の実測・センサ融合のすべてがこれに依存する。**NTP と同じ 4タイムスタンプ方式**を `PING` / `PONG` で行う。実装は `raspi/core/timesync.py`。

### 6.1 測定する2種類の「遅延」を混同しない

| 測りたいもの | 使う仕組み | 時刻同期が必要か |
|---|---|---|
| **エンドツーエンド遅延**（GUI 表示用） | `TELEMETRY.cmd_seq_echo` | **不要**。Pi の時計だけで完結する往復測定。50ms 超で警告 |
| **クロックオフセット**（SLAM・センサ融合用） | `PING` / `PONG` | 必要（本節） |

### 6.2 4タイムスタンプ方式

```
    T1 ── Pi   : PING を送信した時刻              （Pi の時計）
    T2 ── STM32: PING 最終バイトを受信した時刻     （t_ping_rx_us）
    T3 ── STM32: PONG 1バイト目が線に出た時刻      （t_pong_tx_us）
    T4 ── Pi   : PONG を受信した時刻              （Pi の時計）

    往復遅延   delay  = (T4 − T1) − (T3 − T2)
    オフセット offset = ((T2 − T1) + (T3 − T4)) / 2      ※ offset = t_stm − t_pi
```

Pi の実装はオフセットを逆向き（`offset_ns` = t_pi − t_stm）で持ち、STM32 の中点 (T2+T3)/2 と Pi の中点 (T1+T4)/2 を対応点として回帰する。
**`T3 − T2` を引くことで STM32 側の処理・送信待ちが推定から除かれる**が、それは T2/T3 が §5.7 のとおり正確に取れている場合だけ。

### 6.3 実装上の要点

1. **`delay` が小さいサンプルだけを使う。** 直近 256 サンプルのうち `delay` ≤ 最小値×2 + 0.3ms のものを「良い」サンプルとする
2. **線形回帰でクロックドリフトも推定する。** 実機の STM32 の時計は Pi より約 0.35% 速い（故障ではない）ので、傾きを推定しないと1秒で 3.5ms ずれる
   - 良いサンプルの時間スパンが 15 秒に届くまでは回帰せず、良いサンプルのうち最新のもののオフセットを使う（それが 1秒以上古ければ直近 8 個の中で `delay` 最小のもの）
   - 今の窓で回帰できなくなっても**最後に成立した回帰で外挿する**（時計の比は変わらないので外挿で足りる。古い1点のオフセットへ落とすと最大約 0.18 秒ずれる）
   - Pi 側の受け手は、換算後の時刻が受信より後・200ms 以上古いときは受信時刻で代用する（`bus_bridge.py`）
3. **`PING` は 5Hz。** 起動直後の 3秒は 20Hz で打って収束を早める
4. **32bit μs カウンタのラップ（約 71.6 分）。** 差分は必ず符号なし演算（`(uint32_t)(a - b)`）。Pi は `t_us` を基準に最も近い周回へ 64bit に伸ばす。
   生値が 1 秒以上後退し、直前の値がラップの 2 秒手前でもなければ STM32 の再起動と見て時刻同期をやり直す
   （`TimeSync.resets`。io_node は状態の組み立て・LiDAR・調整パラメータもやり直す）
5. 換算後の時刻は Pi 内部の全メッセージの `t_capture`（ns、Pi の `CLOCK_MONOTONIC` 基準）に入れる

## 7. 送信優先度

```
高  PONG  >  TELEMETRY  >  LIDAR_SECTOR  >  CONFIG_ACK / VERSION / LIMITS / STATS  >  LOG  低
```

ファームの送信キューはこの5本（PONG・TELEMETRY・LIDAR・INFO・LOG）。

- **`PONG` が最優先**: LiDAR セクタの後ろに並ぶと T3 以降に非対称遅延が生じ、オフセット推定にバイアスが乗る
- `TELEMETRY` が次点なのは、安全監視と制御に直結するため
- `LOG` は溢れたら破棄する（`STATS.tx_drop`）

**送信待ちは約 1ms で有界。** 送信中の DMA フレームを途中で中断しないので、`TELEMETRY` が LiDAR に阻まれる最大待ちは送信中の1フレーム分
（76 B × 10 bit ÷ 1 Mbps = 0.76 ms、PONG が割り込めば + 0.19 ms）。LiDAR のバーストで上りが数十 ms 滞留することは無い。

## 8. エラー処理と統計

| 事象 | 対応 |
|---|---|
| CRC 不一致 | 破棄。`crc_error_count++`。次の SYNC を探す |
| SYNC ロスト | 1バイトずつずらして `0xAA 0x55` を再探索 |
| `LEN` が TYPE の期待値と不一致 | 破棄。`len_error_count++`。**その場で SYNC の探し直しに戻る**（LEN ぶん読み飛ばさない） |
| `SEQ` 欠番 | `packet_loss_count += 欠番数` |
| 未知の `TYPE` | 破棄。`unknown_type_count++`。**その場で SYNC の探し直しに戻る**（化けた LEN ぶん最大 257B を待つと、STM32 は 75〜110ms 分の `COMMAND` を失い途絶の自動ブレーキに入りうる。両側とも同じ） |
| **`TELEMETRY` が 100ms 途絶** | **Pi → `DEGRADED`**（警告表示。制御は継続） |
| **`TELEMETRY` が 200ms 途絶** | **Pi → `FAULT`**（最大制動の `COMMAND` を送り、止まってから DISARM） |
| **`COMMAND` が 100ms 途絶** | **STM32 → 自動ブレーキ**（安全の第2層） |
| Pi 内部の `cmd` が `[safety] cmd_deadman_ms` 途絶 | Pi の `io_node` → 最大制動の `COMMAND` を送り、止まってから DISARM（`_failsafe_packet`） |
| `md_status[i].comm_ok = 0` | 該当モータの値を無効扱い |
| `protocol_version` の不一致・未受信 | ARM を通さない（DISARM を送り続ける）。通信・表示は続け、`VERSION_REQ` を 1 秒ごとに送り直す |

### `TELEMETRY` 途絶を2段階にする理由

単発の CRC エラーや一時的なロスで即 FAULT に落とさないため（送信待ちは §7 のとおり有界なので、滞留は理由ではない）。
100ms（10発）は「怪しい」と見せるだけ、実際に止めるのは 200ms（20発）。**下りの `COMMAND` は安全に直結するので一段で 100ms にする。** この非対称は意図的。

Pi 側の `crc_error_count` / `packet_loss_count` / 実効受信レートと STM32 の `STATS`（§5.10）を**並べて常時表示**する。
走行中に急にロス率が上がったら、モータのノイズが UART に乗っている。

## 9. 緊急停止ライン（UART とは独立した第1安全層）

UART とは別経路の、ハードウェアレベルの安全機構。**Pi 側 GPIO6 → STM32 側 PB12（`RAS_SIG`）。**

**ハートビート方式にする理由**: 単純なアクティブ Low の E-Stop は、断線するとプルアップで High（= 正常）に戻りフェイルセーフにならない。
矩形波なら Pi のフリーズ・電源断・配線の断線・プロセスのクラッシュを**1本の線で**検出できる。

```
Pi   : GPIO6 に 100Hz の矩形波を出し続ける（専用スレッド。raspi/io/gpio.py）
STM32: PB12 を 2kHz の制御ループでポーリングしてエッジを監視
       エッジが 50ms 途切れたら即ブレーキ + estop_active をラッチ
```

- **STM32 は EXTI ではなくポーリングで受ける。** EXTI はライン番号ごとに1ポートしか選べず、PB12 と前方超音波の ECHO (PA12) が同じライン 12 を使うため
- **Pi はメインループが毎周 `kick()` を呼び、100ms 途切れたら自分で波形を止める**（スレッドだけ生きてメインループが固まる状態を検出する）。
  プロセスが死んでも波形が出続けるハードウェア PWM は使わない

### STM32 側の挙動

**Pi 側はこの表を前提にしてよい。**（実装はファームの `src/comm/heartbeat.[ch]`・`src/vehicle/vehicle.c`）

| 項目 | 挙動 |
|---|---|
| 信号 | 100Hz の矩形波。デューティは問わない（エッジの有無だけを見る）。オープンドレインでもプッシュプルでもよい（外付けプルアップあり） |
| 接続判定 | **エッジを10回数えて初めて「Pi が繋がっている」とみなす**（単発ノイズで接続済みと判定して直後に停止へ落ちない） |
| 未接続時 | ハートビートを一度も見ていない間は**緊急停止を発動しない**（ベンチ確認のため。代わりに `flags` bit25 `no_heartbeat`） |
| 途絶時 | 50ms で**ラッチ**し、`flags` bit3 `estop_active` が立つ |
| 復帰 | **自動復帰しない。** ハートビートが戻っている状態で**車両のボタン2を人が押す**まで解除しない。解除後も `COMMAND` の `arm` が一度 0 になってから立ち上がるまで ARM しない |
| 発動時の動作 | 最大制動トルクで停止（舵角は最後の指令のまま）、ハザード点滅。**制動中は駆動電源を切らない**（切ると MD が制動できず惰行する）。止まったら後輪を位置保持へ移し、**30 秒止まったままなら駆動電源を切る** |

#### Pi 側が守ること

- **E-Stop 解除後は `arm` を一度下ろしてから立て直す。** io_node は `estop_active`（と `drive_power_locked`・STM32 の再起動）を見たら、
  操縦側の `cmd.arm` が一度 False になるまで ARM を通さない（`_update_rearm_latch`）。STM32 も `arm` の立ち上がりを待つので、どちらか片方だけでも走り出さない
- **出し始めたら出し続ける。** 一度も出さなければ緊急停止は発動しないので、ベンチ診断では意図的に出さない選択もできる
- **`estop_active` の間は `COMMAND` は一切効かない。** リンクの健全性（`health`）とは別の軸
- GUI に「**E-STOP 発動中 — 車両のボタン2で解除してください**」と、他の表示に埋もれないよう出す

## 10. 安全層の全体像

安全機構は4層。**層ごとに担当と復帰条件が違う。**

| 層 | 機構 | 反応時間 | 復帰 | Pi の扱い |
|---|---|---|---|---|
| 1 | **GPIO ハートビート断**（`estop_active`） | 50ms | 人の明示操作（ボタン2）＋ ARM の入れ直し | FAULT |
| 2 | **`COMMAND` 途絶**（`uart_timeout`） | 100ms | `COMMAND` 再開で制動は解除。ARM は `arm` が一度 0 になってからの立ち上がりで | DEGRADED → FAULT |
| 3 | **過電流ハード遮断**（`fault_*_overcurrent`, `drive_power_locked`） | 即時（50ms 継続で判定） | **電源リセットのみ**（ラッチ） | FAULT。ただし `arm` 拒否は正常動作 |
| 4 | **低電圧警告**（`fault_*_undervoltage`） | 1秒継続 | 電圧回復で自動 | 警告表示のみ |

**層3と層4を混同しない。** 層3はラッチして走行不能、層4は警告だけで走り続けられる。GUI でも赤（層1-3）と黄（層4）で分ける。

## 11. 帯域予算

### STM32 → Pi（上限 100 kB/s）

既定構成（`param 0x0040 = 0`）:

| パケット | フレーム長 | 頻度 | 帯域 |
|---|---|---|---|
| `LIDAR_SECTOR` (0x01) | 76 B | 120 Hz | 9.12 kB/s |
| `TELEMETRY` (0x02) | 109 B | 100 Hz | 10.9 kB/s |
| `PONG` (0x06) | 19 B | 5 Hz | 0.10 kB/s |
| `STATS` (0x08) | 55 B | 1 Hz | 0.06 kB/s |
| `CONFIG_ACK` / `LOG` / `VERSION` | — | 散発 | 約 0.2 kB/s |
| **合計** | | | **約 20.4 kB/s（約20%）** |

強度 ON（`= 1`）は約 23 kB/s、圧縮（`= 2`）は約 16 kB/s。いずれも余裕がある。判断材料は Pi 側のロス率と `STATS.tx_drop`。

### Pi → STM32（別方向・独立）

| パケット | フレーム長 | 頻度 | 帯域 |
|---|---|---|---|
| `COMMAND` (0x10) | 22 B | 100 Hz（中身が変われば即時にも送る） | 2.20 kB/s（約2%） |
| `PING` (0x12) | 11 B | 5 Hz | 0.06 kB/s |
| `CONFIG_SET` / `CONFIG_GET` / `*_REQ` | — | 散発 | < 0.1 kB/s |

## 12. Raspberry Pi 5 側の実装上の注意

- **デバイス名**: Pi 5 では `/dev/ttyAMA0` が別用途。GPIO14/15 の UART は別名（オーバーレイ次第）なので `ls -l /dev/serial*`・`dmesg | grep -i ttyAMA` で確かめる。
  `/boot/firmware/config.txt` に `enable_uart=1`、`/boot/firmware/cmdline.txt` から `console=serial0,115200` を削除（シリアルコンソールが掴んだままだと通信できない）
- **ボーレート**: 1000000 bps は termios に定義（`B1000000`）があり、pyserial の `Serial(port, baud)` でそのまま通る
- **受信ループ**: 1バイトずつ `read(1)` せず、`ser.read(max(1, ser.in_waiting))` で塊を読んで `FrameParser.feed()` に渡す（`raspi/proto/README.md`）
- **プロセス分離**: 受信は `io_node` 専用プロセスでパースに専念させる。知覚処理を混ぜると、CPU スパイクのたびに UART の受信バッファ（4KB 程度＝本プロトコルで約 200ms 分）が溢れる
- **ラップ**: `t_us` は 71.6 分でラップし実走行で必ずまたぐので、必ず符号なし差分（§6.3）。`STATS.*` と `odom_dist`（0.1mm × 2^32 = 429.5 km）は実質ラップしない
- **アライメント**: ペイロードはフレームの 5バイト目から始まるので `u32`/`i32` は 4バイト境界に乗らない。C は `__packed`（非 packed 構造体へのキャストは未定義動作で、ARM ではハードフォールトしうる）、
  Python の `struct` は必ず `<` で始める（`=`・`@` はパディングが入る）。実際のフォーマットは生成物 `raspi/proto/generated/packets.py` の各クラスの `FMT`。手で書き写さない
- **GPIO**: `RPi.GPIO` は動かない（[`system_overview.md`](system_overview.md) の Pi 5 の注意）

## 13. Pi 側の状態機械

**起動シーケンス**（`raspi/nodes/io_node.py`）:

```
1. UART オープン
2. VERSION_REQ と LIMITS_REQ を送信 → VERSION・LIMITS を最大 1 秒待つ（届かなければ 1 秒ごとに送り直す）
3. ON/OFF 系と自動停止のマージンを CONFIG_GET で読み、GUI の初期値にする
4. [control] を CONFIG_SET で送り、CONFIG_ACK で確かめる（§5.8.4）
5. PING を 20Hz で 3秒 → 5Hz
6. GPIO6 ハートビート開始、COMMAND の 100Hz 送信開始（ARM を通せる条件が揃うまでは DISARM）
```

`io_node` のリンクの健全性（`health`）は `TELEMETRY` の受信間隔だけで決まる（`raspi/core/link_tracker.py`）。

| health | 条件 | Pi の扱い |
|---|---|---|
| `INIT` | `TELEMETRY` をまだ受けていない | — |
| `OK` | 間隔 ≤ 100ms | — |
| `DEGRADED` | 間隔 > 100ms | 警告表示。制御は継続 |
| `FAULT` | 間隔 > 200ms | 最大制動の `COMMAND` を送り、止まってから DISARM。`TELEMETRY` が戻れば `OK` へ戻る |

FAULT で止めるのは、受信（STM32 → Pi）だけが切れている場合、STM32 は `COMMAND` を受け取れてしまい途絶の自動ブレーキが効かないため
（Pi が状態も LiDAR も見えないまま速度指令を送り続けない）。

`health` とは別に、ARM を通してよいかを `_arm_block_reason` が判定する（`diag/link` の `arm_inhibit_reason`）。通さない間は DISARM を送り続ける。
主な条件: `--allow-arm`・E-Stop / `drive_power_locked` / STM32 再起動などのあとは `arm` を一度下ろすまで・`protocol_version` 一致・`LIMITS` 受信済み・
`no_heartbeat` でない・`[control]` の送信完了。`steer_center_valid` が立っていなければ STM32 が MANUAL/AUTO に入らない（GUI に整備手順を出す）。
