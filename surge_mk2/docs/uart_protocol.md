# SURGE Mark.2 UART プロトコル仕様

**バージョン**: v0.26（`protocol_version = 0x001A`。唯一の定義は `raspi/proto/protocol.toml`）
**最終更新**: 2026-10-11
**対象**: Raspberry Pi 5 ⇄ STM32F446RE 間の通信
**状態**: Pi・STM32 とも実装済み。**STM32・MD は未書き込み、実機での動作検証は未了**。
各版の変更の経緯・変更履歴は [`archive/uart_protocol_history.md`](archive/uart_protocol_history.md)（陳腐化。参照しない）。

- 全フィールドはリトルエンディアン。TYPE の方向規約: `0x01-0x0F` = STM32 → Pi、`0x10-0x1F` = Pi → STM32

---


## 1. 物理層

| 項目 | 値 |
|---|---|
| ボーレート | **1000000 bps**（Pi 側は `raspi/proto` の `UART_BAUD`） |
| フォーマット | 8N1（データ8bit / パリティなし / ストップ1bit） |
| フロー制御 | なし |
| 実効スループット | **100 kB/s**（1バイト = 10ビット） |
| 配線 | Pi GPIO14 (TX) → STM32 RX / Pi GPIO15 (RX) ← STM32 TX |
| 論理レベル | 3.3V（両者とも3.3V系のためレベル変換不要） |

**ボーレート誤差は 0%（STM32 側）。**
STM32 の USART1（APB2 45MHz＝HCLK 180MHz の 1/4、オーバーサンプリング16）の USARTDIV は
45M÷(16×1M) = 2.8125 = 2+13/16 で、1/16 刻みで厳密に表現できる。Pi 5 側の実際の誤差は実機で
`STATS` のフレームエラー・CRC エラー数が 0 付近かで確かめる。

**1Mbps の理由**: 同じ基板内の短い配線なので 1µs/ビットでも余裕があり、フレーム1つの線上時間が短く
（TELEMETRY 0.91ms、COMMAND 0.22ms）順番待ちがほぼ無い（使用率は §11）。STM32 側の受信リングは
2048B で、上書きとみなすまでの猶予は約20ms。

## 2. 設計方針

### 2.1 責務分割

| 担当 | 内容 |
|---|---|
| **STM32** | モータ電流/速度制御ループ、ステアリング角度制御ループ、TC、トルクベクタリング、LD06 パース、超音波測距、電流・温度リミッタ、UART タイムアウト時の自動ブレーキ、**モータ機械角 ⇄ 路面舵角の換算**、**車輪角速度 → 周速 [m/s] の換算**、**`speed` の車体中心線方向への射影** |
| **Raspberry Pi 5** | 知覚（点群処理・カメラ認識）、自己位置推定、経路生成、行動判断、テレメトリ配信、**前輪オドメトリの射影**（§5.3） |

**Pi が送るのは「目標速度・加速度上限・目標舵角」だけ**であり、PWM デューティやトルク配分は一切送らない。
TC/TV を含む低レベル制御は STM32 内で閉じており、Pi 側からは有効/無効とパラメータのみを設定する。

理由：TC やスリップ制御は数ms以内に効かせる必要があり、UART往復 + Python 処理の遅延（合計 30〜50ms）を挟めないため。
「速い制御はエッジに、遅い判断は上位に」という階層制御の原則に従う。

**機械定数は STM32 に閉じる。** 車輪半径・ギア比・ステアリングのリンク比を Pi は知らない。
UART 上の物理量はすべて SI 単位（m/s、rad、N·m、0.1mm）で定義するため、
機械定数が実測で変わっても Pi 側の改修は不要。

### 2.2 プロトコル設計の原則

1. **可変長・パケット種別付きフレーム**にする（固定長単一フレームだと拡張時に破綻する）
2. **CRC16 必須**（ヘッダ・フッタだけの検証では単一ビット化けを見逃す）
3. **LiDAR は1周を12分割して送る**（遅延削減・タイムスタンプ付与・バス占有回避・損失局所化）
4. **周期コマンドと設定変更を混ぜない**（設定は個別ID + ack 方式）
5. **全パケットにタイムスタンプを載せる**（後付けは極めて困難）
6. **積算量は「差分」ではなく「累積値」で送る**（パケットロスで情報が永久に失われないため）
   → `odom_dist` と `STATS` の両方にこの原則を適用する
7. **1つの TYPE は 1つの LEN と 1つの方向だけを持つ**
   → `0x01-0x0F` = STM32→Pi、`0x10-0x1F` = Pi→STM32。可変長は `LOG` のみ

## 3. フレーム構造（両方向共通）

```
┌────────┬────────┬──────┬──────┬──────┬───────────┬────────────┐
│ 0xAA   │ 0x55   │ TYPE │ SEQ  │ LEN  │ PAYLOAD   │ CRC16      │
│ 1B     │ 1B     │ 1B   │ 1B   │ 1B   │ LEN bytes │ 2B         │
└────────┴────────┴──────┴──────┴──────┴───────────┴────────────┘
  0        1        2      3      4      5           5+LEN

オーバーヘッド : 7 バイト
PAYLOAD 最大長 : 255 バイト
CRC 計算範囲   : TYPE(offset 2) から PAYLOAD 末尾まで（= LEN + 3 バイト）
エンディアン   : 全フィールド リトルエンディアン（STM32 ネイティブに合わせ変換コストをゼロにする）
```

### 3.1 各フィールド

| フィールド | 説明 |
|---|---|
| `SYNC` (0xAA 0x55) | 同期ワード。**2バイト必須**。1バイトだとバイナリデータ中に頻出し誤検出する |
| `TYPE` | パケット種別（§4 参照） |
| `SEQ` | 0-255 のローリングカウンタ。**送信方向ごとに独立**。欠番でパケットロスを検出 |
| `LEN` | PAYLOAD のバイト数 |
| `CRC16` | CRC-16/CCITT-FALSE（下記） |

`SEQ` は送信方向ごとに1本の通し番号であり、**リンク全体のロス率の指標**である。
STM32 は SEQ を**送信の直前（DMA 起動の直前）に**振る（CRC もそこで計算する。PONG の T3 と同じ場所）。
優先度の高いキューから先に送る（§7）ので、送出順に SEQ が単調に増え、正常なら `RxStats.reordered` は 0 のまま。
**古いファーム**（SEQ をキューへ積むときに振っていたもの）では、後から積んだ `PONG`・`TELEMETRY` が
先に積んだ LiDAR セクタ等を追い越し、Pi から見て SEQ が数個ぶん逆行して `reordered` が正常でも増えた
（実機で 26 分に 242 件）。Pi 側は互換のため、追い越された分をいったん `packet_loss` に数え、遅れて届いたら
差し引く（`packet_loss` は実際のロスだけを表す）。送信キューの溢れは SEQ の欠番にならず、STATS の
`tx_drop` に出る（SEQ が送出時に振られるため）。
「どのストリームが落ちたか」までは分からないが、LiDAR は `sector_idx` の連続性で
個別に追跡できるため実害は小さい。

### 3.2 CRC 仕様

**CRC-16/CCITT-FALSE**

| パラメータ | 値 |
|---|---|
| 多項式 | `0x1021` |
| 初期値 | `0xFFFF` |
| 入力反転 | なし |
| 出力反転 | なし |
| 最終XOR | `0x0000` |
| 検査値 | `"123456789"` → `0x29B1` |

参照実装（ビット単位版・両者共通）:

```c
uint16_t crc16_ccitt(const uint8_t *data, size_t len) {
    uint16_t crc = 0xFFFF;
    for (size_t i = 0; i < len; i++) {
        crc ^= (uint16_t)data[i] << 8;
        for (int b = 0; b < 8; b++)
            crc = (crc & 0x8000) ? (crc << 1) ^ 0x1021 : (crc << 1);
    }
    return crc;
}
```

STM32 側は速度が必要なら 256エントリのテーブル駆動版に置き換えてよい（結果は同一）。
両者とも実装直後に `"123456789"` → `0x29B1` で検証すること。

※ STM32 ⇄ MD 間は別の CRC-8/AUTOSAR を使っているが、これは STM32 内部で閉じており Pi 側とは無関係。

## 5. パケット詳細

### 5.1 `LIDAR_SECTOR` (0x01) — LEN = 69

1周（360点）を12セクタ（各30点 = 30°）に分割して送信する。

| offset | size | type | field | 単位・備考 |
|---|---|---|---|---|
| 0 | 1 | u8 | `sector_idx` | 0-11 |
| 1 | 4 | u32 | `t_start_us` | STM32 monotonic μs（このセクタ先頭点の取得時刻） |
| 5 | 2 | u16 | `duration_us` | **このセクタ30点の取得に要した時間** |
| 7 | 2 | u16 | `rot_speed_dps` | **deg/s そのまま（スケール 1）**。LD06 が報告する回転速度 |
| 9 | 60 | u16×30 | `dist[30]` | mm。**0 = 無効 / 範囲外** |

**合計 69 バイト**

#### 角度の求め方

**角度は `sector_idx * 30 + i` [degree]（i = 0..29）で一意に決まる。実測角度は送らない。**

STM32 側で 1° ビンにビニングした時点で角度は 1° 格子に量子化されており、実測角度を送っても
精度は残らないため、角度フィールドは持たない。

#### ★ 左右の鏡像反転（Pi 側で直す）

**この角度はセンサ基準であり、そのまま車両角として使うと点群が左右反転する。**
LD06 は PCB 面を下にして裏向きに取り付けてあるため、0° は機体前方を向いているが
角度が増える向きが上から見て車両座標（反時計回りが正）と逆になる。

```
車両角 [deg] = (360 - (sector_idx * 30 + i)) % 360
```

STM32 側はこの補正を**あえて行わない**（センサ基準の角度をそのまま送る）。
補正を STM32 に入れると 0°/180° がセクタ境界に乗って1セクタが出力側の隣接2セクタに
分裂するうえ、実際に試したところ原因不明の通信エラー増発が再現したため。
詳細は STM32 の `src/sensing/lidar.h` を参照。

Pi 側では `ScanAssembler`（`raspi/msgs/convert.py`）が**この1箇所だけ**で反転する。
`Scan.dist` の添字は車両角なので、ノード・GUI・地図生成は反転を意識しなくてよい。
反転の結果、**1周は添字の降順に取得される**（センサ角が増える = 車両角が減る）ため、
`sector_t_ns` / `sector_dur_us` / `sector_seen` も車両座標のセクタ番号
`11 - sector_idx` へ移して持つ。セクタ内の時刻は添字が大きい側から流れる。

**30° の境界も 1° ずれる。** セクタ `s` が持つのは車両角 `30*s+1` 〜 `(30*s+30) % 360` で、
`30*s` ちょうどの点は隣のセクタ `s-1` のパケット由来（そのパケットの先頭点）。
歪み補正で点の時刻を引くときは、**車両角をセンサ角に戻してから**引くこと（次項）。

#### 各点の時刻の求め方

```
t[i] = t_start_us + duration_us * i / 29        (i = 0..29)
```

`i` は**パケット内の添字（センサ基準）**であり、反転後の車両角の添字ではない。
`Scan` に組み上げたあとは、車両角 `deg` からこう引く（`raspi/msgs/types.py`）。

```
sensor = (360 - deg) % 360                 # センサ角に戻す
s, i   = 11 - sensor // 30, sensor % 30    # セクタ番号とパケット内の添字
t_ns   = sector_t_ns[s] + sector_dur_us[s] * 1000 * i / 29
```

**車両角のまま `30*s + j` と分解して式を立てないこと。** 上の 1° ずれのせいで
`j = 0` の点だけ別のパケット由来になり、最大1周ぶん（約 100ms）外す。

`duration_us` があることで、**セクタを1つ落としても歪み補正が壊れない**
（前セクタとの `t_start_us` 差分には頼らない）。

`rot_speed_dps` は回転異常の検出と、上式の妥当性チェックに使う。
`duration_us` と `rot_speed_dps` から求まる 30° 分の所要時間が大きく食い違ったら、そのセクタを破棄する。

> **スケールは `1 deg/s`（`0.01 deg/s` ではない）。** u16 × 0.01 では最大 655.4 deg/s にしかならず、
> LD06 の実回転（10 rps ≒ **3600 deg/s**）を表現できない。実機ログ 2403 セクタで生値の中央値が
> **3594**、`duration_us` からの逆算が **3642 deg/s** で一致している（ファームは deg/s をそのまま送る）。

#### 設計意図

- **1周まとめて送らない理由**
  1. 1周（720B）を貯めてから送ると、それだけで **100ms の遅延**が乗る
  2. 720B の送信に **7ms**（250kbps の頃は29ms）かかり、その間 TELEMETRY が割り込めない
  3. セクタごとの**タイムスタンプが自然に入る** → 走行中の点群歪み補正が可能
  4. CRC エラー時の損失が **1/12** で済む

- **点群歪み補正（motion distortion）**
  LD06 は 10Hz 回転のため、1周する 100ms の間に車体が移動する。
  時速 10km/h なら 1周あたり **約 28cm** 移動し、点群が扇形に歪む。SLAM 精度に直結するため、
  Pi 側で `t_start_us` / `duration_us` とオドメトリを突き合わせて各点を補正すること。

- **STM32 側のビニング**
  LD06 の生データ（約 450点/周）を 1° ビンにビニングして 360点に整形する。
  同一ビンに複数点が入った場合は **ビン中心に最も近い点を代表点として採用**する。

  「最小距離を採用（安全側）」は**衝突判定としては正しいが、地図生成用のデータを
  近距離側に系統的に歪ませ、ICP / スキャンマッチングの精度を落とす**ため採らない。
  系統誤差（バイアス）はランダム誤差と違って平均化で消えない。
  安全用途の最短距離判定は STM32 内部で完結させ、Pi に送る点群にはバイアスをかけない。

### 5.2 `LIDAR_SECTOR_I` (0x05) — LEN = 99 / `LIDAR_SECTOR_C` (0x09) — LEN = 39

いずれも既定 OFF。`0x01` と排他で、どれか1種類だけが送られる（§5.8）。

**`LIDAR_SECTOR_I`（強度付き）** — `0x01` と同一レイアウトの末尾に強度を追加。

| offset | size | type | field | 単位 |
|---|---|---|---|---|
| 0-68 | 69 | | (0x01 と同一) | |
| 69 | 30 | u8×30 | `intensity[30]` | 0-255（LD06 の信頼度をそのまま転送） |

**`LIDAR_SECTOR_C`（圧縮）** — `0x01` と同一レイアウトで距離のみ 1バイト化。

| offset | size | type | field | 単位・備考 |
|---|---|---|---|---|
| 0 | 1 | u8 | `sector_idx` | 0-11 |
| 1 | 4 | u32 | `t_start_us` | STM32 monotonic μs |
| 5 | 2 | u16 | `duration_us` | μs |
| 7 | 2 | u16 | `rot_speed_dps` | **deg/s そのまま（スケール 1）** |
| 9 | 30 | u8×30 | `dist[30]` | **2 cm/LSB**。`0` = 無効、`255` = **5.10m 以上（飽和）** |

**合計 39 バイト**（9.12 kB/s → 5.52 kB/s）

**`255` の扱いに注意。** これは「5.10m ちょうど」ではなく「**5.10m 以上**」である。

```python
# 地図生成での扱い
if d == 0:            continue          # 無効。何も更新しない
elif d == 255:        mark_free_upto(5.10)   # 「5.1m まで障害物なし」— 点は打たない
else:                 mark_hit(d * 0.02)     # 通常のヒット点
```

**`255` を 5.10m の実測点として占有格子に打つと、実在しない壁が円状に生成される。**
LD06 の測距精度が ±1.5cm 程度なので、2cm 量子化による情報損失はほぼ無い。
失われるのは 5.1m 以遠の情報だけ。

### 5.3 `TELEMETRY` (0x02) — LEN = 102

> **`t_us` は送信時刻ではなく、中身のスナップショットを取った時刻**（新しいスナップショットができたときに
> 1回だけ送る）。送信は送信キューの順番待ちのあとなので、送信時刻を付けると中身が古いのに新しく見え、
> 制御遅延の同定（`sysid_latency`）がずれる（中身を作るタイマーと送信タイマーが別々だった頃は最大+20ms）。
> **`VERSION.fw_id` が `0x4D463304` 未満のファームで取った記録の `control_latency_s` は使わないこと**
> （ワイヤ形式は同じで `protocol_version` では見分けられない。同定の解析 `tools/sysid/fit.py` の
> `fit_latency` は、記録の `/diag/link` の `fw_id` が古ければ★を出す）。
> `cmd_seq_echo` だけは送信時点で最後に受けた COMMAND の SEQ（他のフィールドより最大1周期新しい。
> 往復時間の測定にはこの方が正しい）。

車両構成: 後輪左右 2モータ + ステアリング 1モータ（いずれも自作 MD 駆動）、
前輪左右にアナログ絶対角エンコーダ、MPU6050、超音波 前後各1、電源2系統。

```
off  size  type    field                 単位 / 備考
──────────────────────────────────────────────────────────────────────────────
  0    4   u32     t_us                  μs (STM32 monotonic, 71.6分でラップ) ★この行のスナップショットを取った時刻
  4    4   u32     flags                 §5.4
  8    2   i16     speed                 0.001 m/s  車速（★車体中心線方向に射影済み）
 10    2   i16     yaw_rate              0.001 rad/s
 12    2   i16     steer_actual          0.0001 rad ★路面舵角（反時計回り正）
 14    2   i16     steer_cmd_echo        0.0001 rad 指令のエコーバック
 16    8   i16×4   wheel_speed[4]        0.001 m/s  車輪周速 [FL, FR, RL, RR] ※射影なし
 24    8   i32×2   odom_dist[2]          0.1 mm  前輪累積走行距離 [FL, FR] ※射影なし
 32    2   i16     accel_x               0.001 m/s²
 34    2   i16     accel_y               0.001 m/s²
 36    2   i16     accel_z               0.001 m/s²
```

#### ★ 前輪データの射影（Pi 側の必須処理）

**`odom_dist[]` と `wheel_speed[FL], wheel_speed[FR]` は「その車輪自身の走行軌跡に沿った
距離・速度」であり、車体中心線方向の値ではない。** 前輪は操舵輪だからである。

自転車モデルにおいて、舵角 δ のとき前輪の走行距離は車体中心線距離の **1/cos(δ) 倍**になる。

| 舵角 δ | 過大評価 |
|---|---|
| 10° | +1.5% |
| 30° | **+15.5%** |
| 60° | **+100%** |

**射影済みなのは `speed` だけ**（STM32 側で処理）。`wheel_speed` と `odom_dist` は生値。

##### 射影は「累積値」ではなく「差分」に適用する

STM32 側の資料にある式

```
d_center ≈ (odom_dist[FL] + odom_dist[FR]) / 2 × cos(steer_actual)     ← 累積値に適用すると誤り
```

を**累積値にそのまま適用してはならない。** 舵角は時々刻々変わるため、
過去の走行分に「現在の」舵角を掛けることはできない。
直進 100m 走った直後にハンドルを 60° 切ると、累積距離が一瞬で半分になる。

**正しくは、1周期ごとの差分に、その時点の舵角で射影して積算する:**

```python
# TELEMETRY（100Hz）を受けるたびに
d_front = ((odom_dist[FL] - prev[FL]) + (odom_dist[FR] - prev[FR])) / 2 * 1e-4   # [m]
d_center += d_front * math.cos(steer_actual)      # ← 差分に対して射影
prev = odom_dist[:]
```

##### パケットロス時の劣化

累積値なので**距離そのものは1発で完全に回復する**が、
**その区間の舵角の履歴は失われる**ため、射影は前後の `steer_actual` による近似になる。

```
ロス区間の射影 ≈ d_front × cos((δ_before + δ_after) / 2)
```

`speed` を積分する方式（区間まるごと消える）より遥かにマシだが、
**大舵角でのロスは誤差が残る**ことは認識しておく。連続ロス時は SLAM 側の
スキャンマッチングに重みを寄せること。

##### 左右差からのヨー角推定

`odom_dist[FR] − odom_dist[FL]` からヨー角変化を推定できるが、
**操舵輪なので後輪差動の式は使えない。** Ackermann により左右前輪の実舵角は異なる
（δ_L ≠ δ_R）。`steer_actual` は**自転車モデル等価の単一値**なので、
厳密解が要るなら車両幾何から δ_L / δ_R を復元すること。

**ヨーレートの第一情報源は IMU（`yaw_rate`）とし、前輪差分は妥当性チェックに使う。**

##### スリップ量の計算にも射影が要る

```python
slip_rear  = wheel_speed[RL] - speed                          # 後輪は非操舵輪 → そのまま
slip_front = wheel_speed[FL] * math.cos(steer_actual) - speed # 前輪は射影してから
```

射影を忘れると、舵角 30° で常時 15.5% のスリップが出ているように見える。

#### 設計意図

- **`speed` と `wheel_speed[4]` を両方送る理由**
  `speed` は車体中心線方向の車速の真値、`wheel_speed` は各輪の生の周速。
  差分がそのままスリップ量になり、TC の挙動が GUI で直接見える。

- **`wheel_speed` を角速度ではなく周速 [m/s] にする理由**
  `speed` と同じ単位になるため Pi は引き算するだけでスリップ量を得られ、
  車輪径やギア比を知らなくて済む。換算定数は STM32 側に閉じる。

- **`odom_dist` を速度と別に累積で送る理由**
  `speed` の時間積分では、パケットが1個落ちると 10ms 分の移動距離が**永久に失われる**。
  100Hz で 1% ロスなら 1分走行で 60回分がそのまま自己位置の誤差になる。
  累積値なら次の1発で回復する。スキャンマッチングの初期値精度は地図の品質に直結する。

- **`torque_cmd` を載せる理由**
  TC が介入したのか単にトルクが足りないのかを切り分けるには、最終的に各輪へ何 N·m 出したかが
  見える必要がある。`flags.tc_active` と併せて見るとチューニングの効率が大きく変わる。
  **実測トルクは存在しない**（MD が返すのは `iq [mA]` のみで、トルク定数 Kt が未実測）。
  これは指令値であり実測値ではない、という点を GUI でも明示すること。

- **符号は「正 = 駆動、負 = 制動」**
  ブレーキ中・停車保持中は掛けている制動トルクが**負値**で入る
  （`brake_torque = 0.05 N·m` で制動中なら `-0.05`）。停車保持中に `0` を入れると、
  押さえているのか何もしていないのか区別が付かないため。
  **「車両が自分で駆動している」判定には正値だけを使うこと。**

- **スケールが 0.0001 N·m/LSB である理由**
  モータの最大トルクが 0.1557 N·m、ステアの上限が 0.1 N·m と**値域が極めて小さい**。
  0.001 N·m 刻みでは 156 段階しか無く分解能が足りない。

- **`steer_actual` / `steer_cmd_echo` は「路面舵角」**
  モータ機械角ではない。Pi 側の自転車モデルや Pure Pursuit が必要とするのは路面舵角であり、
  換算は STM32 側で行う。**リンク比は 0.5 で確定した**（2026-08-20 実測、§14）。

  この2つを同一パケットに入れておけば、差分を取るだけで遅延特性が測定でき、
  別ログの時刻合わせが不要になる。経路追従の遅延補償に必須。

- **`cmd_seq_echo`**
  「Pi が SEQ=57 を送った時刻」と「echo=57 が返った時刻」の差が、そのまま
  **エンドツーエンド遅延**。GUI に常時表示する。50ms を超えたら警告。

- **電源が2系統ある理由**
  駆動系（MD 電源、過電流 5.0A）とシグナル系（マイコン・Pi・LiDAR・ライト、過電流 3.0A）で
  別バッテリー。どちらも 8セル ニッケル水素（放電終止 8.0V / 満充電 11.2V）。
  **モータの突入電流で Pi が落ちる事故を防ぐための分離**であり、両方を監視する必要がある。

- **電流が単方向（u8）でトルクが双方向（i16）である非対称について**
  バッテリー電流センサは INA180A2 + シャントの GND 基準・単方向構成で、
  回生時に逆流しても測定できず 0 に張り付く。一方 MD が返す `iq` は双方向。
  **この非対称は意図的**であり、Pi 側は回生中のバッテリー電流を信用してはならない。

#### 更新レートに関する注意

**フィールドによって実際の更新レートが異なる。** 100Hz で来るからといって
100Hz で更新されているとは限らない。

| フィールド | 実更新レート | Pi 側の扱い |
|---|---|---|
| `us_front` / `us_rear` | **実質 20Hz 以下**（前後交互、往復時間の制約） | 同じ値が連続することを前提にする。エッジ検出に使わない |
| `temp[4]` | 数 Hz 程度 | 傾向監視のみ |
| `batt_*` | 数十 Hz | フィルタ済み |
| `speed` | 100Hz（STM32 内は 2kHz）。**カルマンフィルタの車速**（§5.3.1。v0.24 まではローパス τ≈10ms） | 下記参照 |
| `wheel_speed`（前輪） | 100Hz。ローパス（τ≈10ms）通過後の各輪の周速 | 下記参照 |

**`speed` / `wheel_speed` を微分して加速度を求めてはならない。**
前輪エンコーダはアナログ絶対角の ADC 読みで分解能が粗く、角速度換算で
**1LSB ≈ 1.5 rad/s 相当のノイズ**が乗る（500µs で差分した場合。実測のノイズは±100mV程度）。
STM32 は **ADC を1制御周期ぶん（32スキャン、約444µs）平均した角度**を使う。
**v0.25 以降の `speed` はカルマンフィルタの車速**（§5.3.1。遅れはほぼ無い）で、リアルタイムの用途（プランナー・E2E）に
そのまま使ってよい。ただし微分すれば加速度計の雑音が増幅されるので、**加速度は `accel_x/y/z`（IMU）か `accel_kf` から取ること。**
`wheel_speed[FL/FR]` は各輪の周速を **時定数9.95ms の1次ローパス（`DRIVE_LPF_TAU_FRONT_S`）** に通した報告用の値（車速の計算には使わない）。
100Hz への間引きで 50Hz より上のノイズが折り返すので、**記録を後から解析する用途（システム同定）は
`odom_dist`（ローパス前の積算位置）を前後のサンプルでゼロ位相に微分する方が正確**（`tools/sysid/fit.py`）。
v0.24 以前の記録の `speed` は遅れ約10msのローパス版（今のシムは `speed` を `config/vehicle.toml` の `speed_kf_lag_s`、`wheel_speed` を `speed_filter_s` で遅らせる）。

#### 前輪エンコーダに由来するその他の制約

1. **静止付近で前進/後退の符号がばたつく。** 絶対角のアンラップで符号は出せるが、
   ノイズで反転する。`|speed| < 0.05 m/s` 程度のデッドバンドを設けて 0 とみなすこと。
2. `odom_dist` も同じセンサ由来なので、静止時にゆっくりドリフトしうる。

#### IMU に関する制約

- **MPU6050（6軸: ジャイロ + 加速度）+ Mahony 相補フィルタ。地磁気センサは無い。**
- したがって **yaw の絶対方位は出せず、積分ドリフトする**。
  `TELEMETRY` に `yaw` そのものを載せず `yaw_rate` のみにしているのはこのため。
  **絶対方位は Pi 側の SLAM（スキャンマッチング）で確定させる。**
- `pitch` / `roll` は重力ベクトルで補正されるためドリフトしない。信用してよい。
- ジャイロバイアスは静止時に STM32 が追従補正し、キャリブレーション値は Flash に永続化済み。

#### 5.3.1 車速の推定とその一貫性の診断（★v0.24 で導入、v0.25 で前輪の微分+LPF を廃止、v0.26 で診断を追加）

`speed` は**走行距離と加速度計のカルマンフィルタ**（`src/control/speed_kf.h`）の車速で、車速PI・TC/ABS のスリップの基準・
自動停止の前後判定のすべてがこれを使う。従来の前輪エンコーダの微分+LPF（τ≈10ms）は廃止した（遅れ 10ms と、
`Encoder_Update` の `dt` の誤りによる約 1.8% の過大があった。`dt` は直した）。
**v0.23 以前・v0.24 の記録の `speed` は LPF 版**で、v0.24 の記録だけ `speed_lpf`・`speed_kf` が両方ある。

- `accel_kf`・`accel_bias_kf` はフィルタの状態。`accel_bias_kf` は加速度計の取付ずれと重力の傾き成分の合計で、坂・傾きで動く
- `kf_gated` が走行中に増える＝前輪の距離が予測と大きく食い違った（ロック・スリップ・衝撃）。そのたびに測定ノイズを
  膨らませて効きを弱めている
- **一貫性の診断（v0.26）**: フィルタは測定ごとに「残差 ÷ 自分が主張する標準偏差」= z を作る。調整値（測定ノイズ・プロセスノイズ）が
  合っていれば z は平均 0・分散 1 の**白色雑音**になる。`kf_z_rms_*` は前回の TELEMETRY からの z の RMS（その2乗が NIS。
  1 より大きい＝誤差が主張より大きい、小さい＝大きく見積もりすぎ）、`kf_rho_*` は隣り合う z の相関係数（0 でない＝残差が
  時間的に相関している＝周期誤差などモデルが表せない誤差がある）。**NIS を直接送らないのは、静止で 1e-3 まで小さくなり、
  そのまま量子化すると潰れるため**（RMS と ρ なら窓ごとの NIS・自己相関に正確に戻せる）。`*_dist` は走行距離（2kHz）、
  `*_accel` は加速度（IMU の 200Hz）。z は ±10 で切ってあり、0 はその間に測定が無かったこと。
  調整値の検証は `python3 -m raspi.tools.kf_consistency <記録>.mcap`。
  `front_angle` は前輪エンコーダの絶対角で、角度の関数である周期誤差（INL）を同定するためのもの（車速の計算には使わない）

| 22 | `drive_power_on` | **駆動電源（DRIVE_POWER）が入っている**。`armed` なら必ず 1。ARM が外れたあと停車を待って制動している間（最大3秒）も 1 |
| 23 | `md_fault` | **MD（3台のいずれか）が使えず、STM32 が走行を止めている**。駆動電源を入れて 5 秒待っても揃わない、または走行中に無応答（100ms）・異常ビット・トルク上限の不一致。走行中なら両後輪を最大制動する。**駆動電源が切れるまでラッチ**。どの MD かは `md_status`、理由は `LOG` |
| 24 | `launch_active` | **ローンチコントロール（`COMMAND.flags2` bit3）で今まさに発進している**。要求していても、条件を満たさず始まらなかった・目標車速に届いて終わった、なら 0 |
| 25 | `no_heartbeat` | **STM32 がハートビート（RAS_SIG）を一度も検出していない＝E-Stop の層が働いていない**。検出した時点で 0 に戻る（古いファームは常に 0）。Pi の `io_node` はこの間 ARM を通さない（`--no-heartbeat` で動かすときを除く） |
| 26 | `auto_stop_blind` | **ARM 中に LiDAR も前後の超音波も使えず、自動停止が何も検知できない状態が3秒続いている**。超音波は計測が確定しているか（無反射でも ECHO は返る）で判定する。古いファームは常に 0 |
| 27-31 | — | 予約（0 を送ること） |

- **bit5/6/16/17/18/19/20 は「有効/無効」ではなく「今まさに介入・動作しているか」**を返す。
  GUI で介入タイミングが見えると TC/TV のチューニングが劇的に楽になる。
  bit16/17/18/19 も同じ考え方で、**「なぜ急に減速・固定・点滅したのか」を後から説明できる**
  ようにするためにある（有効/無効そのものは Pi が送った `COMMAND.flags`/`flags2` を見れば
  分かるので返さない）。
- **bit10 は旧 `calib_done` を改名したもの。** 意味も変わり、
  「**今この起動で実行した**」ではなく「**Flash に有効な原点が保存されている**」となった。
  CALIB モードを廃止したため、起動のたびに実行するものではなくなったことによる。
- **bit11/12 はリセットするまで消えない。** bit13/14 は電圧が復帰すると消える。
- **bit15 が立っている間、Pi が `arm` を要求しても bit2 は立たない。これは仕様であり
  Pi 側で FAULT 扱いにしてはならない。** GUI には「駆動電源ラッチ中 — 電源を入れ直してください」
  と表示し、通信 FAULT と区別すること。
- 低電圧警告の条件は STM32 側で 8.0V 未満が 1秒継続、復帰は 8.8V（ヒステリシス付き）。

### 5.5 `md_status[i]` (u8) ビット定義

MD が返す status バイトをそのまま転送し、STM32 側で上位ビットを付加する。

| bit | 名称 | 出所 |
|---|---|---|
| 0 | `running` | MD が**受理済みの指令を実行中**（停止モードでない）。「回転中」ではない |
| 1 | `voltage_out_of_range` | MD 側で電源電圧異常を検知 |
| 2 | `overheat` | MD 側で過熱を検知 |
| 3 | `overcurrent` | MD 側で過電流を検知 |
| 4 | `comm_ok` | **STM32 が付加**。直近 100ms で MD からの状態フレームを受信できている |
| 5 | `limit_synced` | **STM32 が付加**。MD が適用中のトルク上限が指令値と一致 |
| 6 | `uncalibrated` | MD のエンコーダが未校正。MD は制限値を受け付けず動かない |
| 7 | — | 予約 |

**`comm_ok = 0` のとき、そのモータに関する `temp` / `motor_current` / `wheel_speed` /
`torque_cmd` の値を信用してはならない。**
MD が死んで無言になると status は最後の値のまま固まるため、
このビットが無いと過去の正常値を見続けることになる。

Pi 側は `comm_ok = 0` を検出したら該当値を GUI 上でグレーアウトし、FAULT へ遷移する。

### 5.6 `COMMAND` (0x10) — LEN = 15

| offset | size | type | field | 単位 |
|---|---|---|---|---|
| 0 | 1 | u8 | `mode` | 0=DISARM / 1=MANUAL / 2=AUTO（**3 は予約・送らない**） |
| 1 | 1 | u8 | `flags` | §5.6.1 |
| 2 | 2 | i16 | `target_speed` | 0.001 m/s（負 = 後退）**`brake`／`torque_mode` 中は無視される** |
| 4 | 2 | i16 | `target_steer` | 0.0001 rad **路面舵角**（反時計回り正 = 左旋回） |
| 6 | 2 | u16 | `accel_limit` | 0.001 m/s²（加減速のレートリミット） |
| 8 | 2 | u16 | `steer_rate_limit` | 0.001 rad/s（舵角のレートリミット） |
| 10 | 2 | u16 | `brake_torque` | 0.0001 N·m **後輪各輪**。`0` = 未指定（最大で制動） |
| 12 | 2 | i16 | `target_torque` | 0.0001 N·m **駆動トルク直接指令**（負 = 後退方向）。`torque_mode` 時のみ有効 |
| 14 | 1 | u8 | `flags2` | §5.6.5 / §5.6.6 |

**合計 15 バイト**（フレーム 22 バイト、100Hz で 2.20 kB/s）

時刻同期は `PING` / `PONG` に分離したため、`COMMAND` に Pi 側タイムスタンプは含めない。

#### 5.6.1 `flags` (u8) ビット定義

| bit | 名称 | 意味 |
|---|---|---|
| 0 | `arm` | 駆動電源投入を要求 |
| 1 | `brake` | ブレーキを掛ける（強さは `brake_torque`）。**`torque_mode` より優先** |
| 2 | `horn` | クラクション。**立てている間ずっと鳴る** |
| 3-4 | `light_mode` | 0=`OFF` / 1=`DAYTIME` / 2=`NORMAL`（3 は予約・送らない） |
| 5 | `passing` | パッシング |
| 6 | `torque_mode` | 立っている間 `target_speed` を無視し `target_torque` を直接掛ける |
| 7 | `auto_stop` | 立っている間、進行方向の動的停止距離 `d_stop` 未満なら STM32 が自動で最大制動 （判定は LiDAR 主・超音波補助。§5.6.4） |

| `light_mode` | 前照灯 | 尾灯 |
|---|---|---|
| 0 `OFF` | 消灯 | 消灯 |
| 1 `DAYTIME` | 減光（duty 0.1） | 薄点灯（duty 0.1） |
| 2 `NORMAL` | 全光量 | 薄点灯（duty 0.1） |

- ブレーキランプは `light_mode` と独立で、**`brake` が立っている間は尾灯が全光量**になる。
  加えて STM32 は、**`brake` を立てなくても実際の減速度が 1.5m/s² を超えたら点け、0.5m/s² を下回ったら消す**
  （最短 0.3s 点灯。車速指令を下げたときの減速でも点く。しきい値はファームの定数
  `VEHICLE_BRAKE_LIGHT_*`、2026-10-06）。高速点滅（緊急制動表示）は `brake` のときだけ。
- `passing` は立てている間、`light_mode` に関わらず**前照灯だけ**が全光量になる。
  **尾灯は連動しない**（消灯状態でのパッシングが後続車から制動と紛らわしくなるため）。
  離せば `light_mode` の状態へ戻る（モードは STM32 側で保持されている）。
- 緊急停止発動時と `COMMAND` 途絶時は、`horn` と `passing` が STM32 側で強制解除される。

#### 5.6.2 `brake_torque` の約束

- **`0` は「制動トルク 0」ではなく「未指定」**で、STM32 側の最大値で制動する。
  `accel_limit` / `steer_rate_limit` と同じ約束であり、**フィールドの埋め忘れで
  ブレーキが効かなくなる方が危険**なのでゼロ値を安全側に倒してある。
  Pi 側は正の指定が丸めで 0 に落ちないよう最小 1 LSB に留める（`msgs/convert.py`）。
- STM32 側の上限は **0.13 N·m/輪**（`DRIVE_MAX_BRAKE_TORQUE_NM` = `DRIVE_MAX_TORQUE_NM`。`LIMITS.max_torque_nm`
  で届く）。超えた値は黙ってクランプされるので、Pi 側でも同じ上限を持つ（`msgs.convert.MAX_BRAKE_TORQUE_NM`。
  `LIMITS` を受け取っていればそちらでクランプする）。
- **`brake` が立っている間、車速 PI ループは完全に迂回される。** MD を制動モードに切り替えて
  指定トルクを直接掛ける（「目標車速 0」を与えるだけではない）。離すと目標車速 0 から `accel_limit` に従って加速し直すので、
  ブレーキ中に `target_speed` を保持し続けても離した瞬間に飛び出すことはない。

#### 5.6.3 `torque_mode` / `target_torque` の約束

- ラジコン（MANUAL）モードで、速度指令ではなく**駆動トルクを直接指令**したい要望に対応する。
  `brake_torque` と同じ理由（値域が小さい）で `target_torque` のスケールも 0.0001 N·m/LSB。
- **`target_torque` に `0` の特別な意味はない。** `brake_torque` の「0=未指定=最大制動」とは
  違い、そのまま「駆動トルク 0」として扱ってよい。丸めで 0 に落ちても危険側には振れない。
- **上限は 0.13 N·m**（`DRIVE_MAX_TORQUE_NM`。モータ物理上限 0.1557 N·m 未満）。超えた値は STM32 側で
  クランプされる。Pi 側にも同じ上限を持つ（`msgs.convert.MAX_TARGET_TORQUE_NM`。`LIMITS` 受信後はそちら）。
- **`torque_mode` が立っている間、車速 PI ループは `brake` と同様に迂回**し、
  `target_torque` を各輪へ直接掛ける（`target_speed` は無視）。
  **`brake` と `torque_mode` が同時に立っていたら `brake` が優先**（制動は駆動より安全側）。
- TC（トラクションコントロール）/TV（トルクベクタリング）が `torque_mode` 中の
  `target_torque` にどう関与するか（そのまま通すか、TC が空転抑制のため減衰させるか）は
  **未確定**（§14 参照）。STM32 側の実装方針が決まり次第この節を更新する。

#### 5.6.4 `auto_stop` の約束

**STM32 単独で完結する障害物への自動停止。** Pi は許可（bit7）を毎周期出すだけで、
判定にも制動にも関与しない。**Pi 側で `us_front`/`us_rear`/LiDAR を見て速度を落とす
二重制御を書かないこと**（どちらが止めたのか分からなくなる）。

- 立っている間、**進行方向**の障害物までの距離が動的停止距離 `d_stop` 未満になると、
  STM32 が `target_speed`/`target_torque` を無視して**最大制動トルクで停止**する。
- **`d_stop` は固定値ではない**（前後超音波の固定20cm未満ではない）。
  `d_stop = v・t_delay + v²/(2・a_max) + margin` で、`v` は進行方向の実走行速度の
  絶対値。`t_delay`/`a_max` は STM32 側の定数（`VEHICLE_AUTO_STOP_DELAY_S` = LiDAR の1回転 0.1s ＋
  MD のトルクの立ち上がり 4.5ms、`VEHICLE_AUTO_STOP_DECEL_M_S2` = 同定した制動の減速度 2.47m/s²
  （`[dynamics] brake_decel_m_s2`）。駆動の加速度上限とは独立）。走行速度が上がるほど `d_stop` は伸び、早い段階で作動する。
  `margin` だけが `CONFIG_SET`（`param_id = 0x0060`）でcm単位の連続値として直接
  指定できる（§5.8.3）。
- **判定は3つのセンサ条件の OR**（いずれか1つでも成立すれば作動）:
  1. **LiDAR（主センサ）**: 進行方向の**矩形**（前方 `d_stop`＋LiDAR の取付オフセット以内、
     左右は半車幅 9cm＋余裕 6cm の ±15cm）のうち、直近300ms以内に更新された点が
     **3点以上**あれば障害物ありと確定する（1点だけの反射ノイズを弾く設計）。
     扇形にすると遠方ほど幅が広がり、コースの壁で走行中に誤って止まるため矩形にしてある。
  2. **超音波（フォールバック）**: LiDAR の進行方向 ±89° に直近300ms以内のデータが1点も無い
     （死角・センサ不調）場合に限り、超音波の距離を `d_stop` と比較する。
  3. **超音波（近接フェイルセーフ）**: LiDAR の結果によらず、超音波が **5cm未満**を
     検知したら常に作動する（LiDAR の最短測距距離より低い死角・バンパー直下等を補う）。
- **進行方向の判定**は `torque_mode` が立っていなければ `target_speed` の符号、
  立っていれば `target_torque` の符号で行う。`>= 0`（前進・停止）なら前方、
  負（後退）なら後方**だけ**を見る。**逆方向は見ない**ので、前方に障害物があっても
  `target_speed` を負にすれば後退で抜けられる。
- 超音波が検知不能（`ULTRASONIC_NO_ECHO`、検知範囲外）のときはそのセンサ条件は
  作動しない。**`us_front`/`us_rear` の `0 = 無効` を「距離 0」と読まない**のと
  同じ理由で、「見えていない」を「近い」に倒さない設計になっている。
- **`brake` (bit1) と同時に立っている場合は `brake` が優先**され、制動トルクは
  `brake_torque`（未指定なら最大）を使う。`auto_stop` 単独での作動時は
  **常に最大制動トルク**（`brake_torque` の値は見ない）。
  優先順位は **`side_brake` > `brake` > `auto_stop` > 通常指令**（`torque_mode` 中の
  TC/TV と同じ経路。`side_brake` は §5.6.5）。
- **ラッチしない。** 障害物が離れて `d_stop` を上回れば、その周期で自動的に解除される。
  どのセンサ条件にもヒステリシスは無いので、境界付近ではチャタリングし得る。
  壁に詰める作業のようにそれが許容できない場面では、Pi 側（GUI の設定パネル）で
  `auto_stop` を切るか、`margin` を小さい値まで下げること。
- **DISARM はされない。** これは停止手段ではなく衝突緩和であり、E-Stop・DISARM・
  `COMMAND` 途絶とは別系統である。
- **実機での動作検証は未了（2026-08-25）。** `t_delay`/`a_max`/LiDAR点数しきい値/
  超音波5cmフェイルセーフはいずれも実測前の値であり、誤作動・未作動が出た場合は
  一旦 `auto_stop` を切って様子を見ること。

#### 5.6.5 `flags2` (u8) ビット定義・`side_brake` の約束

| bit | 名称 | 意味 |
|---|---|---|
| 0 | `side_brake` | 立てている間、**速度に関わらず即座に**後輪モータを位置制御へ切り替えて機械的に固定（サイドブレーキ／パーキングロック） |
| 1 | `winker_left` | 左ウィンカー点滅を要求（§5.6.6） |
| 2 | `winker_right` | 右ウィンカー点滅を要求（§5.6.6） |
| 3 | `launch` | ローンチコントロール（§5.6.7） |
| 4-7 | — | 予約（0 を送ること） |

- **`side_brake` は既存の `flags` bit1（`brake`）より優先される。** `brake` は速度PI
  ループを迂回して制動トルクを掛けるだけなので惰性で多少動くが、`side_brake` は
  後輪の目標を機械角へ切り替えて**その場に固定**する点が異なる。
- **停止していなくても即座に切り替わる。** `auto_stop` のような距離判定は挟まない。
  走行中に誤ってこのビットを立てると急激な挙動になり得るため、**Pi 側の指令生成
  ロジックで走行中に誤って立てないよう注意すること**。
- Pi 側が明示的にこのビットを下ろすまで有効なまま（`brake` と同様、単発ではなく
  「立てている間ずっと」効く連続コマンド）。
- MD の状態やフレームが無効（給電直後など）で実際に角度を保持できていない場合でも、
  通常の駆動系は自動的に最大制動側へフォールバックする。**実際に位置制御へ切り替わり
  固定できたかどうか**は `TELEMETRY.flags` bit17（`side_brake_active`、§5.4）で確認する。
- **実機での動作検証は未了（2026-08-28）。** 特に「速度に関わらず即座に位置制御へ
  切り替わる」仕様のため、走行中に誤って `flags2` bit0 を立てないよう Pi 側の指令生成
  ロジックで注意すること。

#### 5.6.6 `winker_left` / `winker_right` の約束

**自律走行（AUTO）中に右左折・車線変更の意思表示ができないという実装漏れ**
（`Lighting_SetWinker()` 相当の機能が STM32 側に存在するのに `COMMAND` の解釈側から
呼ばれていなかった）への対応。`light_mode`/`horn`/`passing`（`flags` bit2-5）と同じ
**灯火系**であり、後輪モータの励磁とは無関係なので、`brake`/`side_brake` と違って
**未 ARM でも効く**（Pi 側 `command_from_cmd` は灯火系を `arm` と独立に組む）。

- **`winker_left`/`winker_right` は独立ビット。両方立てるとハザード**（左右同時点滅）
  として扱う。専用のハザードビットは設けない（4状態が2ビットの組み合わせで尽くせるため）。
- **点滅そのものは STM32 側の責務**（周期・位相は STM32 内部で持つ）。Pi は「点灯を
  要求しているか」を送るだけで、点滅のタイミングは関与しない（`speed`/`brake_torque`
  と同じ「Pi は意思だけ、実行は STM32」の原則）。
- Pi 側は `side_brake` と同じく**トグル**で送る（キー・パッドの押下状態からではなく、
  GUI の状態を毎周期そのまま送り続ける）。曲がり終わったら明示的に OFF にすること。
  自動で転舵完了を検知して消灯する機構は無い（実車のウィンカーレバーの自己復帰に
  相当する機能は無い。今回は付けない）。
- **実際に点滅しているか**は `TELEMETRY.flags` bit18/19（`winker_left_active`/
  `winker_right_active`、§5.4）で確認する。他の「介入中」ビット（`tc_active` 等）と
  同じ考え方——要求と実行状態を分けることで、球切れ等で光っていない状態も
  区別できる余地を残す（球切れ検知自体は本版のスコープ外）。
- **`COMMAND.flags2` との単純な並行ビットという関係は、`brake`/`auto_stop`/
  `side_brake` のような優先順位という意味では成立する（互いを上書きしない）。**
  ただし **STM32 側は独自に、`fault_drive_undervoltage`（`flags` bit13、駆動系
  バッテリー電圧低下・遮断はしない警告）が立っている間、`winker_left`/`winker_right`
  の要求内容に関わらず強制的にハザード（両方点滅）にする**（STM32 側実装）。周囲への異常告知を優先する安全設計であり、
  Pi 側が明示的にウィンカーを OFF にしていても、この間は `winker_left_active`/
  `winker_right_active` が両方 True のまま固定される。**バグではない。**
  ウィンカー単体の動作（片側だけの点滅）を確認したいときは、まず駆動系バッテリー
  電圧を 8.8V 以上まで回復させ、`fault_drive_undervoltage` が自動クリアされた
  状態で試すこと（§5.4 のヒステリシス条件）。ブレーキランプ（`brake` 連動）・
  パッシング（`passing`）とは独立に点滅する。

#### 5.6.7 `launch`（`flags2` bit3）の約束

| bit | 名称 | 意味 |
|---|---|---|
| 3 | `launch` | 立っている間、車速指令の、目標が車速より大きく離れた加速（発進）をローンチコントロールで行う |

車速指令（`torque_mode`・`brake`・`side_brake` でない）の加速は、STM32 が目標車速を `accel_limit`（0 なら既定の 3.0m/s²。上限は掛けない）で
ランプさせ、車速PIがそれを追う。PIは偏差が溜まるまでトルクが出ないので、グリップの限界のトルクに届くまで
約0.3秒かかる。`launch` が立っている間、目標が車速より大きく離れた加速では、STM32 がランプとPIを迂回して**全開のトルクを要求し、TC に
グリップの限界へ絞らせる**（= `torque_mode` の全開と同じ加速）。

- **始める**: `launch` が立っている・`target_speed` が車速より 0.5m/s 以上速い（後退も同じ）・目標と逆向きに
  0.3m/s 以上で動いていない・TC が有効（`param_id` `0x0010`）。**車速は問わない**（上位は停止からだけでなく、
  低速で経路に乗ってから要求することがある）。徐行の指令や、上位が自分で目標を刻む加速では始まらない
- **終える**: 車速が `target_speed` の 0.05m/s 手前に届いた／`launch` が下りた／`target_speed` が小さく・逆向きに
  なった／`brake`・`torque_mode`・`side_brake`・フェイルセーフ／3秒経った。終えたら車速PIへ戻り、今の車速から
  残りをランプで詰める（積分は `LAUNCH_EXIT_TORQUE_NM` から始める）
- **1回の要求で1回だけ。** `launch` を下ろす・制動する・止まって惰行する、のどれかでまた使える
  （壁に当たって届かずに時間切れしたあと、止まったまま全開を繰り返さないため）
- **`target_speed` は「そこまで全開で加速してよい速度」になる。いつ立てるかは Pi 側が決める**:
  - **手動操作（今はこちらだけを使う。2026-10-10）**: GUI の設定「ローンチコントロール」（既定 ON）。実車と同じ手順で、
    **止まった状態（0.3m/s 未満）でブレーキとアクセルを両方踏む（準備）→ ブレーキを離す（発進）**。キーボードは
    Space＋W/S、パッドは L2＋R2（9割以上）。発進中、GUI は自分のランプ（加速・発進キック・MT の `mtAccel`）を飛ばして
    目標速度を上限（`maxSpeed`、MT はそのギアの上限）へ直接置き、`launch` を立てる。アクセルを離す・ブレーキを踏む・
    車速が目標に届く・STM32 が発進を終える、で下ろす。手順を踏まない発進は従来どおり。速度制御と MT で働き、
    トルク制御は対象外（元からランプが無い）。状態はラジコン画面のランプ（LC＝準備／LAUNCH＝発進中）
    （`gui/src/input/useDriving.ts`）
  - **自律走行**: planner の `launch` パラメータ（`slam2d_raceline`・`slam2d_route`、**既定 0＝使わない**）。1 にすると
    **発進のときだけ**——車速が 0.3m/s 未満になってから経路の速度に届くまでの間で、経路に乗っていて（乗るまでは
    `join_speed` で走る）、前が空いていて、舵がほぼ真っすぐ（0.12rad 未満）のとき——立てる。周回中のコーナーの
    立ち上がりでは立てない。AUTO では GUI の値は使わない（`telemetry_node._merge_auto`）
  - TC が保つスリップ率（`tc_slip_target`）では横グリップが4割ほどしか残らないので、舵を切った加速には向かない
- 実際に発進中かは `TELEMETRY.flags` bit24 `launch_active`

#### 設計意図

- **`target_speed` は「目標速度」であり、目標加速度ではない。**
  `accel_limit` は「その目標速度へ向かうときの加減速の上限」を意味する。
  速度制御ループ（PI制御）は STM32 側に閉じており、Pi は PWM デューティを一切知らない。

- **`target_steer` はモータ機械角ではなく路面舵角。** STM32 側でリンク比を掛けて変換する。

- **`steer_rate_limit`** は舵角の急変を防ぐ。停車中の据え切りで MD ステアが過熱するのを
  抑える目的もある（`temp[2]` の監視と併せて使う）。

- **`mode` は Pi 側の要求であり、STM32 は拒否できる。**
  実際に採用されたモードは `TELEMETRY.flags` bit0-1 で返る。
  `mode = 3` を送ってはならない（STM32 は無視して現在のモードを維持する）。
  ただし **`drive_power_locked` による `arm` 拒否は正常動作**であり FAULT にしない（§5.4）。

- **`COMMAND` が 100ms 途絶したら STM32 は自動ブレーキ。**
  100Hz 送信に対して 200ms は 20発の取りこぼしを許すことになり緩すぎる。
  3 m/s なら 60cm 進んでからブレーキがかかる計算になる。100ms（10発）とする。
  **緊急停止時・途絶時とも最大制動トルク（現在は 0.13 N·m/輪。STM32 の
  `DRIVE_MAX_BRAKE_TORQUE_NM`）を直接掛ける**（速度 PI 任せにしない）。**停止距離が短くなる。**
  舵角は最後の指令値のまま保持される（直進に戻すと車体が予期しない方向へ動くため）。

### 5.7 `PING` (0x12) — LEN = 4 / `PONG` (0x06) — LEN = 12

時刻同期専用の往復。**STM32 は `PING` を受け取ったら最優先で即座に `PONG` を返す**
（次の定期送信を待たず、送信キューの先頭に割り込ませる）。

**`PING`**（Pi → STM32）

| offset | size | type | field |
|---|---|---|---|
| 0 | 4 | u32 | `ping_id`（Pi が採番する連番） |

**`PONG`**（STM32 → Pi）

| offset | size | type | field | 取得タイミング |
|---|---|---|---|---|
| 0 | 4 | u32 | `ping_id` | 受信した値をそのままエコー |
| 4 | 4 | u32 | `t_ping_rx_us` | **UART IDLE 割り込みで、PING 最終バイト到着の瞬間** |
| 8 | 4 | u32 | `t_pong_tx_us` | **送信開始割り込みで、1バイト目が線に出た瞬間** |

**合計 12 バイト**

**タイムスタンプの取得タイミングは精度に直結する。**

- `t_ping_rx_us` をメインループで取ると、ループ周期分のジッタがそのままオフセット推定の
  バイアスになる。必ず割り込みで取る。
- `t_pong_tx_us` を「送信キュー投入時」に取ると、**送信中のフレーム（LiDAR セクタ1個で 0.76ms）が
  終わるまでの待ち**が T3 以降の非対称遅延になる。**4タイムスタンプ方式でも除去されず、オフセットに
  その半分のバイアスが乗る。** STM32 は PONG を最優先キューに積み、DMA を起動する直前に
  `t_pong_tx_us` を書き込んで CRC を計算し直す（`ras_link.c` の `PumpTx`）。

### 5.8 `CONFIG_SET` (0x11) / `CONFIG_GET` (0x13) / `CONFIG_ACK` (0x03)

```
CONFIG_SET : [param_id : u16][value   : f32]                 = 6 B   (Pi → STM32)
CONFIG_GET : [param_id : u16]                                = 2 B   (Pi → STM32)
CONFIG_ACK : [param_id : u16][applied : f32][result : u8]    = 7 B   (STM32 → Pi)
```

`CONFIG_SET` / `CONFIG_GET` のいずれに対しても `CONFIG_ACK` が返る。

`result` の値:

| 値 | 意味 |
|---|---|
| 0 | OK |
| 1 | 不明な `param_id` |
| 2 | 範囲外（`applied` にクランプ後の値が入る） |
| 3 | 現在のモードでは変更不可 |

#### `CONFIG_GET` を追加した理由

`applied` は書き込んだときしか返らないため、**GUI 起動時に実機の現在値を同期できなかった**。

> **Pi 側の実装**: `io_node`（`raspi/nodes/io_node.py`）は接続時と STM32 の再起動を検出したときに、ON/OFF 系
> （`0x0010`/`0x0020`/`0x0050`/`0x0070`/`0x0090`）と自動停止のマージン（`0x0060`）を `CONFIG_GET` で聞き直し、
> 以降は GUI の操作に応じて `CONFIG_SET` を送る。調整パラメータ（§5.8.4）と `[control]` に書いた ON/OFF は
> `ControlParamSync` が送って確かめる。`MAX_SPEED` 等は §5.8.1 の理由により送らない。

#### 設定は Flash に永続化しない（揮発）

**`CONFIG_SET` の値は RAM 上のみ。STM32 は Flash に書かない。**

```
電源投入   →  STM32 は安全側のデフォルト値で起動
           →  Pi が接続時に CONFIG_GET で現在値を読む
           →  Pi が config/vehicle.toml の [control] の値を CONFIG_SET で push
           →  以降、Pi の値が正
```

設定値の single source of truth を git 管理下のファイルに一元化するため。
STM32 だけに値が残ると、「誰も知らない古い設定が残っていて挙動が変わる」という
再現困難な問題を生む。

**STM32 が Flash を使っているのはステアリング原点と IMU キャリブレーションのみ**であり、
これらは STM32 でしか測れない値なので Flash に持つのが正しい。

> **`CONFIG_SAVE` は無い。** 暗黙に毎回 Flash へ書くのは書き換え寿命の点で避ける。
> 永続化が必要になった時点で別コマンドとして追加する（`0x14` は `VERSION_REQ`）。

#### 5.8.1 なぜ `MAX_SPEED`/`MAX_ACCEL`/`MAX_STEER` を Pi から送らないか

`CONFIG_SET` は Flash に永続化されないため、送っても STM32 の次回リセットで既定値へ
戻ってしまう。RC モードごとに動的にこの上限を変えたい具体的なユースケースも今のところ
無いため、**Pi 側からは意図的に送信しない**方針にした（2026-08-19）。STM32 側は自前の
既定値を単独の権威として持ち続ける前提。動的な上限変更が必要になった時点で改めて検討する。

> **現行**: STM32 側がこの3つの `param_id` 自体を廃止しており、`RAS_CONFIG_UNKNOWN_PARAM` を返す。
> Pi 側は送っていない。

**`param_id 0x0040` — LiDAR 出力フォーマット（enum）**

| 値 | 送信される TYPE | 帯域 |
|---|---|---|
| **0（既定）** | `0x01` `LIDAR_SECTOR` | 9.12 kB/s |
| 1 | `0x05` `LIDAR_SECTOR_I` | 12.7 kB/s |
| 2 | `0x09` `LIDAR_SECTOR_C` | 5.52 kB/s |

**bool を2本（強度 on/off + 圧縮 on/off）にしない理由**:
「圧縮 かつ 強度付き」という**第4の組み合わせが表現できてしまい、未実装のまま
指定される余地が残る**ため。enum なら不正な状態を型で排除できる。

**走行中でも `CONFIG_SET` で切り替え可能。** GUI から試せるようにしておくこと。

#### 5.8.2 片輪浮き対策（Wheel Lift Guard、`param_id = 0x0050`）

後輪が段差等で片側だけ浮く（接地荷重ゼロ）と、その車輪だけモータが無負荷で回転数を
急激に張り上げる問題への対策機構。**既存の TC 本体（`0x0010`）とは独立**に動作し、
「TC だけ OFF」「片輪浮き対策だけ OFF」「両方 OFF」を個別に指定できる。

- 有効時は後輪左右の速度差（エンコーダで検知される差）が閾値を超えると、浮いている方
  （速度が高いと推定される方）だけにトルク上限を絞る。正常な接地側は絞らない
- 加えて後輪角速度が物理的にあり得ない絶対値（`DRIVE_MAX_SPEED_M_S` の1.5倍）を
  超えたときは、左右差の判定結果に関係なく即座にその車輪だけトルク上限を0にする
  最終防波堤を持つ
- 無効にすると、この機構によるトルク上限の絞り込みは一切行われない（TC 本体が有効なら
  そちらのスリップ判定ベースの絞り込みは引き続き効く）
- 設定はエンジン起動時・`COMMAND` 未受信中は既定（有効）に戻る。`COMMAND` が届いている
  間は毎周期、直近に `CONFIG_SET` で設定された値を適用し続ける
- **実機での動作検証は STM32 側で未実施。** しきい値（後輪左右速度差の異常検知・絶対
  車輪速上限）は実測前の暫定値であり、誤介入等が起きた場合は一旦 OFF にして切り分ける
  ことを推奨する

#### 5.8.3 自動停止の安全マージン（`param_id = 0x0060`, `auto_stop_margin_cm`）

`auto_stop`（§5.6.4）が使う動的停止距離 `d_stop = v・t_delay + v²/(2・a_max) + margin`
のうち、**`margin`（安全マージン）だけ**をcm単位の連続値として直接指定する。
`t_delay`/`a_max` は STM32 側の固定定数で、物理項（速度に応じて伸びる分）は
`margin` の値に関係なく一定。

| 値 | 意味 |
|---|---|
| 0.0-100.0（f32、cm単位） | 範囲。**既定 15.0** |

- `CONFIG_SET`/`CONFIG_GET` の `value`/`applied` はそのまま cm 単位の f32
- `applied` に実際に適用された値が入る。0.0〜100.0 の範囲外を送るとクランプして適用し、
  `result` は `RAS_CONFIG_OUT_OF_RANGE`（2）になる
- 走行中でも `CONFIG_SET` で切り替え可能
- 停車中（`v = 0`）は
  `margin` のみが効き、既定の15.0cmで作動する。走行中は速度が上がるほど `d_stop` が
  伸び、早い段階で作動する
- **実機での動作検証は未了（2026-08-25）。** `t_delay`/`a_max` の値自体（制御側への
  流用）・LiDAR点数しきい値・超音波5cmフェイルセーフも含め実測前の値であり、誤作動・
  未作動が起きた場合は一旦 `auto_stop` を切って STM32 側に一報すること

#### 5.8.4 足回りの制御の調整パラメータ

TC・ABS・片輪浮き対策・TV のゲイン・しきい値を実行時に読み書きする。**ON/OFF（`0x0010`/`0x0020`/
`0x0050`/`0x0070`）とは別**で、こちらは連続値。

- **名前・`param_id`・範囲の唯一の定義は STM32 側 `src/control/control_params.h` の表。** 表の「既定値」列は
  **上位が送るまでの仮置き**（各範囲の下限＝何もしない値。ステアのリンクだけ恒等の 1・0）で、本物の値ではない（★v0.23）
  `protocol.toml` の `[params]` はその `param_id` を写したもの（食い違いは `tools/ctrl_tune/tests` が検出）
- 範囲外の値は STM32 が範囲内へ丸め、`CONFIG_ACK.result = 2`（範囲外）・`applied` = 丸めた後の値を返す。
  非数は仮置きの値になる
- **Flash には保存しない。** 値の唯一の定義は Pi 側 `config/vehicle.toml`（`[control]`。車速PI の `speed_kp`・`speed_ki` だけ
  `[dynamics]`）。**全項目が揃っていなければ io_node は読み込みをエラーにして ARM を通さない**（STM32 に値が無いため）。
  TC・TV などの ON/OFF（`tc_enable`・`tv_enable`）も `[control]` に書いて送る（STM32 の既定は無効）
- **Pi 側の手順**（`raspi/core/control_params.py` の `ControlParamSync`）:
  1. 接続したら全項目を `CONFIG_SET` で送り、`CONFIG_ACK.applied` が送った値と一致するまで 0.3s ごとに再送
  2. 一致した後も、0.5s ごとに1項目ずつ順番に `CONFIG_GET` で読み戻す。1つでも食い違えば STM32 だけが
     再起動して既定値へ戻ったと見て、全項目を送り直す（`diag/link` の `control_params_drift` が増え、io_node は
     入り直すまで ARM を通さない）。Pi が送る値を変えたとき（GUI の ON/OFF・同定の一時的な上書き）は増えない
  3. STM32 の再起動を検出したら（`t_us` の後退）最初からやり直す
  4. 結果は `diag/link` の `control_params_status`（`ok`/`pending`/`mismatch`/`unsupported`/`invalid`/`none`）と
     `control_params`（STM32 が答えた値）。GUI の「設定 → 走行アシスト」に出る
- **一時的な上書き**: 同定の試験（`raspi/auto/sysid_wheel.py` など）は `AutoState.fw_overrides` →
  `DriveCmd.fw_overrides` に名前と値を書く（調整パラメータ全部と `tc_enable`/`tv_enable`/
  `wheel_lift_guard_enable`/`abs_enable`）。io_node は**その指令が届いている間だけ**入れ、届かなくなったら
  元の値へ戻す（試験が中断しても TC を切ったままにならない）
- `0x002A`（`TV_TEST_MOMENT_NM`）は同定用（**今これを使う試験は無い**——TV の同定は 2026-10-05 に外した。
  STM32 側の機能は残っている）: 0 以外の間、STM32 は TV の配分を止めてこのヨーモーメント
  だけを出す。`[control]` には書かない（上書きでだけ使う）
- **TV は荷重比例の配分**: `左右差 (右−左) = 総駆動トルク × clamp(TV_LOAD_GAIN_S2_PER_M × 車速 ×
  ヨーレート, ±TV_MAX_RATIO)`。旋回で荷重の乗る外輪へ多く配り、荷重の抜けた内輪を空転させない。
  車速指令の減速（総トルクが負）では外輪が多く制動する（旋回を戻す向き）。定速の旋回（総トルクがほぼ 0）
  では何もしない。積分を持たず、TC はその後段で各輪を絞るだけ。
  ヨーレート PI にしない理由: 規範に実機の舵の効きの同定値を入れていたので偏差が最初からほぼ 0、
  ヨーモーメント→ヨーレートの効きが小さく（0.1N·m で 0.056rad/s）ループゲインが 0.05 しかない、定常の
  ヨーレートは舵の方が約30倍動かせる、回り過ぎの修正は空転している内輪へトルクを足す向きで TC に
  打ち消された（PROGRESS.md 2026-10-08「TV の作り直し」）
- 値を決める手順は `tools/ctrl_tune`（[`development.md`](development.md)「足回りの制御を調整する」）
- **ステアのリンクの換算（`0x0081`/`0x0082`）も同じ仕組みで送る**が、調整値ではなくシステム同定の
  結果: `路面舵角 = gain·x + cubic·x³`、x = ステアモータの角度×0.5（可動範囲 ±30°）。STM32 は指令
  （路面舵角→モータ角、ニュートン法）・報告・`LIMITS.max_steer_rad`・車速の射影のすべてに使う。可動範囲の
  端での傾き `gain + 3·cubic·x²` が 0.3 を下回る `cubic` は STM32 が下回らない値へ丸める（逆変換が一意に
  決まらなくなるため）。丸めたときは `CONFIG_ACK` の `applied` に丸めた値を返し `result=OUT_OF_RANGE` にする
  （`gain` を変えて保持中の `cubic` が丸められたときは `cubic` の保持値だけが変わる。`CONFIG_GET` で読める）。
  **この2つは受けた値を保持するだけで、STM32 が停車して DISARM のときに適用する**（走行中に換算が変わると、
  同じ指令でも舵角の意味が途中で変わる）。適用時に `LIMITS` を送り直す。Pi は DISARM のまま送るので通常は即適用される`tools/sysid` が舵角ごとの曲率から求め、`[control]` の2つ・`[dynamics]` の
  `steer_gain`=1/`steer_gain_cubic`=0・最上位の `max_steer` を**そろえて**書く（`toml_update.apply_dynamics`）。
  記録（mcap）の舵角の意味は、そのとき STM32 に入っていた換算で決まる（`/diag/link` の `control_params` に残る。
  解析は記録時の換算の上に重ねる、`analyze.fold_steer_link`）
- **ローンチコントロール（`0x00A1` `LAUNCH_EXIT_TORQUE_NM`）**: 発進（§5.6.7）を終えて車速PIへ戻すときの
  積分の初期値 [N·m、1輪あたり]。発進中は積分を使わないので、0 から戻すと積分が溜まるまで車速が目標より
  `値×2÷DRIVE_SPEED_KP` [m/s] 落ち込む（戻るのに約0.5秒）。その車速を保つのに要るトルク＝`[dynamics]` の
  `rolling_resistance ÷ speed_plant_gain ÷ 2` を `[control]` の `launch_exit_torque_nm` に書く
- **車速PIの加速度フィードフォワード（`0x00B1` `SPEED_FF_NM_PER_M_S2`・`0x00B2` `SPEED_FF_RR_NM`）**:
  車速PIは偏差が溜まらないとトルクを出せず、車速が目標に約 0.15 秒（＝1÷(車体の利得×Kp)）遅れる。STM32 は
  目標車速を `accel_limit` の傾きで動かしているので、その傾き（時定数 20ms のローパス後）× `0x00B1` と、
  目標車速の向きへ `0x00B2` を PI の出力に足す。制動・トルク指令・ローンチコントロール・停車の惰行の間は
  足さない。値の決め方: `0x00B1` = 1 ÷ `speed_plant_gain`、`0x00B2` = `rolling_resistance` ÷ `speed_plant_gain`

#### 設計意図

**設定を周期 `COMMAND` に混ぜてはならない。**
混ぜると、パケットロスで設定値が化けたまま誰も気づかない状態が発生する。
個別 ID + ack + **`applied` に実際に適用された値を返す**ことで、GUI が常に「実機の真の値」を表示できる。

Pi 側（`ControlParamSync`）は ack が 0.3 秒返らなければ、一致するまで再送し続ける（回数の上限・FAULT は無い。
揃うまでは ARM を通さない）。範囲外で丸められた項目は再送しても同じなので止め、`mismatch` として出す
（送る値を変えれば送り直す）。

### 5.9 `VERSION` (0x07) — LEN = 10 / `VERSION_REQ` (0x14) — LEN = 0

**ファームウェア更新と Pi 側コードの食い違いは必ず起きる。**
バージョン不一致に気づかないまま「原因不明のバグ」を追うのは時間の浪費なので、
リンク確立時に必ず交換する。

**`VERSION_REQ`**（Pi → STM32、LEN = 0）: ペイロードなし
**`VERSION`**（STM32 → Pi、LEN = 10）:

| offset | size | type | field | 備考 |
|---|---|---|---|---|
| 0 | 2 | u16 | `protocol_version` | 上位バイト = メジャー、下位 = マイナー。現行は `0x001A`（`protocol.toml`） |
| 2 | 4 | u32 | `fw_id` | ファームの git short hash 等 |
| 6 | 4 | u32 | `build_epoch` | ビルド時刻（UNIX epoch 秒） |

**合計 10 バイト**

- **要求と応答で TYPE を分けている。**
  Pi 側の初回ドラフトは要求も `0x07`（LEN=0）としていたが、これは
  **「同一 TYPE で LEN が変わる」問題を自ら踏んでおり**（`0x09` を別 TYPE にした理由と矛盾する）、
  `0x01-0x0F` = STM32→Pi という方向規約も崩れてロジックアナライザでの切り分けが難しくなる。
  STM32 側の指摘が正しい。
- STM32 は**起動直後に 3回**（100ms 間隔）`VERSION` を自発送信する。
  ただしこれは補助であり、**Pi はリンク確立時に必ず `VERSION_REQ` を送ること**
  （Pi の起動が遅れていると自発送信は無駄になる）。
- Pi は `protocol_version` が自分の期待値と**完全に一致しない限り ARM を通さない**（メジャー・マイナーを
  区別しない。DISARM を送り続け、通信・表示は続ける。理由は `diag/link` の `arm_inhibit_reason`）。
  `VERSION` を受け取れていない間も同じ。
- `fw_id` / `build_epoch` はログの先頭とテレメトリ記録のヘッダに必ず残す。

### 5.10 `STATS` (0x08) — LEN = 48

1Hz。**上下どちらの線が悪いのかを切り分けるため**の統計。
Pi 側のカウンタだけでは STM32 → Pi の品質しか分からない。

| offset | size | type | field | 備考 |
|---|---|---|---|---|
| 0 | 4 | u32 | `t_us` | このスナップショットの時刻 |
| 4 | 4 | u32 | `rx_frame_ok` | Pi → STM32 で正常受理したフレーム数 |
| 8 | 4 | u32 | `rx_crc_error` | CRC 不一致で破棄した数 |
| 12 | 4 | u32 | `rx_len_error` | LEN が TYPE の期待値と不一致 |
| 16 | 4 | u32 | `rx_unknown_type` | 未知の TYPE |
| 20 | 4 | u32 | `tx_drop` | 送信キュー溢れで破棄した数（主に `LOG`） |
| 24 | 12 | u32×3 | `md_rx_count[3]` | MD 状態フレームの正常受信数 [RL, RR, ST] |
| 36 | 12 | u32×3 | `md_rx_error[3]` | MD 状態フレームの CRC 不一致数 [RL, RR, ST] |

**合計 48 バイト**

#### すべて「累積値」である

「直近1秒の増分」にすると、**`STATS` が1個ロスしたときその1秒分のエラー件数が永久に失われる**。
`odom_dist` を累積で送るのと同じ理屈（§2.2-6）。

`u32` なので 1000件/s でも 49日かかり、実質ラップしない。

#### Pi 側でのレート算出

**連続する2つの `STATS` の差を `t_us` の差で割ればレートが出る。**
途中で `STATS` が落ちても、平均レートとしては正しい値が得られる。

```python
dt = (s.t_us - prev.t_us) & 0xFFFFFFFF          # μs、ラップ考慮
crc_rate = (s.rx_crc_error - prev.rx_crc_error) / (dt * 1e-6)   # 件/s
```

#### 切り分けの指針

Pi 側の `crc_error_count` / `packet_loss_count`（下り側）と並べて GUI に表示する。
**片方向だけエラーが出るのか両方向なのかで、原因の切り分けが変わる。**

| 症状 | 推定原因 |
|---|---|
| Pi 側のみエラー増 | STM32 → Pi の配線 / Pi の受信バッファ溢れ |
| STM32 側（`rx_*`）のみ増 | Pi → STM32 の配線 / Pi 側の送信処理 |
| 両方向で同時に増 | 電源ノイズ、GND ループ、モータノイズの回り込み |
| `md_rx_error` のみ増 | MD 側の配線。UART リンクは無関係 |
| `tx_drop` が増 | 上りの帯域不足。`param 0x0040 = 2` を検討 |

> **提案（任意）**: `u32 lidar_frame_error` を末尾に足して LEN = 52 にしたい。
> `lidar_ok` は「300ms 完全に途絶したか」しか見ておらず、
> **「たまにフレームを落としている」状態が見えない。** 必須ではない。

### 5.11 `LOG` (0x04) — LEN = 1〜128

| offset | size | type | field | 備考 |
|---|---|---|---|---|
| 0 | 1 | u8 | `severity` | 0=DEBUG / 1=INFO / 2=WARN / 3=ERROR |
| 1 | 可変 | char[] | `message` | ASCII、改行なし、NUL 終端なし。空もありうる |

STM32 は本文を 127 文字で打ち切る（スタックの都合。プロトコル上は 254 文字まで載る）。Pi 側は LEN = 0
（`severity` すら無い）を `len_error` として捨てる。

**最低優先度で送信**し、帯域が逼迫したら破棄してよい（破棄数は `STATS.tx_drop` に計上）。
Pi 側は `severity` でフィルタし、既定では WARN 以上のみを GUI に出す。

### 5.12 `LIMITS` (0x0A) — LEN = 16 / `LIMITS_REQ` (0x15) — LEN = 0

**車両の物理的な上限値を STM32 側の権威として Pi に伝える、読み取り専用パケット。**
`MAX_SPEED`/`MAX_ACCEL`/`MAX_STEER`（`param_id 0x0001`-`0x0003`）は廃止済みで STM32 側の固定定数になっているため、
Pi 側がその**実際の値を知る手段**として本パケットがある
（`config/vehicle.toml` の想定値と STM32 の実装値がズレても気づけるように）。

**`LIMITS_REQ`**（Pi → STM32、LEN = 0）: ペイロードなし。応答は `LIMITS` 1回。
**`LIMITS`**（STM32 → Pi、LEN = 16）:

| offset | size | type | field | 備考 |
|---|---|---|---|---|
| 0 | 4 | f32 | `max_speed_m_s` | `COMMAND.target_speed` の上限（`DRIVE_MAX_SPEED_M_S`）。超えると STM32 側でクランプ |
| 4 | 4 | f32 | `max_accel_m_s2` | `COMMAND.accel_limit` に指定できる上限。STM32 は上限を掛けず、ワイヤ（u16×0.001）で表せる最大 **65.535** を返す。`accel_limit = 0` のときの既定の傾きは 3.0m/s²（`DRIVE_DEFAULT_ACCEL_M_S2`） |
| 8 | 4 | f32 | `max_torque_nm` | 1輪あたりのトルク上限。`target_torque`/`brake_torque` 共通（`DRIVE_MAX_TORQUE_NM`） |
| 12 | 4 | f32 | `max_steer_rad` | 路面舵角の上限。原点（直進）からの片側の振れ幅（`Steering_GetMaxRoadWheelAngleRad()`） |

**合計 16 バイト。すべて生の f32（スケール無し）。**

- **読み取り専用。** `CONFIG_SET` のような書き込み手段は無い（`param_id` も廃止済み）
- STM32 は`VERSION`と同じタイミングで**起動直後に3回**（100ms間隔）自発送信する。
  Pi はリンク確立時に `VERSION_REQ` と併せて `LIMITS_REQ` を送り、両方を確実に取る
  （`raspi/nodes/io_node.py` の `handshake()`）
- **実行時に変化しない値**なので、Pi は起動時に一度取得してキャッシュすれば十分。
  以後の毎 `COMMAND` 送信でこのキャッシュ値を読むだけでよい（`_send_command`）
- Pi 側は、RC（MANUAL）・自律走行（AUTO）どちらの指令でも、`LIMITS` を受信済みなら
  **無条件にそちらをクランプに使う。** `--max-speed`/`--max-steer`（Pi 側の設定上限、
  `raspi/setup/install_services.sh` の deploy 引数）は `LIMITS` を**まだ受け取っていない
  間だけ**使うフォールバックで、GUI の `effectiveRange()`（`gui/src/store/ui.ts`）も
  同じ「受信済みならそちらを優先」の方針（「小さい方」にすると、`LIMITS` の方が緩いケースで
  GUI が実測値を見せているのに実車だけ古い値で頭打ちになるため）。モードによらず `IoNode._send_command`
  の1箇所を必ず通るため、送信元を問わず同じ上限が効く
- `LIMITS` が届かない（旧ファームウェア等）場合は Pi 側設定値のみでクランプし、通信は継続する
- `sim/stm32.py`（開発用シミュレータ）も `LIMITS`/`LIMITS_REQ` に対応済み。実機と同じ
  固定値（`DRIVE_MAX_SPEED_M_S`=5.0 等）を返すので、シムでも実機と同じ経路で検証できる
- **実機での動作検証は STM32 側で未実施（2026-08-21時点）。** 特に `max_steer_rad` の
  元になる `STEERING_LINKAGE_RATIO`（モータ機械角→路面舵角の換算比）は実測前の暫定値で、
  実際の路面舵角上限とズレている可能性がある

## 6. 時刻同期（STM32 ⇄ Pi）

SLAM・アクチュエータ遅延の実測・センサ融合のすべてがこれに依存する。
**NTP と同じ 4タイムスタンプ方式**を `PING` / `PONG` で実装する。

### 6.1 測定する2種類の「遅延」を混同しない

| 測りたいもの | 使う仕組み | 時刻同期が必要か |
|---|---|---|
| **エンドツーエンド遅延**（GUI 表示用） | `TELEMETRY.cmd_seq_echo` | **不要**。Pi の時計だけで完結する往復測定 |
| **クロックオフセット**（SLAM・センサ融合用） | `PING` / `PONG` | 必要。これを推定するのが本節 |

責務を分離しているため、`TELEMETRY` にタイムスタンプ交換のフィールドは持たせない。

### 6.2 4タイムスタンプ方式

```
    T1 ── Pi   : PING を送信した時刻              （Pi の時計）
    T2 ── STM32: PING 最終バイトを受信した時刻     （STM32 の時計 = t_ping_rx_us）
    T3 ── STM32: PONG 1バイト目が線に出た時刻      （STM32 の時計 = t_pong_tx_us）
    T4 ── Pi   : PONG を受信した時刻              （Pi の時計）

    往復遅延   delay  = (T4 − T1) − (T3 − T2)
    オフセット offset = ((T2 − T1) + (T3 − T4)) / 2      ※ offset = t_stm − t_pi
```

Pi の実装（`raspi/core/timesync.py`）はオフセットを**逆向き（`offset_ns` = t_pi − t_stm）**で持ち、
STM32 の中点 (T2+T3)/2 と Pi の中点 (T1+T4)/2 を対応点として回帰する。

**`T3 − T2` を引くことで、STM32 側の処理・送信待ち時間が推定から完全に除去される。**
これが 2タイムスタンプ方式（単純な RTT/2）より優れている理由。

ただし**この除去が成立するのは T2/T3 が正確に取れている場合だけ**である。§5.7 の
取得タイミングは理論上の要請ではなく、実測精度に直接効く。

### 6.3 実装上の要点

1. **`delay` が小さいサンプルだけを使う**
   UART の待ち行列や割り込み遅延で伸びたサンプルは推定を汚す。直近 256 サンプル（5Hz で約51秒）のうち、
   `delay` ≤ 最小値×2 + 0.3ms のものを「良い」サンプルとする。

2. **線形回帰でクロックドリフトも補正する**
   `(t_stm, t_pi)` の組を線形回帰し、**切片（オフセット）と傾き（クロック比）の両方**を推定する。
   実機の STM32 の時計は Pi より**約 0.35% 速い**（`drift_ppm` ≈ −3500。故障ではない）ので、傾きを
   推定しないと1秒で 3.5ms ずれる。
   - 良いサンプルの時間スパンが 15 秒に届くまでは回帰しない（短い窓では傾きがジッタで暴れる）。
     それまでは**良いサンプルのうちいちばん新しいもの**のオフセットを使う。それが最新のサンプルより
     1秒以上古ければ（往復遅延が増えたまま続いている）、直近 8 個の中で `delay` 最小のものを使う
   - 回帰は `PONG` が来たときにだけ計算し、**今の窓で回帰できなくなっても最後に成立した回帰で外挿する**。
     往復遅延が増えたまま続く・遅延の小さい点が1つだけ紛れ込む、のどちらでも良いサンプルが古いものだけに
     なり回帰が組めなくなるが、時計の比は変わっていないので外挿で足りる（古い1点のオフセットへ落とすと
     ドリフトのぶん最大約 0.18 秒ずれる）
   - Pi 側の受け手は換算後の時刻が受信より後・200ms 以上古いときは受信時刻で代用する
     （`bus_bridge.py`。`TELEMETRY` と LiDAR セクタで同じ判定）

3. **`PING` は 5Hz。** 起動直後は 20Hz で 3秒ほど打ち、収束を早めてよい。

4. **32bit μs カウンタのラップに注意。**
   STM32 の `t_us` は起動時 0 スタートの 32bit μs カウンタで、**約 71.6 分**でラップする。
   差分計算を必ず符号なし演算で行えばラップをまたいでも正しい値が出る（`(uint32_t)(a - b)`）。
   Pi 側は `TELEMETRY`/`STATS` の `t_us` を見るたびに 64bit へ伸ばす基準を更新し、どの値も基準に最も近い
   周回へ伸ばす。生値が 1 秒以上後退し、直前の値がラップの 2 秒手前でもなければ STM32 の再起動と見て
   時刻同期をやり直す（`TimeSync.resets`。io_node は状態の組み立て・LiDAR・調整パラメータも合わせてやり直す）。

5. 換算後の時刻は、Pi 内部の全メッセージの `t_capture` に入れる
   （単位 ns、Pi の `CLOCK_MONOTONIC` 基準）。

## 7. 送信優先度

```
高  PONG  >  TELEMETRY  >  LIDAR_SECTOR  >  CONFIG_ACK  >  VERSION  >  STATS  >  LOG  低
```

- **`PONG` が最優先である理由**
  **`t_pong_tx_us` を送信開始時点で取ったとしても、PONG が LiDAR セクタの後ろに
  並ぶと T3 以降の経路に非対称遅延が生じ、オフセット推定そのものにバイアスが乗る**。
  PONG は必ず送信キューの先頭に割り込ませること。
- `TELEMETRY` が次点なのは、安全監視と制御に直結するため
- `LOG` は溢れたら破棄する（破棄数は `STATS.tx_drop` に計上）

### 送信待ち時間は約 1ms で有界

優先度キューがあり、かつ**送信中の DMA フレームを途中で中断しない**ため、
`TELEMETRY` が LiDAR に阻まれる最大待ち時間は**送信中の1フレーム分**である。

```
76 B × 10 bit ÷ 1 Mbps = 0.76 ms         （LiDAR セクタ1フレーム）
+ PONG が割り込む場合    ≈ 0.19 ms
────────────────────────────────────
最大でも約 1 ms（250kbps の頃は約 4 ms）
```

**「LiDAR バーストで上りが数十ms滞留する」という状況は発生しない。**
§8 の2段階タイムアウトの根拠として滞留を挙げるのは誤りである。

## 8. エラー処理と統計

| 事象 | 対応 |
|---|---|
| CRC 不一致 | パケット破棄。`crc_error_count++`。同期は維持し、次の SYNC を探す |
| SYNC ロスト | 1バイトずつずらして `0xAA 0x55` を再探索 |
| `LEN` が TYPE の期待値と不一致 | 破棄。`len_error_count++`。**その場で SYNC の探し直しに戻る**（LEN ぶん読み飛ばさない。下記） |
| `SEQ` 欠番 | `packet_loss_count += 欠番数` |
| 未知の `TYPE` | 破棄。`unknown_type_count++`。**その場で SYNC の探し直しに戻る**（`LEN` を信用して読み飛ばさない。ここに来るのは TYPE が化けたか、ペイロード中の偽の SYNC を拾ったときだけ。化けた LEN ぶん最大 257B を待つと、STM32 は 75〜110ms 分の `COMMAND` を失い途絶の自動ブレーキに入りえ、Pi は後続のフレームの受け取りが十数ms 遅れる。両側とも同じ） |
| **`TELEMETRY` が 100ms 途絶** | **Pi → `DEGRADED`**（警告表示。制御は継続） |
| **`TELEMETRY` が 200ms 途絶** | **Pi → `FAULT`**（停止シーケンス） |
| **`COMMAND` が 100ms 途絶** | **STM32 → 自動ブレーキ**（安全の第2層） |
| `md_status[i].comm_ok = 0` | 該当モータの値を無効扱い。継続したら FAULT |
| `protocol_version` の不一致・未受信 | ARM を通さない（DISARM を送り続ける）。通信・表示は続け、`VERSION_REQ` を 1 秒ごとに送り直す |

### `TELEMETRY` 途絶を2段階にする理由

LiDAR バーストによる滞留は理由ではない（§7 のとおり送信待ちは約 1ms で有界）。

**理由は、単発の CRC エラーや一時的なロスで即座に FAULT へ落とさないため。**
100Hz なら 100ms = 10発。ノイズ環境で 10発連続ロスは起こりうるが、
それだけで停止シーケンスに入るのは過剰である。100ms は人間に「怪しい」ことを見せるだけに留め、
実際に止めるのは 200ms（20発）とする。

**下りの `COMMAND` は安全に直結するため一段で厳しく（100ms）する。** この非対称は意図的。

### 統計カウンタを GUI に出すこと

Pi 側の `crc_error_count` / `packet_loss_count` / 実効受信レートと、
STM32 側の `STATS`（§5.10）を**並べて常時表示**する。

パケットロス率は**配線品質とノイズ環境の直接的な指標**であり、「なんとなく調子が悪い」を数値で切り分けられる。
走行中に急にロス率が上がったら、モータのノイズが UART に乗っている証拠。

## 9. 緊急停止ライン（UART とは独立した第1安全層）

UART とは別経路の、ハードウェアレベルの安全機構。
**Pi 側 GPIO6 → STM32 側 PB12。**

### ハートビート方式を採用する

単純なアクティブLow の E-Stop は**フェイルセーフにならない**。
断線するとプルアップで High（= 正常）に戻ってしまい、異常を検知できないため。

```
Pi   : GPIO6 に 100Hz の矩形波を出力し続ける（オープンドレイン推奨）
STM32: PB12 を 1kHz 以上の制御ループでポーリングしてエッジを監視
       エッジが 50ms 途切れたら即ブレーキ + estop_active フラグを立てる
```

**STM32 側は外部割り込み（EXTI）ではなくポーリングで受ける。**
EXTI はライン番号ごとに1ポートしか選べず、PB12 と前方超音波の ECHO (PA12) が
同じ EXTI ライン 12 を使うため共存できない。
エッジ間隔 5ms に対して 1kHz 以上でポーリングすれば 50ms の途絶判定には十分間に合う。
**Pi 側の実装に変更は不要。**

この方式なら、以下すべてを**単一の機構で**検出できる:

1. Pi のフリーズ
2. Pi の電源断
3. 配線の断線・接触不良
4. Pi 側プロセスのクラッシュ

ソフトウェアの生存とハードウェアの導通を、1本の線で同時に保証できる。

### STM32 側の確定挙動（2026-08-07・実装済み）

STM32 側の実装が固まったので、**Pi 側はこの表を前提にしてよい**。ポーリングは 2kHz。

| 項目 | 挙動 |
|---|---|
| 信号 | 100Hz の矩形波。**デューティは問わない**（エッジの有無だけを見る） |
| 駆動方式 | **オープンドレインでよい。基板に外付けプルアップがある** |
| 接続判定 | **エッジを10回（=50ms 分）数えて初めて「Pi が繋がっている」とみなす。** 単発ノイズで接続済みと判定して直後に緊急停止へ落ちるのを防ぐ |
| 未接続時 | ハートビートを一度も見ていない間は**緊急停止を発動しない**（ベンチ確認のため） |
| 途絶時 | 50ms で**ラッチ**し、`TELEMETRY.flags` bit3 `estop_active` が立つ |
| 復帰 | **自動復帰しない。** ハートビートが戻っている状態で**車両側のボタン2を人間が押す**まで解除されない。解除後も、`COMMAND` の `arm` が一度 0 になってから立ち上がるまで ARM しない（`arm` を立てっぱなしの指令で走り出さない） |
| 発動時の動作 | 目標車速0で制動、ハザード点滅。**駆動電源は切らない**（切ると MD が制動をかけられず惰行して停止距離が伸びるため） |

#### Pi 側が守ること

- **E-Stop 解除後は `arm` を一度下ろしてから立て直す。** io_node は `estop_active`（と `drive_power_locked`、
  STM32 の再起動の検出）を見たら、操縦側の `cmd.arm` が一度 False になるまで ARM を通さない
  （`diag/link` の `arm_inhibit_reason`）。STM32 も `arm` の立ち上がりを待つので、どちらか片方だけでも走り出さない
- **出し始めたら出し続ける。** 途中でやめると緊急停止になる。
  逆に言えば、**一度も出さなければ緊急停止は発動しない**ので、
  ベンチ診断では意図的に出さない選択もできる
- **`estop_active` が立っている間は `COMMAND` を送っても一切効かない。**
  リンク断（`health`）とは別の軸なので混ぜない
- GUI に「**E-STOP 発動中 — 車両のボタン2で解除してください**」と明示すること。
  人間が物理操作しに行かないと解除されないため、他の表示に埋もれさせない

### 復帰条件

`estop_active` からの復帰は**必ず人間の明示操作を経由**する。自動復帰させない（原因未解消のまま走り出すため）。

## 10. 安全層の全体像

安全機構は4層。**層ごとに担当と復帰条件が違う。**

| 層 | 機構 | 反応時間 | 復帰 | Pi の扱い |
|---|---|---|---|---|
| 1 | **GPIO ハートビート断**（`estop_active`） | 50ms | 人間の明示操作 | FAULT |
| 2 | **`COMMAND` 途絶**（`uart_timeout`） | 100ms | `COMMAND` 再開で制動は解除。ARM は `arm` が一度 0 になってからの立ち上がりで | DEGRADED → FAULT |
| 3 | **過電流ハード遮断**（`fault_*_overcurrent`, `drive_power_locked`） | 即時 | **電源リセットのみ**（ラッチ） | FAULT。ただし `arm` 拒否は正常動作 |
| 4 | **低電圧警告**（`fault_*_undervoltage`） | 1秒継続 | 電圧回復で自動 | 警告表示のみ |

**層3と層4を混同しないこと。** 層3はラッチして走行不能になるが、層4は警告だけで走り続けられる。
GUI でも赤（層1-3）と黄（層4）で明確に分けること。

## 11. 帯域予算

### STM32 → Pi（上限 100 kB/s）

既定構成（`param 0x0040 = 0`）:

| パケット | フレーム長 | 頻度 | 帯域 |
|---|---|---|---|
| `LIDAR_SECTOR` (0x01) | 76 B | 120 Hz | 9.12 kB/s |
| `TELEMETRY` (0x02) | 109 B | 100 Hz | 10.9 kB/s |
| `PONG` (0x06) | 19 B | 5 Hz | 0.10 kB/s |
| `STATS` (0x08) | 55 B | 1 Hz | 0.06 kB/s |
| `CONFIG_ACK` / `LOG` / `VERSION` | — | 散発 | 約 0.2 kB/s |
| **合計** | | | **約 20.4 kB/s（約20%）** |

強度 ON（`param 0x0040 = 1`）は約 23 kB/s、圧縮（`= 2`）は約 16 kB/s。いずれも余裕があり、
送信キューの滞留は §7 のとおり有界。判断材料は Pi 側のロス率と `STATS.tx_drop`。

### Pi → STM32（別方向・独立）

| パケット | フレーム長 | 頻度 | 帯域 |
|---|---|---|---|
| `COMMAND` (0x10) | 22 B | 100 Hz（中身の変化は即時） | 2.20 kB/s（約2%） |
| `PING` (0x12) | 11 B | 5 Hz | 0.06 kB/s |
| `CONFIG_SET` / `CONFIG_GET` / `VERSION_REQ` | — | 散発 | < 0.1 kB/s |

## 12. Raspberry Pi 5 側の実装上の注意

### 12.1 デバイス名（Pi 4 までと異なる）

**Pi 5 では `/dev/ttyAMA0` が別用途に割り当てられている。**
GPIO14/15 の UART は別名（`/dev/ttyAMA2` 等、オーバーレイ設定次第）になる。実機で確認すること。

```bash
ls -l /dev/serial*        # serial0 のシンボリックリンク先を確認
dmesg | grep -i ttyAMA
```

必要な設定:
- `/boot/firmware/config.txt` に `enable_uart=1`
- `/boot/firmware/cmdline.txt` から `console=serial0,115200` を**削除**
  （シリアルコンソールが GPIO UART を掴んだままだと通信できない）

### 12.2 非標準ボーレート

1000000 bps は Linux の termios に定義がある（`B1000000`）。POSIX 標準の表にない値でも Linux は **termios2** 経由で任意ボーレートを設定でき、pyserial は
どちらも `Serial(port, baud)` でそのまま通る。

### 12.3 受信ループの書き方

```python
# ダメな例 — 1バイトごとに syscall が走り CPU を食う
while True:
    b = ser.read(1)

# 良い例 — 塊で読んでリングバッファに積み、そこからフレームを切り出す
data = ser.read(max(1, ser.in_waiting))   # blocking + 一括読み
buf.extend(data)
while (frame := try_extract_frame(buf)) is not None:
    dispatch(frame)
```

### 12.4 ラップする値の扱い

| 値 | ラップ周期 | 扱い |
|---|---|---|
| `t_us` (u32, μs) | **71.6 分** | **必ず符号なし差分**。実走行で必ずまたぐ |
| `STATS.*` (u32, 件) | 1000件/s で 49日 | 実質ラップしない |
| `odom_dist` (i32, 0.1mm) | **±214.7 km**（u32 全域で 429.5 km） | ミニカーでは**到達しない** |

**`odom_dist` のラップは 429 km であり、429 m ではない。**
`0.1mm × 2^32 = 4.295×10^5 m`。Pi 側の初回ドラフトに 1000倍の誤記があったので訂正した。
実質ラップしないため、`t_us` と違って素直な符号付き減算でよい。
防御的に符号なし差分で扱うのは構わないが、`t_us` と同格の注意事項ではない。

```python
def unwrap_u32(prev_raw: int, curr_raw: int, acc: int) -> tuple[int, int]:
    """t_us 用。符号なし差分を取り 64bit の累積値へ足し込む"""
    diff = (curr_raw - prev_raw) & 0xFFFFFFFF
    if diff >= 0x80000000:          # 逆行（負の差分）
        diff -= 0x100000000
    return curr_raw, acc + diff
```

### 12.5 プロセス分離

**受信は `io_node` 専用プロセスで、パースだけに専念させる。**

ここに知覚処理を混ぜると、CPU スパイクのたびに UART バッファが溢れる。
Linux のシリアル受信バッファは **4KB 程度 = 本プロトコル（上り約 19kB/s）では約 200ms 分**しかない。

### 12.6 構造体アライメント

**ペイロードはフレーム先頭から 5バイト目に始まるため、`u32` / `i32` が 4バイト境界に乗らない。**

- **C 側**: 構造体を丸ごと `memcpy` するなら `__packed` を付けること。
  非 packed 構造体へのキャストは**未定義動作**であり、ARM では実際にハードフォールトしうる。
- **Python 側**: `struct` のフォーマット文字列は必ず **`<` で始める**。
  `=` や `@` を使うとネイティブアライメントでパディングが入り、オフセットがずれる。

実際のフォーマットは生成物 `raspi/proto/generated/packets.py` の各クラスの `FMT`（`protocol.toml` から生成。
`generate.py` が LEN との一致を検証する）。手で書き写さないこと。

```python
TELEMETRY       '<2I8h2i19h14B2h3H2h2H'   # 102 B
LIDAR_SECTOR    '<BI32H'          # 69 B（sector_idx, t_start_us, duration_us, rot_speed_dps, dist×30）
LIDAR_SECTOR_I  '<BI32H30B'       # 99 B
LIDAR_SECTOR_C  '<BI2H30B'        # 39 B
STATS           '<12I'            # 48 B
VERSION         '<H2I'            # 10 B
PONG            '<3I'             # 12 B
COMMAND         '<2B2h3HhB'       # 15 B
CONFIG_ACK      '<HfB'            #  7 B
LIMITS          '<4f'             # 16 B
```

`TELEMETRY` の内訳: `2I`(t_us, flags) / `8h`(speed, yaw_rate, steer×2, wheel_speed×4) /
`2i`(odom_dist) / `19h`(accel×3, pitch, roll, motor_current×3, torque_cmd×2, slip×2, tc_limit_nm×2,
torque_req×2, abs_limit_nm, tv_ratio, tv_moment_nm) /
`14B`(temp×4, batt×4, us×2, md_status×3, cmd_seq_echo) / `2h`(accel_kf, accel_bias_kf) / `3H`(kf_gated, kf_z_rms_dist, kf_z_rms_accel) / `2h`(kf_rho_dist, kf_rho_accel) / `2H`(front_angle×2)

### 12.7 GPIO

Pi 5 は RP1 チップ採用のため `RPi.GPIO` が動作しない。**`gpiozero` + `lgpio` バックエンド**を使うこと。

### 12.8 起動シーケンス

```
1. UART オープン
2. VERSION_REQ (0x14) と LIMITS_REQ (0x15) を送信 → VERSION・LIMITS を最大 1 秒待つ
   （届かなければ以降 1 秒ごとに送り直す。STM32 は起動直後にも 3 回自発送信する）
3. protocol_version が一致するまで ARM を通さない（DISARM を送り続ける）
4. ON/OFF 系と自動停止のマージンを CONFIG_GET で読み、GUI の初期値にする
5. config/vehicle.toml の [control] を CONFIG_SET で push し、CONFIG_ACK で確かめる（揃うまで ARM 不可）
6. PING を 20Hz で 3秒打ってから 5Hz に落とす（時刻同期の収束を早める）
7. GPIO6 ハートビート開始
8. COMMAND の 100Hz 送信を開始（ARM を通せる条件が揃うまでは mode=DISARM）
9. steer_center_valid が立っていなければ STM32 は MANUAL/AUTO に入らない（GUI に整備手順を表示）
10. drive_power_locked・estop_active が立っていないことを確認してから arm 要求
    （立っていた後は arm を一度下ろしてから立て直す。§9）
```

## 13. Pi 側の状態機械

```
        ┌──────────┐  VERSION 一致 + steer_center_valid  ┌──────────┐
        │  INIT    │ ─────────────────────────────────→ │  READY   │
        └──────────┘                                     └────┬─────┘
             ↑                                                │ arm 要求 → armed
             │ 人間の明示操作                                  ↓
        ┌────┴─────┐   estop / 200ms 途絶 / 過電流ラッチ  ┌──────────┐
        │  FAULT   │ ←─────────────────────────────────  │  DRIVE   │
        └──────────┘                                      └────┬─────┘
                                                               │ 100ms 途絶 / comm_ok=0
                                                          ┌────┴─────┐
                                                          │ DEGRADED │ ← 復帰可
                                                          └──────────┘
```

**`CALIB` 状態は廃止した。** ステアリング原点合わせは組み立て・整備時の作業
（タイヤを直進にしてボタンを押しながら起動 → Flash 保存）であり、走行中のシーケンスではない。

`INIT` では `steer_center_valid` の**確認のみ**を行う。立っていなければ `READY` に進まず、
GUI に「ステアリング原点が未設定です。整備手順に従って原点合わせを行ってください」と表示する。
