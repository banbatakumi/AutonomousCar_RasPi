## 1. プロジェクト概要

自律走行ミニカー **SURGE Mark.2** の Raspberry Pi 5 側プログラム。

### 最終目標

- カメラと LiDAR による**自律走行**
- **駐車タスク**（カメラ・センサ情報から指定された枠に自動駐車）
- PC 上の **GUI** による監視・設定・遠隔操縦（ラジコンモード）

### 設計上の前提

- 旧シミュレータ（`surge_sim` / `surge_sim_v2`）は削除済み。**設計から新規に作り直す**
- 参考が必要な場合のみ、明示的な指示に従って `git show v1-sim-archive:<path>` を参照する

## 2. ハードウェア構成

### STM32（制御ボード）

| 接続 | 内容 |
|---|---|
| LiDAR | LD06（10Hz 回転、最大約 12m）。専用 UART 230400bps で STM32 に接続 |
| 超音波センサ | HC-SR04 系 前方 × 1、後方 × 1。測距範囲 2cm〜約4m、**実質 20Hz が上限** |
| 駆動モータ | 後輪 **左 / 右** 独立 2モータ（BLDC + 自作 MD、**トルクモード**） |
| ステアリング | モータ 1個（BLDC + 自作 MD、**位置モード**。サーボではない） |
| 車速センサ | **前輪左右のアナログ絶対角エンコーダ**（ADC 読み。tick 積算ではない） |
| IMU | **MPU6050（6軸）+ Mahony 相補フィルタ。地磁気センサ無し** |
| 温度センサ | 4点（MD後左 / MD後右 / MDステア / STM32 内蔵） |
| 電源 | **2系統**。駆動系（過電流 5.0A）とシグナル系（同 3.0A）。どちらも 8セル NiMH |

**TC（トラクションコントロール）とトルクベクタリングは STM32 側で実装済み。**

#### Pi 側の設計に効く制約

- **絶対方位が出ない。** 地磁気センサが無いため IMU の yaw は積分ドリフトする。
  `TELEMETRY` は `yaw_rate` のみを返す。**方位は SLAM（スキャンマッチング）で確定させる**
- **車速から加速度を微分してはならない。** 前輪エンコーダは分解能が粗く、
  STM32 側で 1〜2Hz の強いローパスを通した値が来る。加速度は IMU から取る
- **前輪は操舵輪。** 左右の回転差からヨーレートを推定するには Ackermann 幾何が要る
- **超音波は 20Hz。** 50Hz の `TELEMETRY` に対し同じ値が連続する
- 詳細は [`uart_protocol.md`](uart_protocol.md) §5.3

### Raspberry Pi 5

| 接続 | 内容 |
|---|---|
| カメラ | 前方 / 後方 の 2台（CSI、`picamera2`） |
| GPIO18 | 圧電ブザー |
| GPIO19 | LED 緑 |
| GPIO13 | LED 赤 |
| **GPIO6** | STM32 の GPIO と接続。**緊急停止ハートビート**（プルアップ済み） |
| GPIO14 | UART TX → STM32 RX |
| GPIO15 | UART RX ← STM32 TX |

### 通信

| 区間 | 方式 |
|---|---|
| STM32 ⇄ Pi 5 | UART **250000 bps** 8N1 + GPIO6 ハートビート |
| Pi 5 ⇄ PC | Wi-Fi（AP / STA 切替）または 有線 Ethernet、WebSocket |

## 3. システムアーキテクチャ

3つの計算機を、**制御周期と安全要求**で階層化する。

```
┌─────────────────────────────────────────────────────────┐
│ PC                                    10〜30 Hz          │
│   GUI（React + TypeScript / ブラウザ）                    │
│   可視化・設定・ラジコン操縦                                │
└────────────────────┬────────────────────────────────────┘
                     │ Wi-Fi / Ethernet
                     │ WebSocket（3チャンネル分離）
┌────────────────────┴────────────────────────────────────┐
│ Raspberry Pi 5                        10〜30 Hz          │
│   認知・判断層                                            │
│   知覚 → 自己位置推定 → 経路生成 → 行動判断                 │
└────────────────────┬────────────────────────────────────┘
                     │ UART 250kbps ＋ GPIO6 ハートビート
┌────────────────────┴────────────────────────────────────┐
│ STM32                                 100 Hz〜1 kHz      │
│   リアルタイム制御層                                       │
│   速度/舵角ループ・TC・トルクベクタリング・保護              │
└─────────────────────────────────────────────────────────┘
```

### 階層化の原則

**「速い制御はエッジに、遅い判断は上位に」**

TC やスリップ制御は数 ms 以内に効かせる必要がある。UART 往復 + Python の処理遅延（合計 30〜50ms）を挟むと成立しないため、STM32 内に閉じる。

同様に、**上位が落ちても下位が自力で安全を確保できる**構造にする。Pi がクラッシュしても STM32 が停止し、PC が落ちても車は自律走行を継続できる。

## 4. 責務分割

| 層 | 周期 | 担当 |
|---|---|---|
| **STM32** | 100Hz〜1kHz | モータ電流/速度制御ループ、ステアリング角度制御ループ、TC、トルクベクタリング、LD06 パース・ビニング、超音波測距、電流・温度リミッタ、UART タイムアウト時の自動ブレーキ、GPIO6 ハートビート監視 |
| **RasPi 5** | 10〜30Hz | 点群処理、占有格子生成、カメラ認識、自己位置推定、経路生成、行動判断、テレメトリ配信、ログ記録 |
| **PC** | 10〜30Hz | 可視化、パラメータ設定、ラジコン入力 |

### Pi → STM32 に送る指令は3つだけ

```
target_speed      目標速度        [m/s]
accel_limit       加速度の上限    [m/s²]   ← レートリミット
target_steer      目標舵角        [rad]
```

**PWM デューティやトルク配分は一切送らない。** Pi 側は「今この瞬間何%出力すべきか」を知る必要がなく、知ろうとすると遅延で破綻する。

## 5. 座標系・単位の規約

**ROS の慣例（REP-103 / REP-105）に従う。** 自作フレームワークであっても、である。

理由：①論文・教科書の式がそのまま使える ②将来 ROS 2 に移行する場合の摩擦がゼロ ③独自ルールは3ヶ月後に思い出せない。

### 5.1 基本規約

| 項目 | 規約 |
|---|---|
| 座標系 | **右手系。x = 前、y = 左、z = 上** |
| 角度 | **反時計回りが正**（左旋回が正） |
| 単位 | **SI 固定**（m, m/s, m/s², rad, rad/s, s） |
| 時刻 | ns 単位の整数、Pi の `CLOCK_MONOTONIC` 基準 |

**内部は絶対に SI。** km/h や度への変換は GUI の表示直前でのみ行う。

### 5.2 フレーム階層

```
map ──── odom ──── base_link ──┬── lidar
 │        │            │        ├── cam_front
 │        │            │        └── cam_rear
 │        │            │
 │        │            └─ 後輪車軸の中心に置く
 │        │
 │        └─ 連続で滑らか。ただしドリフトする → 局所制御はこちら
 │
 └─ SLAM が補正する。跳ぶことがある → 大域経路計画はこちら
```

#### `odom` と `map` を分ける理由

SLAM のループクロージャが効いた瞬間、自己位置は数十 cm「跳ぶ」。これを制御ループに直接食わせると舵が暴れる。

- **制御（経路追従）** … 連続な `odom` 基準
- **大域経路計画** … 補正済みの `map` 基準

#### `base_link` を後輪車軸中心に置く理由

アッカーマン車両の運動学（自転車モデル）が最も簡潔になる。

```
ẋ = v·cos(θ)
ẏ = v·sin(θ)
θ̇ = (v / L)·tan(δ)        L = ホイールベース, δ = 舵角
```

重心基準にするとスリップ角の項が入り式が煩雑になる。Pure Pursuit の標準式も後輪基準。

### 5.3 車両パラメータ

`config/vehicle.toml` に集約し、**全ノードがそこだけを見る**。

> 形式は当初 YAML と書いていたが、実装時に **TOML** にした。Python 3.11+ の `tomllib`
> （標準ライブラリ）で読めるので依存が増えず、`raspi/proto/protocol.toml` と流儀が揃うため。
> スキーマは下記のまま。加えて `[dynamics]`（操舵のむだ時間・1次遅れの時定数など）を持つ。

```yaml
wheelbase:        # L [m]
track:            # トレッド [m]
max_steer:        # 最大舵角 [rad]
wheel_radius:     # [m]
encoder_ticks_per_rev:
footprint:        # 車体外形ポリゴン [m]
sensors:
  lidar:      {x: , y: , z: , yaw: }   # base_link からの固定変換
  cam_front:  {x: , y: , z: , roll: , pitch: , yaw: }
  cam_rear:   {...}
  us_front:   {x: , y: , z: , yaw: }
  us_rear:    {...}
```

## 6. Raspberry Pi 5 内部設計

### 6.1 プロセス構成

Python の GIL があるため、**スレッドではなくプロセスで分ける**。Pi 5 は4コアなので割り当ても素直。

```
                  ┌────────────────────────────────┐
   UART ──────────│ io_node                        │  最優先・実時間性重視
   GPIO6 ─────────│  UART送受信 / パース / 時刻同期 │  他の処理を混ぜない
                  │  GPIO(E-Stop / LED / ブザー)    │
                  └───────┬────────────────────────┘
                          │ scan, vehicle_state
   CSI×2 ──┐              ▼
           │   ┌────────────────────────────────┐
   ┌───────┴───│ camera_node                    │
   │           │  picamera2 → 共有メモリリング    │
   │           └───────┬────────────────────────┘
   │                   ▼
   │       ┌────────────────────────────────────┐
   └──────▶│ perception_node                    │
           │  点群処理 / 占有格子 / カメラ認識     │
           └───────┬────────────────────────────┘
                   ▼
           ┌────────────────────────────────────┐
           │ planning_node                      │
           │  自己位置推定 / 経路生成 / 行動判断   │
           └───────┬────────────────────────────┘
                   │ 目標速度・目標舵角
                   ▼ （io_node へ直行。段数を増やさない）
           ┌────────────────────────────────────┐
           │ telemetry_node   WebSocket サーバ   │◀──▶ PC
           └────────────────────────────────────┘
           ┌────────────────────────────────────┐
           │ safety_node   Watchdog 監視         │  最小依存で作る
           └────────────────────────────────────┘
           ┌────────────────────────────────────┐
           │ logger_node   MCAP 記録             │
           └────────────────────────────────────┘
```

**制御コマンドは `planning_node` → `io_node` の直行パス**にし、遅延段数を最小化する。

#### ★ 実装では `cmd` を1本に絞った（2026-08-13）

直行パスにすると、**`cmd` の publish 元が planning_node と telemetry_node の2つ**に
なる。telemetry_node は操縦者不在でも 50Hz で DISARM を流し続けている（§9.4）ので、
2つが同じトピックに出すと購読側からは区別できないまま交互に上書きし合い、
**止める側が負けることがある**。

そこで `planning_node` は `auto/cmd` に出し、GUI から engage されている間だけ
telemetry_node が**速度・舵・制動だけを差し替えて** `cmd` に流す形にした。

    GUI ──cmd(mode=AUTO, arm, 灯火…)──▶ telemetry_node ──cmd──▶ io_node
    planning_node ──auto/cmd(速度・舵)──▶      ↑ ここで差し替える

増える遅延は telemetry_node の 50Hz 周期ぶん（最悪 20ms）で、**指令の生成元が
1つに定まる価値の方が大きい**と判断した。この形なら自律走行中も人間の安全網
（ARM 保持・150ms 途絶で DISARM・E-Stop）がそのまま生きる。詳細は §8.1。

### 6.2 内部バス

ZeroMQ を土台に、その上のメッセージ規約だけを自作する。輸送層まで自作するのは無駄。

#### 3つの配送パターンを使い分ける

自作で最も多い失敗は「全部同じ配送方式にする」こと。購読者の要求が違う。

| パターン | 用途 | 実装 |
|---|---|---|
| **最新値のみ** | 制御指令、車両状態 | ZMQ PUB/SUB + `CONFLATE=1` |
| **取りこぼし厳禁** | ロガー、記録 | ZMQ PUB/SUB + `HWM` 大きめ |
| **大容量ゼロコピー** | カメラ画像、点群 | `shared_memory` リングバッファ |

#### なぜ CONFLATE が必要か

ZeroMQ の PUB/SUB には **slow subscriber 問題**がある。購読側の処理が追いつかないとキューに溜まり、**制御ノードが2秒前の点群で舵を切る**事態が起きる。しかも見た目は正常に動くため気づきにくい。

制御系は「古いデータは捨てて最新だけ」が常に正解なので `CONFLATE=1`（キュー長1、上書き）にする。ロガーは逆に1フレームも落としたくないので HWM を大きく取る。

**同じトピックを、購読者ごとに違うポリシーで受ける**のが要点。

#### 画像を ZMQ に流してはいけない

640×480×3 のフレームを 30Hz で msgpack 経由にすると **27 MB/s** のメモリコピーが発生する。

```
camera_node     → shared_memory の N枚リングに書く
                → ZMQ には {buf_id, w, h, format, t_capture} の 60バイトだけ publish
perception_node → buf_id から numpy view を作る（コピーゼロ）
```

リングを8枚程度取れば、購読側が読んでいる間の上書きは実用上起きない。厳密にやるならシーケンス番号を読み前後で確認する（**seqlock**）。

### 6.3 メッセージ規約

`msgspec` を使う（Rust 実装で高速、型を `Struct` で書け、msgpack にそのまま落ちる）。

**全メッセージが以下の3フィールドを必ず持つ。**

```python
class MsgBase(msgspec.Struct):
    t_capture: int   # ns  センサが取得した時刻（Pi の CLOCK_MONOTONIC に換算済み）
    t_pub: int       # ns  publish した時刻
    seq: int         # ローリングカウンタ
```

これが無いと、後でセンサ融合を作るときに全メッセージ定義を書き直すことになる。

#### 主要トピック

| トピック | 型 | 頻度 | 発行元 |
|---|---|---|---|
| `scan` | LiDAR 1周分の点群（極座標 + 各点の時刻） | 10 Hz | io_node |
| `vehicle_state` | 速度・各輪周速・路面舵角・累積オドメトリ・IMU・温度・電源2系統・フラグ | 50 Hz | io_node |
| `image/front`, `image/rear` | 共有メモリ参照 | 15〜30 Hz | camera_node |
| `grid/local` | ローカル占有格子 | 10 Hz | perception_node |
| `pose` | 自己位置（map / odom） | 30 Hz | planning_node |
| `path` | 生成経路 | 10 Hz | planning_node |
| `cmd` | 目標速度・舵角 | 50 Hz | **telemetry_node（唯一の発行元。下記）** |
| `auto/ctrl` | どの自動運転モードで走るかの意思 | 5 Hz | telemetry_node |
| `auto/cmd` | 自律走行の目標速度・舵角 | 50 Hz | planning_node |
| `auto/state` | その判断の根拠（選んだギャップ等） | 10 Hz | planning_node |
| `hb/<node>` | ハートビート | 10 Hz | 全ノード |
| `diag` | 統計・エラーカウンタ | 1 Hz | 各ノード |

## 7. 安全設計

自律走行で最初に作るべきは走る機能ではなく**止まる機能**。互いに独立した3層にする。

```
[1] ハードウェア層   GPIO6 ハートビート、STM32 内の電流・温度リミッタ
[2] STM32 ファーム層 UART 受信タイムアウト(200ms)で自動ブレーキ
[3] RasPi ソフト層   障害物近接での減速、Watchdog、通信断検知
```

### 7.1 GPIO6 ハートビート（第1層）

**単純なアクティブ Low の E-Stop はフェイルセーフにならない。** 断線するとプルアップで High（= 正常）に戻ってしまい、異常を検知できないため。

```
Pi   : GPIO6 に 100Hz の矩形波を出力し続ける（オープンドレイン推奨）
STM32: エッジを監視し、50ms 途切れたら即ブレーキ + estop_active
```

この方式なら以下すべてを**単一の機構で**検出できる。

1. Pi のフリーズ
2. Pi の電源断
3. 配線の断線・接触不良
4. Pi 側プロセスのクラッシュ

ソフトウェアの生存とハードウェアの導通を、1本の線で同時に保証できる。既存のプルアップはオープンドレイン駆動の High 側を担うため相性が良い。

**復帰は必ず人間の明示操作を経由する。** 自動復帰させない（原因未解消のまま走り出すため）。

### 7.2 UART タイムアウト（第2層）

STM32 側で `COMMAND` が **100ms** 途絶したら自動ブレーキ。
Pi 側は `TELEMETRY` が **100ms 途絶で DEGRADED（警告のみ）、200ms 途絶で FAULT**。

非対称にしているのは、**単発の CRC エラーや一時的なロスで即 FAULT に落とさないため**。
50Hz なら 100ms = 5発で、ノイズ環境なら 5発連続ロスは起こりうる。
下り（`COMMAND` 100Hz）は安全に直結するため 10発の取りこぼしで即ブレーキ。

※ 「LiDAR バーストで上りが滞留する」は誤り。優先度キューがあれば
`TELEMETRY` の待ち時間は送信中の1フレーム分（3.04ms）で有界
（[uart_protocol.md](uart_protocol.md) §7）。

### 7.2b 電源保護（駆動系ラッチ）

過電流で `DRIVE_POWER` がハード遮断されると**ラッチし、電源をリセットするまで復帰しない**。
このとき STM32 は `drive_power_locked` を立て、Pi が `arm` を要求しても `armed` を立てない。

**これは異常ではなく仕様。** 通信 FAULT と区別して GUI に
「駆動電源ラッチ中 — 電源を入れ直してください」と表示すること。

### 7.3 Watchdog（第3層）

各ノードが 10Hz で `hb/<node_name>` を publish し、`safety_node` が監視。1つでも 300ms 途切れたら FAULT → 停止指令 → GPIO6 ハートビート停止。

**`safety_node` は他ノードに依存しない最小構成にする。** numpy も OpenCV も import しない。監視役が最初に落ちたら意味がない。

## 8. ビヘイビア状態機械

```
        ┌──────────────────────────────────┐
        ▼                                  │
    [INIT] → [IDLE] ⇄ [MANUAL]             │
                │                           │
                ▼                           │
             [AUTO] ─┬─ MAPPING             │
                     ├─ CRUISE              │
                     ├─ AVOID               │
                     ├─ PARK_SEARCH         │
                     └─ PARK_EXEC           │
                                            │
    どの状態からでも ──→ [FAULT] / [ESTOP] ──┘
                          （復帰は IDLE 経由のみ）
```

| 状態 | 内容 |
|---|---|
| `INIT` | 起動・自己診断・バージョン照合・`steer_center_valid` の**確認**（原点合わせ自体は整備時の作業） |
| `IDLE` | 停止・待機。モータ非励磁 |
| `MANUAL` | PC からのラジコン操縦 |
| `AUTO / MAPPING` | 地図生成走行 |
| `AUTO / CRUISE` | 通常自律走行 |
| `AUTO / AVOID` | 障害物回避中 |
| `AUTO / PARK_SEARCH` | 駐車枠の探索 |
| `AUTO / PARK_EXEC` | 駐車動作の実行 |
| `FAULT` | 異常検知による停止 |
| `ESTOP` | 緊急停止 |

### 原則

- **`ESTOP` からの復帰は人間の明示操作が必須**
- **現在状態と、直前の遷移理由を必ず GUI に出す**
  「なぜ止まったか」が分からないのがデバッグを最も消耗させる

### 8.1 自動運転の実装（2026-08-13）

上の状態機械はまだ全部は無い。**行動判断だけを先に作った**（`raspi/auto/`）。
第1号は **Follow the Gap**（`ftg`）で、地図も自己位置も使わず、点群の中で最も
広く空いた方向へ走る。SLAM を作る前に、**点群が実車で使える品質かを確かめる**
のが目的。

#### モードは増える前提で作る

`raspi/auto/` に `Planner` のサブクラスを1つ書き、`registry.py` に1行足すだけで
GUI の選択肢に出る。パラメータのスライダも planner が宣言した `ParamSpec` から
自動生成される。**GUI にモード名を書かない**（書くと増やすたびに2箇所直すことになり、
いつか片方が古くなる）。

| ファイル | 役割 |
|---|---|
| `raspi/auto/base.py` | `Planner` と `ParamSpec`。**バスも WS も知らない純粋な計算** |
| `raspi/auto/follow_the_gap.py` | FTG 本体 |
| `raspi/auto/registry.py` | id → クラス。GUI へ渡す宣言（`catalog()`）もここ |
| `raspi/nodes/planning_node.py` | 配線だけ（購読・周期・publish） |

#### 「走る」より「止まる」を先に決める

| 条件 | 挙動 |
|---|---|
| セクタ欠損が視野の 40% 超 | 計画を放棄（`ready=False`）→ 制動 |
| 通れる隙間が見つからない | 同上 |
| 正面の余裕が `stop_dist` 未満 | 意図的な停止（`ready=True` + `brake`） |
| 点群が 300ms 古い | planning_node が制動指令に読み替える |
| `auto/cmd` が 200ms 途絶 | telemetry_node が制動に読み替える（planner の死亡） |
| 人が舵・スロットル・ブレーキを触った | 自律を解除して手動に戻す（クルコンと同じ作法） |
| E-Stop / 操縦権の解放 / 接続断 | engage も同時に落とす |

**`sector_seen[s] == False` は「障害物なし」ではない。** 欠測した方向は距離 0
（侵入禁止）として扱う。ここを空きとして扱うと、LiDAR が片側だけ落ちた瞬間に
その方向へ舵を切る。

#### engage ≠ ARM

engage は「自律に任せてよい」という意思表示にすぎず、**モータが回るには人間が
GUI で ARM を保持している必要がある**。planning_node は `arm` を立てられない。
engage の状態は保存しない（`config/auto.json` に入るのはモードとパラメータだけ）
ので、**電源を入れただけで走り出す経路が存在しない**。

⚠ **自律走行中だけは無操作タイムアウト（既定 20秒）を掛けていない。** 人が何も
触らないのが正常な状態のため。他の受け皿（Esc・E-STOP・フォーカス喪失・タブが
背後に回る・150ms 途絶）は全部生きているので、**画面を見ていられる間だけ走る**
という前提は変わっていない。

## 9. Pi ⇄ PC 通信

### 9.1 ネットワーク構成 — **Pi は常に STA。繋ぎ先を変えるだけ**（2026-08-08 方針変更）

| 構成 | 用途 | Pi 側の設定 |
|---|---|---|
| **有線 Ethernet 直結** | 据置開発（コード編集・パッケージ導入） | 固定 `169.254.55.2`。走行はできない |
| **STA（研究室 AP）** | 走行テスト（研究室内） | SSID 登録済み |
| **★ STA（持込ルーター）** | **本番・屋外・大会会場** | **SSID を登録しておくだけ** |
| ~~AP モード~~ | — | **実装しない**（下記） |

**Pi のネットワーク設定は一切切り替えない。** 屋外では Wi-Fi ルーターを持ち込んで、
Pi と PC の両方をそれに STA 接続する。**Pi から見れば繋ぎ先の SSID が変わるだけ**で、
モード切替という操作自体が存在しない。

#### ★ なぜ AP モードを実装しないのか

当初は「本番は AP モード」と設計していたが、**持込ルーターの STA 接続が全面的に優れている**
と判断して取りやめた。

| | AP モード | **持込ルーター + STA** |
|---|---|---|
| 電波の強さ | **Pi の内蔵アンテナが上限** | ルーターの外部アンテナ・MIMO |
| Pi の設定変更 | 必要（**失敗すると詰む**） | **不要** |
| 5GHz の可否 | 屋外は W56 のみ・**DFS 必須** | ルーター側で 2.4GHz 固定にできる |
| Pi の CPU 負荷 | ビーコン・DHCP を Pi が負担 | **増えない** |
| インターネット | **来ない**（NTP が効かない） | SIM 付きルーターなら来る |

1. **電波は「弱い側」が親機になると全体が弱くなる。** AP モードでは Pi の基板上の
   小さなアンテナが性能の上限になり、走行して距離が開くと STA より先に切れる。
   **切断は `cmd` の 150ms 途絶 → DISARM に直結する**（走行が勝手に止まる）
2. **ヘッドレスの Pi でモード切替に失敗すると救出手段が消える。**
   屋外で AP 起動に失敗し STA にも戻れないと、その場では SD カードを抜くしかない。
   STA のままなら、この事故が**原理的に起きない**
3. **屋外の 5GHz は日本の電波法で W56 のみ**（W52/W53 は屋内限定）。W56 は DFS 必須で、
   レーダー検出時に**最大60秒**通信が止まる。走行中の1分の途絶は使い物にならない。
   つまり屋外の AP モードは実質 2.4GHz 一択で、混雑した会場では不利
4. **インターネットが来ないと NTP が効かず、Pi の時計がずれる**（実際に約1日ずれた実績あり）。
   記録は `CLOCK_MONOTONIC` 基準なので実害は限定的だが、`.sfl` のファイル名と
   `t0_unix_ns` は壁時計依存

**フォールバックは AP モードではなく Ethernet 直結。** ルーターを忘れた・壊れた場合でも、
直結すれば必ず Pi に入れる。AP モードは「保険の保険」でしかなく、実装の手間に見合わない。

#### 実装：NetworkManager に SSID を登録しておくだけ

Raspberry Pi OS **Bookworm 以降は NetworkManager が標準**。V1（robotcar）の
`hostapd` + `dnsmasq` 手書き設定は競合してハマるため使わない。

**★ 屋外に出る前に、研究室で（直結が使えるうちに）登録しておくこと。**
NetworkManager は知らない SSID に自動接続しない。**現地で登録しようとすると、
Pi に繋ぐ手段が直結 Ethernet しか無い状態になる。**

```bash
# ① 屋外用ルーターの SSID を登録
sudo nmcli device wifi connect "SURGE-FIELD" password "********" ifname wlan0

# ② 優先順位（屋外ルーターがあればそちらを優先し、研究室では自動で戻る）
sudo nmcli connection modify "SURGE-FIELD" connection.autoconnect-priority 20
sudo nmcli connection modify "tplink"      connection.autoconnect-priority 10

# ③ 確認
nmcli -f NAME,AUTOCONNECT,AUTOCONNECT-PRIORITY connection show
```

これで**会場ではルーターの電源を入れるだけ**で繋がり、研究室に戻れば自動で `tplink` に戻る。

#### 持込ルーターの選び方

- **SIM 入りモバイルルーターが最善。** インターネットが来るので NTP も `apt` も通り、
  現地でパッケージを入れ直したくなったときに困らない
- 電波の強さだけなら**据置ルーター（モバイルバッテリー給電）が上**。消費電力 5〜10W
- **屋外は 2.4GHz 固定にする**（5GHz は上記の DFS/法規の問題がある）
- **SSID は固有名にする。** 会場に同種の車両が複数いると衝突する
- WAN 未接続のルーターは、機種によっては Pi が「インターネットあり」と誤認して
  DNS 解決がタイムアウト待ちになることがある（`apt` が妙に遅いときはこれを疑う）
- **IP が変わっても問題ない。** mDNS（次節）で `surge-mk2.local` に届く

#### mDNS — **導入済み・運用中**（2026-08-08）

`avahi-daemon` が Pi で有効になっており、**`surge-mk2.local`** で解決できる。

```
http://surge-mk2.local:8000    # 直結でも研究室でも屋外ルーターでも、これ一つで繋がる
```

**繋ぎ先が変わっても IP を調べ直す手間が消える**（屋外ルーターの DHCP でも同じ名前で届く）。
**名前は `surge.local` ではなくホスト名どおりの `surge-mk2.local`**（実機のホスト名に合わせた）。

- avahi は**生きているインタフェースのアドレスだけを広告する**ので、直結が繋がっていれば
  `169.254.55.2`、抜けていれば Wi-Fi 側の IP が返る。**速い経路が自動で選ばれる**
- **クライアント側は IPv4 に固定すること。** avahi は IPv6 リンクローカルも広告し、
  ssh は IPv6 を優先するため、指定しないと直結があるのに Wi-Fi 経由になる
  （ssh は `AddressFamily inet`、curl は `-4`）
- 実測とフェイルオーバー検証は `setup_credentials.md`

### 9.2 WebSocket チャンネル分離

**1本にまとめない。** カメラのフレームが詰まった瞬間にラジコン入力まで遅延するため。

| チャンネル | 内容 | 方式 | 頻度 |
|---|---|---|---|
| `/ws/telemetry` | 車両状態・点群・占有格子・経路 | **バイナリ**（msgpack） | 20 Hz |
| `/ws/camera/{front,rear}` | JPEG フレーム | バイナリ | 15〜30 Hz |
| `/ws/control` | ラジコン入力・設定変更・状態通知 | JSON（req/res + ack） | イベント駆動 |

点群を JSON で送ると CPU を無駄に食うため、テレメトリはバイナリにする。

### 9.3 帯域見積もり

| データ | 帯域 |
|---|---|
| カメラ 2台（640×480 JPEG q70 @15fps） | 約 7 Mbps |
| 点群 + 占有格子 + テレメトリ @20Hz | 約 1 Mbps |
| **合計** | **約 8 Mbps** |

Wi-Fi の実効帯域からは余裕。**問題は帯域ではなく遅延のスパイク**で、電波状況が悪化すると数百 ms 飛ぶ。

### 9.4 ラジコンモードの安全要件

- **デッドマン**：ボタンを押している間だけ動く（離す = 停止）
- **ハートビート**：PC → Pi に 20Hz。150ms 途切れたら停止
- **ブラウザのフォーカス喪失で自動停止**
- **往復遅延 (ms) を GUI に常時表示。** 50ms 超で警告色

## 10. GUI 設計方針

「何を表示するか」から入ると破綻する。表示したい項目は20個以上あり、全部を同じ大きさで並べると何ひとつ読めない画面になる。

### 10.1 情報を「見る頻度」で4層に分類する

項目の重要度ではなく、**人間がどれくらいの頻度でそこに視線を置くか**で分ける。

| 層 | 性質 | 扱い | 該当項目 |
|---|---|---|---|
| **A. 常時凝視** | 走行中ずっと見ている | 画面の大部分を占有 | 前方カメラ、LiDAR 俯瞰、予定進路 |
| **B. 常時周辺視** | 横目で追う | 小さく固定配置、色で異常を伝える | 速度、舵角、モード、遅延、超音波 |
| **C. 異常時のみ** | 普段は見ない | **平常時は畳み、閾値超えで自動的に前に出す** | 温度4点、電圧、CPU、パケットロス |
| **D. 診断・設定** | 走行後・調整時 | **別タブに隔離** | パラメータ、グラフ、キャリブレーション |

**C の扱いが設計の肝。** 温度や電圧を常時大きく出しても、正常な間は情報量がゼロ。小さく置き、閾値超過時のみ強調する。これで A に使える面積が増える。

**ラジコンビューでは C/D をもう一段ふるいにかける。** 同じ「異常時のみ」でも、運転者にとって
意味があるもの（温度・電圧＝走行を切り上げる判断に使う）は常時出し、開発者にしか意味が
ないもの（CRC・パケットロス・時刻同期・スリップ量）は画面から外して診断タブへ寄せる。
**隠すのは正常時の数字だけで、異常は必ず出す**（E-STOP・ARM・ラッチ警告・通信断は例外なく表示）。

### 10.2 画面モードを分ける

```
[ラジコン]  運転を楽しむための画面        ← 既定タブ。メータ主体、設定は ⚙ ドロワー
[自動運転]  自律走行の操作・監視・デバッグ  ← モード選択と engage・指令と実測・判断の根拠
[診断]      現在値 + 時系列グラフ(uPlot)   ← 走行画面から外した数字はすべてここ
[ログ]      記録の再生・エクスポート
```

**同じデータを2つの運転画面が見る。** 違うのは選び方の基準で、ラジコンは「周辺視で読めるか」、
自動運転は「原因を切り分けられるか」。介入（TC/TV/自動停止）はラジコンではランプだけ、
自動運転では数値も出す。

設定は独立タブをやめ、ラジコンタブの ⚙ から出るドロワーに畳んだ（2026-08-11）。中身は
すべてラジコン操作のための値で、他のタブでは使わない。**走らせながら開いて詰められる**
ことの方が、タブ1枚ぶんの面積より価値がある。閉じる操作に Esc は使わない（E-STOP のため）。

「地図」タブは削除した（プレースホルダのままだった）。SLAM を実装する Phase 3 で、
自動運転ビューに入れるか独立させるかを決め直す。

#### ラジコンビューのレイアウト

```
┌──────────────────────────────┬───────────────┐
│ ┌────────┐                   │               │
│ │後方PIP │                   │  LiDAR 俯瞰   │
│ └────────┘                   │               │
│                              ├───────────────┤
│      前方カメラ（左 2/3 全面） │  ╭速度╮  ╭ G ╮ │
│                              │ TC TV STOP …  │
│                              │ 温度▮ 駆動▮ 信号▮│
│                              │ 灯火          │
│              [進路ガイド][後方を表示] │      ⚙ │
└──────────────────────────────┴───────────────┘
```

**操縦は前方の映像を見て行う。** 計器の帯を下に積むと映像が縦に潰れるので、
左 2/3 を映像だけに使い、右 1/3 を LiDAR（上）と計器（下）で分けた。
後方はバックミラーとして左上に PIP で重ね、**消すと `CameraView` ごと外れて
WS が閉じる**（後方の JPEG が止まり、前方のフレームレートに帯域が回る）。

補機は計器パネルの下段に畳んだ。**走行中に触るのは灯火だけ**にし、押下状態
（ホーン・パッシング・ブレーキ）は介入ランプの列に吸収した。マウスで押しっぱなしに
するボタンは置かない — カーソルが外れた瞬間に取り残されるとクラクションが鳴り続ける
（`AuxPanel.tsx` 冒頭と同じ理由）。自動停止は「走りながら切り替えるもの」ではなく
「作業の性質で決める設定」なので設定パネルへ移した。

**灯火・ホーン・パッシングは ARM していなくても効く。** ARM 中でないときは
`mode=DISARM` / `arm=false` / 速度・舵 0 の cmd を送り、灯火とホーンのビットだけを
載せる（`command_from_cmd` は灯火/ホーンを `arm` と独立に組む）。モータが回る余地は
無いまま灯火だけが届く。⚠ 出すものが無いときは送らない — 送り続けると
**操縦権を握りっぱなしになり、2枚目のタブが操縦できなくなる**。

数値は「メータで読めるもの」を重複させない。舵角・超音波の距離・ブレーキ実トルクは
計器パネルから外した（すべて自動運転ビューと診断タブにある）。電圧だけは駆動・信号の
2系統を並べる — **片方だけ落ちる**（駆動を切っても Pi と STM32 は生きている）ため。

┌──────────────────────────────────────────────────────────────┐
│ SURGE Mk.2  [AUTO▸CRUISE] ARMED   ⏱12ms  📶-48dBm  loss 0.0% │ ステータスバー

「舵角の実測と指令を並べる」のは、アクチュエータ遅延の実測をそのまま画面に出す狙い。

### 10.4 React の状態管理（実装前に決めるべき事項）

**20〜30Hz のデータを React の state に入れると、再レンダリングで即座に破綻する。**

```
WebSocket ─┬─▶ [Canvas / WebGL に直接描画]  React を経由させない
           │    点群・占有格子・カメラ
           │    → useRef + requestAnimationFrame
           │
           ├─▶ [数値表示]  5〜10Hz に間引いて setState
           │    人間は 30Hz で変わる数字を読めない
           │
           └─▶ [接続状態・モード・設定値]  イベント時のみ setState
```

| 用途 | 採用 | 理由 |
|---|---|---|
| 状態管理 | **Zustand** | 軽量、selector による部分購読が簡単。Redux はこの規模には過剰 |
| 時系列グラフ | **uPlot** | Chart.js / Recharts はリアルタイム更新だと重い |
| 点群・占有格子 | **Canvas 2D** | 360点なら十分。占有格子は `ImageData` に一括書き込み |
| カメラ | `<img>` + blob URL または `ImageBitmap` → canvas | |

### 10.5 設定の同期

**Pi 側を single source of truth にする。**

- GUI 起動時に全設定を取得して表示
- 変更は個別に SET → `CONFIG_ACK` の `applied` で確定
- **楽観的更新をしない**
  範囲外の値はクランプされるため、GUI が「12.0 m/s に設定した」と表示しているのに実機は 8.0 m/s、という食い違いが起きる
- 設定変更は全クライアントに broadcast（2画面開いても矛盾しない）

### 10.6 モックデータで先に作る

**Pi も車体も無い状態で GUI 開発を完結させる。** ダミーのテレメトリと点群を吐くモック WS サーバを1つ書いておけば、PC 上だけで GUI を完成させられる。Phase 0 のログ再生機能ができたら、そのまま実データ再生に差し替わる。

## 11. ログ記録と再生

**Phase 0 で作ること。** 開発効率を最も大きく左右する。

- 全トピック（点群・カメラ・テレメトリ・コマンド）を**タイムスタンプ付きで記録**
- 記録ファイルを `io_node` の代わりに流し込む **`replay_node`** を用意

### 効果

- 実車がなくても知覚・SLAM・経路生成を PC 上で開発できる
- バグ再現が確定的にできる（「あの時だけ壁に突っ込んだ」を再現できる）
- 同じ入力で複数アルゴリズムを比較できる
- GUI の開発も車なしでできる

旧シミュレータを削除した今、**「実データの記録・再生」が事実上のシミュレータ代わり**になる。ゼロから物理シミュレータを書くより安上がりで、しかも本物のセンサノイズが入っている。

### フォーマット：MCAP を採用

Foxglove 製のロボットログ標準フォーマット。Python ライブラリあり。

- 追記型・インデックス付きで、シーク再生が速い
- **記録したログをそのまま Foxglove Studio で開ける** — GUI を作る前から点群を目視確認できる
- 自作 GUI と併存できる（自作 GUI = ライブ用、Foxglove = オフライン解析用）

自作フレームワークを選んだ以上、標準に乗れるところは乗っておく。

### 記録は2段構え（`.sfl` と `.mcap`）— 2026-08-08 実装

MCAP を「唯一の記録形式」にはしなかった。**実時間で回る `io_node` に外部依存を
持ち込まない**という方針（§13）と両立しないため。

| | `.sfl`（`io_node` が書く） | `.mcap`（`logger_node` が書く） |
|---|---|---|
| 中身 | UART を流れた生バイト（送受信とも） | 解釈済みのトピック **＋ カメラ画像** |
| 依存 | stdlib のみ | `mcap` |
| 目的 | 異常の証拠・確定的な再生 | 解析・Foxglove で目視 |
| 量 | 約 2.5MB/分 | **10.3MB/分（実測）**。数値は 1MB/分未満で残りは画像 |

### ★ 記録の置き場所は「Pi は最小限、MCAP は PC」— SD の書き換え寿命のため

**`.mcap` を Pi の SD に常時書くのはやめた**（2026-08-08）。実測 10.3MB/分は
**1日 15GB** に相当し、28GB の SD を毎日半分書き潰す勢いになる。SD は
書き換え回数に寿命があるので、これは払う価値のないコストだった。

しかも**数値だけなら `.mcap` は `.sfl` とほぼ同じ内容**（どちらも UART 由来）で、
SD に二重に書く価値があるのは実質**カメラ画像だけ**。そこで:

| | どこに書くか | 量 |
|---|---|---|
| `.sfl`（io_node） | **Pi の SD に常時** | 2.5MB/分 |
| `.mcap`（logger_node） | **PC に流す**（`tools/record.sh`） | SD には 0 |

`logger_node -o -` は MCAP を標準出力に出すので、`ssh` のパイプに乗せれば
**SD には1バイトも書かれない。** 帯域は画像込みで約 200KB/s。

SD への書き込みは、ブロックデバイスで測って
**10.54MB/分 → 2.42MB/分（77%減）**になった（`/sys/block/mmcblk0/stat`）。
Pi 単体で画像も録りたいときだけ `install_services.sh --with-logger`。

**`.sfl` は常時記録のまま残す。** PC を繋いでいない間や、Wi-Fi が切れた瞬間の
記録が失われては意味がない。`.sfl` にしか残らないもの（CRC エラー・SEQ 逆行・
再同期バイト数）と、`.mcap` にしか残らないもの（カメラ画像）がある。

`.sfl` は後から `python3 -m raspi.tools.sfl2mcap` で MCAP に変換できる。
**変換は `replay_node` + `BusBridge` をそのまま通す**ので、実機・再生・変換の
3つで同じ解釈コードが動く（書き直すと必ずズレる）。

#### MCAP の中身

ワイヤ形式は **JSON + jsonschema**。Foxglove Studio が MCAP で読める符号化に
msgpack が無いため、内部バス（msgpack）とは形を変えている。スキーマは
`msgspec.json.schema()` が型から生成するので手書きしない。

| トピック | 中身 |
|---|---|
| `/vehicle_state` `/scan` `/diag/link` `/cmd` `/hb/*` `/image/*` | バスのメッセージそのまま |
| `/viz/scan` | `foxglove.PointCloud`。**無効点（`dist=0`）は落とす** |
| `/viz/image/front` `/viz/image/rear` | `foxglove.CompressedImage`（JPEG） |
| `/uart/tx/*` `/uart/rx/*` | UART フレームの生値（`sfl2mcap` のみ） |
| `/events` | `.sfl` の EVENT（linkstats・health 遷移。`sfl2mcap` のみ） |

時刻は **UNIX epoch に直して書く**（`log_time`）。`CLOCK_MONOTONIC` のまま
書くと Foxglove が 1970年と表示する。**メッセージ内の `t_capture` / `t_pub` は
単調時刻のまま**なので、`.sfl` と突き合わせられる。換算に使った1組は
MCAP のメタデータ `surge` に残してある。

#### ★ `.mcap` は尻切れに弱い（`.sfl` と違う点）

**MCAP は最後に `finish()` を呼んで初めて索引が書かれる。** 電源が落ちて
`logger_node` が終了処理を通らなかった `.mcap` は、データ本体が書けていても
普通のリーダが開く前に落ちる。`.sfl`（追記のみ・索引なし）が尻切れでも
必ず前半を読めるのとは対照的。

**Pi には原因不明の再起動の実績がある**ので、復旧経路を用意してある:

```bash
python3 -m raspi.tools.mcap_repair logs/surge_20260808_233813.mcap
```

先頭から舐めて切れたところで打ち切り、索引付きで書き直す。実機の記録中の
ファイル（87MB）から 10万件・画像 4869枚を救えることを確認済み。

## 14. 開発ロードマップ

| Phase | 内容 | 達成条件 |
|---|---|---|
| **0** | UART プロトコル実装、GPIO（E-Stop / LED / ブザー）、時刻同期、**ログ記録・再生**、WS サーバ、GUI 骨格 | PC からラジコン操縦できる / 全データが記録できる |
| **1** | 可視化の完成（LiDAR 俯瞰・カメラ・全メータ）、設定反映、**カメラ内部・外部パラメータ校正**、アクチュエータ遅延の実測 | 走らせながら状態が全部見える |
| **2** | 反射行動（緊急停止、壁沿い走行、障害物回避） | 地図なしで壁にぶつからず走り続ける |
| **3** | 自己位置推定と環境地図（**方式未定**。§15-1） | コースを走り切るのに足る位置情報が得られる |
| **4** | 大域経路計画 + 経路追従（Pure Pursuit → MPC） | 地図上の目標点へ自律走行 |
| **5** | カメラ認識の本格活用（レーン・枠検出）、**駐車タスク** | 指定枠への自動駐車 |

**Phase 0 と 1 に時間をかけるほど、後が速くなる。**

### 各 Phase の重要な注意

#### Phase 1：アクチュエータ遅延の実測を必ずやる

制御則（Pure Pursuit 等）は「指令した舵角が即座に実現する」前提で書かれている。しかし実際は **ステアリング機構が 50〜200ms 遅れ**、さらに UART 往復 + Python 処理で 30〜50ms 乗る。合計 150ms、時速 10km/h なら **40cm 進んでから舵が効き始める**。

結果として「低速では動くのに、速度を上げた瞬間に蛇行が発散する」という典型的な失敗が起きる。

対策の順序：
1. **まず実測する。** ステップ入力（舵角 0 → 最大）を与え、`steer_cmd_echo` と `steer_actual` をログに取る
2. 1次遅れ + むだ時間 `e^(-Ls)/(Ts+1)` でフィッティング
3. 制御則に遅延補償を入れる（最も簡単なのは、判断を「現在位置」ではなく「L 秒後の予測位置」で行うこと）
4. Pure Pursuit の lookahead を速度比例に：`Ld = k·v + Ld_min`

**この計測のために Phase 0 のログ機能が必要**になる。

#### Phase 3：点群の歪み補正

LD06 は 10Hz 回転のため、1周する 100ms の間に車体が移動する。時速 10km/h なら **1周あたり約 28cm** 移動し、点群が扇形に歪む。

`LIDAR_SECTOR` の `t_start_us` とオドメトリを突き合わせて各点を補正する。SLAM 精度に直結する。

#### Phase 5：駐車タスクが早期に要求すること

詳細設計は Phase 5 だが、**今の段階から効いてくる要件**が3つある。

1. **後方カメラの外部パラメータ校正**（画像上の駐車枠 → 地面座標への変換）。Phase 1 のカメラ校正でリアカメラも必ず含める
2. **後退時の低速精度**。エンコーダ分解能と最低走行速度を早めに実測する
3. **超音波が主役になる場面**。LiDAR は車止めのような低い障害物を見落とすため、`us_rear` の測距周期と最小検出距離が駐車精度を直接左右する

## 16. シミュレータ

実車が無い場所（Mac）で、**実機と同じ制御コードのまま**走らせるための仕組み。
詳細は [`sim/README.md`](../sim/README.md)。

### 16.1 入れ替え点は `SerialLink` の位置

`IoNode` は link をコンストラクタ注入で受け取り、`import serial` はリポジトリ全体で
`raspi/io/serial_link.py` の 1 箇所だけ。ここに `SimLink`（同じ 7 つの約束を満たす偽物）を
差すと、**`io_node` より上流は 1 行も変わらない**。

```
                            ┌─── SerialLink ──→ 実 STM32
io_node ── link.poll/send ──┤
                            └─── SimLink ────→ 仮想 STM32 + 車両モデル + 仮想LD06 + コース
```

これにより、`protocol.toml` のパケット定義・CRC・フレーミング・`convert.py` の換算と
クランプ・`ScanAssembler` の鏡像反転・時刻同期・`--allow-arm` ゲート・`cmd` 150ms
タイムアウト・`bus_bridge`・`telemetry_node`・GUI がすべて実機と同じコードで走る。

**`raspi/tools/bus_demo.py` とは役割が違う。** あちらは「GUI の配管と見た目の確認」用の
運動学モックで、UART 層を一切通らない。育てて物理シミュレータにしないこと（§10.6）。

### 16.2 シミュレータの概念を実機側に持ち込まない

**シミュレータが偽装するのは STM32 だけ。** コース切替・LiDAR のノイズ量・欠損率は
実機に対応物が無い概念なので、その操作 UI は実機 GUI（React）ではなく
シミュレータ自身の GUI（pygame、`sim/gui.py`）に置く。

実機 GUI に入れると、表示判定を 1 つ間違えた瞬間に実車の画面にシム用コントロールが出る。
GUI がシミュレータを知らなければ、その事故は原理的に起きない。

同じ理由で **シム ↔ シミュレータGUI は §6.3 の内部バスを使わず UDP ループバック**にした。
バスに乗せると `raspi/msgs/types.py` に真値のメッセージ型を、`raspi/bus/zbus.py` に
トピックの持ち主を登録することになり、実機側の語彙にシムの概念が入る。

代償として真値は `.sfl` / mcap に残らない。将来「真値つきデータセット」が要るなら
シム側で独立したファイルに書くのが筋で、バスに戻すのではない。

### 16.3 唯一の例外 — SIM バッジ

`LinkDiag.sim`（bool 1 個）だけは実機側に持たせ、GUI のステータスバーに **SIM** バッジを出す。

**これは利便性ではなく安全要件。** シムと実機の画面が見分けられないと
「シムのつもりで `--allow-arm` した実車が動く」が起きる。`SerialLink` には何も足さず、
`getattr(link, "is_sim", False)` で読む（実機側のコードは偽リンクの存在を知らない）。

### 16.4 モデル化の深さ

運動学（自転車モデル）と遅れ（操舵のむだ時間 + 1次遅れ、速度の 1 次遅れ）まで。
タイヤモデル・スリップ・TC/TV は入れていない。**§15 #2/#3 が未実測で、
合わせ込む相手がまだ無い**ため。実測後に `config/vehicle.toml` を直せば全体が追随する。

センサ側は逆に作り込んである（距離ノイズ・点欠損・**セクタ単位の欠損**・伝送遅延・
走査ゆがみ・UART の線上時間による順番待ち・独立した STM32 クロック）。
知覚と経路生成を書くときに効いてくるのはこちらで、綺麗すぎる点群で開発すると
実車で初めて破綻するため。
