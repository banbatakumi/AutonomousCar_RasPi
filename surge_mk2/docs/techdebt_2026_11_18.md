## 0. 全体所感

- **デッドコードと未使用の依存はほとんど無い。** 参照が0なのは `_next_v`・`SWEEP_STEP`・`useElementSize` くらい。依存はすべて使われている。
  Pi に scipy が無いことを理由にした自前実装（`nav/mpc.py`・`nav/centerline.py` など）は、理由がコメントにあり妥当。
- **負債の中心は「機能を足すたびに同じ形をコピーしたこと」。** 例:
  - telemetry_node のモデル選択処理が5組
  - ONNX セッション生成が5箇所
  - ml_* の GUI・学習ループ
  - GUI の WebSocket 再接続が8箇所

- **次が巨大ファイル。** telemetry_node 4049行、slam2d_raceline 3854行、useDriving 1363行、CameraView 1091行。
- **安全系の値が手作業での同期に頼っている所がある**（GUI と Pi の定数、`vehicle.toml` の読み方）。「設定の正は1箇所」という方針と矛盾する。
- **始める順番**: まず動きを変えない共通部品の抜き出し（高4、中1〜5）。
  巨大ファイルの分割（高2・高5・高6、中6）は、テストと ESLint を整えてから。

## 4. 調査の方法

- raspi/、sim・slam2d・tools・ml_*、gui/ の3つに分け、それぞれ読み取り専用で調べた。
- デッドコードかどうかは、ast による参照数の集計と grep（sim・tools・tests・launcher・docs も含む）で判断した。
- 主な指摘はコードを開いて照合した。例: `_next_v` と `SWEEP_STEP` の参照が0、`_e2e_fusion_model_pump` の中身、`verify_parity`・`pick_device` の重複、`Vehicle._from_dict` の外部呼び出し、`MAX_BRAKE_TORQUE_NM` の二重定義、`useElementSize` が未使用、GUI の npm scripts。
- `npx tsc`・テスト・ベンチは実行していない（棚卸しだけで、変更は無い）。
