## 2. モジュール間の連携に潜む重大な指摘

### 2.1 C1 — 自律走行の非常制動が、GUI のブレーキスライダ値に格下げされる 【C】

**連鎖**: `planning_node` → `telemetry_node._merge_auto` → `cmd` → `io_node` → STM32

`planning_node` は「わからない・障害物あり・枝が陳腐化」のとき、
`brake_torque = 0.0` を送る。`0` は本プロジェクト全体（`msgs/types.py`・`convert.py`・
ファーム `vehicle.c:336-338`）で **「未指定 → STM32 が最大で制動」** を意味する。
これはフィールドの埋め忘れでブレーキが効かなくなるのを防ぐ、意図的な安全側の規約である。

しかし中継の `_merge_auto` がこの規約を**破る**。

```python
# raspi/nodes/telemetry_node.py:3247-3253
brake_torque = gui.brake_torque
if auto.brake and auto.brake_torque > 0:
    brake_torque = auto.brake_torque
    if gui.brake:
        brake_torque = 0.0 if gui.brake_torque <= 0 else max(gui.brake_torque, auto.brake_torque)
```

`auto.brake_torque == 0`（=最大制動の意思）は `if` に入らず、結果は **GUI のスライダ値**になる。
GUI のスライダ範囲は 0.005〜0.15 N·m（`gui/src/store/ui.ts:299`）。既定の 0.15 は上限と一致するため
**既定では実害がない**が、人が「/mole な減速のためブレーキを弱くする」ためにスライダを
0.02 N·m に下げて自律走行ordingすると、**障害物回避の非常制動が 1/7.5 のトルクになる**。

同じ関数の**陳腐化経路**（`auto/cmd` が 200 ms 超）は `brake_torque = 0.0`（=最大）を正しく送出しており、
**同じファイル内で新経路と旧経路が逆の意味になっている**。
さらに docstring（同関数 3218-3219 行）は
「brake_torque は GUI のスライダの値を使わず 0（= STM32 の最大）にする——弱く設定したまま
自律走行していると、planner が止まったときの制動まで弱くなる」と**逆の仕様を明記している**。
コードが自分のドキュメントと矛盾している。

- **場所**: `raspi/nodes/telemetry_node.py:3247-3253`（受領） /
  `raspi/nodes/planning_node.py:481-499`（発生）
- **確認**: コード（発生側・中継側・下流の規約を 3 箇所で確認）
- **注意**: 現行の挙動は `raspi/tests/test_cmd_path.py:790` に
  「指定なし→GUI」という**明示的なテスト**として固定されている
  （2026-09-27 付）。したがって**意図的な設計が安全側の根拠から乖離した**状況であり、
  静かなパッチではなく**明示的な意思決定**が要る。
- **修正案**: `_merge_auto` で `auto.brake and auto.brake_torque <= 0` のとき
  `brake_torque = 0.0`（STM32 最大）を強制する。テストは
  「planner が brake=True かつ brake_torque=0 → 出力は 0.0」に更新する。
  併せて、GUI 側の弱スライダは**手動ブレーキのときだけ**弱く、
  自律走行中は最低値を保証する設計を検討。

### 2.3 H3 — 一つの「車」が 3 つ定義されている 【H】

`config/vehicle.toml` の 3 つの節が、互いに矛盾する摩擦係数を持つ。

| 節 | キー | 値 | 意味 | 読むもの |
|---|---|---|---|---|
| `[sim]` | `mu` | **0.41718** | 車全体の横 μ | `sim/vehicle.py:211-220` |
| `[limits]` | `a_lat_m_s2` | **4.0912** | = 0.4172 × g | `raspi/core/vehicle.py`、`sim/vehicle.py`、`control_params.DERIVED` |
| `[control.plant]` | `mu` | **1.3227** | タイヤのピーク μ | `tools/fwsim/plant.py:124` |

`tools/calib/tyre.py:512-515` は **`mu` と `a_lat_m_s2 = mu·g` を同時に書く**。
1.3227 × 9.80665 = **12.98** だが、実値は **4.09**。両者は同時に書きemiasれない。
`tyre.py:521` の警告分岐が「書かない」判断をしたために**意図的に残ったずれ**である。

結果として、

- **実車 runtime** は μ = 0.417 で走る（`[limits]` 経由）
- **`sim/`** は μ = 0.417 で走る（`[limits]` が `[sim]` を上書き）
- **`tools/fwsim/`** は μ = 1.3227 の**Peak 無しのタイヤ**で走る
  （`tyre_c = 0.3` は `tyre.py:246 _C_MIN = 0.3` の**ちょうど下限**であり、
  `Curve.degenerate`（`tyre.py:150-152`）が True になる形状。
  `sin(C·atan(Bκ))` は C<1 なので単調増加で、ピークが存在しない）

**fwsim の全ての「予測」（校正 5 の検証、校正 9）は、校正系が一度も検証していないタイヤで
計算されている。**

さらに `tools/fwsim/plant.py:119-120` に**無効な参照**がある。

```python
if dyn.get("mu"):
    over["lateral_accel_max_m_s2"] = float(dyn["mu"]) * 9.80665
```

`[dynamics]` に **`mu` キーは存在しない**（実測: `[dynamics]` のキーは 18 個、`mu` なし）。
よって fwsim の横加速度上限は**ハードコードの 4.48 m/s² のまま**、
一方ロードされるタイヤは 12.98 m/s² 相当を暗示する。**長LAT と横が別々の出典**。

- **場所**: `config/vehicle.toml:265-267` と `:126` /
  `tools/fwsim/plant.py:104-125` / `tools/calib/tyre.py:503-521`
- **確認**: 突合（toml の実際のキー集合を `tomllib` で列挙 + `tyre.py` の適合範囲を突合 + 計算）
- **修正案**: ① `[control.plant].mu` の意味を「タイヤのピーク μ」に固定し、
  `[limits].a_lat_m_s2` との関係を**校正 7 が必ず一緒に書き**、
  書けないときは両方を書かない（現状は片方だけ残る）。
  ② `tyre_c` が退化領域に入ったら**永続化させない**ガードを `tyre.py` に追加。
  ③ `Plant.load()` の横加速度上限を `[limits].a_lat_m_s2` から読む。
  ④ `[sim].mu` と `[control.plant].mu` の**キー名衝突を解消**（`tyre_mu` 等）。

### 2.4 H4 — E2E LiDAR モデルの `dt` 契約が空で、学習周期と実機周期が 2 倍違う 【H】

**連鎖**: `ml_lidar/env.py`（学習） → `export_onnx_rl.py`（契約 JSON） → `raspi/auto/e2e_lidar.py`（推論）

`raspi/auto/e2e_lidar.py:103-108` に「学習時の制御周期が実機と違えば読まない」という
ガードがある。

```python
dt = float(cfg["dt"]) if "dt" in cfg else None
if dt is not None and abs(dt - PLAN_PERIOD_S) > _DT_TOLERANCE_S:
    raise ValueError(...)
```

**しかし、 Cote contract 27 個すべてに `dt` が無い**（実測: v1〜v27 すべて `dt=None`）。
`dt` は None なので**ガードは永久に実行されない**。

| 学習 run | 学習時の `dt` | 契約 JSON の `dt` | 実機での実効 |
|---|---|---|---|
| v1〜v12 | 0.05 | **無し** | ロード不可（`steer_rate_max_rad_s` 欠落で拒否） |
| **v13〜v20** | **0.05（20 Hz）** | **無し** | **0.10（10 Hz）で実行される** |
| v21〜v27 | 0.10 | 無し | 0.10（偶然一致） |

推論側の舵の積分は

```python
# raspi/auto/e2e_lidar.py:313-316
if dt > 0:
    dt = self._model_dt if self._model_dt is not None else min(dt, _DT_MAX_S)
self._steer_target = ... self._steer_target + steer_norm * self._model_steer_rate_max_rad_s * dt
```

学習は dt=0.05 で 1 判断あたり `rate × 0.05` 動くが、**実機は 0.10 で `rate × 0.10` 動く**。
**1 判断あたりの舵の移動量が 2 倍**になり、離散時間閉ループの舵ゲインが倍増する。
これは `ml_lidar/env.py:76-82` が実車での「舵の発散と壁衝突」の原因として挙げている
症状そのものである。

v13〜v20 は GUI から選択可能（`telemetry_node.py:2181` が `models/e2e_lidar/*.onnx` を列挙）、
**ロードも成功する**。

- **場所**: `raspi/auto/e2e_lidar.py:103-108, 313-316` / `models/e2e_lidar/v13..v20.json`
- **確認**: 突合（契約 27 個と `ml_lidar/runs/*/env_config.json` の全組合せを機械照合）
- **修正案**: ① 現行の `export_onnx_rl.py` で v21〜v27 を再エクスポートし、`dt`/`steer_tau` を契約に載せる。
  ② v13〜v20 は `dt` が 0.05 なので**再エクスポートではなく隔離**（ロード拒否）する。
  ③ 「`dt` が無い契約」を**エラー**にする（既定値続行ではなく）。
  ④ **観測ベクトルと `dt` の一致を検証する CI テスト**を追加する（後述 §4）。

### 2.6 H6 — Hybrid A* の margin 緩和が**経路全体**に効く 【H】

**連鎖**: `raspi/nav/hybrid_astar.py` → `raspi/auto/park_to_point.py`

```python

if goal_clear <= -cfg.goal_slack:
    return HybridResult(...)
margin = min(cfg.margin, max(-cfg.goal_slack, goal_clear - 0.005))
```

`margin` は**探索全体**の硬い拘束（`hybrid_astar.py:460` の `if w < margin: continue`）である。
comments の趣旨は「駐車は意図的に壁へ詰めるので、目標の余裕が `cfg.margin` より小さいのは普通に
起こる」——**確かに正しい**。だが実装は**目標の余裕を全経路に適用**している。

実測（`LocalMap` 2 cm、1 m 通路、`cfg.margin=0.05`、`goal_slack=0.03`）:

| 目標位置 | 目標の余裕 | 実際に使われた margin |
|---|---|---|
| goal_y = 0.89 | +12.4 mm | **7.4 mm** |
| goal_y = 0.80 | +92.4 mm | 50.0 mm（正常） |

つまり**目標が 12 mm 余っているだけで、離れた位置から进入する経路全体の壁クリアランスが
5 cm → 0.74 cm になる**。最後の数 cm だけでなく、**进入のほぼ全体が 0.74 cm の壁際を走る**。

さらに `park_to_point.py:613-622` の安全側判定が**計画側と別の閾値**を使っている。

```python
# 地図側は推定誤差を含むので、計画が受け入れた閾値で見る
thr = min(0.0, self._plan_margin)
```

`self._plan_margin` は*緩和された*値（例 0.0074）。`min(0.0, 0.0074) == 0.0` となり、
安全側は「**0 mm 必要**」＝計画より**厳しい**判定になる。
`HybridResult.margin` の docstring が約束する「安全判定は計画と同じ閾値を使う」が**破られている**。

- **場所**: `raspi/nav/hybrid_astar.py:334-338, 460` / `raspi/auto/park_to_point.py:613-622`
- **確認**: コード + 数値実験（実 LocamMap で margin を実測）
- **修正案**: `margin` は `cfg.margin` のまま維持し、`goal_slack` は
  **終端ノードの受容判定の緩さ**としてのみ使う（「最終ノードはこの余裕を許す」）。
  併せて `park_to_point` の `thr` は `self._plan_margin`（緩和値）を使い、
  緩和値が負のときだけ `min(0, m)` にする。

### 3.5 支える仕組み（再確認 — ここは設計として正しい）

- **フレーム解析**: バッファ有界・CRC/_LEN 不一致で 2 バイトだけ破棄（実 SYNC を飲まない）・

  欠落セクタは `sector_seen=False`（0 m 扱いしない）・鏡像を一貫して適用。
- **`shm_ring`**: seqlock + 実メモバリア（ARM64 の `dmb`）・上書き検出・`track=False`。
- **停止経路 16 種**: 独立 2 層以上。**ほぼ全部が STM32 に届く**（§2.1, §2.23 の 2 穴のみ）。
- **engage ゲート**: 制御権・モード必須・モード変更で engage 解除・
  `engaged` は永続化されない・`planning_node._engage_ok` が「再起動直後の即時 engage」を拒否。
- **SLAM の退化検出**: 固有値の比による判定が**実測で機能**（壁に沿った掃引で情報量が厳密に 0）。
- **false loop closure への耐性**: `max_correction` ゲート + Huber kernel + χ² 再ject。

## 6. 総括

このリポジトリは**「型と生成」を极高まで已完成している**。
`VehicleState` 60 フィールド・`LinkDiag` 53・`AutoState` 72 が**完全に一致**し、
`CmdOut` 20・`ControlStatus` 35 も**孤児ゼロ**で、`gui/src` に `any` は 1 つもない。
`tsc -b` は strict + `noUncheckedIndexedAccess` で通り、フレーム解析は
**継続的なゴミ入力でも固まらない**ことを実装が保証し、停止経路は 16 種ある。

**弱点は、許容できる範囲のさらに外側にある。** 弱さの中身は「**意味論**」である。

> コードは**形**（型・構造・生成）を严格に守っているのに、
> **値の意味と規約の適用範囲**がモジュール境界で漏れる。
> 0.15 N·m のトルク上限は 5 箇所に書かれ 4 箇所は検査されているのに、
> `brake_torque = 0` が何を意味するかは**中継 1 行で消える**。
> `max_steer` は 1 箇所が正なのに**既定値・unit 引数・文書・learning 契約**が
> 4 つの別の値を持っている。
> 「正の伝播網」を支えているのは**検査 3 本と CI 1 本**で、
> **その CI は 2 日前から壊れている**。

**したがって優先順位は明確**で、**最初に直すべきは個別の数値ではなく検査網**である。
CI を直し、意味論の検査（firmware の並び・convert のスケール・契約の `dt`）を足し、
**「正」を 1 箇所に集める仕組み**（`control_params.DERIVED` のuate）を広げる。
それが済めば、§2 の High のうち **半分以上は構造的に発生しなくなる**。

逆に言えば、**これをやらずに個別のバグを 1 つずつ直していくと、
同じ穴から 3 つ目のバグが生まれる**（既に `brake_torque` は
`planning_node` → `telemetry_node` → `io_node` の 3 者在る）。

最後に、**偽阳性を取り下げる過程**そのものが、報告の信頼性の根拠である。
5 件の「最上位の指摘」が再検証で**取り下げ**られ、
うち 1 件は**文献の文脈読み違い**によるものであった。
**残った 60 件の深刻度は、本報告の要旨から 1 段保守的に読むのが安全**である。
