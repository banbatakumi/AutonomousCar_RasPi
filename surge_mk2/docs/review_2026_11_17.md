## 0. 実測（2026-11-17、実機）

ARM は手動モード・速度0・舵0で、車輪は動かしていない。各サービスの CPU は `/proc` の 20 秒平均で、1 コア＝100%（4 コアで 400%）。

| サービス | DISARM（1.5GHz・48℃） | ARM（2.0GHz・51℃） |
|---|---|---|
| surge-stereo | 0.3% | **53.4%** |
| surge-io | 10.6% | 18.1% |
| surge-camera | 0.1% | 16.5% |
| surge-telemetry | 5.8% | 11.1% |
| surge-planning | 2.8% | 4.2% |
| 推論ノード（cam_e2e・e2e_fusion・line・track） | 各 0.6% | 各 1% |
| 合計 | 約 0.2 コア | 約 1.1 コア |

throttled=0x0（スロットリングなし）。

**Pi 上の単体ベンチ**（`nice 10`、約 500 点の周回経路）:

| 処理 | 1 回の時間 |
|---|---|
| `MPCFollower.follow` | 0.82 ms |
| `speed_profile`（C 版） | 0.1 ms |
| `_speed_profile_var`（Python 版） | 1.6 ms |

**結論**: 今の CPU の余裕は大きい。ARM 中の負荷の半分はステレオ照合が占める（照合は既に OpenCV と `stereo_native.c`）。

MPC と速度プロファイルは C 化の必要がない。周期 20〜100ms に対して 1〜2% にとどまるため（§4 の「C 化しないもの」）。

### H1. 自律指令の中継が planner の「idle 指令」を本物の指令として流しうる 【バグ】

**済（2026-11-17）**: `_merge_auto` の `fresh` に `mode == 2 and arm` を足した（外れたら stale と同じ最大制動＋舵保持）。試験 `test_auto.py::test_planning_idle_is_treated_as_stale`

- **場所**:
  - `raspi/nodes/telemetry_node.py:3525`（`_merge_auto` の `fresh`）
  - 対比する箇所: 同 `_handover_cmd`（3485）、`planning_node.py:574-576`
- **内容**:
  - `fresh` は、時刻と isfinite だけを見て判定している。
  - planning_node は engage していない間、`DriveCmd(mode=0, arm=False, source="planning:idle")` を出す。中身は速度 0・舵 0・制動なし。
  - telemetry 側が engage 中でも、planning 側が engage していない瞬間がある。
    - planning_node が走行中に再起動し、`_engage_blocked` になったとき
    - engage が planning に届くまでの数十 ms
  - この間は idle 指令が「新鮮」として `cmd` に載る。

  - 外れたら stale と同じ経路（最大制動＋舵保持）に落とす。
  - テスト `raspi/tests/test_cmd_path.py` に「planning:idle が届いたら stale 扱い」を足す。

### H2. 安全に効く設定 4 つが、STM32 の既定値で決まっている 【STM32⇔Pi の認識差】

**済（2026-11-17）**: `[control]` に `abs_enable`・`wheel_lift_guard_enable`・`brake_hold_enable`・`auto_stop_margin_cm` を必須で書き、`ControlParamSync` で送って確かめる（ずれたら ARM しない）。GUI の変更は `set_wanted()`。マージンは `LINK_PARAM_IDS`（ファームの調整表ではなく `ras_link` の設定）。**ファームの既定（有効・15cm）は残した**: 走行中に STM32 だけが再起動したときの最大制動に ABS を効かせるため。Pi が送るまで ARM しないので、既定は走行の値を決めない

- **場所**:
  - ファーム: `src/comm/ras_link.c:756-760`。既定は wheel_lift_guard=有効、abs=有効、brake_hold=有効、`auto_stop_margin_cm`=`RAS_AUTO_STOP_MARGIN_DEFAULT_CM`(15)
  - Pi: `raspi/core/control_params.py:96-104`（`ENABLE_KEYS`）、`config/vehicle.toml:160-163`
  - Pi の GUI 操作: `io_node.py:917-920`
- **内容**:
  - `abs_enable`・`wheel_lift_guard_enable` は vehicle.toml に書けるが、「ファームの既定が有効なので今は書いていない」。
  - `brake_hold` と自動停止のマージンは、vehicle.toml に書く場所が無い。GUI からの送信だけで、値はメモリ（`_ui_settings`）に置かれる。
  - io_node や STM32 が再起動すると、ファームの既定（有効・15cm）に戻る。
  - `control_params.py:96` のコメント「STM32 の既定は**無効**」は、TC・TV にしか当てはまらない。
- **影響**:
  - 方針「校正値・設定は Pi の vehicle.toml で一元管理し、ファームに既定値を置かない」に反する。
  - 自動停止のマージン（安全に直接効く値）の正体が、ファームの定数になっている。
  - ファームを書き換えると黙って変わる。
- **対策**:
  - `[control]` に `abs_enable`・`wheel_lift_guard_enable`・`brake_hold_enable`・`auto_stop_margin_cm` を**必須**で書く。
  - それを `ControlParamSync` で送って確かめ、ずれていれば ARM を止める。
  - GUI での変更は今と同じく `set_wanted()` で上書きする。
  - 後でファームの既定を「無効・0」に揃える（ファームと Pi は一緒に入れ替える）。

### M2. 停止点へ向かう速度に、固定の下限 0.15 m/s がある 【対処療法】

**済（2026-11-17）**: 下限 `_STOP_APPROACH_MIN_M_S` を合流・coast の上限より**前**に掛けるよう移した（停止判定の 0.03 も定数 `_STOPPED_M_S`）。下限そのものの原因のログ確認はまだ

- **場所**: `raspi/auto/slam2d_route.py:1037`
  ```python
  st.target_speed = max(st.target_speed, min(p["creep_speed"], 0.15))
  ```
- **内容**:
  - 先に効いた上限より後で `max` を取っているので、上限を**押し上げる**。押し上げられる上限は2つある。
    - 合流の上限 `_join_cap`
    - 自己位置が怪しいときの `coast_speed`
  - 停止判定の `abs(vs.speed) < 0.03` も固定値。
- **影響**: 自己位置が怪しくて減速すべき場面で、0.15 m/s までは必ず進む。
- **対策**:
  - 下限は「停止点の手前で止まり切らない」ことへの対処のはず。原因（creep の速度で車速 PI が動き出せない等）をログで確かめる。
  - 必要なら下限をパラメータにし、coast と join の上限より**前**に適用する。

### M3. stereo_e2e の推論が実効 7.5Hz になっている 【バグ・仕様差】

**済（2026-11-17）**: 間引きを「予定を周期ずつ進める」形にし、15Hz の視差から平均 10Hz（67ms と 133ms が交互）。推論時間は Pi にモデルが無く測れていないので 15Hz 化は保留

- **場所**: `raspi/nodes/stereo_e2e_node.py:280-290`
- **内容**:
  - 間引きの通過条件は「前回から 100ms×3/4 = 75ms 以上」。
  - 視差は ARM 中 15Hz（66.7ms 間隔、`telemetry_node.STEREO_DEPTH_FPS_ARMED`）で届く。
  - そのため 1 組おきにしか通らず、133ms 間隔（7.5Hz）になる。docstring と文書は「10Hz」。
- **対策**: 次のどちらかにする。
  - 既定を 15Hz（全部通す）にする。推論の時間を Pi で測ってから決める。
  - 明示的に「2 組に 1 回」とし、文書を 7.5Hz に直す。

## 4. C 化について

**C 化しないもの**（実測で不要と判断）:
- MPC（0.82ms）
- `_speed_profile_var`（1.6ms）
- Hybrid A*・局所地図（既に C）
- slam2d（既に C、ビット一致）

**C 化を検討する価値があるもの**:
- **ステレオの照合（ARM 中 53%）**。すでに OpenCV の SGBM と C の後処理なので、「C に置き換える」余地は小さい。効くのは処理量を減らす方向。
  - ISP の lores（YUV の Y 面）で照合し、RGB→灰色の変換とコピーを省く（stereo_plan.md「調べたこと」）
  - 平行化の表を `cv2.convertMaps` で固定小数点（CV_16SC2）にする
  - 照合を帯（150〜260 行）だけに限る。今も限っているなら確認だけでよい
- **stereo_e2e・e2e_fusion の前処理**（左右 2 枚の `resize_area` と正規化。PROGRESS で約 10ms）。推論を 15Hz にするなら C 化か、ONNX のグラフに移すことを検討する。先に Pi で測ること。
