## 0. 先に結論

走行の安全に直接関わる指摘が10件、検証器（シム・同定）の信頼性に関わる重大な指摘が4件ある。
それ以外は条件付きの誤り・性能・文書の陳腐化で、約110件。

いちばん重い問題は個々のバグではなく、**「一度止めたら人が操作するまで止めたまま」を保証する層が
どこにも無い**ことである（§2.1）。GUI・telemetry_node・io_node・STM32 のそれぞれが「上位が ARM を
落とすはず」と考えており、E-Stop の解除・通信の復帰・STM32 の再起動のどれでも、ARM 付きの指令が
流れ続けていれば車はそのまま走り出す。

次に重いのは、**実機未検証の機能の根拠になっているシムのベンチが、実機の誤差と時刻の経路を
通っていない**ことである（§2.4）。「衝突0」「ラップ −8〜12%」は車速が真値・ジャイロ倍率誤差なしの
条件で得た数字になっている。

## 2. 全体の評価（モジュール間の連携と設計）

### 2.1 「止めたまま」を保証する層が無い

S1・S2・S9 は同じ根を持つ。関連する指摘を並べる。

- STM32: E-Stop の解除後、COMMAND 途絶からの復帰後、ウォッチドッグリセット後のいずれも、
  ARM 付き COMMAND が届けば即走行に戻る。文書（`docs/stm32_interface.md:1006-1014, 1332`）は
  「Pi が明示的に再武装するまで動かさない」と書くが、実装（`ras_link.c:426`、`vehicle.c:511`）は違う。
- io_node: `cmd` 途絶や FAULT で DISARM に落ちた後、ARM 付きの `cmd` が戻れば即再 ARM する
  （`io_node.py:743-757`）。
- telemetry_node: ソフトの E-Stop は「操縦権の解放」だけ。デッドマン後も engage を保持する。
- GUI: 操縦権を失うと 250ms ごとに自動で取り直す。失っていた間の速度の積分値も残る
  （`useDriving.ts:875-882`）。
- STM32: ハートビートを一度も検出していないと E-Stop の層が黙って無効のまま ARM できる。
  TELEMETRY にも出ない（`vehicle.c:377`）。

直す場所は1か所に決めるのがよい。io_node が最も適している（全指令が通り、STM32 の状態を知っている）。
`estop_active`・`drive_power_locked`・デッドマン発動・STM32 再起動検出のどれかが起きたら、
`cmd.arm` が一度 False になるまで ARM を通さない、という条件を `_arm_block_reason` に足す。
STM32 側でもラッチ解除後に ARM の立ち上がりを要求すれば二重になる。

### 2.2 自律走行中の5秒の猶予と、UI 側の詰まり

`[safety] auto_link_grace_ms = 5000` により、自律走行中は GUI のリンク断を5秒許す。この間、
人が車を止める手段は GUI しか無い。ところが GUI 側には5秒を使い切る経路が複数ある。

- S5（止まったクライアント1台で全員が詰まる）
- ErrorBoundary が無く、例外1つで画面が白くなる（`gui/src/main.tsx:11-15`）
- `window.confirm` が出ている間はメインスレッドが止まる（「走行中です。本当に削除しますか？」など）
- 認証なしの HTTP GET がイベントループ上で同期 I/O をする（`/logs/` は最大64MB。
  `telemetry_node.py:749`）。観戦者がログを落とすだけで `_cmd_pump` が止まりうる
- 操縦権もトークンも無い接続が、engage 中の `params`・`park_target`・`load_map`・`clear_map`・
  `shutdown` を送れる（`telemetry_node.py:1019-1034, 1204`）。実機は `--host 0.0.0.0`・トークン無し

### 2.3 時刻の軸

- 時刻同期は、往復遅延が段階的に増える（例 0.4ms → 1.5ms）か、遅延の小さい外れ値が1個入ると、
  最大約178ms **未来側**にずれた時刻を15〜52秒返す（`raspi/core/timesync.py:159-163, 176-177,
  187-192`、再現）。実機の現在の往復遅延は 0.36ms なので、しきい値は約1.0ms。
- その時刻は `VehicleState.t_capture` にガード無しで入る（`raspi/core/bus_bridge.py:77`）。
  LiDAR 側には「受信より後なら受信時刻」のガードがある。
- slam2d の `TwistBuffer` は未来の時刻が1件入ると、その時刻まで正常なサンプルを全部捨て、
  直前の速度を一定として積み続ける（`slam2d/core/deskew.py:149-175`、再現）。
- シムのベンチはセクタの時刻に受信時刻を渡しており、時刻同期の経路を通らない
  （`sim/bench.py:537, 549`）。この連鎖はシムでは見えない。

### 2.5 Pi 5 の実時間性

slam2d の処理時間を実機で測った（合成オーバル 360点/周、16m 格子。Pi は他のサービスが動いた状態）。

| 処理 | Mac | Pi 5 |
|---|---|---|
| 地図作成の1スキャン（平均 / p99 / 最大） | 2.9 / 16.6 / 47.0 ms | 16.5 / 104.9 / 133.2 ms |
| うちループ探索が走る2周目（平均 / 最大） | 3.6 / 16.9 ms | 20.7 / 110.8 ms |
| ループ閉じの `flush`（360 キーフレーム） | 222 ms | 1761 ms |
| 凍結地図（RACE）の1スキャン（初回 / 平均 / 最大） | 13.0 / 1.3 / 1.8 ms | 55.8 / 8.2 / 11.1 ms |
| 全域探索の1ステップ（24回）/ 仕上げ | 1.7 / 28 ms | 10.2 / 170 ms |

- Pi 5 は Mac の約5.5〜8倍遅い。コード中のコメントや見積りは「2〜3倍」を前提にしている。
- RACE は余裕がある。地図作成中は p99 が LiDAR の周期 100ms を超える。
- `flush` はキーフレーム数に比例する（約4.9ms/個）。手動地図作成を数分続けて 3000 個になると
  約15秒かかり、その間 planning_node は指令を出せない（`_slam2d_nav.py:324-325`）。
- Pi 上の slam2d は Mac の作業ツリーとソースのハッシュが一致しなかった。配備済みの版での値である。

同じ前提（Mac の計算時間）で設計されている箇所:

- Hybrid A* の時間予算 120ms に対し Mac で 124〜143ms（`raspi/nav/hybrid_astar.py:355`）
- ラインの仕上げ計算が1本のワーカーを占有し、障害物の引き直しと停止経路を待たせる
  （`raspi/auto/slam2d_raceline.py:381, 941-947`）。停止経路が 0.4 秒より遅れると
  「始点から追う」前提が崩れる（`raspi/auto/slam2d_route.py:543-547`）
- surge-io に実時間の優先度が無い（`Nice=0`）。実機のアイドル時はハートビートの遅れ最大 4.5ms・
  ループ最大 5.7ms で問題ないが、推論と SLAM と記録を同時に回した状態は未計測
- `.sfl` の書き込み・開始・停止が io_node のメインループと同期（`io_node.py:884-885, 401-424`）

### 2.6 例外1つで io_node が落ちて E-Stop になる経路

io_node のメインループには try が無く、落ちるとハートビートが止まってラッチする。安全側だが、
復帰にボタン操作が要り、S1 につながる。

- 有限だが巨大な指令値で `OverflowError`（`raspi/msgs/convert.py:212-219`、再現）
- ディスクが満杯だと、ログ出力先が同じディスクなので print が ENOSPC で落ち、再起動ループになる
  （`raspi/setup/install_services.sh:141-142`）
- `vehicle.toml` の `[control]` に `1e39` があると `struct.pack` が落ちる
- LEN=0 の LOG フレームで `struct.error`（現ファームは送らない）

planning_node も同様で、壊れた地図ファイル（`zlib.error`）や保存時のディスク満杯で落ちる
（`raspi/auto/mapstore.py:259-262`、`planning_node.py:476-478`、再現）。

### 2.7 契約に版と単位が入っていない

v0.18 で舵角の意味が「モータ角×0.5」から「実際の路面舵角」に変わったが、追従していない所が残る。

- GUI の `maxSteer` の既定が 0.785rad（45°）で、クランプを通らない（`gui/src/store/ui.ts:254, 451,
  479, 891-895`）。実上限は 0.4618rad
- io_node のフォールバックの `--max-steer 0.524`（LIMITS 未受信でも ARM が通る。`io_node.py:747-754`）
- LiDAR モデルの契約 JSON に `dt` と `steer_tau` が無い。dt=0.05 で学習した v13〜v21a を実機の
  10Hz で選べてしまい、舵の権限が2倍になる（`ml_lidar/export_onnx_rl.py:159-166`）
- `env_config.json` に `max_steer`・`steer_link` が無く、旧 run を今の設定で再評価すると条件が変わる
- カメラ E2E の契約に舵角の意味が無い（`models/cam_e2e/v1`・`v2` は旧単位）
- セグメンテーションのモデルに前処理の版が無い（v1・v2 は学習時と推論時で縮小方式が違う）
- ファームは生成物 `surge_proto.h` を使っておらず、パケット定義は手書きの複製。一致を保証する
  仕組みは param_id にしか無い（現時点ではホスト実行で全パケットの一致を確認済み）
- 最高速の上限が3か所にある（GUI の静的上限 3.0・io_node の `--max-speed`・LIMITS の 5.0）。
  3.0 より上に設定してもリロードで 3.0 に戻りうる（`ui.ts:202, 410-422, 860`）

### 2.8 設定の反映の抜け

- `deploy.sh --restart` だけでは `[control]` が STM32 に入らない。io_node は起動時に1回だけ読む。
  同定の「適用」後に `--restart` だけだと、planner は新しい `max_steer`・リンク換算の前提で走り、
  STM32 は古い値のまま。状態表示は `ok` のまま。sysid の GUI はこれを案内しない
- `install_services.sh --safe` は稼働中の surge-io に効かないのに「arm 封印」と表示する（`:372`）
- STM32 だけが再起動すると、`auto_stop_margin_cm`・`brake_hold_enabled` の表示が古いまま残る
  （`io_node.py:360-374, 691-696`）
- `deploy.sh --test` はテストの失敗を検出できない（`tail` の終了コードを見ている。`:120`）
- `deploy.sh` は `ml_lidar/runs`（1.8GB）などを除外せず Pi へ送る。`--delete` が `gui/dist` にしか
  無く、Mac で消した planner が Pi に残る
